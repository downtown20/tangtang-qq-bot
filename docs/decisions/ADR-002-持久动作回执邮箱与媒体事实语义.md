# ADR-002：持久动作回执邮箱与媒体事实语义

## 状态

Accepted（分阶段实施）

## 日期

2026-08-28

## 背景

[ADR-001](ADR-001-统一动作信封与真实回执.md) 已确定统一 `ActionEnvelope/ActionReceipt`，但还没有回答三个会直接影响崩溃语义的问题：媒体动作何时算完成、回执如何跨回合交给 LLM、谁拥有失败重试。

当前语音和贴图工具只把意图放进 `turn_actions`，真实发送发生在工具循环之后。工具返回的“准备发送”不是送达事实；进程在发送后、下一轮对话前重启时，内存回执会丢失。贴图动作还依赖文字回复成功才能执行，导致纯贴图行为被迫补一段虚构文字。这些路径共同违反“系统只执行并报告事实”的单脑边界。

项目已有两个可靠性所有者：NapCat outbox 负责即时 QQ 发送的确定失败重试，TaskManager 负责任务 claim、到期执行和崩溃恢复。回执层不能再建立第三套动作重放队列。

## 决策

### 1. 请求、受理和送达分层

- `ActionEnvelope` 是不可变动作请求，不携带“已送达”含义。
- `draft/accepted/dispatching` 是执行受理阶段；`accepted` 只作为当前工具调用的临时受理响应，不持久化、不进入 receipt 枚举，也不能作为成功事实。
- `ActionReceipt` 只报告一次实际执行的终局：`confirmed/uncertain/failed`。迁移期保留旧 `draft` receipt 兼容读取，但新媒体路径不得生成它。
- `uncertain` 表示副作用可能已发生，禁止自动重放；`failed` 是否重试仍由 outbox 或 TaskManager 决定。

### 2. 持久 ReceiptMailbox

在现有 SQLite 访问层内建立独立、持久、按 scope 隔离的回执邮箱。它只保存事实并向 LLM 交付上下文，不拥有动作执行、重试或重放。

每条记录至少包含：

- `schema_version/action_id/kind/channel/target/status`；
- `source_id/scope_id/ordinal`，用于来源追踪、同源幂等和群私隔离；
- `message_ids/actual/error_code`；
- `created_at/leased_at/consumed_at`。

邮箱设置 TTL、每 scope 上限和全局上限；首版 lease 为 15 分钟、TTL 为 24 小时，必须保持 `lease timeout < TTL`。lease 超时且未过 TTL 的记录回到 deliverable；TTL 过期只影响上下文交付，不改写原动作事实或触发补发。`action_id` 的稳定来源是 scope、真实来源事件、动作序号和规范化 payload；相同来源重试得到同一 ID，不同来源即使文本相同也必须得到不同 ID。

### 3. 下一成功决策恰好消费一次

回执只在同一 scope 的下一轮 LLM 决策中注入，不为讲述回执额外启动 LLM：

1. 调用 LLM 前 lease 尚未消费的有界回执；
2. 以结构化、带来源的“系统动作结果”注入上下文；
3. LLM 调用成功后 ack 为 consumed；
4. LLM 调用失败时释放或让 lease 超时，同一事实可在重试决策中再次交付。

因此交付语义是“每个成功决策至多一次”，而不是“每次调用至多一次”。失败决策期间的重复注入只重复上下文事实，绝不能重新执行动作、写聊天记录、改关系或提交成功记忆。同 scope 内保持 `created_at + ordinal` 顺序，不跨群、私聊或用户泄漏。

### 4. requested 与 actual 都必须保真

typed payload 最小形态：

- text：`text/mode/attribution`；
- voice：`text/emotion/speed/pause`；
- sticker：`emotion/count/library_role?`；
- image：`asset_ref|url/caption`；
- sing：`song_id/title/version/sections`。

receipt 的 `kind` 保留 LLM 请求的动作类型，`actual.delivery_kind` 报告真实交付类型。语音技术降级成文字时仍为 `kind=voice`，但必须记录 `delivery_kind=text`、`voice_generated=false` 和降级原因；只有实际文字确认送达时状态才是 `confirmed`。若原语音的可重试失败已经进入 outbox，则重试所有权已交给 outbox，禁止再发送或排队降级文字；只有明确不可重试的失败才允许一次文字降级。

批量动作在 `actual.items` 中逐项记录。部分确认、部分失败的批次整体为 `uncertain`，`error_code=PARTIAL_DELIVERY`；已确认项永不重放。

文字转告的 `requested.text` 原样保存。若平台实际发送增加主人归因包装，包装后的可见内容写入 `actual.text`，原文另存独立字段，不能再声称两者完全相同。

### 5. 媒体动作独立于文字回复

语音或贴图可作为一个回合的唯一动作。工具循环不得为了结束回合强制生成占位文字，群聊和私聊后处理也不得把 `reply` 非空作为媒体执行前提。

只有 `confirmed` 的真实发送可进入聊天记录、窗口事件、关系反馈或“已完成”自我记忆。`accepted/dispatching/uncertain/failed` 只能作为执行状态或待核验事实，不能制造成功叙事。

## 实施切片

1. **B0 合同收口**：补齐 envelope/receipt 的版本、来源、scope、序号和 typed payload 校验；把 `accepted` 从 receipt 终局中明确剥离；增加兼容适配测试。
2. **B1 持久邮箱与语音首接**：完成 lease/inject/ack、崩溃恢复、TTL/容量和 scope 隔离；群/私语音先接 terminal receipt，并让 NapCat outbox 在终局时原子移交回执。复合贴图改由 B2 统一执行器接入，避免给仍依赖文字后处理的旧路径伪造批次终态。
3. **B2 即时贴图统一**：建立共享 `StickerPayload`、匹配器和执行器；补齐纯贴图独立终态，使它不再依赖文字或第二轮 LLM，然后接入同一邮箱。
4. **B3 定时贴图统一**：TaskManager 复用同一 payload、匹配器、执行器和邮箱，同时保留现有 claim/uncertain 语义。
5. **B4 兼容层清理**：迁移 CG、图片、唱歌和旧 relay 分支；用生产计数证明旧路径无调用后再删除。

每个切片独立回归、独立上线观察、独立回滚；B1 上线前后的生产观察不得与 B2/B3 混在同一对照窗口。

### 实施状态（2026-08-28）

- B0 已完成。
- B1 邮箱、同 scope 下一成功决策的 lease/inject/ack、群私语音直接终态、retryable outbox 终态移交、重启 `uncertain` 和损坏/冲突隔离已完成本地门禁。
- 任意 `actual.text` 只作持久对账事实，不进入 system prompt；LLM 只看到白名单执行字段。
- 延迟 outbox `confirmed` 对聊天记录/窗口的幂等事实归账仍待单独设计；复合/纯贴图均留在 B2，未计入 B1 完成范围。

## 不采用的方案

### 仅用内存保存回执

实现简单，但 bot 重启会丢失“已经发生、尚未告知 LLM”的事实，无法满足频繁重启和崩溃恢复要求。

### ReceiptMailbox 同时负责重试动作

会与 NapCat outbox 和 TaskManager 形成三重所有权，增加重复发送与 `uncertain` 重放风险。邮箱只交付事实。

### 发送后立即再调用一次 LLM 讲述结果

增加延迟、token 和刷屏，并把工具执行变成新的对话驱动力；回执只在自然发生的下一轮决策中提供。

### 用成功占位文字绕过媒体 early return

会污染聊天记录和记忆，也掩盖媒体动作缺少独立终态的问题。应修正动作终态与后处理顺序。

## 后果

- 进程重启不会丢失尚未交给 LLM 的真实媒体结果，也不会因此重放媒体。
- LLM 能区分“已受理、已确认、结果未知、明确失败”和“语音降级为文字”。
- SQLite 增加一个有界邮箱及 lease 状态；需监控未消费数量、最老年龄、lease 超时、`receipt_expired_unconsumed` 和按 scope 丢弃数。
- 迁移期同时存在旧 `turn_actions` 适配与新 envelope；任何成功事实只能从 terminal receipt 提交，防止双写。

## 回滚

每个媒体入口保留旧适配开关一个发布周期。回滚 B1 时停止新写入和注入，不删除邮箱记录；回滚 B2/B3 时恢复旧执行入口，但不得重放已有 `uncertain/confirmed` 动作。数据库变更采用可重复迁移，旧代码忽略新表即可运行。
