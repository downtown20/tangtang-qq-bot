# ADR-003：确认送达的永久事实归账

## 状态

Accepted（P1-3b4 本地实现完成；生产 canary 后启用；B2 前置条件）

## 日期

2026-08-28

## 背景

[ADR-002](ADR-002-持久动作回执邮箱与媒体事实语义.md) 已让语音终态持久化并交给下一次同 scope LLM 决策，但 ReceiptMailbox 是有 TTL、会消费和清理的交付邮箱，不是永久业务账本。

直接发送成功时，handler 会把 bot 可见正文写入 `chat_log` 并更新窗口；语音因离线进入 outbox 后，稍后重放即使已确认，当前 `settle_send_outbox()` 也只写 mailbox 并删除 outbox。结果是 QQ 和 LLM receipt 都认为“已经说过”，聊天记录与窗口却认为“没有发生”。

QQ 平台调用与 SQLite 之间没有跨系统事务。平台响应尚未收到时，只能冻结为 `uncertain`；一旦本进程已经收到平台 `confirmed + message_id`，该事实不能再降级为 `uncertain`。此后本地归账失败进入 `confirmed_unaccounted`，冲突进入 `confirmed_conflict`，两者都只能 DB-only repair，禁止再次调用 QQ。

## 决策

### 1. B2 前先完成最小 P1-3b4

首版只覆盖一个 envelope 对应一个物理发送的群/私语音及语音降级文字。普通 `ReplyPipeline` 会分段发送，部分成功时不能把整段正文归账，必须等逻辑动作与 `receipt.parts` 聚合完成后再接入。

### 2. 动作必须携带严格的对话归属

`ActionEnvelope/ActionReceipt` 下一版本增加 `conversation_ref`：

- `projection_kind=conversation_reply|none`；
- `conversation_user_id`：这条回复所属的对话对象；
- `group_id`：私聊为空，群聊为实际群号；
- `source_chat_id`：可空的原始 `chat_log` 行；
- `self_memory_eligible`：只表示是否可进入后续幂等 effect，不立即执行。

群聊的发送目标是群，不等于对话对象。缺少 `conversation_user_id` 时必须 `projection_kind=none`，禁止用 bot QQ、群号、昵称或正文猜归属。旧模板没有该字段时只完成运输和 mailbox，不回填、不猜历史。

契约同时增加冻结的 `identity_version=1`。`schema_version` 可以升级到 v2，但稳定 `domain_action_id` 继续使用 v1 canonical 算法；`conversation_ref` 不参与 ID 哈希。v2 receipt template 额外保存 `identity_payload`，终局化时重新计算并核对 action ID，防止手工/损坏模板伪造来源身份。同一动作若被错误绑定到另一用户，必须撞到同一个 ID 并形成 immutable conflict，不能悄悄变成第二个动作。

`conversation_ref` 的交叉约束：

- `none`：用户、群、来源行都为空，`self_memory_eligible=false`；
- 群 `conversation_reply`：用户非空，`group_id == target`；
- 私聊 `conversation_reply`：用户等于 `target`，群为空；
- `source_chat_id` 只能为空或正整数；提交时必须核验它指向同用户、同群的非 bot、未合成且未 quarantine 的原始消息，否则进入 `confirmed_unaccounted / PROJECTION_INVALID_SOURCE`，不得写 chat/window。

### 3. transport ID 与 domain ID 分离

- `outbox_id`：一次传输队列记录，当前 `send_outbox.action_id` 的随机 UUID；
- `domain_action_id`：receipt template 内由来源、scope、typed payload 和序号派生的稳定动作 ID。

所有永久归账和幂等键使用 `domain_action_id`。不得继续让两个不同语义都叫 `action_id`。

数据库保留旧物理列 `send_outbox.action_id` 以支持代码回滚；新代码的参数、局部变量和日志一律称 `outbox_id`。新增 `domain_action_id`、`confirmed_message_ids`、`confirmed_at`、`projection_error`，并对非空 domain ID 建唯一索引。

### 4. 永久事实、聊天投影和窗口事件同事务提交

新增 Store 内部 conn-level 提交入口；`settle_send_outbox()` 的 confirmed 分支在现有 `BEGIN IMMEDIATE` 内完成：

1. 先查不可清理的 `confirmed_action_facts`；
2. 新事实用 `event_key=action:<domain_action_id>:chat` 插入 bot `chat_log`；
3. 写 `confirmed_action_facts` 和 `conversation_window_events`；
4. 写 terminal mailbox receipt；
5. 删除 confirmed outbox；
6. 一次 commit。

`confirmed_action_facts` 保存 transport/domain ID、schema/source/scope、kind/channel/target、conversation_ref、actual、message_ids 和 confirmed_at。`conversation_window_events` 保存 action、scope、用户、群、chat_log_id、正文和 occurred_at。Mailbox 的消费或过期不影响这两类永久事实。

永久事实必须先于 mailbox 判重：完全相同视为幂等，终结当前 outbox，但不得因 mailbox 已消费/清理而再次插入 receipt；任一 immutable 事实不同写入 `action_projection_conflicts` 并进入 `confirmed_conflict`。平台确认事实不得因此改写成“未确认”，也绝不能再次发送。

本地 operational/projection 异常先回滚原事务，再用独立短事务把平台 message IDs、确认时间和错误保存到 outbox，状态置为 `confirmed_unaccounted`。`repair_confirmed_projection(outbox_id)` 只重试数据库归账，不触碰 QQ。

### 5. DB 事务之外只做可重建缓存

`conversation_window_events` 是真值，`ConversationTracker` 只是缓存。Store 提供按递增 event id 的 high-water 查询；Tracker 启动时加载仍可能活跃的 durable 事件，消息进入窗口判断前再 read-through。同步按稳定 `domain_action_id` 重算/替换 scope 状态，不能对重放事件执行 `count += 1`，也不能调用即时路径的 `on_reply_sent/on_private_reply`。commit 后可通知刷新；通知前崩溃由启动或下一次读取重建。SQLite 事务内禁止调用 QQ、LLM、JSON 状态文件或内存 tracker。

延迟 projector 不重放亲密度、关系、驱动力、经验、mood、反馈、贴图、CG、点赞或 poke。这些路径含累加、随机或外部副作用，当前也无法与 SQLite 原子提交。

`self_memory_eligible` 当前只作为 dormant eligibility 永久保存。未建立 item 级唯一键前不创建 pending worker，也不能重跑现有非幂等 `_extract_self_memories()`。

### 6. 崩溃语义

- claim 后、平台调用前崩溃：现有保守策略仍转 `uncertain`，不自动重放；
- 平台调用后响应丢失：`uncertain`，不写 chat/window；
- 平台请求已发出但尚未收到响应时崩溃：跨系统不可判定，重启后为 `uncertain`；
- 已收到 confirmed 后本地提交失败：`confirmed_unaccounted`，只允许 DB-only repair；
- 已收到 confirmed 但 immutable 事实冲突：`confirmed_conflict`，保留新旧快照供审查；
- SQLite 事务中崩溃：receipt/fact/chat/window/outbox 全部回滚；
- commit 后、缓存刷新前崩溃：永久事实保留，缓存可重建；
- 同一 domain action 再次投影：相同事实无操作，冲突事实隔离。

## 开源取舍

- OpenClaw `message-lifecycle-refactor.md`（官方仓库文件 SHA `70b8882...`）明确采用 durable intent、平台 receipt、`unknown_after_send` 和多 part receipt；也明确 exactly-once 只在适配器提供原生幂等或 unknown reconcile 时成立。本项目采用其事实边界，不采用 QQ 无法安全承担的默认 at-least-once 重放。
- Nekro Agent 2.3.0 本地快照 `nekro_agent/services/message_service.py:480-640` 在平台响应后创建 canonical `DBChatMessage`，再触发记忆调度和广播；本项目采用“先 canonical fact、后派生”，但补上其 `DBChatMessage.message_id` 缺少唯一约束所不能提供的持久幂等。
- Letta Code `src/channels/message-channel-idempotency.ts`（commit `0655491...`，文件 SHA `583a77f...`）只抑制同 turn 的 in-flight/相邻成功重复，并向 agent 显式报告 duplicate；本项目采用稳定 scope key 与显式重复反馈，但不把内存 Map 当崩溃保证。

## 不采用的方案

### 让 ReceiptMailbox 兼任永久账本

Mailbox 会 consumed/expired 并受容量整理，不具备永久审计与重建语义。

### 在 LLM ack 时写 chat_log

ack 表示一次 LLM 决策成功，不表示动作刚送达；lease 还可能释放或过期，会导致迟写、漏写或重复写。

### 群聊统一记在 bot QQ 名下

普通群回复现有语义是按当前用户归属，主动群发言才记 bot QQ。统一写 bot 会让按人历史、记忆提取和关系上下文串位。

### `INSERT OR IGNORE` 吞掉所有冲突

只能证明唯一键重复，不能证明两份 immutable fact 相同；静默吞掉不同正文或 scope 会掩盖数据损坏。

### 顺手重放所有 handler 成功副作用

多数副作用不是幂等且跨 SQLite/JSON/内存/外部平台，重放比漏掉一次关系增量更危险。

## 实施与验收

1. schema + durable window 只读重建器 dormant 上线；
2. voice producer 写 v2 `conversation_ref`，保持 identity v1；
3. confirmed 原子 fact/chat/window projection 与 DB-only repair；
4. 隔离平台发送/本地 settle 异常域，启用窗口启动恢复与路由前 read-through；
5. 故障注入和生产 canary；
6. 通过后才进入 ADR-002 B2 贴图统一。

最小门禁覆盖稳定 golden action ID、群/私归属与 source row 核验、重复 settle、事实冲突、`uncertain/dead` 零投影、known-confirmed 本地失败不重发、事务中各崩溃点、commit 后重启重建、重复 sync 不增量、跨群/跨用户隔离，以及 ReplyPipeline 部分送达不得写整段 chat。

## 回滚

先停止 v2 producer 和 projector，保留新增表、列、索引及已确认事实；旧模板继续只走运输/mailbox。不得删除事实表，也不得重放任何 confirmed/uncertain 动作。
