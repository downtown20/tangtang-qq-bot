## 一、记忆

| 名称 | 定义 | SQL | 陷阱 |
|------|------|-----|------|
| `memories` | 全部记忆行（含 superseded/retracted） | `SELECT COUNT(*) FROM memories` | **不要用它当「她记得多少」**——含已推翻的 |
| `memories_active` | 当前有效的记忆 | `... WHERE COALESCE(status,'active')='active'` | 所有「可用率」的分母都该是它 |
| `trusted_injectable` | 能进可信召回的活跃记忆 | active **且** `trust_level IN ('verified','manual','corrected')` | 口径**必须**用 active，不是全量 |
| `trusted_blocked` | 活跃但被信任门挡住 | `memories_active − trusted_injectable` | 与 `trusted_injectable` 严格互补 |
| `trusted_cover` | 可信召回覆盖率 | `trusted_injectable / memories_active` | 单人口径 ≠ 全局口径（见 §四） |
| `memories_with_evidence` | `evidence_ids` 非空的活跃记忆 | active 且 `TRIM(COALESCE(evidence_ids,''))<>''` | **≠ 证据关系行数**（见下） |
| `memory_evidence` 行数 | 关系表行数（一条记忆可挂多条原话） | `SELECT COUNT(*) FROM memory_evidence` | 与上一个口径实测差 8 条：legacy 行可能早带着审计线索行 |
| legacy 占比 | 非可信 / 总数 | 分子分母**都是全量**时得到「74.4%」；都用 active 时得到「58.3%」 | **两个都对，但必须说清是哪个**——混用就是今天错误 #2 |

**关键区分**：
- 「有证据」= `memories.evidence_ids` 字段非空（记忆自己声称有证据）
- 「证据覆盖」= `memory_evidence` 表里有关系行（真的挂上了原话）
- 前者是**字段状态**，后者是**关系事实**。汇报里说「有证据 N 条」时，
  默认指前者（`memories_with_evidence`）。

## 二、信任等级

| 等级 | 含义 | 是否放行 |
|------|------|----------|
| `verified` / `manual` / `corrected` | 有证据、或被人工/纠正路径确认 | ✅ 放行 |
| `unverified` | 有引文但未达 verified 的中间态 | ❌ |
| `legacy_unverified` | 2026-08 之前的历史数据，证据字段不可信 | ❌（2026-08-16 事故防线） |
| `NULL` | 等同于 legacy | ❌ |

唯一放行集合：`store.TRUSTED_TRUST_LEVELS`（记忆召回门与画像注入门共用）。
**改这个集合 = 改信任模型**，`health_check.py` 里 6 处只读 SQL 仍写字面量，需同步。

## 三、画像

| 名称 | 定义 | SQL | 陷阱 |
|------|------|-----|------|
| `people_profiled` | 有画像的人 | `COALESCE(notes,'')<>''` | **不过滤 dirty** |
| `people_profiled_injectable` | 能注入的画像 | 非空 **且** `notes_dirty=0` **且** `notes_trust_level IN trusted` | 与 `active_notes()` 同口径 |
| `people_profiled_blocked` | 有画像但不能注入 | `profiled − injectable` | dirty 也算「被挡」 |
| 可合成条件 | `synthesize_profile` 的实际门槛 | ① 输入 `len(memories)≥5`；② 输入过滤后仍 ≥5；③ `len(source_scopes)==1`（**多域直接返回 None**）；④ 非冷却期 | 统计「能重生几人」必须同时满足 ①③，且用**过滤后**的条数（今天错误 #3/#4） |

输入过滤（`synthesize_profile` 内部，2026-08-16 事故防线）：
排除 `key IN ('profile_synthesis','fact_synthesis')`；
再排除 `confidence < 0.75` **除非** `importance ≥ 8` 或 `cognitive='episodic'`。

## 四、作用域（最容易错的一节）

| 名称 | 定义 | 陷阱 |
|------|------|------|
| 私聊域 | `TRIM(COALESCE(source_group_id,'')) = ''` | **名字是私聊，内容不一定是私聊！** |
| 群域 | `source_group_id` 非空 | |
| 跨域 | `recall(source_group_id=None)` 不过滤 | 只有私聊注入召回允许用（单向） |

**最大的坑（2026-10-24 实证）**：`source_group_id` 为空**不等于**「私聊里说的话」。
1,569 条 scope 为空的记忆，其原话都在群消息里——它们是**丢了 scope 的群记忆**。
判据只有一个：去 `chat_log` 看证据原话落在哪个 `group_id`。

**单人口径 vs 全局口径**：剖面页 `counts` 是「与这个人相关」的**混合口径**
（含 ta 说的话 + 关于 ta 的记忆）。主体口径（`qq_id` 严格）会小很多——
3922400700：混合 423 活跃 / 264 可注入；主体 248 活跃 / 26 可注入。
两个都写进汇报时，必须标明是哪一个。

## 五、打分字段（不可当质量用）

| 字段 | 谁写的 | 可靠性 |
|------|--------|--------|
| `importance` 1-10 | 提取器 LLM 在提取时随手打 | **差**。`importance=10` 的样本里有「我觉得可以炒」「我要建个餐厅」 |
| `confidence` 0-1 | 同上（明确陈述=1.0 / 暗示=0.7-0.8） | 中。它是**合成门槛**的依据，不是真值 |

`importance` 筛的是**影响面**，不是**内容价值**。用它分批可以，用它判断
「这条记忆重不重要」不行。

## 六、计数器（运维用）

| 名称 | 定义 |
|------|------|
| `memory_reverification_events` | 受控重验证事件（每次 legacy→verified 一条）。`reviewer` 含批次号，是回滚句柄 |
| `memory_revisions` | 变更流水（append-only）。`actor` 标明是谁改的，`before_value`/`after_value` 可还原 |
| 回滚定位 | 按 `reviewer IN ('backfill:substring:<批次>', 'backfill:semantic:<批次>')` |

## 七、常用查询（可直接跑）

```sql
-- 全局可用率（唯一正确的口径）
SELECT
  SUM(COALESCE(status,'active')='active') AS active,
  SUM(COALESCE(status,'active')='active'
      AND COALESCE(trust_level,'legacy_unverified')
          IN ('verified','manual','corrected')) AS injectable
FROM memories;

-- 单人主体口径（不是剖面页的混合口径）
SELECT COUNT(*) FROM memories
WHERE qq_id=? AND COALESCE(status,'active')='active'
  AND COALESCE(trust_level,'legacy_unverified') IN ('verified','manual','corrected');

-- 私聊域的真实构成（配合 §四 的坑）
SELECT CASE WHEN TRIM(COALESCE(source_group_id,''))='' THEN 'empty' ELSE 'group' END,
       COUNT(*) FROM memories WHERE COALESCE(status,'active')='active' GROUP BY 1;
```
