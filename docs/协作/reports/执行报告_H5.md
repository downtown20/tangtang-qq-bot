## P3-1 窗口统计审计与修复：完成

### 已确认根因

2026-09-02 C1 的 `skip=11 / total=19` 不是同一日或同一批次的漏斗：其查询读取逐指标 `metric:latest:*` 镜像。该镜像在每次 flush 时把每个指标单独覆写为**该指标最后一次有增量那一天的日计数**；它不是多指标原子快照。

本批生产库只读复核的原始行：

```text
metric:2026-08-28:window_decisions_reply=145
metric:2026-08-28:window_decisions_skip=11
metric:2026-08-28:window_decisions_total=156
metric:2026-09-01:window_decisions_reply=19
metric:2026-09-01:window_decisions_total=19
metric:latest:window_decisions_skip=11       # 更新于 2026-08-28
metric:latest:window_decisions_reply=19      # 更新于 2026-09-01
metric:latest:window_decisions_total=19      # 更新于 2026-09-01
```

每个有样本的日分区均满足 `total = reply + skip`；C1 把异日镜像拼接为同一分母才产生假不一致。

### 各表口径

- `decision_runs`：所有含 `ChatContext` 的 LLM 终态，现有 schema 没有窗口标记；不能以整表 group 行数作为窗口分母。
- `conversation_window_events`：仅确认发送后的 bot 对话投影，用于重启恢复窗口；不是 skip/fade 事实表。
- `reply_metrics`：所有已发送回复的匿名质量特征；没有窗口字段，不能作为窗口决策分母。
- `window_decisions_*`：当前窗口 LLM 回合的日计数；`fade` 是连续 skip 触发的窗口状态转换，为 skip 子集而非第三个互斥决策。

### 最小修复

- `MemoryMetrics.record_window_decision()` 现在只接收 `status=completed` 的 `DecisionRun`，统一递增 `total` 与互斥的 `reply/skip`；`action` 按既有“本回合已响应”语义归为 reply。
- `handle_group_message()` 先消费本回合终态 `DecisionRun`，再由该唯一对象派生计数、连续 skip 的 tracker 状态转换与 reply/skip 日志。删除原先分散在 `turn_actions.respond` 两支中的 `total/reply/skip/fade` 直接计数与窗口日志判定。
- `fade` 仍是连续 skip 后的窗口状态转换，保留为 skip 子集；因此分母恒为 `total = reply + skip`，不把 `fade` 误加成第三个互斥结果。
- 观察器已经只读取按日分区的 `metrics`/`metrics_total`，不使用 `latest` 镜像；`conversation_window_events` 与 `reply_metrics` 继续只服务各自的发送恢复/质量遥测用途，不参与窗口决策分母。

## P3-2 持久生命周期验证：完成（2 项通过、2 项未满足）

### 1. 驱动力：显式快照恢复通过；自动持久化节律未满足

临时 `.tangtang_self.json` 演练先设置 `social=0.456`、`commitment=0.654` 并调用 `save()`，新建 `TangTangSelf` 的 `get_state_json()` 与保存前快照完全一致。

随后不调用 save，直接执行 `tick()` 和 `release('social', 0.10)` 后重建对象，重启态回到上次已保存快照；本次 tick/release 的变化丢失。真实输出：

```text
drives_explicit_restore=exact
drives_tick_release_without_save=lost_on_restart
```

根因位于 `agent/self_state.py:443-450,490-495`：`tick()` 只更新 drives，`_auto_save()` 只由 `update_relationship()` 触发，且为每 10 次关系更新一次。群/私消息和 10 分钟自治循环都可调用 tick；多条自治 `release()` 也不触发保存。因此“重启最多丢 ≤9 次增量”只适用于恰好伴随关系更新的路径，不是 drives 的全局保证；在没有关系更新的自治运行中，未落盘的 tick/release 数没有上界。本批不改动力学参数，也不把这一验证失败伪报为可接受。

### 2. Feedback：写入可读取，但没有 cursor 清除语义

`Store.record_feedback()` 已在临时库写入可信反馈；`MessageHandler._get_feedback_reflection_context()` 能读取并写入 `feedback:last_reflection_id:<qq>` 与 `feedback:last_consumed`。但全局 `feedback:last_consumed` 保存的是时间戳，不是可推进的 id cursor；该方法仍会在下一次读取返回同一条反馈，不清除也不按此 key 过滤。

```text
feedback_written=1 feedback_rows_after_two_reads=1 repeated_context=True
```

所以“DB 行不丢”成立，但“无重复消费/消费后清除”不成立：同一可信反馈会被重复注入当前用户上下文，直到出现更晚的反馈。此项为验证失败，不在本简报“验证而非新写”的授权范围内修复。

### 3. 主动意图：持久化和重启恢复通过（含遗漏状态提示）

临时 SQLite 覆盖了 `pending/claimed/executing/confirmed/failed/uncertain/skipped`：重启恢复将 `claimed→pending`、`executing→uncertain`，并保留 pending 与三个终态；租约清理由 store 原子更新完成。

```text
proactive_recovery={'pending': 'pending', 'claimed': 'pending',
 'executing': 'uncertain', 'confirmed': 'confirmed', 'failed': 'failed',
 'skipped': 'skipped', 'decided': 'decided'}
```

现有 schema 另有 `decided` 状态，且 `recover_proactive_events_after_restart()` 不转换它；本批未把它擅自归入任何终态。

### 4. promise → completion：通过

以真实 `MemorySystem`、`Store` 和 handler 的 `_extract_self_memories_llm()` 在临时库执行：有同对象同作用域的 promise 与 action_completed 时，`fulfill_self_promise()` 将 promise 置为 `fulfilled`、重启后不再返回为 active；handler 随后精确调用一次 `drives.release('commitment', 0.2)`。

```text
promise_settlement=fulfilled release=[('commitment', 0.2)]
```

#### 方案理由

- drives 的共同根因是状态写入与关系更新绑定。把回调放在 `DriveSystem.tick/release` 这一对统一变更入口，自治和消息路径不必逐个补写；每 10 次独立变更形成一个保存批次，因此没有关系更新时最多跨一个批次未持久化。既有异步保存/幂等写入机制继续复用。
- `feedback:last_consumed` 现有键名无用户后缀，并且 H5 已将它定位为全局消费记录，故保留**全局 cursor**语义；原来的 `feedback:last_reflection_id:<qq>` 只是未参与查询过滤的旁路标记，去除后不再制造双真相。全局 cursor 的日报时间戳职责转移到 `feedback:last_reported`，避免任何路径把 id 覆写回时间字符串。
- 旧值若是时间戳或其他非整数，解析失败即按 `0` 查询：保持既有 30 天反思窗口的首次全量读取，成功消费后自然迁移为 id。
