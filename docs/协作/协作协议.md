# 协作协议 —— 主负责人 × Codex 副负责人

> 角色定义见《Codex角色卡.md》。本文件是干活规矩：通信格式、质量闸门、裁决流程。双方一致遵守，任何一方发现违反即打回。

## 一、通信格式（docs/协作/ 下）

| 文件 | 谁写 | 内容 |
|---|---|---|
| `briefs/任务简报_XX.md` | 主负责人 | 目标、现状取证、范围、验收标准、危险区、禁入区 |
| `reports/执行报告_XX.md` | Codex | 改动清单、验证证据、遗留问题、异议栏 |
| `rulings/裁决_XX.md` | 主负责人 | 通过/返工/搁置 + 对异议栏的逐条回应 |

简报编号：`A`=legacy 审计批次，`B`=重启 canary，`C`=P1 优化，`D`=矩阵收尾。同一简报的返工用 `_R2` 后缀。

## 二、执行报告格式（Codex 必填，缺项即返工）

1. **改动清单**：文件:行号 + 一句话说明
2. **验证证据**：pytest 输出摘要、pyflakes 输出、DB 查询结果——粘贴真实输出，不许转述
3. **影响面**：GitNexus impact 结论（触及符号的调用方、风险等级）
4. **遗留问题**：没做完/没验证的，明确列出
5. **异议**：对简报的任何质疑或改进建议；没有就写「无」

## 三、共享质量闸门（双方一致）

1. **Read before Edit**——不读不改；大段替换用 Edit 工具逐字匹配，禁 heredoc 正则盲改
2. **One change, one verify**——一批一验证，不连续改多个文件后一把梭
3. **pytest 全量绿**——最低底线；定向回归必须覆盖新路径
4. **pyflakes undefined 清零**——`python tools/静态检查.py`（它自己 glob 并打印实际扫描文件数；不要手写带 glob 的 pyflakes 命令，pwsh/cmd 不展开会静默漏扫——教训 #30）
5. **GitNexus impact 先行**——改任何符号前跑 impact；HIGH/CRITICAL 必须上报主负责人
6. **detect_changes 提交前检查**——核对影响面只在预期符号内（本项目无 git，用作影响面审计）
7. **破坏性操作备份先行**——生产 DB 写操作、大段删除、配置变更，先备份
8. **修复假设先取证**——查 DB、查日志、查注入源，再动手
9. **方法定义只插在方法边界处**——`def` 插进 `__init__` 中段 = 后续初始化全部变死代码
10. **schema 变更走项目迁移纪律**——store.py 有 schema checksum/manifest 机制，改表必须同步

**常设条款（2026-09-03 起，不再逐简报重复）**：Codex 沙箱内无 `python`/pytest/pyflakes 且网络被拒（WinError 10013）——正式 pytest 全量、pyflakes undefined 门禁一律由主负责人环境复跑；执行报告只允许如实记录「未能执行」，禁止宣称通过。沙箱产物（如 `.uv-cache`）由主负责人清理。

**模型策略（2026-09-03 夜，主人指定，已纠正过一次）**：一般任务用 `gpt-5.6-terra` + `model_reasoning_effort="xhigh"`；**难度大的任务用 `gpt-5.6-sol` + `high`**。派发时在 dispatch 提示词里注明用哪个档位。

**H 批次追加条款（2026-09-03 夜）**：
- **迁移必须声明用户可见行为是否保持**（H6-R2 教训：把一条消息拆两条是未授权 UX 改变）——简报危险区必答：本次改动用户看到的行为有无变化？变化必须由主负责人批准
- 备份命名带批次号：`.bak-YYYYMMDD-<批次>`（同一天多批次共用 `.bak-20260903` 会互相覆盖——G1 已发生一次、H1 又覆盖一轮）
- Terra/xhigh 大会话（>300K tokens）会在中转端触发 remote compact 失败导致会话不可 resume——简报必须要求执行方**边做边写报告草稿**（每完成一个阶段把关键改动/证据追加进报告文件），即使会话中断，报告也从磁盘可重建
- `codex exec resume` 不接受 `-s` 参数（sandbox 继承原会话）；compact 失败时改派新会话从 `.bak` diff 重建报告

## 四、裁决流程

```
简报 → Codex 执行 → 执行报告 → 主负责人独立验证（自己跑测试、读 diff、查 DB）
     → 裁决：通过 / 返工（rulings 写明原因） / 搁置（写明原因）
```

主负责人不依赖 Codex 的自评——必须独立验证。Codex 也不依赖主负责人的假设——简报有错就写异议栏。

## 五、变更管理（无 git 项目的替代）

- 改文件前对受影响文件做 `.bak-YYYYMMDD` 或 backups/ 副本（项目惯例）
- 每批变更在简报→报告闭环内自洽；rulings/ 是变更历史的事实源之一
- 阶段总结、验收矩阵的更新是变更的一部分，批次 D 统一收口
