## Important 1：群反馈没有绑定被回复对象，错误材料已进入 LLM 反思链

**位置**：`agent/handler.py:285`、`agent/handler.py:1361-1369`、`agent/handler.py:2230-2232`、`agent/handler.py:6959-6977`、`agent/perception.py:28-50`。

**证据**：

- `_last_bot_reply` 在群聊仅保存 `{group_id: (reply_text, timestamp)}`，没有目标用户、bot 消息 ID或引用关系；发送后写入群级单槽，下一条任意群消息会 `pop` 并进入 `PerceptionEngine.evaluate()`。
- DB 近 7 日有 545 条群反馈，其中 210 条“反应”明确 `@QQ` 了另一个人，103 条只是图片；没有一条显式 @ 机器人。时间接近只能证明先后，不能证明回应方向。
- `feedback#4911` 是实存反例：bot 上一条在聊歌曲，下一条消息却 @ 另一名群友问睡没睡，仍被配成 bot reply 的反馈。
- GitNexus 确认 `_get_feedback_reflection_context` 同时被群聊和私聊主链调用；这些错误配对不是只用于报表，而会作为带来源的“反思”重新交给 LLM。

**根因**：反馈模型只有时间邻近，没有“bot 回复发给谁、用户回复了哪条消息”的因果键。把群聊时序误当作对话方向，随后又以 `user_qq` 归属给碰巧说下一句话的人。

**最小修复建议**：群聊反馈槽至少保存 `bot_message_id + target_user + group_id + sent_at`。只采集两类客观候选：明确引用该 bot 消息，或同一目标用户仍在其活跃窗口内继续说话；其余消息不进入反馈表。旧群反馈应标记为 `untrusted_legacy` 或在反思读取时排除，私聊链保持现状。补三条回归：A 回复 bot、B 紧接着说话、B 引用别人，只有 A/明确引用 bot 的事件可入库。

## Important 2：`chat_log` 无索引叠加逐用户扫描，每 10 分钟阻塞事件循环约 7.7 秒

**位置**：`agent/store.py:44-50`、`agent/store.py:56-61`、`agent/store.py:1450-1466`、`agent/store.py:2622-2629`、`agent/handler_autonomy.py:1057-1096`。

**证据**：

- `PRAGMA index_list('chat_log')` 返回空；`EXPLAIN QUERY PLAN` 显示用户计数只能借 rowid 范围搜索，群最近记录/最后群记录为 scan。
- 当前兜底风格先 `GROUP BY` 一次，再对 458 个用户逐个 `count_unprocessed_messages()`：459 次连接，生产库只读实测 7,717.86ms。
- 运行日志同样给出墙钟证据：`tangtang.log:847751` 于 15:45:23 开始本周期健康/扫描，第一批兜底任务到 `847752` 的 15:45:30 才被调度。
- 在包含同一批 231,216 个键行的内存副本上做 A/B：458 用户计数无索引 2,178.81ms；加入 `(qq_id,is_bot_reply,id)` 后 5.03ms，结果相同，快 432.9 倍。实际库额外叠加连接与磁盘开销。
- 普通单用户查询目前仍较轻：`get_user_recent_messages` 中位 0.93ms、`find_last_group` 1.53ms。问题集中在周期性 N+1 全量扫描，不应先重写所有 Store 查询。

**根因**：高频过滤列没有复合索引；异步自治循环里同步执行全量 N+1 SQLite 调用，I/O 和扫描时间直接占住事件循环。

**最小修复建议**：先增加 `chat_log(qq_id,is_bot_reply,id)`，必要时增加 `chat_log(group_id,id)`；再把积压统计收口为 Store 的单次批量查询，禁止自治层逐用户开连接。731MB 数据库建索引需显式迁移进度、启动外执行或可恢复迁移，不能在 bot 启动主线程悄悄建。验收目标：完整 stale 扫描 p95 <100ms，扫描期间消息入口延迟无可见尖峰。

## Important 3：正常 `[]` 被计为 LLM 失败，提取健康度与真实质量相反

**位置**：`agent/memory.py:970-1179`、`agent/handler.py:7155-7205`、`agent/metrics.py:32-44`、`agent/health_check.py:167-178`。

**证据**：

- 当前重启后的前两轮兜底共 12 次抽取：9 次严格返回 `[]`、2 次返回有效记忆、1 次 `Extra data` 解析失败。协议明确要求“没有新信息返回 []”，因此 LLM 协议成功率是 11/12（91.7%），产出率是 2/12（16.7%）。
- 调用方只看 `if items`：9 个合法空数组与 1 个解析失败都会 `record_extract_empty()`，等价成 2 次成功、10 次失败。
- 只读探针复现：`extract_semantic_memories()` 对 `[]` 返回 `items=[]`、`stats={'raw':0,'valid':0,'rejected':0}`，随后指标产生 `extract_llm_failures=1`。
- 持久指标为 attempts=180、successes=8、failures=172，健康日志因此报告“成功率仅 5%”；这不能推出 LLM 经常失败。
- 解析器用 `find('[')` + `rfind(']')` 后整体 `json.loads`；探针输入两个 JSON 数组 `[]\n[]` 与现场相同地得到 `Extra data: line 2 column 1`。

**根因**：一个二元组同时承担协议是否成功、是否产出、被拒绝多少条三种语义；指标把“产出条数”误当“调用成功”。解析失败也没有独立类型。

**最小修复建议**：返回显式结果对象或枚举：`success_with_items / success_empty / rejected_all / invalid_json / transport_error / busy`。健康检查分别展示协议成功率、记忆产出率、解析失败率和 busy 率；有效 `[]` 推进游标但不记失败。解析应只接受一个完整 JSON 文档，重复/尾随内容记录原始长度与独立错误码，可做一次有界修复，不能静默吞并多个数组。

## Important 4：发送失败仍写入“已发送”历史，关系状态也发生成功式收尾

**位置**：`agent/handler.py:7901-7967`、`agent/self_check.py:135-139`、`agent/handler.py:2211-2267`、`agent/handler.py:3010-3067`。

**证据**：

- `_checked_send()` 在 `sent_ok = await self.reply.send(...)` 后无条件 `record_sent(target_id, reply)`，只有遥测才受 `if sent_ok` 保护。
- 只读 fake sender 探针让 `ReplyPipeline` 返回 False：函数正确返回 False，但 `_sent_history` 仍出现该文本，证明“返回值闭环”和“状态提交闭环”不一致。
- 群聊 `agent/handler.py:2242` 与私聊 `agent/handler.py:3044` 无条件增加亲密度；群聊后续情绪事件也不受 `ok` 约束。近 20 万行日志中出现 500 条“发送失败”相关记录，失败分支并非不可达；当前重启后暂未再出现发送失败。

**根因**：生成、尝试发送、成功提交散落在多个位置；没有以 `sent_ok` 为唯一提交边界。

**最小修复建议**：把 `record_sent`、bot chat_log、自忆、窗口续期、发送型亲密度、发送情绪和记忆强化统一放进成功提交段。被自检拦截时，兜底文本也必须根据真实发送 bool 决定是否 `record_sent`。保留“用户主动 @/叫名字”产生的到达型关系信号，但与“糖糖成功回应”分开计数。补群/私聊发送 False、兜底也失败、分段部分失败三类测试。

## Important 5：已有 `_safe_task`，关键 fire-and-forget 仍大量绕过它

**位置**：`agent/handler.py:671-685`、`agent/handler.py:1486`、`agent/handler.py:7218-7237`、`agent/handler_autonomy.py:1095`、`agent/handler_autonomy.py:1135`。

**证据**：

- `agent/` 下有 50 个直接 `asyncio.create_task()` 调用点；`_safe_task()` 已能登记、命名、统一取消并读取异常，但记忆抽取、画像、整合、Episode、反馈等关键任务仍直接创建。
- 近 20 万行历史日志有 8 次 `Task exception was never retrieved`，全部来自裸调度的 `_extract_memories_with_llm()`；异常是跨模块参数契约漂移，任务未被业务指标捕获。
- 当前 `_extract_memories_with_llm()` 只有 `try/finally` 清 in-flight 集合，没有 `except`；未来 Store/模型契约异常仍会沿同一裸任务路径交给事件循环兜底。

**根因**：后台任务创建没有收口；“异常可观察、停止时可取消”的正确工具存在，但使用纪律未建立。

**最小修复建议**：handler 内所有不 await 的业务协程统一走 `_safe_task(coro,name)`；计时器/组件自持 loop 可保留各自句柄，但必须有 done callback 或 stop。为抽取任务增加 `scheduled/succeeded/empty/failed/cancelled` 指标，并用一次会抛异常的测试证明不会出现 `Task exception was never retrieved`。

## Minor 与优化项

### 1. 工具 schema 是最大可量化 token 成本

- 近 20 万行日志有 1,967 个带工具回合：schema 平均约 11,582.8 token，中位 11,168，合计估算 22,783,451 token。
- 只有 411/1,967（20.9%）回合发生至少一次工具调用；1,556 个无工具回合仍携带约 17,904,703 token 的 schema。
- 34 工具回合占 1,589 次，工具命中率 18.4%；46 工具回合 277 次，命中率 35.0%。
- 单独的 19 个记忆/行为工具约 6,472 token；其中 6 个工具在该日志窗中调用不超过 5 次，却常驻约 1,946 token。

建议保持 LLM 单脑，不用中文关键词替模型选能力。先按客观权限/渠道裁剪不可能执行的工具，再试“核心工具 + `discover_capabilities`/二阶段加载低频 schema”。A/B 必须同时看 schema token、首 token 延迟、工具漏调用率和最终任务完成率；在没有漏调用证据前不要直接删除低频能力。

### 2. “hourly” 健康检查实际每 10 分钟执行，且启动后立即重复

- `_autonomous_loop()` 每轮末尾 sleep 600s，但每轮都直接 `run_hourly()`；没有小时门。
- 启动先 `run_startup()` 全量检查，紧接第一次循环又 `run_hourly()`。探针注册一个 hourly 项后连续调用两入口，得到零等待执行 2 次。
- 日志 `stale_extraction` 在 15:35:13、15:35:16、15:45:23 重复；这既放大日志噪音，也额外执行同步 DB 扫描。
- `_check_extract_busy` 又用 `skipped/(attempts+skipped)`，但 skipped 已包含在 attempts 中。探针 attempts=10、skipped=6，真实 60%，函数算 37.5% 并返回正常。

建议让调度器根据 `last_run` 真正做小时门；启动刚跑过的 hourly 项不要立即重跑。健康读取用 `get_current()` 或先 flush，busy 比例改为 `skipped/attempts`。feedback 健康检查还应检查消费时间/覆盖面，而不只是全局 key 是否存在。

### 3. 群聊证据纪律重复注入

`agent/handler.py:1978` 和 `1980` 连续追加完全相同的 `MEMORY_EVIDENCE_CONTRACT`。单份估算 156 token，当前群聊会变成约 312 token；删除重复项即可，测试应断言背景标签只出现一次。

### 4. 长方法已经妨碍状态边界审查，但不宜大爆炸重构

AST 测量：`handle_group_message` 981 行/236 个分支，`_execute_tool` 767 行/295 个分支，`handle_private_message` 651 行/152 个分支，`_execute_natural_action` 455 行/109 个分支；全 agent 有 9 个超过 200 行的方法。发送失败状态散落和群反馈错误都发生在这些长编排方法中。

建议先修上述可证明缺陷，再按稳定边界小步提取：反馈候选收集、回合成功提交、工具目录、后台任务调度。每次只搬一个边界并补入口回归；不要用大段文本替换切 handler。

## 不应优先优化的部分

- `chat_index` embedding 约 295.2MB，`memory_embeddings` 约 32.9MB，但数据库 freelist=0、chat_index orphan=0；当前最大用户 13,141 个向量的语义检索中位 66.45ms。存储较大但尚无失效或不可接受延迟证据，不应抢在 `chat_log` 7.7s 阻塞前动量化格式。
- 语音、ASR、角色动态模型与独立贴图库当前没有新的错误证据；继续换引擎/重做媒体链不是本轮主要矛盾。
- 窗口自主回复已有协议和单元测试，但重启后尚无真实 `window_decisions_*` 样本。应先观察 reply/skip/fade 分布，不凭零样本继续调 prompt。

## 建议实施顺序

1. **反馈真值止血**：先停止不具方向证据的群反馈进入 LLM 反思；加目标/消息 ID 绑定并隔离旧数据。
2. **后台延迟止血**：补 `chat_log` 复合索引、批量化 stale 统计，把 7.7s 阻塞压到 100ms 内。
3. **抽取可观测性根治**：显式 outcome、合法空结果、解析失败与 busy 分开；再判断真实提取质量。
4. **发送事务边界**：只有实际送达后才提交已发送历史与发送型关系状态。
5. **任务与健康调度收口**：统一 `_safe_task`，修 hourly 门和 busy 算法。
6. **成本优化**：建立工具 profile/discovery A/B；最后再拆长方法。

## 复验清单
