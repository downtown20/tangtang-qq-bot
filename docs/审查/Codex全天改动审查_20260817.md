## 问题清单

### High

1. **[agent/handler.py:6797] 昵称交叉上下文用 `nnick in text` 做中文子串匹配，可把普通话语误判为提到某人，随后把该人的画像和最近 5 条私聊交给 LLM。** 解析出的 QQ 会在 `agent/handler.py:2600-2622` 加载第三人的画像及私聊；虽然 `agent/handler.py:6806` 对 QQ 路径和昵称路径共用了“主人或亲密度≥50”闸门，没有出现直接越权绕过，但高亲密用户说到与昵称相同的普通词（如昵称“外卖”，消息“我今天吃外卖”）仍会意外引入第三人隐私。此实现也直接违反项目“中文不得用子串匹配，须用 jieba 完整词匹配”的纪律。另有契约漂移：`find_qq_by_nickname(fuzzy=False)` 会忽略昵称开头的 `@`，而 `list_people_nicknames()` 返回原值，`_resolve_mentioned_people()` 不归一化，因此库中 `@昵称` 无法由消息里的“昵称”命中。**建议修复：权限闸门前置；规范化 `@`；用 `word_match`/jieba 完整词与明确 @ 提及解析，排除纯标点/过短通用词；按消息出现顺序稳定选最多 3 人。**

2. **[agent/store.py:600] “精确昵称解析”遇到同名时用无排序、无唯一性检查的 `LIMIT 1` 任取一人；精确别名同样会在重名中取最新一条，随后可进入破坏性纠正。** 真实库已存在重复规范化昵称（4 组）和重复别名（7 组，例如同一别名对应多人）；最小临时库探针也确认两个同名对象会静默返回第一个。`agent/handler.py:4051-4054` 把该结果直接作为 subject，主人纠第三人时权限检查必然通过，可能重演“纠正错人”。当 `subject_qq` 与 `subject_name` 同时传入时，执行器还会完全忽略 name，不复核两者是否一致。为什么是问题：`fuzzy=False` 只消除了模糊命中，没有消除歧义，工具描述中“匹配不到或不确定时拒绝”与实现不符。**建议修复：Store 返回全部精确候选或显式 ambiguous 状态；候选数不等于 1 时 fail-closed；同时提供 QQ/name 时必须解析并校验一致；新增真实重复昵称、重复别名和 QQ/name 冲突测试。**

3. **[agent/handler.py:356] 亲密模式把一次会话中的敏感激活状态无限期恢复，且配置撤权不会清除旧状态，重新授权后会自动复活。** 每轮权限确实由 `scenario_targets` 重算，因此撤权期间不会套用亲密场景；但 `_sed_active` 中的旧 QQ 不会被移除。以后重新授权或配置误恢复时，下一条普通消息会直接进入亲密 overlay/专用模型，无需重新 `[进入色色]`。重启后继续激活也把“冷却/配额必须持久化”的铁律错误套到了应随会话/同意状态过期的敏感模式。当前 DB 恰好为空，只说明此刻没有即时暴露，不消除状态机缺陷。**建议修复：把激活记录改为带时间戳和短 TTL/会话边界的结构；加载时只恢复仍有效且仍获授权的记录；撤权/配置重载时主动清除；重新授权要求再次进入。若产品明确要跨重启保留，也至少要求过期、显式同意与审计日志。**

### Medium

4. **[agent/handler.py:6825] marker 解析接受回复任意位置的标签，并固定“先退出、后进入”，没有执行文档声明的“单个、回复末尾”协议。** 若回复同时含两个标记，最终状态永远是激活，无视文本先后；讨论或复述 `[进入色色]` 也会切换。无权限私聊不会切换且标签会剥除，这一点正确；用户输入本身也不会直接进入处理器，但诱导 LLM 原样输出仍可触发。**建议修复：只接受末尾唯一 marker；两个同时出现或 marker 位于正文时只剥除并拒绝切换/记录告警；补顺序、双标记、正文引用、纯标记导致空回复测试。**

5. **[agent/handler.py:1737；agent/handler.py:2077] 新状态机只接了私聊，群聊若显式配置 seductive 仍是永久常驻，LLM 输出 marker 只会被 clean 剥掉而不会改变状态。** 当前群配置没有亲密场景，所以现网暂不触发；但架构允许群 `scenario_targets`/默认场景选 seductive，届时会复现本批声称已解决的“静态常驻、无法退出”。**建议修复：明确产品契约。若亲密模式只允许私聊，群场景解析应 fail-closed 拒绝 seductive；若群聊也支持，则在 `_enrich_reply` 前接同一状态机，并按 `(group_id,user_id)` 隔离状态与权限。**

6. **[tools/cleanup_wrong_subject_correction_20260817.py:106] 清理脚本不是可重复收敛的幂等脚本；当前真实 DB dry-run 仍报告 `B4 群主 notes_dirty=1`。** 后台画像重合成会把 `notes_dirty` 清零，而 `plan_b/apply` 不检查错误事实是否仍存在，之后每次重跑都会再次标脏。另有误伤面：A1 会撤销 owner 下所有包含“高一新生”的 active `fact_correction`，B1/B2 会撤销 target 下所有包含“33岁/三十三/上班族”的 active 事实，硬编码恢复 id=7644、修改 id=17477 时也没有同时校验 qq_id/key/value。为什么是问题：脚本保留着 `--apply` 且文档宣称可重复执行，未来运维重跑可能撤销同文本的无关事实或制造无意义重合成。**建议修复：用事故行 ID + qq_id + key + 预期 value/status 做 CAS 条件；B4 仅在本次实际撤销了错误行时设置；apply 后重新 plan 并断言零项；为临时 DB 增加事务回滚、相似但不相关事实、第三次运行仍零变更测试。** 单个 `with conn` 事务覆盖 A/B 是正确的，异常可整体回滚。

7. **[agent/handler.py:6810；agent/handler.py:7476] `_sed_active` 的集合修改与 KV 保存之间没有 `await`，在单事件循环内不会发生协程级撕裂；但落盘异常被 `_save_state_kv` 静默吞掉，调用方仍记录“进入/退出成功”。** SQLite 写是同步调用，遇到锁可在事件循环阻塞最多 5 秒；失败后内存状态和重启状态分叉，违背本功能的持久化承诺。`_resynthesize_profile_later` 不访问 `_sed_active`，未发现与画像后台任务的直接竞态。**建议修复：让保存返回成功/失败并限频告警；敏感状态切换至少在日志中区分“内存成功、持久化失败”；若保留落盘，考虑短事务放线程或专用状态写队列。**

8. **[agent/handler.py:6800] 每条私聊都同步查询并遍历全量 people，且低权限用户也是遍历完成后才清空结果。** 当前 459 行尚不构成严重性能瓶颈，SQLite 单查询快照也保证了本次列表内部一致；但它发生在事件循环上，规模增长后延迟线性上升，并且 set→list[:3] 让三人上限选择不稳定。**建议修复：先做权限短路；建立规范化昵称索引/缓存并在人物更新时失效，或用分词候选反查；保留确定性的消息出现顺序。**

9. **[tests/test_protocols.py:247；tests/test_memory_correction.py:182] 新增测试以 `object.__new__` 和源码正则为主，没有走完整私聊/群聊装配，形成多处假绿空间。** marker 测试证明了小函数切换和剥除，但没证明生产顺序确实在 `_enrich_reply/clean` 前，也没覆盖群聊、重启 round-trip、撤权/重授权、双 marker；“无权限用户发出的标记”实际测试的是 LLM reply 参数，不是用户输入路径。昵称测试没有 `@` 归一化、普通词误命中、同名/同别名、三人稳定顺序和完整交叉上下文隐私测试；清理脚本无测试。**建议修复：优先补上述 High 的路径级测试，并用临时 SQLite 做真实持久化和脚本三次运行测试。**

## 跨模块契约结论

- `correct_memory()` 的生产消费者只有 handler 执行器；成功与零匹配返回均含 `matched`，执行器只在 `matched>0` 后设置 `turn_actions["memory_correction_applied"]`，这部分正确。空 `wrong_fact` 的内部早退仍没有 `matched`，但生产执行器在调用前已拒绝空值，当前不构成路径错误；建议顺手统一返回结构。
- correct/forget schema 把 subject 从 required 移除后，executor 会在 subject_qq/name 均缺失时 fail-closed，不会默认写当前用户；非主人纠第三人也在昵称解析后再次复验，未发现权限绕过。剩余风险是“唯一解析”并不唯一，以及 QQ/name 同传不校验。
- `list_people_nicknames()` 与 `find_qq_by_nickname(fuzzy=False)` 语义不一致：前者原样返回 `@`，后者归一化；必须统一。
- `correct_memory()` 的零匹配路径不会写 corrected fact；记忆、簇事实、notes 全不命中时返回 matched=0，符合事故修复目标。

## 明确未发现问题的方面

- 私聊 marker 的调用顺序正确：LLM reply → `_process_seductive_markers()` → `_enrich_reply()` → `ReplyPipeline.clean()`；clean 不会先吃掉 marker 导致状态不切换。
- 无 seductive 权限时，即使 LLM reply 含 marker，也只剥除、不写 `_sed_active`；用户输入文本不会被直接当作状态命令执行。
- `_seductive_knowledge_cache` 只是全局只读内容缓存。退出后 `private_scenario=None`、`knowledge=""`，缓存虽留在内存但不会继续注入，未发现跨用户状态污染。
- 私聊昵称与 QQ 两条交叉上下文解析共用同一权限闸门；未发现昵称路径绕过“主人/亲密度≥50”。
- B 的零匹配 fail-closed、真实纠正后才设置 turn action、后台重合成在主 LLM 工具调用结束后启动，均符合既有工具锁和自忆门控契约。
- D 的 A/B 写操作处于同一个 SQLite 事务内，具备异常整体回滚能力；问题在命中条件和重复运行语义，不在事务边界。
