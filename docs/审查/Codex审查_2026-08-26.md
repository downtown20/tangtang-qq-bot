## 复查补记（当日整改）

三项 Important 已完成代码整改：积压按用户消息行精确计数，倒序查询受前向游标下界约束，历史用户进入统一兜底队列；dirty 非空画像进入带 6 小时冷却的重试队列；feedback 以当前用户最近的原文对、`feedback#ID`、时间和群来源注入群/私聊 LLM 背景，不向模型提供情绪分数，也不由系统据此门控回复。

游标取证同时得到一条修正：`COUNT(id > last_extracted_id)` 是“前向游标后的消息数”，不能一概称为真实未处理数，因为旧版倒序回填没有持久化起始高水位，区间可能重叠。整改选择保守策略：不跳过无法证明已覆盖的消息，允许前向路径一次性去重重放；新倒序查询不再扩大重叠。此限制已写入结论，避免再次把游标推断当事实。

## Important 1（已整改）：记忆积压统计使用全局消息 ID，且旧回填游标会遮蔽正向积压

**位置**：`agent/health_check.py:180-195`、`agent/handler_autonomy.py:928-1087`、`agent/store.py:1401-1424`。

**证据**：

- 日志 `tangtang.log:840605-847144` 从 00:14 到 14:45 持续报告 15-18 个用户积压。
- DB/状态探针比较 `.extraction_state.json` 与 `chat_log`：健康检查按 `MAX(id)-last_id` 判断前20人得到 16 个 stale，但精确 `COUNT WHERE qq_id=? AND id>?` 只有 8 个，说明一半是全局自增 ID 间隙造成的假阳性。
- 精确 COUNT 显示 4 个样本的前向游标后分别有 4048、4185、226、1638 条用户消息；这些是待推进区间，旧倒序回填可能已覆盖其中一部分。
- 例：QQ 2470404655 的 `last_extracted_id=16937`、`backfill_to_id=16903`，两个标量游标已经交叉，但旧状态没有保存倒序起始高水位，无法证明 `id>16937` 的 4048 条分别由哪条路径处理过。

**根因**：`chat_log.id` 是全表自增值，不能用 ID 差表示某个用户的消息条数；正向提取和倒序回填使用两套标量游标，旧版未保存倒序起始高水位，交叉后无法无歧义合并。兜底又只看近3天活跃用户，历史大洞不会进入队列。

**最小修复建议**：

1. Store 增加统一的 `count_unprocessed_messages(qq_id,last_id)`，健康检查、回填排序和控制台只用精确 COUNT；
2. 倒序查询增加 `id>last_extracted_id` 下界，禁止越过前向游标；旧状态无法证明覆盖的区间由前向路径保守推进；
3. 兜底队列按真实积压数排序，保留每轮上限，但不要只依赖近3天活跃榜；
4. 加回归测试：构造 A/B 用户交错 ID，证明 ID 差大但 A 实际无积压时不告警；证明倒序查询不会越过前向游标，历史用户仍进入正向消化。

## Important 2（已整改）：纠正后的 dirty 画像只有一次重合成机会

**位置**：`agent/handler.py:7376-7408`、`agent/handler_autonomy.py:1089-1119`、`agent/health_check.py:238-274`。

**证据**：

- 日志 `tangtang.log:840606-844757` 多次报告“3 个 dirty 画像未清算”。
- DB 探针确认当前仍有 3 人 `notes_dirty=1`，各自已有 43、67、84 条 active 记忆，不是缺少合成材料。
- `_resynthesize_profile_later` 失败时只保留 dirty；注释称后续日常合成会重试，但自治扫描 `get_people_with_memories_gt(..., empty_notes=True)` 只选画像为空的人，非空 dirty 画像不在队列中。

**根因**：纠正闭环的“写脏标”和“清脏标”已接线，但失败重试入口按“notes 为空”筛选，与 dirty 状态契约不一致。

**最小修复建议**：Store 查询改为“notes 为空 OR notes_dirty=1”，沿用已有 6 小时 `synth_attempt` 冷却；补“首次重合成失败、自治下一轮重试成功并清 dirty”的回归测试。

## Important 3（已整改）：反馈唯一消费者挂在已关闭的每日播报上

**位置**：`config.yaml:72-75`、`agent/handler.py:648-665`、`agent/health_check.py:277-292`。

**证据**：

- `daily_report.enabled=false`。
- `feedback` 表现有 4929 行；健康日志当日反复显示近7日 866→922 条数据且没有 `feedback:last_consumed`。
- 全仓检索显示唯一设置 `feedback:last_consumed` 的业务点是 `_report_stats_with_feedback`，它只由 DailyReport 的 `get_stats` 调用；播报关闭后，写入继续、消费永远不发生。

**根因**：反馈采集是常驻能力，消费却耦合到可选且已关闭的播报功能。健康检查准确发现了孤儿管道，但没有恢复入口。

**最小修复建议**：先明确反馈用途。若只做诊断，独立生成每日反馈摘要/指标并记录消费；若要影响行为，应作为带来源的反思材料交给 LLM，不用系统分数直接决定回复。若没有用途，则停止常驻写入并制定保留期，避免继续积累“看起来像学习、实际没人读”的数据。

## 效率与结构证据

### 1. 工具 schema 是当前最明确的 token 成本

- 日志最近40个样本：普通回合 34-35 个工具约 11,885-12,270 token；扩展回合 46 个约 14,420-14,561 token。
- 对照本机 DB 热路径实测（20次平均）：`get_unprocessed_messages` 1.13ms、`query_memories` 3.57ms、`search_chat_keywords` 32.85ms。当前最显著成本不是 SQLite，而是每轮完整工具说明。
- 建议借鉴 OpenClaw 的工具 profile，但不能按中文关键词替 LLM 选能力。可按客观权限/渠道静态分层（群、私聊、主人），再提供紧凑的 `discover_capabilities` 让 LLM 自主发现低频工具。改造前先建立“工具 token、工具命中率、首 token 延迟、漏调用率”基线。

### 2. 单文件与备份噪音

- `handler.py` 8242 行；`store.py` 2605 行；`memory.py` 2002 行。
- `agent/` 下 31 个 `.bak/archived` 文件，共 4,458,648 字节；GitNexus 会把多份历史 handler 一并索引，增加导航歧义。
- 这不是立即重构理由。建议先把备份移出活动源码树，再按稳定边界拆：回合编排、工具目录/执行、记忆提取调度、媒体收尾。历史上发生过大段切割致启动崩溃，必须小批次迁移并加入口冒烟测试。
