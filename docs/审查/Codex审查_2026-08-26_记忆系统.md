## Critical 1：私聊可跨用户读取原始聊天和关系记忆

**位置**：`agent/handler.py:4577-4593`、`agent/handler.py:4860-4979`、`agent/handler.py:5018-5039`。

**证据**：执行层只在群聊统一检查 `_GROUP_MEMORY_TOOLS`。私聊分支中，`get_recent_messages`、`get_messages_by_date`、`search_keywords`、`count_messages`、`get_first_met`、`get_last_conversation` 都直接使用调用参数中的 `subject_qq`；只有 `search_facts` 有第三人亲密度闸门。隔离探针让低权限私聊用户调用 `get_recent_messages(victim)`，实际返回 `SECRET_SENTINEL:victim`；用昵称调用 `search_relations`，实际返回 `PRIVATE_RELATION`。关系工具只在输入看起来像数字 QQ 时做脱敏。617 项测试中没有覆盖这些私聊跨用户分支。

**根因**：授权逻辑分散在各工具分支，并把“私聊场景”误当成“可以读取第三人”。资源对象解析、昵称解析和权限判定没有统一的先后契约。

**最小修复建议**：在 `_execute_tool` 入口建立唯一的 `resolve_and_authorize_subject(tool, args, scope, caller)`：先把昵称/QQ/默认值解析成确定用户，再按资源类型授权。原始聊天只能本人或主人读取；第三人事实只能返回明确脱敏的认识级信息；任何 `*` 全局搜索只允许主人。群/私聊所有记忆工具使用同一策略，按工具参数化，不再各写一套条件。必须补“数字 QQ、昵称、缺省对象、`*`、群聊、私聊、主人/普通人”矩阵测试。

## Important 1：新证据纪律没有隔离无证据存量，旧幻觉仍会自动进入上下文和画像

**位置**：`agent/memory.py:237-255`、`agent/handler.py:1829-1834`、`agent/handler.py:2672-2679`、`agent/handler.py:6352-6373`、`agent/memory.py:608-657`、`agent/memory.py:1240-1250`。

**证据**：`MemorySystem.recall()` 已有 `grounded_only`，但群聊、私聊的常规自动召回均未开启；只有糖糖自忆使用它。`format_compact_memories()` 会把非合成候选标为 `💭` 注入。生产 12,114 条 active 记忆只有 31 条有原始聊天证据；7,575 条可通过自动质量门，其中 7,535 条无证据。画像合成同样从未限定 `grounded_only` 的 `recall()` 读取，因此旧记忆还可被再次压缩成看似稳定的画像。

**根因**：这次升级完成了“新写入带来源”，却没有完成“读路径信任分级”和“存量迁移策略”。字段存在不等于证据纪律已经生效。

**最小修复建议**：给记忆建立显式信任层：`verified`（原文证据校验通过）、`manual/corrected`、`legacy_unverified`。自动背景、画像、关系和 Episode 只消费 verified/manual/corrected；legacy 只能作为工具查询线索，并明确提示需查原文核验。不要用模糊相似度给旧数据批量补证据；无法确定来源的就隔离。随后从 verified 事实重建画像，避免旧画像继续旁路注入。

## Important 2：提取进度是非事务双游标协议，当前积压无法满足千人规模承诺

**位置**：`agent/handler.py:7695-7725`、`agent/handler_autonomy.py:35-112`、`agent/handler_autonomy.py:930-1043`、`agent/handler_autonomy.py:1045-1088`、`agent/memory.py:990-996`、`agent/store.py:2528-2570`。

**证据**：

- `.extraction_state.json` 当前记录 143 个前向游标。精确按用户 COUNT 得到 138 人共 48,629 条待推进消息，75 人超过 30 条，最大 5,025 条。
- 健康检查只抽取游标字典前 20 人，因此日志只报告“8 个用户 >30 条”，掩盖了实际 75 人；本次重启后的 219 行日志已出现 24 次兜底触发。
- 兜底每 10 分钟最多处理 6 人，每次主提取最多 20 条，单靠兜底理论上限 120 条/10 分钟；在没有新流量和等待的理想条件下，当前积压也需至少约 67.5 小时。
- 倒序回填每小时最多 10 批、数据库每批取 50 条，但 `extract_semantic_memories()` 固定只把 `messages[-20:]` 交给 LLM，然后回填游标直接跨过这 50 条的最小 ID。探针输入 50 条倒序消息，prompt 只出现较旧的 20 条，最新 30 条没有进入该批 prompt；前向路径之后还会重新扫描重叠区间。
- `_save_extraction_state()` 直接以 `w` 覆盖 JSON 并吞掉 `OSError`。故障探针在写出 `{"fact":` 后抛错，文件保持截断；下一次 `_load_extraction_state()` 返回空状态。到 1000 用户时，一次断电/磁盘异常即可让全量游标回退并触发大规模重放。

**根因**：提取进度不在数据库事务里，而由前向、倒序两个标量游标和非原子 JSON 共同表达；队列没有可声明、可确认、可重试的消息范围。批读取与实际送模窗口又不相等。

**最小修复建议**：把进度迁入 SQLite `extraction_jobs/progress`，以 `(qq_id, range_start, range_end, direction, status, lease_until, attempts)` 表达工作；写入记忆和确认范围在同一事务或幂等事务边界完成。单批读取多少就送多少，或明确把未送的 ID 留在队列；失败释放租约，不推进。保留优先级，但用全量积压 P50/P95/max 和最老等待时间监控，不再抽前 20 人。

## Important 3：派生记忆没有保存“事件时间 + 入库时间 + 不可变来源”，Episode 时间不可信且整合会丢证据

**位置**：`agent/memory.py:132-141`、`agent/handler.py:7347-7383`、`agent/store.py:1040-1057`、`agent/memory.py:1691-1771`、`agent/memory.py:1820-1870`、`agent/memory.py:1927-1988`。

**证据**：持久化提取结果时没有把证据聊天的 timestamp 传入 `remember()`；`insert_memory()` 因而默认使用“提取发生时间”。Episode 聚合再按这个字段分组并写 `time_start/time_end`。生产中可校验的 11 个 episodic 事实，其记忆时间与原始聊天时间差中位数 45.71 天，11/11 都超过 30 天。462 个 Episode 共引用 2,622 个 paragraph，只有 1 个 Episode 至少含一条带证据 paragraph，另有 5 个引用已找不到目标记忆。

隔离合并探针还证明：把两个事实簇合并后，迁移事实的 `evidence_ids` 从原值变成空串。源码中簇迁移没有传该字段；长期记忆整合则更新第二条文本后直接删除第一条，也不合并双方 evidence/origin/confidence。去重路径会用新 evidence 覆盖旧 evidence，而不是求并集。

**根因**：当前数据模型把“事实文本”当作主实体，来源只是可选附属字符串；事件时间、系统获知时间、有效时间和派生关系没有分开。压缩/合并被当成覆写，而不是有来源的派生版本。

**最小修复建议**：保留原始 `chat_log` 为 immutable episode/source；记忆增加 `event_time`、`ingested_at`、`valid_from/to`，证据改为关联表 `(derived_type, derived_id, chat_id)`。去重合并只新建派生版本并 union 来源，旧版本标 superseded，不物理删除谱系。Episode 按证据事件时间生成；来源缺失时不得声称具体日期。

## Important 4：检索先截断再语义排序，且零相关结果也会固定注入 6 条

**位置**：`agent/store.py:1059-1109`、`agent/memory.py:237-375`、`agent/handler.py:6375-6424`。

**证据**：`recall()` 先调用默认 `limit=200` 的 `query_memories()`，SQL 按 importance/timestamp 截断，再对这 200 条做向量排序。生产有 16 人超过 200 条，合计 3,784 条 active 记忆永远进不了语义候选。`_bge_pick_memories()` 只排序没有最低相似度：隔离探针给 7 条记忆全部返回相似度 0.0，函数仍返回前 6 条；只有关键词降级路径会在无重叠时返回空。

**根因**：粗筛把业务权重当成检索召回门槛，并把 top-k 当成“相关”判定。相对排名不能替代绝对可用性。

**最小修复建议**：按 `qq_id` 作用域从向量/关键词/实体三个通道召回，再融合 importance、置信度和时间；不要先用 top-200 重要度截断语义空间。建立中文群聊黄金集和负例集，校准 BGE/reranker 的拒绝阈值；低于阈值返回空，让 LLM 明确“不记得”。对于很短的问题，可以保留画像但不强塞事实。

## Important 5：群聊工具 schema 与执行权限闸门失配，LLM 的主动核验能力被系统误伤

**位置**：`agent/handler.py:4000-4225`、`agent/handler.py:4577-4593`、`agent/handler.py:5085-5208`。

**证据**：群聊闸门要求 `_GROUP_MEMORY_TOOLS` 的参数必须含 `subject_qq/qq_id=current_user`。但 `search_memories` schema 根本没有对象字段；`search_chat_history` 明确允许省略并默认当前用户；`search_episodes` 也没有对象字段。运行时按正常 schema 参数调用这三项，三项都返回“群聊只能查询你自己”，业务分支从未执行。现有 `test_group_memory_evidence_contract_is_injected_once` 只数协议字符串出现次数，没有验证工具可执行。

**根因**：参数定义、默认值解析和安全闸门由不同代码段维护，没有跨模块契约测试。安全修复 fail-closed 是对的，但把合法的当前用户查询一起关掉了。

**最小修复建议**：安全入口先按工具定义解析对象；没有对象字段或允许省略时，群聊默认绑定 `current_user`，不能把空值当第三人。`search_memories` 要么显式增加 `subject_qq`，要么只允许当前用户并在执行层固定注入。为每个公开工具跑“schema 生成参数 → 权限解析 → 业务执行”的端到端契约测试。

## Important 6：dirty 画像虽然不再展示，却仍被回喂给记忆提取器

**位置**：`agent/memory.py:106-116`、`agent/handler.py:7395-7415`、`agent/handler_autonomy.py:976-1004`。

**证据**：正常显示路径已统一走 `active_notes()`，会屏蔽 `notes_dirty=1`；但实时提取和倒序回填都直接读取 `person.get("notes")` 作为 `existing_summary`。当前生产仍有 1 个 dirty 画像。隔离探针写入 `KNOWN_BAD_PROFILE` 且 `notes_dirty=1`，`_do_extract_memories()` 原样把该文本传给 LLM。

**根因**：同一个“画像是否可用”契约没有成为唯一读取接口，后台写路径绕过了前台的 dirty 门。

**最小修复建议**：所有消费者只调用 `active_notes(qq_id)`；dirty 时 existing summary 必须为空。补实时提取和回填两条回归测试，确保错误画像不会成为新记忆的先验。

## Minor 与优化项

### 1. 为 `memories` 增加作用域索引，但不要误判为当前主要瓶颈

**位置**：`agent/store.py:108-125`、`agent/store.py:1059-1109`。

**证据**：生产 `PRAGMA index_list(memories)` 为空，查询计划是全表扫描并建临时排序树。当前最大用户的 `query_memories` 实测中位约 2.0 ms、P95 约 2.2 ms，尚可接受。临时库模拟 1000 用户 × 200 条记忆：无索引中位 4.041 ms、P95 4.528 ms；增加 `(qq_id, importance DESC, timestamp DESC)` 后中位 0.096 ms、P95 0.104 ms，约 42.1 倍改善。

**建议**：先完成正确性修复，再增加覆盖 status/qq_id/order 的索引并用实际查询计划验收。若改为混合召回，索引应按最终 SQL 设计，避免先加一个很快被弃用的索引。

### 2. 现有监控和测试会“绿着漏掉”关键故障

**证据**：健康检查的 stale 只取游标前 20 人，显示 8 而实际为 75；历史指标曾出现 `extract_busy_skipped > extract_attempts`，说明跨版本计数语义不一致。617 项测试覆盖了 evidence 写入、自忆隔离、JSON outcome，却没有私聊跨用户、群工具 schema、原子游标、零相似度拒绝、合并证据保留和事件时间。

**建议**：指标增加版本号/定义，健康检查展示全量 P50/P95/max；建立“1000 用户 × 群私聊作用域 × 记忆类型”的合成数据验收套件。测试必须断言行为结果，而不只是源码中有某段协议字符串。

## 开源项目对照与可吸收设计

本项目不需要因为这些问题立刻更换成外部记忆引擎。当前 SQLite、BGE、reranker、状态和工具骨架足以承载一次渐进式治理；应学习成熟项目的契约，而不是把现有问题搬进新依赖。

1. **Mem0 OSS v3**：官方迁移说明采用单次 ADD-only 提取，并用 semantic + BM25 + entity 三路混合检索；官方示例按 `user_id` filter 召回。可吸收：用户作用域是检索入口的必填约束，提取负责新增，冲突由确定性版本/纠正层治理，检索不能只靠向量 top-k。[Mem0 官方仓库](https://github.com/mem0ai/mem0)、[Mem0 OSS v3 官方说明](https://docs.mem0.ai/migration/oss-v2-to-v3)
2. **Graphiti**：官方 README 把 raw episode 作为 ground truth/provenance，派生事实保存有效时间并可追溯到 episode，同时使用语义、关键词和图遍历混合检索。它直接对应本项目事件时间错位和合并丢来源的问题。可吸收：原文不可变、派生事实有有效期、每次压缩保留来源边。[Graphiti 官方仓库](https://github.com/getzep/graphiti)
3. **Letta**：官方 context hierarchy 将少量重要 memory block 常驻上下文，大量 archival memory 只通过工具按需查询。可吸收：把经过验证的短画像作为热记忆，把 legacy/大规模历史放到工具层，而不是每轮固定注入多条事实。[Letta 官方文档](https://docs.letta.com/v1-sdk/memory/context-hierarchy)
4. **LangGraph**：官方文档区分 thread 短期状态和自定义 namespace 的长期记忆，也明确区分 semantic/episodic/procedural 与 hot-path/background 写入。可吸收：把 `(user, group/private scope, memory type)` 作为 namespace，后台写入用可观测队列，不让会话线程和全局用户记忆混在一起。[LangGraph 官方文档](https://docs.langchain.com/oss/python/concepts/memory)

## 建议实施顺序

### P0：先恢复安全与真值边界

1. 统一所有记忆/原始消息工具的对象解析和授权；封住私聊第三人原始记录。
2. 自动注入、画像、Episode 和关系只消费 verified/manual/corrected；legacy 全部隔离为待核验线索。
3. 给 P0 两项补权限矩阵和存量隔离回归测试，先重启观察再继续迁移。

### P1：把提取和来源改成可恢复的数据协议

1. 提取进度迁入 SQLite 范围队列，记忆写入与范围确认幂等；消除 JSON 覆盖和双游标歧义。
2. 引入 event time / ingestion time / validity 和证据关联表；合并改为新版本 + 来源并集。
3. 从 verified 来源重建画像和 Episode，不修改无法证明的旧事实。

### P2：改善检索和工具契约

1. 修群工具默认对象契约。
2. 建混合召回与绝对拒绝阈值，消除 top-200 盲区。
3. 按最终查询增加索引；修全量积压监控和指标版本。

### P3：千人验收后再给生产承诺

至少建立以下可自动复跑的门槛：

- 1000 个用户作用域互不串读；普通私聊对第三人原始记录 100% 拒绝。
- 自动注入事实 100% 有有效证据，或明确为 manual/corrected；legacy 0 条自动注入。
- 强杀进程、截断旧 JSON、重复执行任务后，记忆不重复、进度不倒退、来源不丢。
- 1000 用户合成库中，正例召回与“应返回空”的负例同时达标；阈值用中文群聊黄金集校准，不凭经验写死。
- 积压监控展示全量 P50/P95/max 和最老等待时间；持续流量下队列不发散。
- SQL 与召回组装 P95 达成预设预算，并记录 LLM 提取调用量、空产出率、每条有效记忆成本。

## 最终评价

如果“胜任”只指 SQLite 能不能放下 1000 人的数据、单次查询会不会慢，答案接近“可以”；临时 200k 记忆压测没有显示数据库引擎需要替换。

如果“完全胜任”指长期不串用户、不会把幻觉当事实、能记住正确时间、崩溃后不重放、群私聊都能主动核验，并能在持续流量下及时消化，答案是**目前不可以**。先完成 P0/P1，再做千人闭环压测；无需先更换引擎，也不应先做表面上的 prompt 微调。
