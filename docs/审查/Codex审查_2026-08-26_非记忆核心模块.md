## 2. Critical（必须先修）

### C1. 图片上下文是实例级全局槽，可跨用户/会话泄漏

**位置**：`agent/handler.py:631` 的 `self._pending_image`；群/私聊分别在 `2044`、`2921` 写入；`2138`、`2981` 以该全局值决定是否注入识图能力；`4843-4850` 执行 `analyze_image` 时未校验当前用户、群、消息 ID。

**证据**：只读 fake handler 探针先写入 A 用户图片 `https://private-A/image.jpg`，再以 B 用户 scope 调用 `MessageHandler._execute_tool(..., "analyze_image", ...)`，结果仍为 `vision_of=https://private-A/image.jpg|file=A-file`。近 30MB 日志有 369 次 `analyze_image`，其中 211 次最近入站消息不是图片（并发会造成统计偏差，但源码的全局读路径是确定的）。

**根因**：回合动作已改为局部 `turn_actions`，图片仍留在 Handler 单例字段；事件任务又是并发的，导致“上一回合的图片”成为下一回合的隐式输入。

**最小修复建议**：把图片放入不可变 `TurnContext`/回合动作，键为 `(channel, group/private, user, message_id)`；只向该回合注入/执行 `analyze_image`，成功或超时后 pop，增加 TTL；为群→私聊、私聊 A→B、并发两图补回归测试。此项属于隐私边界，未修复前不得宣称多模态链路安全。

### C2. 任意用户上传文件被直接写入全局知识库，未授权、无隔离、可覆盖

**位置**：群文件 `agent/handler.py:1471-1475`；私聊文件 `2540-2543`（早于机器人过滤 `2545` 和黑名单 `2551`）；下载 `napcat/ws_client.py:993-1033`；落盘 `handler.py:6579-6670`，其中 `6632-6642` 将清洗后的同名文件写入 `knowledge/{safe_name}.md`；`agent/file_reader.py:15-47` 对未知格式按文本读取；知识工具默认是全局检索。

**证据**：日志出现同一文件名在 18:54、19:03、19:04、19:38、19:46 被重复写入全局目录；知识库目录当前 17 个文件。代码没有 owner/group ACL、来源 scope、版本/hash 或防覆盖机制；私聊黑名单在下载和解析之后才判断。测试有 41 个文件/知识相关用例，但没有“用户 A 上传不可被 B 搜索/读取”边界用例。

**根因**：把“本回合附件”与“可信、长期、全局知识”合并成一条写路径；文件输入也没有大小、页数、MIME/扩展名和提示注入不可信标记。

**最小修复建议**：附件先进入按 scope 隔离的 quarantine（记录 owner、group、message_id、hash、MIME、大小），默认只在当前回合可见；显式人工/LLM 工具动作才 promote 到全局 KB。黑名单必须在下载前执行；设置字节/页数/超时上限；同名采用不可变版本，不覆盖；`search/read` 强制 ACL。该项同时是机密性和知识完整性 Critical。

### C3. 工具循环内同步调用 LLM，可重入全局锁导致整机冻结

**位置**：`handler.py:3271-3286` `_call_llm` 持有 `_llm_lock`；工具循环 `3685` 后执行 `_execute_tool`；`handler.py:4654-4664` `group_say`、`5906` `send_private_message`、`handler_commands.py:572` `relay_message` 的长文本路径再次调用 `_call_llm_with_skills`/`_call_llm`。

**证据**：源码调用链证明同一 asyncio Task 在工具循环中仍持有非重入 `asyncio.Lock`，再次 `await acquire()` 没有超时；Claude Code 独立复核将其列为 Critical。现有注释只修复了 opinion/profile 两处，未覆盖上述三个特权工具；测试没有“持锁工具回调”用例。

**根因**：教训 #27 只靠人工清单，执行器没有统一的“禁止嵌套 LLM”机器闸门。

**最小建议**：工具执行器入口检测当前回合是否持有 LLM 锁，禁止同步嵌套调用；需要生成文本的特权动作改为锁外后台任务/既有回执，或拆成“工具返回意图→主 LLM 收尾”；增加超时死锁回归测试和 AST/静态扫描闸门。修复前，长公告/传话是整机不可用风险。

### C4. 成人内容文档与普通群聊共用全局知识工具，绕过群聊场景边界

**位置**：`agent/knowledge.py:76-86` 递归加载 `knowledge/**/*.md/.txt`；`handler.py:342-349` 将 `search_knowledge` 注册为普通常驻工具；`8124-8134` 搜索时没有 scenario/年龄/scope 过滤。相对地，群聊在 `handler.py:1825-1830` 明确将 seductive 场景 fail-closed 禁止。

**证据**：当前知识库包含 `knowledge/色色参考/*.md`；只读真实探针 `knowledge.search('色色写作指南')` 在普通上下文直接返回约 663 字成人写作内容。也就是说，场景注入被禁止，但同一内容仍可由普通群聊 LLM 通过常驻知识工具取回。

**根因**：知识文档没有 public/private/adult/admin 分级，检索 ACL 也没有接收当前 channel、scenario 和授权上下文；“场景安全”和“知识安全”是两套断开的机制。

**最小建议**：为文档/块建立稳定 doc_id、scope、sensitivity、origin/owner；群聊默认排除 adult，只有明确验证且允许的私聊场景才能检索；`search/read/extract` 统一执行同一 ACL，输出后再做边界校验。补普通群、未授权私聊、授权私聊三类回归。未修复前不得把全局知识库开放视为安全。

## 3. Important（应按顺序修复）

以下每条均采用“位置 → 证据 → 根因 → 最小建议”。

### I1. 入口事件裸 `create_task`，无会话顺序、去重和背压

**位置**：`napcat/ws_client.py:179-194` `_dispatch`；每个群/私聊事件直接 `asyncio.create_task`。

**证据**：只读探针让消息 1 睡眠 50ms、消息 2 立即完成，完成顺序为 `[2,1]`；1000 个事件在约 0.0037s 内生成 1000 个 pending tasks。没有按 `message_id/event_id` 的 seen 集，也没有队列上限。历史代码注释却要求群窗口“逐条、有序”。

**根因**：传输层并发模型直接暴露给有顺序依赖的 Handler 状态。

**最小建议**：建立不可变事件 envelope（boot/turn/message/scope ID）；按群/私聊会话使用有界 FIFO 单消费者，全局 semaphore 限制并发；以 `(post_type,message_type,message_id)` 做短 TTL 去重；定义 overflow/coalesce 策略并记录 queue depth、lag、drop。

### I2. 停机时在途事件任务未取消，可能继续写库/发消息

**位置**：`napcat/ws_client.py:855-868` `close()` 只取消 poll/heartbeat，不登记或取消 `_dispatch` 创建的任务。

**证据**：fake handler 探针 `dispatch` 一个等待 Event 的任务后执行 `close()`：`before_close_tasks=1`、`after_close_pending=1`、`cancelled_seen=[]`。

**根因**：事件任务无 registry，关闭顺序是“先关 HTTP，再任由回调运行”。

**最小建议**：维护 `_event_tasks` 集合；close 先停止接收，再 cancel+gather 事件任务，最后关 HTTP；每个 handler 在 cancellation 边界释放回合/锁状态。

### I3. 发送 API 单次请求且结果语义贫乏，失败/重复/不确定无法治理

**位置**：`napcat/ws_client.py:535-560` `_call_api` 单 POST、30s timeout；`562-658` send group/private 只返回 bool；`577-596`、`609-618` 对 `message_id=0/缺失` 仍返回 True。

**证据**：跨版本历史日志共出现“API 调用异常”132 条、非 200 80 条（含 401/502），样例见日志行 649988（401）、676977（502）、840293（status failed）。这些是原始事件数，因早期一请求可能记多行、私聊还混有预期的“非好友”失败，**不能据此计算真实失败率**。fake IDs `{0,-7,5}` 的群/私聊发送结果均为 True；负 ID 是合法签名 ID，不应当作失败。当前短窗口恰好无失败，不能代表历史可靠性。

**根因**：没有 `confirmed/uncertain/retryable/permanent` 状态、request/action ID、幂等键、退避或 outbox；上层把 transport success 当业务送达。

**最小建议**：引入 `SendResult`（HTTP/retcode/status/message_id/latency/action_id）；网络/5xx/超时指数退避并限制次数，业务拒绝不重试；`message_id` 缺失/0 标记 uncertain，负 ID 保留；outbox 记录待确认/最终失败和 dead-letter。按目标群/用户单写队列保证发送顺序。

### I4. 重连与 QQ 在线状态没有确认闭环

**位置**：`main.py:167-176` `_connected_already` 单向置 True，且 WS 建连即乐观写 `_qq_online=True`；`napcat/ws_client.py:320-416` lifecycle/heartbeat 后才可能确认真实 QQ；`糖糖控制台_qt.py:4398-4434` 只探测 TCP、按镜像名 `taskkill`，3 秒后无条件记录自动重启完成。

**证据**：启动日志行 850668 先 WS connected，850674 已发送主人更新，850680/850682 才收到 lifecycle connect/enable；二者顺序证明发送早于 QQ 认证。850681 与 850683 又各记录一次“QQ 账号已恢复在线”，显示 connect/enable 回调没有边沿去重。历史有 140 条重启信号但没有成对恢复确认；控制台 TCP 探针不校验 OneBot 鉴权/API/QQ 登录。`close()` 相关任务也未纳入生命周期。

**根因**：transport、QQ authentication、process readiness 被压成一个布尔值；重启信号没有 controller ack/新 session/登录确认。

**最小建议**：实现 `requested→process_stopped→port_ready→ws_connected→qq_authenticated→resync→ready` 状态机和 generation；发送只在 authenticated/ready 后放行；重连清理旧代任务并重新刷新群信息/补读；控制台按 PID/路径操作，启动后轮询 readiness，指数退避和熔断。

### I5. 主回复、后台抽取、自治共用全局 LLM 锁，吞吐和尾延迟不适合千人流量

**位置**：`handler.py:103`、`3218-3271` 全局 `_llm_lock`；入口却在 `ws_client.py:186-188` 并发创建任务；`1710-1728` `_busy` 在随机打字 sleep 后才置 True；`_pending_reply` 是实例级无上限 list。

**证据**：尾部 25MB 日志按“入队后下一个处理记录”配对 499 个候选，等待 p50 9s、p95 54s、最大 337s，≥30s 77 次、≥60s 21 次；缺少 turn_id，故这些是候选队列指标而非严格逐请求 SLI。健康日志曾报 `extract_busy` 67%；当前日志发现约 191 个用户有未处理抽取 backlog。另有 1611 条打字记录，delay p50 1s、p95 2s、最大 14.8s。探针显示 `_busy` 入场晚于 sleep，多个任务可同时通过检查后在锁上排队。

**根因**：admission、用户体验延迟、主/后台资源隔离和顺序保证耦合在一个布尔值/锁。

**最小建议**：按会话 FIFO 保序；主回复优先的有限全局 semaphore；后台抽取可合并/丢旧并有明确预算；收到需处理消息即占位，打字延迟放进已占位 task；pending 设置容量/TTL/coalesce。以 p50/p95、队列深度、丢弃率和抽取成功率压测验收，不能简单删除锁。

### I6. 常驻工具 schema 仍然偏大，普通无工具回复也付出约 7102 token

**位置**：`handler.py:3337-3553` 构建工具；`_call_deepseek:3629-3644` 每轮发送 active tools。

**证据**：重启后 21:32 日志两次记录 `常驻15个 ≈7102t；按需31个 ≈7674t`；普通“糖糖你好”无工具调用仍约 7102 schema token、3.0s。历史尾部工具计量 p50≈11,168t、p95≈13,703t、最大≈14,561t。

**根因**：按需发现已接入，但 15 个行为/控制/数据工具仍常驻，工具描述中还含完整歌单等高基数数据。

**最小建议**：只保留真正通用行为与 `discover_capabilities`；知识/图片/群控/历史等类别按需加载；对工具描述做 token budget 和命中率 A/B，保留 LLM 自主决定，不加关键词路由。

### I7. 自治冷场枚举与消费分支不一致

**位置**：`agent/handler_autonomy.py:384-416`。提示要求 `warmly_received/lukewarm/ignored/rejected`，消费仍比较 `warm`、`reject`。

**证据**：fake LLM 探针：`warmly_received`、`lukewarm`、`ignored`、`rejected` 全部落入冷场分支；只有未在提示中的旧值 `reject` 才进入“暂停自治”分支。现有测试未覆盖该函数。

**根因**：只改了全等比较，未同步协议枚举和消费者。

**最小建议**：统一四个全等枚举，未知值 fail-closed；补四值回归和日志指标。

### I8. 对话窗口清理绕过 GRACE/FADE，并连带丢失跨窗口摘要

**位置**：`agent/conversation_tracker.py:23-24,79-98,209-224,390-395`。

**证据**：代码定义 GRACE=10、FADE=300，`get_window_bonus` 在到期后 300 秒内应返回渐变分数并在最终关闭时摘要；固定时间探针在到期+100s得到 `(True,65)`，先触发 unrelated `force_engage` 后 `_cleanup` 直接删除，窗口变 `(False,80)`；`_extract_window_summary` 只在最终关闭分支调用。

**根因**：新渐变状态机与旧的立即 eviction 逻辑存在两套删除入口。

**最小建议**：统一 finalization/eviction，只在 `expires_at+FADE_PERIOD` 后删除；删除前必做摘要，失败至少 warning+metric；加“无关窗口不能删除渐变窗口”回归。

### I9. 活跃窗口全局上限为 3，千人场景会无提示驱逐未过期对话

**位置**：`agent/conversation_tracker.py:75-77,168-183`。

**证据**：固定时间无副作用探针连续激活 4 个用户，最终只保留 3 个，`u0=False`、`u3=True`。常量是整个实例全局而非按群/用户容量。

**根因**：小规模时期的容量常量未随目标规模和会话重要性演进。

**最小建议**：按群/租户隔离容量，或使用带 TTL/LRU 的有界缓存但不得驱逐未过期活跃窗口；记录 eviction_total、原因和被驱逐 scope。

### I10. 驱动力无条件 tick，承诺压力与有证据的未完成事项脱钩

**位置**：`agent/drives.py:173-221` 六项驱动力无条件累积；`agent/handler_autonomy.py:305-360` internal digest；`agent/.tangtang_self.json` 当前快照。

**证据**：只读快照显示 `unfinished_people=0/items=0`，但 `commitment=.96`、`curiosity_info=.977`、`express=.999`、`curiosity_explore=.999`；日志有约 430 条“内部消化”，自治关闭时每 10 分钟只释放 dominant 0.05。压力长期饱和与未完成承诺不一致。

**根因**：驱动力被实现为无条件 homeostatic hunger，未绑定原始承诺/逾期证据，释放不足。

**最小建议**：commitment 只由绑定用户、原始消息、未完成/逾期事项计算；无事项时压力归零；其它驱动加衰减/上限校准，digest 落盘后再释放；离线仿真限制长期 >.9 的比例。

### I11. 群氛围存在持久 SelfState 与内存 GroupStyle 两套断开的实现

### I17. 视觉重复调用与贴图逐图 embedding 带来可测延迟/RSS

**位置**：群/私聊入口 `handler.py:2046,2922` 先自然识图；LLM 仍可在同回合调用 `analyze_image`；`agent/sticker.py:247-300` 每次语义匹配逐图 `e.encode`。

**最小建议**：单图只做一次基础推理，以图片内容 hash + prompt class 做 vision cache，工具读取同一结果或仅对追加问题增量分析；代码侧按句界/字符强制截断，不依赖 VLM 遵守长度提示；限制 URL/本地图片字节和像素上限（当前 `handler.py:5271-5287` 全量 `r.content`，`vision_router.py:87` 再 base64，存在额外拷贝）；贴图向量按库/模型版本持久化并增量更新。记录 latency/image_bytes/output_chars/cache_hit，以命中率、P95、RSS 前后对比验收。

### I18. 知识库每次上传都可能全量 warm embedding，持续上传会抢占主资源

**位置**：`agent/knowledge.py` 的 `reload/warm_embeddings` 调用链；文件上传完成后 `handler.py:6632-6670` 立即 reload 并后台 warm。

**证据**：当前知识库 17 个文件、158 个 chunk；本机探针 `EmbeddingEngine.load` 17.294s，单次全新 `warm_embeddings` 4.444s。重复上传会反复丢缓存并重算，且没有合并/限流指标。

**根因**：增量文档变更被实现成全量索引刷新，没有以文件 hash/version 做增量索引。

**最小建议**：按文件 hash 增量更新向量，上传事件合并 debounce，限制 warm 并发；记录 reload/warm 队列和耗时，确保主回复资源预算不被索引任务挤占。

### I19. 指标 flush 非事务，部分失败后重试会重复累计

**位置**：`agent/metrics.py:112-125`。flush 逐项 `kv_get + kv_set`，只有整个循环完成才清空内存计数；异常仅 debug。

**证据**：fake Store 探针在写完 `a` 后让 `b` 失败：数据库 `a=1`，内存仍保留 `{a:1,b:1}`；下一次重试后数据库变成 `a=2,b=1`，实际发生一次的 `a` 被重复计数。

**根因**：持久化没有 atomic batch/snapshot-ack 语义，成功项和待重试项无法区分。

**最小建议**：Store 提供事务性批量增量；flush 先冻结快照，事务提交成功后再 ack 清除；持久化 flush_fail_total/last_error，增加部分写入失败回归。

### I20. 反向 WebSocket 只按本机地址放行，没有校验 access token

**位置**：`napcat/ws_client.py:66-74,120-130`。构造函数接收 `access_token`，但 `start_server` 只检查 `remote_address` 是否 localhost；注释也明确当前协议入口未做鉴权。

**证据**：OneBot 11 官方协议将鉴权作为独立能力；本项目只限制地址，任何本机进程都可连接 `127.0.0.1:3001` 注入伪事件，绕过 QQ 身份检查，触发记忆写入、工具链或刷屏。当前没有拒绝计数和鉴权失败测试，故未将其升为 Critical，但这是明确的本地信任边界缺口。

**根因**：把“仅本机”误当成完整认证；配置 token 未贯穿 WebSocket 握手。

**最小建议**：校验 `Authorization: Bearer <token>`（常数时间比较），无 token 时启动显式警告并提供仅测试模式开关；记录拒绝原因/计数；补合法、缺失、错误 token 和 IPv6 localhost 测试。

### I21. 强关键词证据在 RRF 截断时可能被其它语义候选挤掉

### I22. 语义检索降级链把 0.55～0.66 的有效相似度误判为空

**位置**：`agent/knowledge.py:237-268` 的 `_search_sequential`。语义门槛是 `sim > 0.55`，随后却将分数 `int(sim * 3)` 交给统一 `min_score=2` 的格式器。

**最小建议**：语义结果使用独立格式器/浮点分数，或在进入统一格式器前显式标记语义证据；补 0.55、0.60、0.66、0.67 四点回归。

### I25. 贴图发送忽略 bool 结果，失败仍记录“成功”

### I27. 回调异常被吞掉且无重试/死信，消息会静默丢失

**位置**：`napcat/ws_client.py:846-853` `_safe_callback` 捕获所有异常，只写 error 日志，不返回状态、计数或重放。

**证据**：跨版本日志共有 717 条“回调执行出错”原始事件，样例行 413905（NoneType.parse）、414443（`_pending_voice`）、422888（`time` 未定义）、671755（`re` 未定义）。这些计数不能直接推导当前失败率，但代码路径确定：异常事件不会重试，也不会进入 dead-letter。

**最小建议**：回调返回结构化结果；短暂错误按 event_id 有界重试，永久错误写持久 dead-letter（保留 message_id/scope/error）；新增 callback_fail/retry/drop 指标和重放工具。

### I28. 图片 URL 回退直连缺少 SSRF 边界（静态 source→sink 已证，实网利用待验证）

**位置**：`agent/handler.py:5279-5285` `_call_vision` 在 `get_image` 失败后对 CQ 中 URL 直接 `self.llm.get`；偷图路径也直连外部 URL。

**证据**：代码没有 scheme/host/IP allowlist、DNS 私网检查、重定向限制和响应大小上限。结合 I20 的本机 WS 无鉴权，伪 OneBot 事件可提供攻击者控制的 URL；真实 QQ 是否允许任意 CQ URL 仍需受控验证，因此不宣称已有利用。

**根因**：把消息附件 URL 当可信 CDN 地址，下载层没有统一的不可信 URL 策略。

**最小建议**：仅允许 HTTPS 和 QQ 可信 CDN/受控下载代理；DNS 解析后拒绝 loopback、私网、link-local，禁跨域重定向并限制响应大小/超时；记录拒绝原因并补本地地址、DNS rebinding、重定向测试。

### I29. 不可信文档可通过自动摘要把指令升级为全局知识事实

**位置**：`agent/handler.py:8084-8121` `_analyze_and_index_document` 将文档前 6000 字直接拼入 LLM user prompt，随后把摘要写到文档首部并全局 reload/warm。

**根因**：文档解析、LLM 摘要、可信知识晋升和全局发布在同一自动路径，没有 provenance/approval 边界。

**最小建议**：文档内容始终标为 untrusted data；摘要输出使用结构化字段并携原文引用/片段 hash，禁止执行文档中的操作指令；摘要默认留在 scope quarantine，审核/授权后才 promote；content hash 幂等，避免同文档重复摘要和两次全量 warm。

## 6. 共因判断

本次跨模块的主要矛盾不是“LLM 不够聪明”，而是三个基础契约没有统一：

1. **作用域契约缺失**：Handler 全局字段承载回合图片，附件直接进入全局 KB，角色提示与图库角色生命周期分离。
2. **事件/副作用没有事务边界**：OneBot 事件裸并发；发送只有 bool；关闭、重连、指标 flush 都不是可确认的状态机/事务。
3. **资源与决策耦合**：一个 LLM 锁同时承担主回复、后台抽取和自治；工具 schema 静态常驻；系统评分在主动插话时替 LLM 路由。

“LLM 单脑”原则本身应保留：LLM 决定是否回答、调用何种能力及内容；系统负责作用域、权限、顺序、容量、持久化、送达确认和安全边界，不替 LLM 做语义判断。
