## Important 1：证据化记忆迁移后，生产提取消费能力仍不足

**位置**：agent/handler_autonomy.py:1042-1085 → agent/store.py:3696-3707 → agent/health_check.py:232-244；现有规模验收见 tools/记忆千人验收.py:23-35、63-69、142-153。

**证据**：

- 生产库精确按 extraction_cursors 聚合：456 个用户共有 64,236 条未处理用户消息；270 人超过 10 条，191 人超过 30 条，中位 17、P95 647、最大 3,625。
- 当前启动 04:05 与 05:05 均报告“191 个用户有>30条未提取消息”。与此同时 extraction_jobs 全部 501/501 done、积压总量较前次快照继续下降，证明消费者没有死亡，而是长期容量/准入不足。
- _maybe_extract_stale 每 10 分钟最多准入 6 人，并以 fire-and-observe 方式启动提取；对数万条历史积压没有“最老消息年龄、每小时到达量、每小时完成量、预计清空时间”的闭环。
- 千人验收用 _EmbedStub 固定向量，并把 1000 个任务直接标记为 success_empty 后提交；它证明 SQLite 隔离、查询和任务原子性，不证明真实 LLM 在持续到达、429/5xx、慢响应和重启交织时的服务能力。
- 活跃记忆中 97.9% 是 legacy_unverified，默认可信检索会隔离它们。这是正确的止幻觉策略，但在证据化重提取完成前，会表现为“安全但记不起来”。

**根因**：上一阶段解决了记忆真值、隔离和崩溃语义，却还没有把历史重提取做成可度量、可公平调度、能根据实时负载让路的生产消费者。当前健康检查只看存量阈值，无法区分“未运行”和“运行但吞吐不足”。

**最小修复建议**：

1. 建立单一持久提取调度器：按用户公平、积压年龄和主人优先级准入；后台并发有硬预算，实时对话始终优先，不改变 LLM 的语义决策权。
2. 增加 backlog_messages、backlog_users、oldest_age、arrival_rate、service_rate、LLM latency/error/throttle 指标；健康文案区分 stopped、degraded、draining。
3. 旧 legacy_unverified 只在同用户/同会话范围内逐批重提取；有证据替代后再退役旧行，避免一次性清库或恢复不可信记忆。
4. 用脱敏生产分布做 2 小时冒烟和 12 小时 soak；同时注入 429、5xx、15 秒慢调用和进程强杀。验收以积压单调下降、实时回复 P95 不恶化、跨用户泄漏=0、重启不重放为准。

## Important 2：QQ “已接受但未确认送达”仍被上层当作成功提交

**位置**：napcat/ws_client.py:33-46 → agent/reply_pipeline.py:349-390 → agent/handler.py:8324-8394；测试缺口见 tests/test_send_result.py:98-104 与 tests/test_send_commit_boundary.py:22-39。

**证据**：

- SendResult 明确包含 ok 与 delivered；message_id 为 0 或负数时返回 ok=True、delivered=False、error=MESSAGE_ID_UNCONFIRMED。
- SendResult.__bool__ 返回 ok。ReplyPipeline.send() 的局部变量与返回类型仍是 bool，并仅用 if not ok 判断；因此未确认结果会被当成“全部发送成功”。
- _checked_send() 在 if sent_ok 下写入 _sent_history 和回复指标，最后返回 bool(sent_ok)。
- 无副作用运行探针输入 SendResult(ok=True, delivered=False, message_id=-7)，得到：pipeline_returned=True、history_committed=['正常回复文本']、metric_committed=True。系统没有送达证据，却已经提交了“糖糖说过”。
- 现有测试刻意断言 message_id=0 时 bool(result) 为 True，但提交边界测试只覆盖普通 True/False，没有覆盖 unconfirmed。

**根因**：底层为兼容旧调用点保留 bool(ok)，而 ReplyPipeline 的“成功”契约没有同步升级。transport accepted、delivery confirmed、business state committed 三层语义在兼容层重新合并。

**最小修复建议**：

1. ReplyPipeline 返回聚合 SendResult；分段回复只有每段 delivered=True 才能形成 confirmed。
2. _checked_send 及所有关系、情绪、聊天历史、反馈候选和成功指标只在 confirmed 后提交。
3. ok=True/delivered=False 记为 uncertain，进入 outbox/观测但不盲目重发，也不声称失败或成功。
4. 增加 message_id=0、负 ID、分段一段未确认、富媒体降级未确认四组回归，断言所有成功式状态均不变化。

## Minor / 继续验证

### 1. stale_extraction 健康文案会误判原因

**位置**：agent/health_check.py:232-244。

**证据**：消费者任务在完成、积压也在下降，但健康检查只凭“超过 30 条的用户数 >3”输出“兜底可能未触发”。

**根因**：只观察存量，没有消费者心跳、完成率和最老积压趋势。

**建议**：与 Important 1 的速率指标一并修正；不要单独加更多阈值。

### 2. 当前窗口自主回复没有运行样本，暂不能继续改 prompt

**位置**：窗口指标与当前 boot 日志。

**证据**：当前 boot 的 466 条日志没有窗口决策样本，且没有 ERROR；零样本既不能证明刷屏，也不能证明自然。

**根因**：重启后的实际聊天量尚不足，不是已证 bug。

**建议**：先累计 reply/skip/fade 各至少 100 个带 scope 的匿名样本，再看连续回复率、沉默长度和用户追问率；LLM 仍是决策者，系统只记录和提供窗口状态。

### 3. 既有千人脚本命名容易被误读为“生产吞吐验收”

**位置**：tools/记忆千人验收.py:23-35、142-153。

**证据**：脚本使用固定 embedding，顺序创建任务，并直接提交空 LLM 结果；报告中的 jobs/s 实际是 SQLite 提交吞吐。

**根因**：正确性/存储基准与端到端容量基准共用“千人验收”名称。

**建议**：保留现脚本并明确命名为 memory_storage_acceptance；新增 memory_llm_soak，不用一个数字替代两种结论。

## 扬长避短

应保留的优势：

- 单脑原则已经落到行为层：LLM 决定回复、沉默和工具使用，系统负责权限、顺序、容量、作用域与持久化。
- 记忆系统的用户/群私隔离、证据来源、事件时间、纠正谱系、永久保留和崩溃恢复已经具备成熟骨架；当前主要问题是消化速度，不应再次推倒数据模型。
- QQ 事件 FIFO、去重、ready 状态、outbox、boot/correlation 和健康快照形成了比多数个人 QQ bot 更完整的可靠性底座。
- 语音、多角色模型、独立贴图库、视觉缓存与知识检索目前没有证据表明需要抢占下一阶段资源。

应避免的方向：

- 不因积压重新开放 legacy_unverified 给普通回复；这会用“记得多”换回幻觉和串用户风险。
- 不用关键词或系统评分替 LLM 决定是否回复；窗口问题必须以 LLM 决策统计验证。
- 不对 unconfirmed 自动无限重发；QQ 可能已接收，盲重放会制造重复消息。
- 不先更换数据库、记忆引擎或语音引擎；当前证据指向调度与状态契约，不是底层选型。

## 完成门槛

- 记忆：连续 12 小时 service_rate > arrival_rate，oldest_age 和 backlog 总量持续下降；跨用户/群私泄漏=0；真实 LLM 错误后可恢复。
