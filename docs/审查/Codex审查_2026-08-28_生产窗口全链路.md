# 小糖糖生产窗口全链路审查（2026-08-28）

## 判定

**Request Changes。** 本报告是对 2026-08-27 21:00—23:00 运行窗口和当前代码链路的只读审查；没有修改业务代码、配置或生产数据库。结论不是“ASR、识图、贴图各自偶发不稳定”，而是入站消息、媒体引用、LLM 决策、行为执行和发送回执没有使用同一份可追踪事件。结果是：媒体在批处理或跨回合时丢失，行为工具只能依附文字，定时任务只能发提醒文字，记忆可能把多人合并消息归到第一人，LLM 还会在没有原始证据时回答过去事实。

本轮不能证明“1000 人持续流量下完全胜任”。观察器实际覆盖 **21:02:57—22:43:06（6009 秒，约 1 小时 40 分）**，不是完整 2 小时；而且窗口决策样本显示的是**过度回复**（35/36 回复），不是足以证明所有漏答的完整候选集合。

## 关键问题清单

### Critical 1：群批处理把多人的原始消息归到第一人，存在记忆/反馈串用户风险

**位置**：`agent/message_batcher.py:144-166`；`agent/handler.py:1622-1648`。

**证据**：`_reply_batched_group` 将多条消息拼成 `combined_text`，只保留 `first['user_id']`、`first['nickname']` 和首条 `msg_id`，并把 `raw_message` 直接替换成合并文本；随后群处理器只调用一次 `memory.log_chat(user_id, ...)`。原始事件接收层没有另一处逐条落库（`memory.log_chat` 仅在群/私聊 handler 使用）。因此同一批中其他人的发言没有自己的 `chat_log` 行，会被第一人承担主体、记忆提取、关系/反馈和权限上下文。生产 DB 进一步证明污染已经发生：约 `13,912` 条 `chat_log` 是“同时有 N 个人找你”的合并伪消息，至少 `57` 条 active memory 的证据指向这些 synthetic rows；例如 memory `#20859` 的主体事实引用 chat_log `#229804`，而该行正文实际混合了 3 个群友的发言。

**根因**：批处理把“给 LLM 的视图”错误地当成“事实存储事件”，没有事件 ID 幂等的原始事件层。

**最小修复建议**：先逐条持久化 `InboundEnvelope`（保留 event/message/user/scope/raw/segments），再构造只供 LLM 使用的合并视图；合并视图不得作为唯一 `chat_log`。记忆提取和反馈必须携带真实 source IDs 与 participants，禁止从合并字符串推导单一主体。补两人/三人同批隔离回归测试。历史 synthetic rows 不直接删除：先标记/quarantine，默认历史查询与记忆提取排除；57 条受污染记忆降为 `needs_review/unverified`，无法恢复原主体时不得继续进入 trusted recall。

### Critical 2：记忆消费者存在可证明的永久卡住路径

**位置**：`agent/handler_autonomy.py:1128-1156`；`agent/store.py` 的未处理消息查询/游标更新。

**证据**：生产只读快照显示前向积压约 `1347` 条、`318` 人；其中 1 人有 `114` 条，另 317 个低流量用户各自不足 10 条却合计约 `1233` 条。`_maybe_extract_stale` 先取混合的 `limit=20` 消息，再按本批 `user_count < 10` 跳过；该批实际出现 `user=9/bot=11`，游标不推进。高流量用户会被混合窗口卡住，低流量用户又因永远达不到单用户阈值长期饥饿。观察器也验证 backlog 在窗口内上升、最老时间未前进。

**根因**：调度准入在混合消息批上计数，而不是在 SQL 层按用户选取未处理用户消息；没有公平、年龄和吞吐闭环。

**最小修复建议**：Store 提供按 scope/user 的原子候选查询（直接筛选 `>=N` 条未处理用户消息，并带前后文）；使用年龄 + backlog + 公平轮转调度，不依赖“混合 20 条后的用户数”；游标只在成功提交或明确失败重试策略后前进。健康指标增加 backlog/users/oldest/arrival_rate/service_rate/预计清空时间。

### Critical 3：证据 ID 合法不等于记忆 claim 被原文支持

**位置**：`agent/store.py:1310-1341`、`2250-2298`、`2340-2346`。

**证据**：`_validate_memory_evidence` 只检查 evidence IDs 指向正确主体、群组和说话人，不校验生成的 memory value 是否能由原文 quote/span 支持；`_apply_extraction_item` 接受 `confidence >= 0.5`，随后把结果写成 `trust_level='verified'`。生产库仍有 6 条 active `origin=summarized` 合成记忆被标为 verified，却没有 evidence 关系；另有 42 条 extracted/backfill verified 记忆 confidence 低于 0.75。LLM 因此可以用真实消息 ID 包装推断或幻觉进入 trusted recall。

**根因**：来源存在性、claim 支持度、模型置信度和 trust level 被合并成一个“有 evidence 即 verified”的布尔结论。

**最小修复建议**：提取 schema 强制 `claim_text/evidence_quote/evidence_ids/claim_type`；提交前做 quote/span 与规范化原文支持校验，推断和低置信结果只能进入 unverified/待复核层。清理无关系化证据的 synthesized verified 行；alias 也要保存 source/scope/confidence/trust，支持撤销与纠正。

### Important 3：群语音未进入 ASR，轻量 LLM 空回复是次生症状

**位置**：`agent/handler.py:2705-2719`（私聊有 ASR）；`agent/handler.py:1455-1469`（群入口）；`agent/message_batcher.py:144-165`（媒体字段被覆盖）。

**证据**：

- 21:14:20 日志收到群 `[语音]`（`tangtang.log:876014`），但整个后续链路没有 `糖糖.ASR`、下载、转码或“语音转文字”日志；21:14:27 只出现 `0字 (30.2s, length, 思考5643字)` 和轻量 LLM 空回复告警（`876021-876023`）。
- 旧日志 20:49—20:52 有多条私聊 ASR 成功记录，说明 SenseVoice/ASR 引擎本身并非整体不可用。
- 私聊 handler 明确检测 `[CQ:record]` 并调用 `_transcribe_voice`；群 handler 没有对应分支。

**根因**：群路径没有统一媒体规范化；批处理还把 `raw_message` 替换成纯文本，后续即使想补 ASR 也失去 CQ record。

**最小修复建议**：在群/私聊进入批处理前统一解析 typed segments，语音先生成带 event/message scope 的 transcript；批处理只合并文本视图，不丢原始 segments。对“轻量 LLM 0 字 + 长推理”另立指标和模型/预算策略，不把它误报为 ASR 成功。

### Important 4：图片引用只存在当前回合，跨消息追问必然失去图片

**位置**：`agent/handler.py:1467-1469`、`1590-1605`、`1980-2001`；`agent/handler.py:4616-4621`。

**证据**：

- 21:17:03 群收到图片，21:17:12 用户分开发问“帮我看看这种图有哪些内容”（`tangtang.log:876053-876054`）。21:18:55 回复声称没有识图能力（`876087-876092`），21:19:34 只调用 `discover_capabilities(image)`（`876111-876113`），没有 `analyze_image`。
- 相同窗口中，图片和问题在当前回合绑定时能成功：21:20:25—21:20:29 私聊 `get_image`、本地识图、`analyze_image` 均成功（`876150-876162`）；群内 22:22:20 也有同回合识图成功（`877294-877304`）。这排除了视觉引擎整体不可用。
- 代码用局部 `turn_image`，没有带 TTL、用户/群、原消息 ID 的待处理媒体引用；无当前图片时还会从工具列表移除 `analyze_image`。

**根因**：媒体能力以“当前 handler 回合”而不是“有界、可核验的事件引用”建模；用户对上一条图片的自然语言追问无法重绑定。

**最小修复建议**：建立 `PendingMediaRef(scope_id,user_id,message_id,kind,path/hash,expires_at)`，图片和 transcript 均保留原始 source；仅在同一作用域、短 TTL、明确引用/最近一张条件下提供 `analyze_image`。工具结果返回实际 source ID，避免 LLM 依据能力描述猜测。

### Important 5：定时任务是“文字提醒”，不是可执行的定时行为；主动发送未统一开窗

**位置**：`agent/handler.py:4673-4703`（`set_reminder`）；`agent/tasks.py:63-95`、`96-120`；`agent/conversation_tracker.py:39`、`agent/handler.py:1681-1689`。

**证据**：

- 21:32 设置的描述要求到点在群里发一张表情包；21:37:16 仅调用 `send_group_msg` 发送一条由 `_compose_message` 生成的文字，并记录“任务提醒已发送”（`tangtang.log:876494-876497`）。21:37:54 用户问“那表情包呢？”没有被回复，直到 21:38:23 叫“糖糖？”后才在 21:38:30 调用 `send_stickers`（`876501`、`876506`、`876514-876520`）。
- `set_reminder`/`TaskManager` 只持久化和改写 `description`，没有 action payload；`ConversationTracker._auto_initiated` 只由自治消息路径设置，任务发送没有统一回调进入窗口。

**根因**：计划数据模型只有自然语言备忘；定时器出口绕过统一行为计划和对话窗口。

**最小修复建议**：任务保存 typed `ActionEnvelope`（目标、文本/贴图/语音、模式、幂等键、scope）；到期后由 LLM 决定或执行已确认动作，写入 outbox 并返回 `ActionReceipt`。所有确认的主动发送（自治、任务、生日）都发出 `ProactiveEvent`，由窗口追踪器按 scope 建窗；失败/不确定不得提交“已说过”记忆。

### Important 6：贴图动作依附文字成功，无法实现 sticker-only

**位置**：`agent/handler.py:5001-5020`、`2331-2335`、`2402-2438`。

**证据**：`send_stickers` 只把路径写入 `turn_actions['stickers']`；真正发送在 `_checked_send` 文字成功后的 `if ok` 分支（`2434-2438`）。清洗后文字为空会在 `2331-2335` 直接返回；工具调用若想只发贴图，当前回合仍可能被强制补一轮文字。观察期内贴图 4/4 成功只能证明“有文字的贴图”链路，不证明贴图独立行为。

**根因**：回复结果用单一 `ok/reply` 布尔和文本作为主轴，媒体动作没有自己的提交边界。

**最小修复建议**：把 LLM 回合结果改为 `TurnPlan(actions=[...], text?)`；`send_stickers`、`send_voice`、`send_text` 分别执行和记录回执，允许 `text=null`。窗口、记忆、关系只依据各 action 的 confirmed receipt 更新。

### Important 7：传话与自然私信契约重叠，二次改写会改变主人原意

**位置**：`agent/handler.py:6153-6222`；`agent/handler_commands.py:572-650`；工具定义 `agent/handler.py:8897-8907`。

**证据**：

- 21:59:54 `relay_message(target, "再验收一会吧")` 已实际调用私信并收到 HTTP 200/发送日志（`tangtang.log:876934-876939`）。22:00:01 糖糖却说系统把内容改成“睡眠/饼干”，并提出要重发（`876941-876946`）。
- `_do_relay` 把主人原话放在隐藏 system 背景，并要求“禁止提到主人”“假装自己想来关心”，用户可见内容因此被重新创作；短文本自然私信另有一套 `pm` 分支。
- `/传话` 22:10:12—22:10:14 直达发送成功，说明 QQ 发送不是主因（`877135-877145`）。

**根因**：发送意图、归因方式和可见文案没有结构化；行为已执行但回合上下文没有统一 receipt，后续 LLM 又凭自己的生成结果描述行为。

**最小修复建议**：合并为一个 `send_message` 行为工具，显式参数 `target/scope/content/convey_as(verbatim|natural|relay)/attribution/from_requester|as_self/review`。工具结果返回 requested/actual payload、目标、message_id、状态和时间；`verbatim` 禁止改写，其他模式也必须保留意图。将执行回执注入同一回合，禁止模型声称“未执行”。

### Important 8：窗口自治协议负向偏置，系统既漏筛选又在已开窗时几乎必答

**位置**：`agent/handler.py:1673-1755`、`2300-2325`；`agent/protocols.py:117-123`；`agent/conversation_tracker.py:22-27`。

**证据**：完整日志窗口决策 36 条，`reply=35, skip=1`（97.2% 回复）；直接 @/叫名样本也被设置为 `window_llm_decision`，应与连续窗口样本分开统计。窗口外消息只有 active-interjection 评分通过才进入 LLM，意味着大量候选在 LLM 之前被系统筛掉；窗口内又以 `should_reply=True` 直接送入 LLM，唯一负向工具是 `skip_response`，产生默认回复偏置。观察器 `reply=24, skip=0` 的汇总也反映未覆盖实际候选总量。

**根因**：入口准入和回合行动没有统一结构；系统在窗口外替 LLM 做语义筛选，在窗口内又没有正交的 `respond/observe` 结果协议。

**最小修复建议**：系统只保留权限、去重、容量和隐私硬闸门；把可处理候选以 `ConversationEvent` 批量交给 LLM，LLM 返回结构化 `engagement=observe|respond`、目标、理由和 action。记录 candidate/routed/reply/skip/fade/entry_direct/continuation，先累计各类样本再调 prompt。连续沉默只推进渐变，不删除可核验窗口状态。

### Important 9：历史事实查询没有严格时间/顺序工具，且工具目录与注入集合不一致

**位置**：`agent/handler.py:4191-4209`、`5290-5334`、`4616-4638`。

**证据**：

- 21:45:04 用户问晚上第一句话；21:45:09 未调用检索就回答“可以看到吗？”（`tangtang.log:876592-876609`）。
- 21:47:02 用户要求查对话；21:47:12 连续调用 `search_chat_history`，并尝试调用未注入的 `get_messages_by_date`，被拦截（`876649-876662`）；21:47:25 才更正为“糖糖？”（`876670-876675`）。
- `search_chat_history` 群聊是关键词 LIKE；私聊主要是向量相似度，不能表达 `from/to/order/limit` 的“第一条”；提示文本提到多个历史工具，但 `get_messages_by_date` 被标为 deferred。

**根因**：把语义检索线索当作时间事实查询，LLM 被允许在无证据时先回答；工具 catalog 没有保证“描述的能力就是本回合可调用能力”。

**最小修复建议**：提供始终可用的 `history_query(scope,speaker,from,to,order,limit,match_mode)`，确定性按 timestamp/message_id 返回 `source/chat_id/speaker/time/text`；语义记忆只做线索。过去事实、承诺、完成动作必须先得到证据引用，冲突以原始 timeline 为准；移除未注入工具的提示或让模型先请求 capability。

### Important 10：轻量 LLM 有预算耗尽空回复，未与业务失败隔离

**位置**：日志 `tangtang.log:876021-876023`；相关轻量调用入口由 handler 的背景/选择链触发。

**证据**：同一事件出现 `0字`、`finish=length`、推理 5643 字、30.2 秒，随后两次空内容告警；并非 HTTP/429/5xx。观察器对主 LLM 统计为 PASS，说明该故障被主路径健康口径掩盖。

**根因**：轻量任务沿用高推理预算/模型配置，没有“空结果即明确失败原因、有限重试、降级”的独立契约。

**最小修复建议**：为轻量分类/记忆筛选调用独立模型和 max output/reasoning 上限，关闭不必要 thinking；空结果记录 `reason=budget_exhausted|invalid|transport`，最多一次退避重试并降级到确定性结果，不把空文本送入对话回复链。

## 其他需要修复或验证的缺口

### Important 11：媒体和文本只在当前回合处理，无法保证群/私链路同构

群、私聊 handler 目前有重复的语音/贴图/回复收尾代码；重复分支使发送提交、记忆、窗口和媒体顺序容易漂移。应先抽出统一的 `TurnPlan`/`ActionExecutor`，再保留平台适配器，而不是继续在两个 handler 内各修一个分支。

### Minor 12：工具 token 常驻成本高，且 deferred 名称造成误调用

日志显示群回合常驻 16 个工具约 `7357—7696t`，按需 18 个约 `4902t`；这不是未经基准验证的“必须优化”，但工具目录与按需注入应统一。优化目标应是“决策准确率不降、前台 P95 不升”，不能只追 token 数。

### Minor 13：观察器覆盖不足且健康失败口径混杂

本次报告区间只有 1 小时 40 分；自治、生日、定时图片、点赞、群语音输入等为 INSUFFICIENT，不应解释为 PASS/FAIL。后台任务/健康检查的 WARNING 被汇总为 FAIL，但没有把“消费者停止、吞吐退化、预期业务阈值”分层。应让观测器输出候选数、服务率、最老年龄和覆盖缺口，并把业务 WARNING 与真正异常分开。

### Minor 14：群聊输出偏长、能力声明可能与事实不符

21:18:55 的“没有识图权限”与同一时段本地识图成功证据冲突，属于能力/上下文缺失导致的 LLM 自我描述幻觉。短群消息还常被扩写成多段解释。应由工具回执提供 capability/source，增加群聊简洁度和“不得声称不可用，除非本回合工具失败”的输出约束；需再积累带正文的样本评估，不直接改人格提示。

### Important 15：自忆缓冲在 LLM 忙时会静默丢前置条目

**位置**：`agent/handler.py:7647-7659`。

**证据**：只有 counter 达到阈值且 `_llm_lock` 空闲才启动；锁忙期间 buffer 可继续增长。真正执行时只取 `buffer[-5:]`，随后清空整个 buffer，前面未处理条目没有任务、游标或失败记录。

**根因**：自忆仍是内存列表和全清空语义，没有持久队列与批次提交边界。

**最小修复建议**：改为持久 pending 队列，按批 `pop/claim`，仅成功提交后 ack；失败可恢复，记录 admitted/processed/dropped/retried。

### Important 16：私聊窗口过期与摘要是未接通的假能力

**位置**：`agent/conversation_tracker.py:301-391`。

**证据**：`_save_state/_load_state` 不保存/恢复 `last_active`；`is_private_expired` 无该字段时返回 False，且全项目没有调用它。窗口 `summary` 字段没有任何更新点，`get_private_context` 又不注入保存的 `their_msgs`。重启后的私聊窗口不会按设计过期，所谓窗口摘要也从未生成。

**根因**：状态字段、持久化和消费方没有形成闭环。

**最小修复建议**：在统一 ChatContext 中明确私聊窗口 TTL/永久会话策略；若保留窗口，持久化 last_active，接通定期 cleanup + evidence-backed summary；否则删除死状态，避免继续宣称不存在的能力。

### Important 17：原始聊天没有平台消息幂等键

**位置**：`agent/store.py:120-127`、`2525-2549`。

**证据**：`chat_log` 只有内部 id/qq/group/message/timestamp，没有 QQ `message_id/event_id/dedupe_key`；写入路径无条件 INSERT 并递增 total_chats。NapCat 重投或重连重复事件会重复记账、进入提取，无法满足崩溃后不重放的目标。

**最小修复建议**：InboundEnvelope 增加 platform_message_id + scope 唯一约束（或独立 dedupe 表），先幂等持久化再批处理；补重复投递、重启重放回归。

### Important 18：提醒类行为工具分类回退为 agent，导致多余收尾轮

**位置**：`agent/handler.py:3837-3849` 的方法类型表及相关工具注册。

**证据**：`set_reminder/group_say_later` 未列入统一 behavior 类型；未注册时默认 `agent`，会强制额外 LLM 收尾轮。收尾空或失败时容易出现过程文字未兑现、重复调用或“稍后再查”没有最终回复。

**最小修复建议**：建立单一工具注册与分类表，返回 `action_result + user_visible + continue_reason`；行为完成后由 TurnPlan 决定是否再生成文字，不依赖默认 agent 分支。

## 统一架构方案（供实施设计）

### 1. 入站事件信封

适配层统一生成：

```text
InboundEnvelope {
  event_id, correlation_id, platform, chat_type, chat_id, user_id,
  message_id, event_time, raw_message,
  segments: text|image|voice|file|reply|at,
  normalized_text, media_refs, dedupe_key
}
```

先幂等落原始事件，再交给批处理/路由。批处理只产生临时 `ConversationView`，绝不覆盖 raw/segments/主体。

### 2. 单脑回合计划

LLM 仍是唯一语义决策者；系统只做权限、隐私、去重、容量和可靠性硬约束。LLM 输出：

```text
TurnPlan {
  engagement: observe|respond,
  actions: [send_text|send_voice|send_sticker|send_message|schedule],
  target_scope, source_event_ids, concise_mode?, reason?
}
```

`observe` 是可记录的正常结果，不再依赖只有负向的 `skip_response`；动作可以无文字（sticker-only/voice-only）。

### 3. 统一动作出口与回执

所有外部副作用先写 outbox，使用 `action_id/idempotency_key`；执行后记录 `accepted|confirmed|uncertain|failed`、目标、实际 payload、QQ message_id、时间和重试次数。只有 `confirmed` 才写 bot chat_log、自忆、关系、反馈候选和窗口续期；`uncertain` 禁止盲重放和“已发送”断言。

### 4. 作用域媒体引用

图片/语音/文件均保存 `scope_id + source_event_id + owner + TTL + hash/path + normalized result`。同作用域短窗口内的“刚才那张/这段语音”才能重绑定；工具结果必须带 source ID 和实际能力状态。

### 5. 时间线真值与记忆消费者

原始 timeline 是事实层；带证据 ID 的自忆是派生层；摘要/画像仅是低信任线索。`history_query` 提供严格时间、顺序、数量和说话人过滤。提取调度以用户公平、积压年龄和实时负载为优先级，保证游标 exactly-once/可恢复，并持续暴露 arrival/service/backlog SLIs。

## 开源项目借鉴（不直接移植）

- 本地 Nekro Agent 2.3.0 已验证 `TOOL/AGENT/BEHAVIOR/MULTIMODAL_AGENT` 分层、统一 AgentCtx、typed message segment、历史漫游先定位再拉原文、`push_system_message(trigger_agent=True)` 主动事件入口。对应源文件见 `D:\claude code相关资源\nekro-agent-2.3.0`，学习报告 `docs/开发规划/归档/Nekro_Agent_2.3.0_学习报告.md:146`。
- Nekro 的 timer 仍只保存 `event_desc`，到点注入系统消息，不能直接解决定时贴图；糖糖必须增加 action payload、幂等键和 receipt。
- [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)：可借鉴按 thread 持久化 checkpoint 的思想，但外部 QQ 发送仍需 outbox/幂等回执。
- [Mem0](https://github.com/mem0ai/mem0)：可借鉴记忆按用户/会话/租户 scope 管理和事实更新接口；不能用其相似度结果取代糖糖的原始聊天真值。
- [Letta](https://github.com/letta-ai/letta)：可借鉴持久状态与工具调用的可观察性；仍需保留糖糖的 QQ 发送确认边界。
- [OpenClaw ambient room events](https://docs.openclaw.ai/channels/ambient-room-events)：可借鉴“环境消息作为安静上下文、由 agent 决定是否发言”的入口协议；系统不能把环境消息先按关键词裁掉。
- [Nekro Agent](https://github.com/KroMiose/nekro-agent)：可继续参考其消息服务与后台 Agent 触发，但只吸收契约，不复制插件市场、沙盒等与本项目无关的复杂度。

## 实施顺序与验收门槛

### P0：停止继续污染（先做）

1. 原始入站事件逐条落库，修复群批处理主体串线；补隔离回归。
2. 群/私统一媒体规范化，接通群 ASR；批处理保留 segments。
3. 作用域 pending media 引用，支持同一窗口“刚才那张图”核验。
4. 贴图/语音从文字提交边界解耦；动作回执独立记录。
5. 定时任务保存 action payload；所有主动发送确认后统一 seed 对话窗口。

### P1：统一发送与历史事实契约

1. `send_message` 统一自然私信/传话/群目标，显式 verbatim/natural/attribution；回执注入 LLM。
2. `history_query` 严格时间线工具，删除 catalog 中不可调用的工具提示。
3. 轻量 LLM 独立预算/空结果契约。

### P2：窗口自治与记忆吞吐

1. `TurnPlan` 的 observe/respond/action-only 协议；记录候选、直达、连续、回复、沉默、渐变。
2. 公平年龄优先提取调度器与 backlog SLIs；先保证 service_rate > arrival_rate，再扩大用户规模。

### P3：真实验收

- 脱敏回放：双人同批、群语音、图片后追问、贴图-only、定时贴图、传话 verbatim、第一句话查询、LLM 429/5xx/15 秒慢调用。
- 至少 12 小时持续流量，另做进程强杀/重启；验收：跨用户泄漏=0、未确认不提交、无重复发送、媒体 source 可追溯、backlog 单调下降、前台 P95 不被后台拖垮。
- 每类窗口决策（direct/continuation/observe/respond/action-only）至少 100 条带 scope 样本后再调 prompt。
