## Important（应该修）

### I1. `.env` 写入的「禁换行」只挡 `\n`/`\r`，读侧却按 `splitlines()` 全集切分 —— 可注入任意新键，且失败不回滚

- **位置**：`tools/desktop_bridge.py:334-335`（写入侧判定）、`tools/desktop_bridge.py:112`（读侧解析）、`tools/desktop_bridge.py:373-378`（写盘与回读校验）
- **证据**：
  - 写入侧（`:334-335`）：
    ```python
    if "\n" in value or "\r" in value:
        raise ValueError("value 不能包含换行")
    ```
  - 读侧（`:112`）：`for line in ENV_PATH.read_text(encoding="utf-8").splitlines():` —— `str.splitlines()` 除 `\n\r` 外还按 `\v \f \x1c \x1d \x1e \x85 \u2028 \u2029` 切分。
  - 实测（`python -c`，纯标准库，无副作用）：
    ```
    v = 'sk-real' + chr(0x2028) + 'EVIL=1'
    len(v.splitlines()) -> 2 ; ['sk-real', 'EVIL=1']
    ('\n' not in v and '\r' not in v) -> True
    ```
    即该值**能通过**写入侧检查，却会在读侧被切成两行。
  - 落盘顺序（`:373`）：`ENV_PATH.write_text(nl.join(out) ...)` 先写；背书校验（`:376-378`）在写完**之后**才执行：
    ```python
    env = _load_dotenv()
    if value and env.get(name) != value:
        raise RuntimeError("写入 .env 后回读不一致——已备份，请检查文件编码/权限")
    ```
    于是 `DEEPSEEK_KEY=sk-real<U+2028>EVIL=1` 写进去后，`_load_dotenv()` 得到 `DEEPSEEK_KEY="sk-real"` ≠ 原值 → 抛 500，**但被注入的 `EVIL=1` 已经留在 `.env` 里**，没有任何回滚（`:368-372` 只备份，不还原）。
  - 现有测试只覆盖了 `\n`：`tests/test_desktop_bridge_env.py:70-74` 用的是 `"ok\nARBITRARY_KEY=evil"`。换行族里其余 8 个码点没有阳性对照（教训 #30/#55 的形态：安全边界的样本只种了最窄的一种）。
- **根因**：判定口径与解析口径不一致——写侧用的是「换行」的一个子集，读侧用的是 `splitlines()` 的全集；且安全校验放在「写盘之后」，失败时没有事务语义。这类洞不会自己暴露，因为回读校验会把它变成一条 500，看起来像「写失败」，实际上「部分写入成功」。
- **最小修复建议**：
  1. 判定改成与解析同口径：`if len(value.splitlines()) != 1: raise ValueError("value 不能包含任何换行类字符")`（一行，覆盖全部 9 个码点，将来 Python 扩表也自动跟上）。
  2. 把校验挪到写盘前；写盘后若回读不一致，用 `backup` 覆盖回去再抛（`shutil.copy2(backup, ENV_PATH)`），保证「报错 == 文件没变」。
  3. 测试参数化覆盖 `\v \f \x1c \x1d \x1e \x85 \u2028 \u2029`，并断言「抛错后 `.env` 字节与调用前完全一致」。

### I3. `allow_groups` 是「补一个字段」，不是「修一类」——白名单仍是第二份字段表，下一次加字段还会静默丢

- **位置**：`tools/desktop_bridge.py:561-573`（保存白名单）vs `agent/scenario_packs.py:34-45`（`PACK_DEFAULTS`）、`agent/scenario_packs.py:74-88`（`normalize_packs`）
- **证据**：

### M1. `--recover-all` 的退出码是恒量，残留 meta 永不清除

- **位置**：`tools/变异对照.py:113`
- **证据**：`return 0 if found >= 0 else 1` —— `found` 是计数，`found >= 0` 恒真，故这个三元表达式恒为 0（教训 #41「监控一个恒为常量的量」）。另外 `:106-109` 只在 `target` 不存在时删 meta；若 `bak` 不存在而 `meta` 还在，`_recover_if_dirty()` 在 `:84` 直接 `return False`，meta 永不清理，`--recover-all` 每次都会扫到它并报「恢复完成：0」。
- **根因**：判据写成了「不存在的失败分支」，等于没有失败分支；meta 与 bak 的生命周期没有成对管理。
- **最小修复建议**：`return 0 if found else 0` 直接删掉这段判断（或 `found == 0` 时打印「没有残留」）；`_recover_if_dirty` 在 `bak` 缺失时顺手 `_meta_path(path).unlink(missing_ok=True)`。

## 待验证假设（证据不足，不进上面任何一级）

1. **混合行尾的 `.env` 可能在替换时吞掉紧随其后的一行**。`tools/desktop_bridge.py:345` 用 `nl = "\r\n" if "\r\n" in text else "\n"` 决定分隔符，`:346` 用 `text.split(nl)` 切分。若文件是 `"A=1\r\nB=2\nC=3\r\n"`，切完第二段是 `"B=2\nC=3"`；替换 `B` 时整段被 `f"{name}={value}"` 覆盖，`C=3` 消失。需要一份真实混合行尾的 `.env` 才能确认风险面（当前 `.env` 的实际行尾我没去读，避免把密钥读进上下文）。

3. **`安装糖糖.py::bootstrap_config(dry_run=True)` 返回 True**（`工具` 里 `return True` 在 dry-run 分支，等价于「本次新建了配置」）。若某个调用点用它的返回值决定「后续接线无需再征求同意」，dry-run 会走出真实分支。我没读到该返回值的使用点，故不下结论。
4. **`_load_raw_config()` 返回 `{}` 时从桌面端保存 scenario_reference**，可能写出一份只含该块的 config.yaml。`api_scenario_packs_save`（`:540`）的注释说它走 `api_config_save`（有 `merge_missing_fields`），但两者都缺文件时的实际行为我没有读到，属未验证。

## 待验证假设 1（混合行尾吞行）—— **已验证不成立**，但顺带挖出一个真 bug（已修）

审查者假设「混合行尾的 `.env` 替换时会吞掉紧随其后的一行」。实测：**不成立**
（`C=3` 保留了），因为 `read_text()` 的 universal newlines 已经把行尾统一成 `\n`。

**但正是这个 universal newlines 造成了另一个真 bug**：
`nl = "\r\n" if "\r\n" in text else "\n"` 因此**永远**判成 `"\n"`，
于是 **CRLF 的 `.env` 保存一次就被整文件改成 LF**（实测：3 个 CRLF → 3 个 LF）。
这违反本项目「Windows 文件读写两端 `newline=""`」的铁律，也把「最小编辑」变成「整文件重写」。

已修：改走 `read_bytes().decode("utf-8")` 保留原始行尾。
**证据**：`test_crlf_env_keeps_crlf`（CRLF 保持 3 个、无 LF-only 行、紧随其后的一行还在）。
