审查对象：用户反馈「装不上/跑不了」的发布版 `v1.08.00`；来稿 `项目问题梳理_20261113.md`（他人 AI 整理，13 条主张）。

## 结论

**Request Changes（阻塞）**。用户"运行不了"不是环境问题，是**发布包结构性残缺**，且**能残缺出厂是因为三道闸门同时失效**：白名单没有覆盖校验、援引的闸门测试根本不存在、快照类完整性断言在无快照时 `skip`。

## 三、来稿漏掉的（本次实测新发现）

### A1【Critical】援引的闸门测试不存在——假闸门

- **位置**：`tools/准备发布.py:184`
- **证据**：注释写「闸门同上（`test_referenced_tools_are_whitelisted`）」，全仓 grep 该名字**只此一处**；`tests/test_release_bundle_contract.py` 里有 22 条测试，**没有一条**校验"被引用的 tools 是否都在白名单"。`tests/test_release_sanitizer.py:348` 钉的是 `SCAN_EXEMPT_FILES`，与 TOOLS 白名单无关。
- **根因**：白名单从 2026-09-05 泄漏事故后收窄到约 20 项，但"收窄的代价"没有闸门承接；注释把"计划中的闸门"写成了"现有的闸门"。
- **后果**：`tools/` 全仓 108 个 → 包内 20 个，**没有任何一条测试会红**。

### A2【Critical】完整性断言在无快照时 `skip`——skip 型假绿

- **位置**：`tests/test_release_sanitizer.py:362-367`（`test_release_snapshot_is_clean`），另 `:236/:369/:386/:416` 同类
- **证据**：`pytest.skip("快照不存在——先跑 python tools/准备发布.py")`。clone 主仓的人和 CI 都**永远不会**跑这些断言 → 发布包完整性从未被自动验证。
- **根因**：把"需要外部产物"的断言写成了 skip 而不是 fail，等于宣布"检查不通过也没关系"。

### A3【Important】当前仓库状态已经无法出包（发布闸门红灯）

- **证据**：本次跑 `tools/准备发布.py` 直接中止：
  ```
  [×] 扫描命中，已中止（快照已生成但**不要推送**）
  agent/paths.py:44: ...{"旧根": ["D:/qq-小糖糖", ...]}
  tests/test_paths_legacy_rebase.py:10/39/51/55/59/63/64/68/79/85/90/102/104/125/134: D:/qq-小糖糖 ...
  ```
- **含义**：这些是**旧盘符样本**（项目现居 `F:`），属"测试装载泄漏样本"的正常情况，却没进 `SCAN_EXEMPT_FILES`（该表只有 `tests/test_release_sanitizer.py` 一项，且被 A2 同族的断言钉死"不许变长"）。→ **v1.08.00 之后没人跑过完整发布流程**，这正是 A1/A2 没被触发的现实解释。

### A4【Important】知识库索引静默降级

- **证据**：同一次运行打印 `⚠ BGE 不可用（No module named 'numpy'）——索引只建文本`，随后 `✅ knowledge/ 索引现场重建（0.2 秒，56 篇 581 块，不含向量）`，仍判 ✅ 并继续出包。
- **含义**：发布物质量取决于"执行者用哪个 python 跑准备发布"。用错解释器 → 包内知识库**无向量**，用户装好后语义检索能力退化，而安装器、体检、`[√]` 全都是绿的（与 A2 同族：降级不阻断）。

### A5【Important】运行期文案指向未随包发布的脚本

- **证据（全部是文案，不是 import，这点要说清——不能夸大成"主程序崩"）**：
  - `agent/handler.py:9283` → 让用户跑 `tools/_build_chat_index.py`（不在包内）
  - `agent/store.py:1406` → `python tools/迁移_chat_log_索引.py`（不在包内）
  - `agent/paths.py:277-279` 明确写「这里不 import tools/（agent 层不依赖 tools 层）」，只读同名键 `依赖位置.json` → **主程序本身不会因为缺 tools 启动失败**，这是对来稿"整套不可用"的重要限定
- **结论**：缺 tools 的杀伤面是**安装器 + 桌面端 + 用户照文案操作**，不是 `main.py` 启动。修的时候别把 tools 当运行期依赖整体拷进去（会踩 09-05 的泄漏风险），要按"被谁引用"精确放行。

### A6【Important】安装器数歌的判据与生产口径不一致

- **位置**：`tools/安装糖糖.py:1266` 只 `glob("*.wav")`；`agent/songs.py:64` 同时认 `.wav` 与 `.mp3`
- **含义**：包内歌曲是 mp3 形态（发布包转码后），安装器数出来 **0**，生产却能播——"数字不可复现"的典型。来稿把"0 首"归因到判据，方向对，但要注意 mp3 是**发布包的正确形态**，错的是计数口径，不是转码。

## 四、共因：为什么这种包能出厂

三个独立缺陷叠在一条链上，任何一个生效都不会出事：

1. **白名单制**（`准备发布.py:174 TOOLS_KEEP_NAMES`，约 20 项）——收窄的初衷是安全（09-05 泄漏），但**没有"够不够"的校验**。
2. **援引的闸门不存在**（A1）——给了维护者"有人在盯"的错觉。
3. **快照断言 skip**（A2）——即使有人补了闸门，只要不生成快照，CI 也全绿。

再往前一层：**发布链被拆成两个脚本**（`准备发布.py` 出快照 → `打包发布版本.py` 出 zip）。曲库、桌面端 exe、`INSTALL_NOTE`、SnowLuma 说明全在**第二段**补，而第一段的说明文案（`songs/摆放说明.txt` "已自带"）**先写死**。两段之间没有"数量对得上才放行"的契约 → 补失败只 print 一行 `[!] 转码失败，跳过`（`打包发布版本.py` 的 `_add_bundled_media`），zip 照出、文件名已是最终名（注释 147-151 自己记过这个事故）。

**这不是"漏了几个文件"，是"发布物没有任何一处以包内实际内容为输入做验收"。**

## 八、修复落地与复验（2026-11-14 01:0x 追加）

### 8.1 来稿 §7 的口径要下修：0 首的**真根因在转码器**，不在判据

来稿把「曲库 0 首」归因为「判据只看目录存在（`is_model=False` → 只 `path.exists()`）」。
这只解释了**为什么 0 首还能打 [√]**（没有报警），没解释**为什么是 0 首**。

取证后真根因在 `tools/打包发布版本.py::_to_mp3`：

```
tmp = out.with_name(out.name + ".part")     # → 歌名.mp3.part
ffmpeg ... -b:a 128k str(tmp)
→ ffmpeg 返回 4294967274 (-22)
  Unable to choose an output format for '...\歌名.mp3.part'
```

ffmpeg 按**扩展名**选 muxer，`.part` 认不出来就退出。实测 **40/40 糖糖声线、
41/41 原声全部转码失败**，而 `_add_bundled_media` 对失败只 `print` 一行
`[!] ... 跳过` 然后 `continue` —— 包照样生成，文件名照样是最终的
`tangtang-vX.zip`。这就是「文件名是最终名、里面没有歌」的完整机制
（打包脚本 147-151 行的注释早就记下过这个症状，但从没定位到 `.part`）。

修法：`-f mp3` 显式指定 muxer；并在写 zip 前加数量闸门
（`n_voice < want_voice` → `SystemExit`）。**闸门当场生效**：修复前的第一次
重打包就是被它以「糖糖声线只进了 0/40 首」拦下的。

## 十、追加：桌面端「后端桥退出」——不是 PySide6，是第二跳 import（2026-11-14）

### 10.1 用户的判断方向与事实

用户观察：安装时没勾第 6 项（图形控制台 / PySide6），随后桌面端报
「后端桥退出（code=2）」，怀疑是这个没勾导致的。

**与 PySide6 无关**，运行时证据：

```

→ 81 条 import 记录，零 PySide6 / shiboken / PyQt
```

Qt 只在 `运维/糖糖控制台_qt.py` 里，与 Electron 桌面端是两条独立路径。

### 10.2 真病灶：包内缺 `scenario_rename.py`

在 v1.08.02 包内直接跑桥（系统 python、无 PySide6）：

```
Traceback (most recent call last):
  File "tools\desktop_bridge.py", line 54, in <module>
    from tools.asset_edit import AssetError as _AssetError
  File "tools\asset_edit.py", line 37, in <module>
    from tools.scenario_rename import sync_rename as _sync_scenario_targets
```

**同一个根的第二个面**：v1.08.01 的修法（白名单 ∪ 被引用）只认路径字面量
`tools/xxx.py`，而 Python 更常见的引用是 `from tools.xxx import`。
`scenario_rename` 只出现在 `asset_edit` 的 import 行里 → 没进包；
而 `desktop_bridge → asset_edit` 两跳都在包内，于是**桥在 import 期就死**。

链条：`desktop_bridge.py`（Electron 按路径引用）→ `asset_edit.py`（desktop_bridge 按路径引用）
→ `scenario_rename.py`（**只在 import 行里，没人按路径提到它**）→ 缺。

### 10.3 修法

1. `_refs_in_text()`：路径字面量 + `^\s*(?:from|import)\s+tools\.(\w+)` 两类都算；
2. `closure()`：随包集合补到不动点（包内模块自己 import 的也带上），
   `tools_to_pack() = closure(白名单 ∪ 被引用)`；本次带进 4 个，tools 36 → 46；
3. **扫描命中阻断下游**：准备发布.py 的敏感扫描跑在快照写完**之后**，而打包是另一条
   命令。本轮实测：扫描报命中（`scenario_rename.py:12` 一个真 QQ）并 `SystemExit(1)`，
   手工再跑打包脚本，zip 照样产出、名字照样是最终名——与 v1.08.01 曲库事故同一个形状。
   现在命中时写 `快照/.release-blocked`，打包脚本开头检测到即拒绝出包；通过时删除标记。

## 十二、追加：安装依赖全失败——`No module named pip` 与悬空的 site-packages（2026-11-14）

### 12.1 用户现场

```
$ python.exe -m pip install websockets>=12.0 ... 
python.exe: No module named pip
[!] 安装失败: ['websockets>=12.0', 'httpx>=0.27.0', ...]——请手动重试
```
三条 pip install 全失败（核心组、记忆组、torch）。而「请手动重试」在同一解释器上
同样会失败——用户被卡死在死循环里。

### 12.2 第一层：安装器从不检查 pip

`_install()` 直接 `sys.executable -m pip install`。`install_groups()` 之前没有任何
前置检查。修法：`ensure_pip()`（先自检 → 缺则 `-m ensurepip --upgrade` 离线自愈 →
再复检），在 `install_groups()` 开头调用；`check_environment()` 增加
`pip: [√]/[×]` 一行。

### 12.3 第二层（更根本）：`<Python>\Lib\site-packages` 是失效的目录联接

```
C:\Users\Administrator\AppData\Local\Programs\Python\Python310\Lib\site-packages
  LinkType = Junction
  Target   = \\?\D:\qq-小糖糖\依赖\site-packages      ← 目标已不存在
  读该目录 → 未能找到路径的一部分
```

来源：`tools/依赖迁移.py` 的设计是「把 Python 的 site-packages 用目录联接指向项目
依赖目录，sys.path 一个字不变」。项目从 `D:` 搬到 `F:`、旧目录被删之后，联接悬空。

后果：Python 读不到任何包（pip 也没有），`ensurepip` 崩在

```
FileNotFoundError: [Errno 2] No such file or directory:
  '...\Python310\Lib\site-packages\distutils-precedence.pth'
```

**判据要点（否则认不出来）**：

| 表达式 | 悬空 junction 的结果 |
|---|---|
| `os.path.exists(p)` | **False** |
| `os.path.lexists(p)` | True |
| `os.path.islink(p)` | **False**（junction 不算 symlink！） |
| `os.readlink(p)` | `\\?\D:\qq-小糖糖\依赖\site-packages` |

所以判据必须是 `lexists and not exists`；用 `islink` 会漏掉全部 junction 场景。

### 12.4 修法与实测

`ensure_pip()` 两道前置：

1. **site-packages 必须是真实可写目录**：悬空 → 打印来源 + 两条命令；
   交互环境问一次「删除失效联接并重试？[y/N]」（`os.rmdir` 只删链接、不动目标）；
   非交互（`stdin` 非 tty）**不擅自改系统目录**，只打印命令。
2. 目录可用但没 pip → `ensurepip` 自愈。

本机实测（这台机器原本就坏着，正好当样本）：

```
python310 -m pip --version            → No module named pip
python310 -m ensurepip --upgrade      → FileNotFoundError: ...\distutils-precedence.pth
rmdir "<site-packages>"               → 删除悬空联接（只删链接）
python310 -m ensurepip --upgrade      → Successfully installed pip-23.0.1 setuptools-65.5.0
python310 -m pip install --dry-run pyyaml → Would install PyYAML-6.0.3
安装糖糖.py 安装 --dry-run            → pip: [√] pip 23.0.1 from ...\site-packages\pip
```

### 12.5 顺带：「6. 图形控制台」的处理

用户问「已经换桌面端了，这条是不是没必要」。判断：**不必预勾，但不能删**。

- 主入口是 Electron 桌面端，PySide6（~100MB）只服务 `运维/糖糖控制台_qt.py`
  （`python start.py console`）与 `外观预览器/color_panel/icons/ui_anim`；
- 删除条目会让 `FEATURES` 下标整体错位——`write_manifest()` 记的是**下标**，
  已安装机器的 `状态/安装清单` 会指错功能；
- 因此 `DEFAULT_FEATURES` 从 `[0,3,5]` 改为 `[0,3]`（不再打 `*`），
  条目描述改为「旧式 Qt 控制台 + 图标/外观预览，PySide6 约 100MB，日常请用桌面端」，
  `GROUPS["控制台"]` 与 INSTALL_NOTE 同步。
