# Codex 对话质量方案（2026-08-17）

> 结论先行：四批修复方向大体正确，但目前更像“压缩症状”，还没有完成“从说明书驱动改为身份 + 当前事实驱动”的结构转换。最优解不是继续加反模板规则，而是修正背景选择器、消除重复状态源、把能力说明迁回工具 schema，并用真实对话盲测决定保留什么。
>
> 审查方式：逐行核对指定文件、GitNexus 符号上下文、只读 SQLite 聚合及本地函数探针。GitNexus 因项目不是 git 仓库无法给出 freshness 状态，故图结果仅用于辅助定位，最终证据均回到源码。本文只给实施方案，不修改运行代码。

## 一、对我方四批修复的独立评估

### 批次 1：背景预算 + 风格锚

**做得对**

- 把框架材料限制在预算内，是对“短消息被材料综述淹没”的直接修复；用户原文仍由 `assemble_user_message()` 保持无标签且最后，协议仍紧贴原文，来源契约没有被破坏（`agent/protocols.py:186-196`，`agent/handler.py:2052-2068`、`2803-2822`）。
- 引用缺失和困难轮次协议不被普通背景淘汰，方向正确；这两块不是聊天素材，而是纠错控制信息。
- 用真实片段替代“自然一点”的抽象命令，方法上优于继续堆规则。

**不足**

- `BACKGROUND_PRIORITY` 名存实亡。`fit_backgrounds()` 从未排序，只按调用列表先来先占预算；优先级数值除 `<=1` 的保护判断外没有参与选择（`agent/protocols.py:207-243`）。群聊实际顺序是姿态/提及/文件/记忆/情绪/自忆/知识库/图片/窗口/补读/关系/交叉/日记/引用/协议（`agent/handler.py:1927-2063`），私聊也把记忆放在图片、窗口、交叉之前（`agent/handler.py:2736-2818`）。因此“当前刚发的图片”会被旧记忆抢掉，恰好损害当前轮理解。
- 本地探针实测：400t 预算、输入顺序为记忆→图片→窗口→引用→协议时，输出为“记忆 397t + 引用 7t + 协议 7t”，图片和窗口全丢，总量还达到 411t。它不是按优先级淘汰，而是按 append 顺序淘汰。
- “引用/协议永不丢”同时意味着预算不是上限。本地构造两个各 1000 汉字的保护块，100t 预算最终保留约 3600t。保护语义可以保留，但必须明确记录 overflow，并在请求总预算层从历史等可裁区域让位。
- `_truncate_bg_block()` 只找字符级标点（`agent/protocols.py:246-256`）。它可能切断记忆条目、窗口角色对、知识库引用或文件结构，留下语法完整但语义错误的半条事实。
- 预算只计算内容，不计算 `<背景·标签>` 包装；也没有输出 kept/dropped/reduced 的逐块账本，线上无法知道质量下降究竟丢了什么。

**风险**

- `tests/test_dialog_quality.py:43-48` 的上限断言实际写成 `assert ... if False else True`，永远通过；“按优先级”测试又恰好按期望优先级排列输入，没有覆盖乱序。449 全绿不能证明预算器正确。
- `STYLE_ANCHOR` 四条都采用“先反应、再追问/留钩子”的近似节奏，3/4 以问句推进，2/4 带“喵”，会把旧模板换成新模板（`agent/protocols.py:263-269`）。第一条“刚醒”还是材料外状态，与不编造个人状态的既有原则相冲突。

### 批次 2：CoT 瘦身 + 状态信号化

**做得对**

- 中性状态零注入、去掉 `/100` 数值、弱驱动力不出现，确实减少“汇报仪表盘”的诱因（`agent/mood.py:168-185`，`agent/self_state.py:153-176`，`agent/drives.py:258-281`）。
- 自我叙事从履历清单缩成总结与一条领悟，减法方向正确；驱动力只投影主导项，也比多项百分比报告自然。
- 没有用中文关键词决定糖糖说什么，仍然由 LLM 决定回复内容。

**不足**

- 6→3 仍是常驻 CoT，且第 2 条把指代不清、纠正复述重新常驻（`agent/personality.py:302-312`），与“理解协议/思考段只在 hard_turn 注入”语义重复。困难轮次协议虽在 handler 门控，内容却被普通 CoT 复制了一份。
- 状态仍有三个可冲突来源：`_get_time_context()` 按时段直接规定“刚起来/饭后懒散/晚上话多/深夜走心”（`agent/personality.py:463-481`）；`MoodEngine` 给事件驱动情绪；`ExistenceState` 又按时间生成另一套精力/心情（`agent/self_state.py:398-428`）。例如上午可同时出现“精力充沛、温暖”和 MoodEngine 的“心情低、不想热闹”。压短不等于单一事实源。
- “感受口吻”中仍混入动作指令：`回复短一点、软一点`、`可以多开玩笑`、`会追问/解释/跟进`（`agent/self_state.py:158-173`，`agent/drives.py:272-278`）。状态层应只说“现在是什么感觉”，不替 LLM 决定行为。
- 关系仍是三到四套并行：五参数 tier（`agent/personality.py:392-459`）、RelationshipField（`agent/self_state.py:282-320`）、私聊关系摘要和画像（`agent/handler.py:2670-2684`）、记忆背景。尤其 tier 仍把五个行为维度逐项讲解，是剩余“表演手册”的大头。

**风险**

- tier 的“说骚话都随意”只看亲密度，不看 `sed_allowed`（`agent/personality.py:408-415`）。即使真正的 seductive 场景有显式成年人白名单，这条常驻关系提示仍可能把“亲密”误当成敏感内容权限。关系强度不应授予内容权限。
- `SelfNarrative.to_context()` 仍每轮注入最近领悟（`agent/self_state.py:90-99`），与当前话题无关时仍会诱导自我表述。

### 批次 3：anti-tell 诊断

**做得对**

- 先观测、不阻断、不做回复后字符串改写，是正确的安全姿态；否则会把自然表达误删成残句。
- 把诊断放在统一 self-check 出口，覆盖面比散落在发送路径里好。

**不足**

- 七个正则只覆盖非常窄的固定短语（`agent/self_check.py:74-85`），没有括号动作、耳朵/尾巴镜头、每轮“喵”、固定开场、总以问句结尾、二段式安慰、同义模板等真正的分布问题。
- 日志只有命中字符串，没有结构化计数、模型/场景/hard_turn、prompt 各段 token、后续反馈，无法做因果归因。
- 诊断的是单条句子，不诊断跨回复重复；“少用模板”本质上更接近群体分布和 n-gram 重复，而不是单条禁词。

**风险**

- 只读 DB 基线（2026-08-16 00:00 至修复时间 2026-08-17 12:38）共有 983 条 bot 回复：现有 anti-tell 近似规则命中 0 条，但含耳朵/尾巴/蹭/笑等括号动作镜头的回复为 116 条（11.8%），含“喵”为 844 条（85.9%），含问号为 512 条（52.1%）。说明当前指标几乎测不到用户所说的问题。修复后截至 DB 最新时间只有 2 条回复，不能据此声称改善。
- 若未来把这七条直接升级为阻断，会优化一个基线为零的代理指标，并制造误伤。

### 批次 4：minimal 模式

**做得对**

- 遥控说话、私信、群发言、遥控唱歌不需要关系场、状态投影和普通对话 CoT；按调用场景裁剪是比全局砍功能更稳妥的做法（`agent/handler_commands.py:447-467`、`1119-1129`，`agent/handler.py:5022`、`5344`、`5421`）。
- 本地构造探针显示：普通 `build_system_prompt()` 约 1460 字，minimal 约 846 字，方向上确有减负。

**不足**

- 注释称“身份+风格锚”，实际无场景时仍从完整 `_cached_base` 起步（`agent/personality.py:260-285`）；只是跳过后续动态手册，不是真正的最小身份核。
- minimal 每次仍加 `_get_time_context()`，因此遥控发言也会被“刚起来/饭后懒散/深夜走心”塑形。
- 正常唱歌路径 `_build_singing_system_prompt()` 仍走完整 prompt 并可再带 memories（`agent/handler.py:6379-6396`）。这不一定是 bug，但说明“唱歌已轻量化”只覆盖遥控唱歌，命名和测试应说清边界。

**风险**

- **违反铁律：** `minimal=True` 在 `agent/personality.py:283-285` 提前返回，而 `CORRECTION_CONTRACT` 到 `:306-312` 才注入；所以 minimal system prompt 不含无条件纠正契约。现有测试只断言普通模式含契约，漏测 minimal（`tests/test_dialog_quality.py:119-126`，`tests/test_memory_correction.py:141-146`）。
- 同类旧漏洞仍在：`_voice_role_override` 在所有协议和动态块拼完后用整张角色卡覆盖 `base`（`agent/personality.py:343-346`），也会抹掉纠正契约。`reload_role_card()` 又没有复用 `_build_cache()` 的正确拆分逻辑（`:167-176`），热重载后 replace 场景的 minimal cache 可能只剩标题/尾段。四批修复没有覆盖提示词变体矩阵。

## 二、我发现的额外问题（按严重度排序）

### Critical

1. **[agent/personality.py:283-285, 306-312, 343-346] 纠正契约并非无条件。** minimal 与语音角色覆盖都能绕过/抹掉契约；测试只覆盖默认普通模式。为什么是问题：直接违反项目铁律，并可能出现“口头说记住了但未落库”。建议：把身份选择与全局契约拼装分层，所有变体最后都经过同一个不可绕过的 contract 装配器。

2. **[agent/protocols.py:207-243；agent/handler.py:1927-2068, 2736-2822] 背景优先级没有生效，当前轮证据可能被旧材料挤掉。** 为什么是问题：图片、窗口、知识检索结果比自动记忆更贴近当前问题，却因 append 靠后被丢弃；这会直接产生答非所问。建议：先选择、后恢复展示顺序；选择按来源类型和当前轮直接性，展示仍保证协议贴近用户原文。

3. **[agent/handler.py:3149-3161, 3290-3299；agent/context_builder.py:235-239] 实际请求携带全量 Native Tool schema，但 token 账本完全不计 tools。** `build_tool_definitions()` 会把所有注册技能逐个加入，每轮再合并记忆、唱歌、语音、CG 等工具；审查里的 5500-9000t 没有量化这部分。为什么是问题：工具 schema 同样占输入注意力；在删 100t 状态块时，可能漏看了数千 token 的工具描述。建议：在 `_call_llm_with_skills()` 完成 `all_tools` 后序列化计量，先测占比，再决定是否做 LLM 主动调用的 `discover_capability` 二阶段工具发现；禁止用关键词替系统裁工具。

### High

4. **[agent/handler.py:763-813, 2080-2082, 2840-2843, 3541-3550；agent/context_builder.py:217-230] 能力说明三重重复且占据 system 尾部。** 工具 schema 已有描述，`capability_note` 又列一次，`_tool_instructions` 再列一次；capability 还享受截断豁免。私聊画像/关系摘要又拼进同一个豁免字符串（`agent/handler.py:2670-2722`）。为什么是问题：尾部高注意力位置被“如何使用工具”占据，模型更像助手而不是角色；画像也逃离正常预算。建议：工具能力只在 schema 表达；system 仅保留 schema 无法表达的当前身份/安全边界，控制在一行；画像和关系档案改成带来源标签、可计量的背景块。

5. **[agent/personality.py:463-481；agent/mood.py:168-185；agent/self_state.py:153-176, 398-428] 时间、Mood、Existence 是三个状态真源。** 为什么是问题：同轮可能给出相反情绪，且时间层凭时段编造“刚起来”“饭后”并规定说话风格。建议：时间只给客观时段；Mood 作为当前 affect 主源，Existence 只提供无冲突的昼夜能量底色；由一个投影器合成最多一行。

6. **[agent/personality.py:392-459；agent/self_state.py:282-320；agent/handler.py:2670-2684] 关系状态重复、内容权限与亲密度耦合。** 为什么是问题：模型需综合多份“该怎么和 ta 说话”，自然进入报告/表演模式；“亲密即可说骚话”还绕开成年人场景权限。建议：关系层只保留一个姿态信号（陌生/熟悉/亲近 + 一条真实纹理）；事实、往事、未完成承诺分别走记忆/任务来源；敏感权限只由显式成人 scenario 决定。

7. **[agent/protocols.py:263-269] 风格锚本身模板化并教会虚构状态。** 为什么是问题：所有示例都偏主动、偏追问，模型会学到“每次留钩子”；“刚醒”没有事实来源。建议：使用经过真实正反馈筛选的多形态片段，包含短答、直接答、不追问、不同意、温柔承接、群聊插一句；不出现材料外经历，且问句/猫口癖只占少数。

### Medium

8. **[agent/context_builder.py:95-100, 217-239；agent/handler.py:2069-2074, 2823-2828] 没有请求级总预算。** system 先裁，user 后计但不再裁，tools 完全漏计，history 固定 15 条也未与其余部分联动。建议：预算对象覆盖 system + history + current user + tools，按“身份/契约不可裁 → 当前用户不可裁 → 当前轮直接证据 → 最近历史 → 召回材料”退让。

9. **[agent/context_builder.py:37-48；docs/审查/对话质量全链路审查_20260817.md:76] DeepSeek V4 的 tokenizer 比例和“50 轮约 30%”没有可复现来源。** 当前配置名为 `deepseek-v4-flash`（`config.yaml:117-124`），但本项目没有官方模型卡/论文或本地评测支撑这些精确数字。建议：把它们标为假设；用实际 API usage token 校准估算器，并做 head/middle/tail 位置扫描，不把未经验证的百分比写成架构前提。

10. **[tests/test_dialog_quality.py:23-52, 104-147] 回归测试证明“字符串存在”，没有证明“对话更自然”。** 还存在永真断言。建议：单元测试守结构契约，质量结论交给固定语料盲测、线上分桶与反馈指标，二者不要混称。

**明确没有发现问题的方面：** 用户原文仍最后且无标签；正常群/私路径的困难轮次协议仍由 hard_turn 门控并紧贴用户原文；本轮改动没有向 role_card 添加规则；anti-tell 没有做危险的输出后改写；状态持久化字段未因压缩而被删除；敏感场景的主开关仍采用显式 scenario + 持久化动态激活。

## 三、最优方案（按优先级批次）

### P0：先修契约和选择器正确性（应立即做）

#### 1. 统一 system prompt 装配出口

- **改什么文件：** `agent/personality.py`，`tests/test_personality.py`，`tests/test_memory_correction.py`，`tests/test_dialog_quality.py`。
- **怎么改：** 将“选择身份底座”和“追加稳定契约/动态状态”拆开；`CORRECTION_CONTRACT` 放进所有模式共享的稳定契约段，普通、minimal、overlay、replace、voice override、热重载都必须经过。voice override 只替换身份底座，不覆盖已装配协议。`reload_role_card()` 直接复用 `_build_cache()`，不维护第二套切割逻辑。
- **同时调整 CoT：** 保留缓存契约要求的稳定“回复前先想”位置，但只留一句普通轮路由（是否在对你说话）；删掉指代/纠正复述的常驻副本。`THINKING_PROTOCOL + COMPREHENSION_PROTOCOL` 仍只由 handler 的 hard_turn 注入。纠正落库契约独立于 CoT、始终存在。
- **为什么：** 先消除“绿测下违约”，也真正落实困难轮次按需思考。
- **风险与验证：** 风险是改变缓存前缀。更新测试时不能放松顺序：角色卡→群风格→权力→短思考/纠正契约→动态块。增加 6 种 prompt 变体参数化测试，逐一断言契约存在；断言普通轮不含 `THINKING_PROTOCOL/COMPREHENSION_PROTOCOL`，hard_turn user block 才含。实施前对 `build_system_prompt`、`reload_role_card`、`load_role_file` 做 GitNexus upstream impact；若 HIGH/CRITICAL 先告警。

#### 2. 重写背景选择为“语义安全选择器”

- **改什么文件：** `agent/protocols.py`，群/私背景构造处 `agent/handler.py`，`tests/test_dialog_quality.py`。
- **怎么改：** `fit_backgrounds()` 分三步：① 清洗并记录原始 index；② 保护块先计量，flex 块按明确优先级选择；③ 选择后按原始 index 恢复展示顺序，保证协议仍紧贴用户原文。预算计算包含标签包装。保护块允许 overflow 但必须返回/记录 `overflow_tokens`，由总请求预算从历史让位。
- **优先级建议：** 当前轮直接证据（引用、协议、提及、图片、文件）> 连贯性（窗口、交叉、补读）> 已召回事实（记忆、自忆、关系档案）> 可选氛围（日记、情绪、泛知识）。知识库若是本轮工具/检索明确返回，应标成“当前证据”，不能永远按标签排最后；这不是关键词判内容，而是按来源可靠性分层。
- **禁止通用硬截断：** 记忆按完整条目裁；窗口按最近完整 role pair 从尾部保留；知识按完整检索 chunk；图片/引用/协议不切。给 reducer 返回 `reduced/dropped` 原因。
- **为什么：** 预算的目标是保留最能回答当前消息的事实，不是机械保留最早 append 的块。
- **风险与验证：** 风险是改变材料可见性。用乱序、保护块超预算、图片+大记忆、知识 chunk、未知标签、包装开销测试；修掉 `if False else True`。对线上只记录标签和 token，不记正文。

### P1：完成真正的“去说明书化”（P0 后一批一验）

#### 3. 能力信息回归 Native Tool schema

- **改什么文件：** `agent/handler.py` 的 `_build_capability_note`、`_build_memory_tools`、`_call_llm_with_skills`，`agent/skills.py`，`agent/context_builder.py`，相关集成测试。
- **怎么改：** 先把 `all_tools` JSON 的估算 token、工具数写入 TokenReport。删除 capability_note 中已由 schema 表达的“其他工具”清单，删除 `_tool_instructions` 与 schema 重复的 1-6/8 条；隐私限制下沉到相应搜索工具 description。system 只留 schema 无法表达的当前角色/运行模式差异，目标不超过约 80t，且不再用 marker 截断豁免。
- **若实测 tools 占请求 >25%：** 保留高频且高风险的原生工具（纠正、记忆查询、语音等），把低频能力放到一个 `discover_capability(query)` 元工具后按 LLM 主动请求加入下一轮工具集合。不能由关键词预裁工具，也不能由系统猜用户意图。
- **为什么：** 工具 schema 本来就是能力的单一事实源；三份自然语言说明只会增强助手腔。
- **风险与验证：** 工具发现多一轮调用、可能降低罕见工具召回。离线回放“唱歌/识图/实时搜索/纠正/切角色/普通闲聊”各 20 例，比较工具召回与误调用；普通闲聊必须显著降低输入 token，关键工具成功率不下降。

#### 4. 合并状态与关系投影

- **改什么文件：** `agent/context_builder.py`，`agent/personality.py`，`agent/mood.py`，`agent/self_state.py`，`agent/drives.py`，`agent/handler.py`，对应状态测试。
- **怎么改：** ContextBuilder 增加唯一的 `current_state_line` 投影：时间只给客观时段；Mood 是当前 affect 主源；Existence 只补不冲突的昼夜能量；dominant drive 只给欲望事实，不写“会追问/该解释”等动作。整块最多 1-2 句，无标题也可。
- **关系单一来源：** `_get_tier_prompt()` 压成“陌生/熟悉/亲近 + 一句边界”，删除五参数说明和任何敏感内容授权；RelationshipField 只保留一条关系纹理与未完成承诺。私聊画像、关系摘要从 capability_note 移到 `<背景·画像>/<背景·关系档案>`，进入预算。SelfNarrative 不再常驻，作为 `_get_self_memory_context()` 的一个语义召回候选；是否使用仍由 LLM 决定。
- **为什么：** 持久状态应该成为感受输入，不应变成每轮自我说明书。
- **风险与验证：** 风险是“生命感”变淡。做冲突测试（时间高能量 + Mood 低落、avoid + warm 等），断言最多一个状态块且无相反词；用“问糖糖自己/普通闲聊/低落陪伴/老朋友续聊”盲测连续性。持久数据结构不删字段，只改投影，避免破坏历史。

#### 5. 把风格锚改成“分布锚”

- **改什么文件：** `agent/protocols.py`，`agent/personality.py`，`tests/test_dialog_quality.py`；样本筛选脚本可放 `tools/eval_dialog_quality.py`，不把真实私聊正文提交仓库。
- **怎么改：** 从真实回复中筛选有明确正反馈、无隐私、无幻觉的片段，组成多形态小集合：短答、直接解答、承接但不追问、明确不同意、群聊插一句、认真长答各一例。删“刚醒”；问句不超过约 1/3；“喵”不超过约 1/3；长度和句式故意不同。固定集合总预算控制在现有锚附近，不在每一轮随机旋转。
- **为什么：** 示例应锚定“可能性空间”，不是锚定一个两句式模板。
- **风险与验证：** 风险是模型复刻示例。监控示例 4-gram 与线上回复重合率；一旦明显上升就撤掉具体片段，保留更短、更分散的示范。A/B 决定风格锚是否真的优于只用 role_card，不能先验认定示例一定有益。

### P2：建立能回答“是否更自然”的验证系统

#### 6. 结构化质量遥测，不做阻断

- **改什么文件：** `agent/self_check.py`，`agent/store.py`（或现有统一 SQLite 迁移入口），`agent/handler.py`；新增 `tests/test_dialog_quality_metrics.py`。
- **怎么改：** 每条已发送回复落一行聚合指标：时间、匿名会话键、群/私、模型、scenario、hard_turn、prompt 四部分 token（system/history/user/tools）、回复长度、括号动作、助手腔、问句结尾、猫口癖、固定开场、与近 N 条 bot 回复的字符 4-gram/Jaccard。关联已有 positive/negative/silence/shutdown 反馈，但不保存额外正文。
- **为什么：** 用户抱怨的是重复分布，必须跨回复看；日志 grep 不能做分桶、趋势或反馈关联。
- **风险与验证：** 指标本身不能成为生成规则；不阻断、不自动重写。迁移需幂等，运行状态和 A/B 分桶必须落盘，满足重启铁律。

#### 7. 离线回放 + 线上粘性 A/B

- **改什么文件：** 新增 `tools/eval_dialog_quality.py`、匿名评测配置；若加开关，`config.yaml` 与 `糖糖控制台_qt.py` 同步。
- **怎么改：** 从真实流量按群聊/私聊、短消息/困难轮、图片/记忆/工具、陌生/亲密分层抽 150-200 个匿名上下文。旧 prompt 与候选 prompt 同温度多次生成，盲序双评。主评分：自然度、像糖糖、是否直接回应、是否编造、是否安全；人类评价为主，独立模型裁判只作辅证。
- **线上门槛：** 按会话做持久粘性分桶，每臂至少 300 条有效回复再判断；候选人类偏好胜率目标 >55%，负反馈/答非所问/工具失败/敏感越权均不得恶化。当前 983 条基线中的“括号动作 11.8%”可作观察指标，但“喵 85.9%”不能简单设成越低越好，应结合身份偏好。
- **为什么：** pytest 只能守契约，不能证明自然；两条修复后样本没有统计意义。
- **风险与验证：** 群体差异可能淹没效果，所以必须按会话粘性、场景分层，而不是逐消息随机。

#### 8. DeepSeek 位置与长度实测

- **改什么文件：** `tools/eval_dialog_quality.py` 增加 position-sweep；TokenReport 接入 API 返回的真实 usage（若端点提供）。
- **怎么改：** 同一事实分别放在 system 首部、中部、system 尾部、user 背景靠前、紧邻用户原文；在 1k/3k/6k/12k 输入和 5/15/30 轮历史下测事实提取、指代、工具选择。每格重复至少 20 次。
- **根据结果排序：** 无论模型结果如何，身份与无条件契约保持 system 首部稳定前缀；用户原文永远最后；hard_turn 协议紧邻原文；能力元数据迁入 tools；历史从最近完整轮次向前裁。只有实测证明有效后，才进一步调整关系/状态在 system 尾部的位置。
- **为什么：** “首尾效应”可作为实验假设，不能用无来源的“约 30%”替代本模型、本端点、本 prompt 的测量。

### P3：请求级预算治理（数据证明需要后再做）

- **改什么文件：** `agent/context_builder.py`，`agent/handler.py`，工具装配处与 token 诊断测试。
- **怎么改：** 建一个覆盖 system/history/user/tools 的 RequestBudget；普通闲聊目标总输入约 3k-4k（需先用真实 usage 校准），困难/文档轮允许扩张。退让顺序固定为：身份与契约、当前用户、当前轮直接证据不可丢；再保最近完整历史；最后才是召回记忆、关系档案、氛围材料。不要用用户关键词分预算。
- **为什么：** 单独给 system 3000t、背景 1200t、history 2500t 并不能形成 6000t 总上限，尤其还漏 tools。
- **风险与验证：** 过度压缩会损伤长讨论和工具能力，因此必须按任务型/闲聊型的真实评测曲线设阈值，不拍脑袋一次砍到极短。

## 四、不要做的清单

1. **不要把 anti-tell 词表直接变成阻断器或回复后替换器。** 当前七模式基线几乎为零，拦它们只会优化错指标；字符串改写还可能破坏语义。
2. **不要继续往 role_card.md 加“少用模板/别表演/别追问”等规则。** role_card 只写身份；新增规则既违反四章节契约，也会重复制造说明书。
3. **不要为了短而删除 CORRECTION_CONTRACT、来源标签、用户原文最后、hard_turn 协议或敏感场景白名单。** 这些是正确性/安全契约，不是可牺牲的风格装饰。
4. **不要按关键词选择工具、背景或“是否该温柔”。** 工具发现应由 LLM 主动调用；预算只按来源、可靠性、时效和已发生的客观模态分层。
5. **不要把所有状态都删掉。** 问题是多源重复和行为指令化，不是持久状态本身；保留落盘结构，收敛投影出口。
6. **不要把关系亲密度当成成人内容权限。** 内容权限只来自显式指定的成年人 scenario；tier 只描述关系姿态。
7. **不要每轮随机换风格示例。** 这既破坏稳定前缀缓存，又制造风格漂移；先用固定候选做 A/B，证明有效再决定。
8. **不要把 capability_note 简单搬到 user message。** 那仍是常驻说明书，还会污染“用户原文最后”的信任边界；能力应回到 tool schema 或由 LLM 主动发现。
9. **不要用固定 1200t/15 条历史作为永恒真理。** 先把 tools 和真实 usage 算全，再根据任务曲线设预算；文档问答与“嗯嗯”不应同一预算。
10. **不要以 449 测试全绿或两条修复后回复宣布成功。** 测试证明结构没有明显回归，不能替用户证明“自然”；最终裁决必须来自盲测、真实反馈和足够样本。
