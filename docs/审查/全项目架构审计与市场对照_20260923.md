## 一、执行摘要

> **架构多处领先，但"排气管"没接。**

**领先的**（六域对照后确认）：LLM 自主决定引用与分条、不确定即冻结永不重放、证据先于信任、六驱动力 + 情绪 + 关系场这一整套内在状态结构。

**但写进去的东西不回流**：

| 症状 | 数字 |
|---|---|
| 驱动力长期贴顶 | 4/6 在 **0.91~0.99**，每 30 分钟印同一句 |
| 情绪事件零发射 | **15 个里 11 个没有发射点**；而"心情"是 `random.randint(-15,15)` |
| 承诺只记账不闭环 | **193 active / 0 fulfilled** |

| 记忆的时间语义 | **486 条 value 冻结着"昨天 / 上周"**，正被当新闻复述 |

### 最要紧的三件事

1. **装好内部张力的排气**（驱动力消化 + 情绪接线 + 承诺闭环）——**这正是 CLAUDE.md 零章自陈的主要矛盾**
2. **让发生过的事按确认粒度落账**（部分送达前缀 / 离线重放 / 兜底文案 / 多气泡 / 延迟群发言——都已真实送达用户，却在她自己的历史里不存在或变形）
3. **给时间语义**（解析相对时间 + 注入"多久以前"）

**外加一条当天可修可验**：语音引擎失败时**静默把丛雨换成微软晓伊**（08-30 共 14 次），日志/回执/历史三处都称丛雨。

## 二、共同根因（合并六域去重后）

### RC1 · 只写不读——状态的生产远多于消费，而质检闸门看不见消费侧

**出现在**：自我状态 / 记忆 / 自治 / 能力层 / 消息链路（**五个域**）

**证据**：
- `agent/drives.py:320` `reply_commitment` **零调用**
- `unfinished / learned / vibe` **无任何写入方**（223 个关系全空）
- `agent/reflection.py:358-361` **排除**消化日记
- mood 的 **11/15 事件零发射**
- `agent/metrics.py:56-79` **五个方法零调用**，而 `/状态` 仍照常显示它们

**元根因（这条最要紧）**：
> 零调用闸门**只扫模块级函数**（`tests/test_integration_contract.py:130-137`）——**类方法与枚举成员在网外**，实际只覆盖约 **8%** 的可调用定义。

→ 也就是说：**"写了没接上"这个本仓反复踩的坑，它的检测器本身有个 8% 的覆盖率上限。**

### RC2 · 粒度二值化——事实的粒度细于账本的粒度

**出现**：消息链路 / 自治 / 能力层

**证据**：
- `agent/reply_pipeline.py:503-544`：首段未确认即停 + `delivered=all` + payload 只在整轮成功时写
- `agent/handler.py:12867-12882`：兜底文案**已送达**却 `return False`
- `onebot/ws_client.py:336-339` 与 `agent/store.py:9070-9071`：延迟重放的 confirmed **无归账**
- `agent/handler.py:10195-10218`：语音回执**无引擎字段**

### RC3 · 时间语义混用，且从不交给 LLM

**证据**：
- `agent/store.py:6039-6043`：`event_time = 证据消息时间`（不是事件发生时间）
- **486 条 value 冻结着"昨天 / 上周"**
- `agent/handler_autonomy.py:1230-1242`：**自记时间幻觉事故**，而修复只做了主动私聊路径
- `agent/scheduler.py:246-263`：`fire_at` **全等比较**，错过即丢
- `agent/daily_report.py:50` 的 `'9:00'` 与 `:124` 比较的 `'09:00'` **互斥**

### RC4 · 同一事实两个家

**证据**：
- `intimacy` vs `closeness`（`personality.py:381` vs `self_state.py:363-370`）
- `config.yaml` vs 控制台（`secret_refs.py:161` 的启发式；控制台保存会写回旧明文 token——**这正是 09-23 那次 401 的产生路径**）
- `scheduler` vs `tasks` 两套定时语义
- `准备发布.py:479` vs `发布前检查.py:52` 扫描口径不一
- **401 告警与"检查连接"给出相反建议**

### RC5 · 失败路径不产生可观测事实（静默降级）

**证据**：
- `agent/voice.py:345-355`：**换嗓，且日志/回执/历史三处都称"丛雨"**
- 自检拦截**不进观察器白名单**（`tools/runtime_observer.py:176-183`）
- 观察器把"内部消化"**当健康信号**（同文件 `:75`）
- `main.py`：解析失败一律 collapse 成空串

#### P0-1 · 驱动力没有消化回路：4/6 长期贴顶，每轮注入同一句

**域**：自我状态与内在动力　**代价**：中　**置信**：中　**拟人性**：高

#### P0-3 · 部分送达前缀不入账 + 多气泡在账本里压成一条
**域**：消息进出与发送链路　**代价**：中　**置信**：高　**拟人性**：高

**证据**：
- `agent/reply_pipeline.py:503-544`：首段未确认即停，`delivered=all`，`last_confirmed_payload` 仅整轮成功时写、**且是无分隔拼接**
- `agent/handler.py:12888-12895`：否则 `committed_reply` 为空串
- `agent/handler.py:4105/5129` 的 `if ok` 门控 chat_log / 窗口 / 自忆 / 亲密度
- **探针复现**：两段实际发出 2 个气泡，账本里粘连成一条

**建议**：`partial` 时按**确认粒度**写已确认前缀（段边界 + chunk id）并把 partial 事实交给 LLM；多气泡 payload 保留边界以恢复"条"语义；**保留"前段未确认不发后段"**。

> ⚠️ **附**：本仓项目自己的 ADR 早已要求这么做——
> `docs/decisions/ADR-002:64`「批量动作在 `actual.items` 中**逐项记录**」；
> `ADR-002:72`「**只有 `confirmed` 的真实发送可进入**聊天记录、窗口事件、关系反馈」；
> `ADR-003:23`「部分成功时不能把整段正文归账，**必须等逻辑动作与 `receipt.parts` 聚合完成后再接入**」；
> `ADR-003:128` 门禁「ReplyPipeline 部分送达**不得写整段 chat**」。
> **现状既不是"整段归账"、也不是"按条归账"，是"零归账"——ADR 里那个"再接入"从没做。**
> ⚠️ **但同时**：08-30 日志有**反向**的真实事故——`tangtang.log.2026-08-30:333321` 段 2 明确失败（`retcode=100 image source is empty`），`:333322` Handler 仍打 `📤 已发送`。**"过度记账"是这仓踩过的另一边。** 所以修法只能是"**只记平台已确认的那几段**"，绝不能回到整条入库。

## 五、不要动（12 条）

**这份清单和改造清单一样重要。** 本仓已积累 35 条踩坑教训，很多"不优雅"是有原因的。

| 设计 | 为什么别动 |
|---|---|

## 六、编程语言选型（专项）

### 结论

> **全 Python 是唯一正确解。但理由不是"Python 够快"，而是本地 ML 的「训练/导出链」只有 Python 实现。**

换任何语言都只能变成 **「新语言做壳 + Python 常驻做 ML」**——付了 5.6 万行重写费，**却没省掉 Python**。

**证据链**：`agent/voice.py:270-279`（`.ckpt/.pth`）、`tools/train_rvc.py`、`agent/diff_singer.py:1-8`、`tools/separate_vocals.py:15`（`venv_demucs`）；连 `GPT-SoVITS-cpp` 自己的 README 第一步都是跑 Python 的 `export_onnx.py`。

### 三条实测（都与直觉相反）

| 直觉 | 实测 |
|---|---|
| 「Python 启动慢」 | 裸解释器 + site **6.3ms**、asyncio 51.9ms、sqlite3 7.8ms → **纯 CPython 语言项 < 0.5%**。17 秒启动里 **transformers 单次导入 8,580ms（含 torch 2,953ms）≈ 50%**——**不是语言的锅** |
| 「Python 慢所以端到端慢」 | **60~80% 是 LLM 往返**（流式完成 n=1679：p50=1.90s / p95=17.00s / max=53.9s） |
| 「最大本地开销是解释器」 | **是 SQLite 提交争用**：生产 `commit_ms=366.8`（p50≈480ms）vs 隔离副本同规模 **FULL 提交 median 1.70ms**——**差约 200 倍**，成因是**同进程多写者争用**。**换谁都得自己写写者队列** |

**GIL**：**未测到，也未被证伪**。全仓无 cProfile/py-spy 产物，日志没有可聚合的事件循环阻塞直方图——**这是观测缺口，不是结论。谁要主张这里有损失，先补遥测。**

### 🔴 顺带挖出的一个真 bug：写门漏判（我本人已实测确认）

```
operation                        func                     判为写?
log_chat.group_reply             log_chat               [×] 绕过写门
log_chat.private_reply           log_chat               [×] 绕过写门
log_chat.trigger                 log_chat               [×] 绕过写门
autonomy.log_chat.private        log_chat               [×] 绕过写门
register_inbound_event           register_inbound_event [×] 绕过写门
find_last_group.checked_send     log_chat               [×] 绕过写门
persist_write_probe              log_chat               [√]  ← 测试用的合成名
```

**根因在 `agent/async_io.py:67-79`**：

```python
candidates = (
    str(operation or "").rsplit(".", 1)[-1],   # ← 只取最后一段
    getattr(func, "__name__", ""),
)
```

`"log_chat.private_reply"` → 取到 **`private_reply`** → 不匹配任何前缀；而 **`register_` 根本不在前缀表里**（表里有 `record_`/`release_`/`reduce_`… 就是没有 `register_`）。

**为什么至今没被发现**：测试用 `"persist_write_probe"`——恰好命中 `persist_` 前缀，**所以恒绿**，真实 op 名**零覆盖**。

> **这正是 CLAUDE.md 教训 #30「安全检查必须做阳性对照」的镜像形态（只种了合成正样本）；用字符串前缀做判定，正撞 #13/#19 的老病。**

**代价**：`register_inbound_event` 是**慢调用榜第一名**（n=96，p50=484ms，max=1068ms）。ROADMAP 自己记录过"写门同协议对照 219.97ms→86.85ms"——**证明这道门有效，只是它没覆盖最常发生的那几种写**。

**修法三选**（**未实施，等你拍板**）：
1. 调用点显式标 `write=True`
2. op 名收敛到 Store 方法名
3. **未知即按写处理的 fail-closed 默认**（最稳，牺牲一点读并发）

### 判断依据（7 问，可复用）

1. **产品里有没有只能在某生态跑的东西——尤其训练/导出链？** 是 → 一票否决除 Python 外全部
2. **端到端延迟主导项是什么？** LLM 占 >60% → 「语言性能」这一维整体作废
3. **峰值并发什么量级？** <1 msg/s → GIL/goroutine/JIT 全是纸面论据
4. **分发的硬约束？** 要新建跨平台签名流水线的直接淘汰
5. **能增量迁移吗？** 不能就扣掉全量重写成本
6. 只有并列候选时才问「语言本身给什么」——**答案里不含 agent 质量**（检索不到任何把宿主语言当自变量的对照实验）
7. **最后：上面这些收益，有多少是用现有语言今天就能拿到的？** 本仓三项（类型安全→mypy、启动→模型移出进程、并发→写者门）**全都不用换语言**

**唯一能翻转结论的条件**：产品砍掉本地语音/歌声/识图，变成纯云 API 的文本聊天 → 那时 C#/.NET 才值得重估。
