## 1. 写门 bug —— 现在修，用 fail-closed

### 为什么现在就修

它不是一个「风格问题」，是**已被测量到的写争用**：register_inbound_event 实测
p50≈484ms / max≈1068ms，其中 commit_ms≈266ms，是同进程多写者争用的直接代价
（审计第六节：生产 p50≈480ms vs 隔离副本 1.70ms，差约 200 倍）。多等一天就多一天
的 200× 提交延迟，而且它在慢调用榜上排第一。

### 取证过程（先取证再改）

静态扫描 + 日志解析，得到**真实的 244 个 op 名**（_run_store_io / _run_outbox_store_io
/ run_bounded_store_io 三类调用点）。旧判定下 **124 个绕过写门**，其中确属写的有：

- log_chat.group_reply / .private_reply / .private_action / .private_command /
  .private_opinion / .trigger，以及 autonomy.log_chat.group / .private
  —— 旧实现 rsplit(".", 1)[-1] 取到 private_reply，不匹配任何前缀
- register_inbound_event —— register_ **根本不在**旧前缀表里
- index_chat.private_reply（index_ 在前缀表里，但旧实现只看最后一段）
- kv_set_*、command.memory.delete / .remember、reinforce_memories、
  proactive.claim/finalize/finish/record、daily_aggregate.owner_memory_write …

### ⚠ 审计那张表里有一行要更正

审计第六节把 find_last_group.checked_send 列为「func=log_chat → 绕过写门」（暗示应判写）。
**取证结论：它是读。** handler.py:12869 传的 func 是 self._find_last_group，
而 _find_last_group（handler.py:12407）只调 store.find_last_group(user_id) 查群号，
没有任何写。其余 find_last_group.* 同源。**所以这一行不是漏判的写，是误判的读** ——
本次实现把它保持为「读」，并由 tests/test_extraction_async_store.py 钉死。

### 修法：fail-closed（审计给的三选一里的第 3 种）

不选 1（调用点显式 write=True）和 2（op 名收敛到 Store 方法名）的原因：
两者都只修**实例**、不修**类别** —— 新增一个写操作，仍会静默绕过写门。
那正是审计元根因（「检查器本身有覆盖率上限」）的同形问题。

agent/async_io.py 新口径：

    · 任一名字片段（operation 的每一段 + func 名）命中写前缀 → 写
    · 有可识别的读信号且无写信号                        → 读（保留 16 路并发）
    · 其余（未知）                                      → 写（fail-closed）

写前缀补了 log_ / kv_set_ / register_；新增读前缀白名单（get_ load_ list_ query_
fetch_ read_ count_ search_ scan_ find_ has_ exists_ select_ is_ describe_ snapshot_
dump_ export_ peek_ kv_get_）与 13 个无前缀读操作的整名。

### 代价与方向

漏判的**方向是安全的**：把读误判成写只会变慢（少一点读并发），不会写坏数据。
244 个 op 分类后：154 写 / 90 读；被误判成写的读都是低频（日聚合、生日检查、上下文构建）。

  （教训 #30：旧测试只用合成名 persist_write_probe，恰好命中 persist_ 前缀，**恒绿**）
- 端到端断言：log_chat.private_reply 并发度 peak==1；get_recent_chats peak==6

## 4. 驱动力地板 —— 0.60，但必须连方法一起改

### 先把话说清楚：**只降地板不解决问题**

取证：natural_decay 只在 value > 地板 时按**固定速率**衰减，而 tick() 每次都按
alpha（0.03–0.10/h）积累。旧速率是 0.01/h —— **小于任何 alpha**，所以净速率恒为正，
驱动力照样一路升到 1.00 并停住。地板只决定「最低能降到哪」，不决定「会不会贴顶」。
把 0.85 改成 0.60（或 0.0）都不会改变贴顶。

### 拍板：把「固定速率 + 硬地板」换成「按超出幅度成比例松弛」

    SATURATION_FLOOR = 0.60                 # 地板：低于全部阈值（0.65~0.75）
    SATURATION_RELAXATION_PER_HOUR = 0.5    # 松弛系数 k
    衰减 = k · (value − floor) · dt          # 越饱和越容易被时间冲淡

净速率 alpha − k·(v−floor)，平衡点 v* = floor + alpha/k —— **可推演，不是试出来的**。

### 仿真（48 小时无行动消费，每 10 分钟 tick+松弛）

| 驱动力 | alpha | 阈值 | 旧口径 48h | 新口径 48h |
|---|---|---|---|---|
| 社交渴望 | 0.08 | 0.70 | **0.998** | 0.747 |
| 承诺压力 | 0.10 | 0.65 | **0.998** | 0.783 |
| 信息饥渴 | 0.06 | 0.70 | **0.998** | 0.710 |
| 表达冲动 | 0.07 | 0.70 | **0.998** | 0.728 |
| 好奇心 | 0.04 | 0.75 | **0.998** | 0.673 |
| 回避欲 | 0.03 | 0.70 | **0.998** | 0.655 |

全部落到 0.85 以下且**有高低差**；同时「不是静音」 —— 4/6 仍在阈值之上，
行动级释放仍能把它们打到 0.3~0.4 再爬回来（测试 test_released_drive_still_climbs_back_over_threshold）。

### 三条与审计原文有出入的取证

1. **P1-6 的返回值语义不能改。** tests/test_send_commit_boundary.py 里
   `test_successful_self_check_fallback_is_recorded_as_the_actual_text` 明确断言
   「兜底已送达时 `_checked_send` 仍返回 False」（语义＝她的原话没发出）。
   **所以修法是加一个投递事实，不是改返回值**——改返回值会让唱歌路径
   （`if ok or not reply`）在自检拦截后照样把歌唱出去，那是审计没要求的行为改变。
2. **[不说话] 的裸写判定其实极窄。** 原文 `"不说话" == reply[:4]` 只能匹配
   **恰好等于**「不说话」的整条串（4 字符切片切不出 3 字符的结果），所以
   「收窄它」是个错觉；本次保持等价，并补上旧代码会漏掉的「不说话。」
   ——那条以前会被当正文发给用户。
3. **[不说话] 的行首形态本来就被 clean() 的通用短标签规则吃掉。**
   「无 clean 兜底」真正漏的是**非行首**位置（`好呀[不说话]`）。测试因此只钉非行首，
   免得写成一条永远绿的假闸门。

### M2 剩余两项（同日补完）

- **延迟群发言落盘**：`group_say_later` 不再用 `asyncio.sleep` 内存任务，改走
  **TaskManager**（SQLite `tasks` 表）——与 `set_reminder` 同一条链路。
  这一步同时拿到三样：重启不丢、终态回执、「任务不直发 + 唯一 retry owner」。
  - 为什么不走 `CronScheduler`：取证发现它除 `__RESTART__` 哨兵外**生产零使用**
    （`add_one_shot`/`add_daily` 的唯一生产调用点就是 handler.py:1126 的重启哨兵）
    ——正是审计 RC4「scheduler vs tasks 两套定时语义」。塞进去只会把重复固化。
  - 两个必须同时处理的坑：① `TaskManager` 里 `group_id` 为空代表**私聊**，所以默认群
    必须**在创建时**解析（旧实现是到点才解析，会把人发成人人私聊）；
    ② `tasks.remind_at` 只有分钟级精度，秒级按 `set_reminder` 同一口径**明确拒绝**，
    不静默四舍五入成 1 分钟。
  - 另修 `_compose_message`：群任务此前套的是私聊口吻（「给 {nickname} 发这条提醒」），
    现在群侧改对群说话的口吻；无 LLM 兜底也不再贴「糖糖小闹钟～」这个私聊外壳。
- **scheduler `once` misfire**：`fire_at == now.strftime(...)` 全等比较改为**迟到窗口**
  （`ONCE_GRACE_MINUTES = 30`，沿用 daily_report 的 `catchup_minutes` 口径）。
  - 超过窗口不补发（四小时前的「5分钟后叫我」补发出去是噪声），但终态记 `missed`
    并告警——**丢可以，静默丢不行**。
  - ⚠ 换区间比较必须同时加**终态护栏**（`_ONCE_SETTLED_STATUS`）：旧的全等比较天然
    不会重放，区间比较会让冻结的 `uncertain` 每个 tick 重新触发——那会直接违反
    「uncertain 永不自动重放」铁律。已用阳性对照测试钉住（`test_frozen_uncertain_
    once_task_is_never_refired`）。

## 追加 · M3 第 3 项取证：承诺为什么**恒不闭环**（P1-1 完整根因）

### 因果链（每一环都有证据）

1. **结算链是接好的**：`handler.py` 在 LLM 提取出 `action_completed` 且带
   `fulfills_memory_ids` 时调用 `memory.fulfill_self_promise`。
2. **提取器在正常工作**：查库 `origin='self' AND key='action_completed' AND status='active'`
   有 **21 条**。
3. **候选承诺是有的**：175 条 active promise 且 `trust_level=verified`（能过 `trusted_only`）；
   **9 个作用域**同时存在 promise 与 action_completed。
4. **但 `fulfilled` = 0，且日志里连一条"拒绝结算"都没有** → 结算分支**从未进入**，
   即 `fulfills_memory_ids` 恒为空。
5. 恒为空的原因在 prompt 里：「只有标注 `confirmed_action=是` 的回复才允许考虑
   action_completed」；而该标记取 `'是' if r.get('confirmed_action_id') else '否'`，
   而 **`_self_memory_action_id` 只在语音路径被赋值**（`handler.py:4054` / `5046`），
   文字回复恒为 `""` → 永远「否」→ LLM 照规矩不点名 → 不结算。
6. 语音能、文字不能的原因：锚点校验要求 `confirmed_action_facts` 里有
   `projection_kind='conversation_reply' AND self_memory_eligible=1` 的行；
   查库全库只有 5 条 conversation_reply 事实，**eligible 全是 0**——文字回复根本没有
   action envelope（`_build_voice_action_envelope` 只服务语音）。

→ **P1-1 剩下的唯一堵点就是「文字回复没有回执锚点」**，正是审计 M3 写的
「文字回复纳入回执锚点点火」。

### 本轮做了什么（安全的部分）

1. **候选截断是真 bug，已修**：候选查询原为「取 `limit=20` 的混合行 → Python 里筛
   promise」，而 active `said`(importance 5) 有 301 条、promise 175 条。实测
   target=2180254043 的 20 行里只有 5 条 promise（该对象共 25 条 active）。
   → `store.query_memories` 新增可选 `key=` 并**下推 SQL**；候选查询改用 `key="promise"`。
2. **可观测性补上**（审计 RC5「失败路径不产生可观测事实」）：候选为空、以及
   「提取到 action_completed 却没指向任何承诺」两处此前**完全静默**——这就是它能烂
   几周无人发现的直接原因。现在各留一条带候选数的 INFO。

### ⚠ 未做，需要你拍板的一件事（**会动安全闸门**）

要让 `fulfilled > 0`，必须让文字回复能拿到锚点。两条路：

| 方案 | 代价 | 风险 |
|---|---|---|
| A. 主文字回复走 ActionReceipt 投影（`self_memory_eligible=1`） | 要把主发送路径接进 outbox/receipt；投影会**自己写 bot chat_log 行**，与今天 `handler.py:4118/5134` 的直接 `log_chat` 打架（`handler.py:2448` 的注释已点过这个坑） | 牵动 P0-3/M4 正在处理的归账与 receipt，爆炸半径大 |
| B. 把「确认送达的文字回复」本身认作锚点（chat_log bot 行） | 小 | **放松 2026-08-28 P0-C 刻意加的闸门**——`store.py` 的 docstring 明写「普通文字回复没有这个锚点，因此不会被误记为外部动作已经完成」。这是「她自己的话算不算动作完成的证据」的**语义决定** |

我**没有单方面做**这个决定：它不是纯 bug 修复，而是改一条事故后刻意加的安全语义。
倾向 B（对 *self* 承诺而言，她确认送达的原话本就是最直接的证据，且仍需 LLM 显式点名
同作用域的候选 id），但请你拍板。

### ① 私聊人物画像注入 —— **恢复**（只开私聊，不开群聊）

### ② 秒级延迟发言 —— **保持拒绝**，但文案改成可操作

- **依据**：`tasks.remind_at` 只有分钟级精度、任务循环也是分钟级——接受「30秒」等于**静默
  改掉承诺时间**，那正是本仓在 `set_reminder` 里明文反对的；两套工具口径不一致还会再养一个 RC4。

  一条出路，否则她只会对用户说「做不到」。

### ③ 承诺回执锚点 —— **方案 B**（把确认送达的文字回复认作回执锚点）

**先取证，比审计更狠**：

- `action_completed` 自忆最后一次写入停在 **2026-08-30**，此后一条都没有。
- 全库 5 条 `conversation_reply` 事实的 `self_memory_eligible` **全是 0**。
- 闸门有**两道**（`handler.py` 写入前 + `memory.remember_self`），而 `memory.py` 里
  **已经**对每条自忆校验过 `validate_self_memory_source`（同一对象、同一作用域、

  而 envelope 只有语音会产生 → 文字回复全被挡在写入之前。

**落地**（收窄成「传输层确认」，不是「有罪推定」）：

| 情形 | 处理 |
|---|---|
| 提供了动作回执 | 必须**真实有效**，无效一律拒（fail-closed 不变） |
| 没有动作回执 | 走上面**已经通过**的证据校验（文字回复路径） |

## 追加 · M3 第 4 项：情绪事件接真实信号（P0-2）

### 取证：比审计写的更彻底

审计说「15 个事件里 11 个没有发射点」。实测这 11 个事件**在定义之外零引用** ——
全局只有 5 处 `mood.update(...)`（BEING_AT×2 / INTERJECTED / SENT_LONG_REPLY / SENT_REPLY）。
也就是说：**正向事件（被夸/被感谢/被想念/帮到别人/亲密聊天/空闲恢复）一个都没有发射点**，
负向（被无视/被骂/连续追问/深夜/说话太多）同样一个都没有。

### ⚠ 一处我先搞错的推断（记在账上）

我一度推断「情绪只会单向衰减到 0」。**查 `_apply_decay` 后推翻**：

- 精力：-1/h
- 心情：**每半小时朝中性 70 收敛 ±5**
- 耐心：**+10/h 恢复**

所以真实缺陷不是「单向棘轮」，而是**「心情没有任何输入」**——它只会收敛回 70，
任何经历都推不动它（这正是审计 P0-2「无负向输入」的意思）。
跑偏的那一步记在这里，因为它是教训 #1/#18 的现场：**修复假设必须先取证**。

### 本轮接线（全部用**已有**的真实信号：零新增检测、零关键词匹配）

| 事件 | 信号源 | 说明 |
|---|---|---|
| `BEING_IGNORED` | `_judge_autonomous_cold` 里**已有的** LLM 判定 `ignored`（未知枚举按同一口径） | 语义完全对应 |
| `BEING_SCOLDED` | 同一处的 `rejected` | 事件表里最接近的负向档 |
| `LATE_NIGHT` | **真实时钟** 23:00–06:00 | 放在活跃时段判定**之前**——深夜正是它该生效的时候 |

**刻意不映射** `warmly_received` / `lukewarm`：事件表里的正向条目是「被夸/被感谢/被想念」这类
**他人指向她**的事件，把「温暖回应」硬塞进去等于给状态机编造体验（教训 #9/#19 同族）。
正向输入留给 M3 那一项「回复 LLM 自报情绪标签回灌」——那才是它的正主。

### 三个工程细节

1. **窗口/冷却放模块级**而非类属性：本文件测试用 `SimpleNamespace` 直接调 mixin 方法，
   类属性在那种 harness 上取不到（我第一版就是这个错，被自己的测试当场抓住）。
2. **深夜每小时最多一次**是刻意的：该事件是 -3 精力的"整段时间"语义，若每 10 分钟周期都扣，
   一夜会把精力打到 0（clamp）再靠重启复位，反而失真。
3. `mood` 用 `getattr(self, "mood", None)` 保护——harness / 离线调用可能没有 mood。
