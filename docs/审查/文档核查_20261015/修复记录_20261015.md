## 3. 判定为「不是缺陷」的核查发现（附证据）

**`handler.py` 租约路径的 `existing_summary=""` 不是漏改。** 审查报告把
`handler.py:12012`（租约/worker 路径传空串）与 `:12283`（前向路径传画像摘要）的差异
判为「1 行漏改，3 次重提无人认领」。实际代码上方就写着理由：

> 画像可能混有其他会话，且不是当前批次原始证据。提取只看冻结消息，防止旧摘要把幻觉重新写成 verified。

这是**有意的 fail-closed 设计**（与「真值生命周期」的信任门一致），不是遗漏。
两条路径口径不同是刻意的：前向路径是增量画像更新，租约路径是证据只读重放。
**建议**：这个差异值得在 ADR 里写一句，但不改代码。

> 记录这条的意义：审查报告也会出错。项目纪律是「没有证据的发现降级为待验证假设」——
> 同理，**审查结论本身也要拿代码复核**才能进修复清单。

# 第二轮（同日）：歌词与「分段唱歌」整体删除

## 8.1 为什么是「整体删」而不是「留个空壳」

段落与歌词是**同一份数据的两面**——`[主歌1]`/`[副歌]` 这些段落标记本来就写在歌词文件里。歌词没了，段落就只剩「完整」一个值：`DEFAULT_SECTION_ORDER` 的每个候选（副歌/主歌1/主歌/段落1）都匹配不到、`find_section` 的模糊映射永远落空，「选段」逻辑恒等于「放整首」。留着它只会让下一个接手的人以为分段唱歌还在。

已经写进 `agent/songs.py` 的模块 docstring：删了什么、为什么**不能**因为「以后可能恢复歌词」而把它从 git 里捞回来（要恢复就得连段落语义一起重新设计）。

## 8.3 刻意保留的一个东西

`agent/songs.py` 的 `FULL_SECTION = "完整"` **保留着**，它也是 `_send_song_section` 签名里 `section_name` 参数至今仍在传的值。理由：ActionPlan child 的 `payload["section"]` **参与 `derive_action_id`**，去掉这个键等于换掉所有 sing 子动作的 id——已持久化的出站记录重放时会认不出自己（幂等保护失效）。它现在不是「分段能力」，是**兼容已持久化记录的常量**，代码里写明了这一点。

## 8.4 顺带抓到的一个真隐患（值得单独记）

改 `tools/打包发布附件.py` 时，我先删了 `txts = sorted(...)` 的定义，但 12 行之后还有 `for t in txts:` 和一处 `len(txts)` —— `tools/静态检查.py` 只扫 `agent/` 与 `onebot/`，**扫不到 `tools/`**，`ast.parse` 也不查名字，所以两边都不会报。这正是教训 #26 的原形状（移除定义但留下消费者，调用期才炸）。

发现方式：改完立刻 grep 被删符号 `txts`，命中两处 → 一并删掉循环、改掉打印。

**结论**：改 `tools/` 下的脚本时静态检查帮不上忙，必须自己 grep 一遍被删符号。
