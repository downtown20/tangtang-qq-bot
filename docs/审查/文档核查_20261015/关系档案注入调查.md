## 0. 结论摘要

1. **主要矛盾不是「关系档案优先级低」，是「单池零和 + 上游块总量超订」。** 私聊背景块共用一条 1200 token 的单池预算（`agent/protocols.py:260`），而排在关系档案前面的三类高频材料——窗口块（P5，实测 p50 **539** tok）、记忆块（P7，p50 **362**）、反思块（P7，p50 **301**）——**中位数合计 1202 tok，已经等于整池**（复刻实验实测）。预算在轮到关系档案（P9）之前就被吃光。
2. **淘汰是「整块消失」而不是「截断」，判定线是 120 tok**（`agent/protocols.py:334-335`）。关系档案实测 p50 **471** tok、最大 **716** tok（23 份非空档案），是私聊 flex 池里**第二大的块**——剩下的零头几乎从不 ≥147（120 + wrap 27）。
3. **截断的语义与块结构冲突**：关系档案块第 2 行是反编造契约（`agent/handler.py:5003-5006`），而 `_truncate_bg_block` 从尾部切（`agent/protocols.py:378-389`）→ **一旦被截断，先丢的正是契约行**，留下的是半截叙事复述（实测 uid 2524950083 原文 381 字 → 131 字，契约行消失）。
4. **结构性错配**：档案只属于高活跃关系（每 80 条私聊才合成，`agent/relationship.py:26`），而高活跃者的窗口/记忆块恰好最满——**越可能有档案的人，档案越进不去**（有档案者记忆块 p50 441 vs 无档案者 348，23/22 人样本）。
5. **两个观测盲区**：只有「真有块被淘汰」才记一行日志（`agent/protocols.py:362-363`），**截断完全不记**；TokenReport 未落盘（40 万行日志里没有任何「📊 Token 报告」行）→ 「档案被砍残、契约行丢了」这件事在生产日志里不可见，只能靠复刻实验发现。

## 2. 机制：私聊背景块是一条单池零和赛道

### 2.1 池与规则（`agent/protocols.py:255-350`）

| 规则 | 位置 | 含义 |
|------|------|------|
| 总预算 1200 tok | `protocols.py:260` | 一条池子，群/私聊共用常量 |
| 单块上限 600 | `protocols.py:261` | 大块先被裁到 ≤600 |
| 保护块（prio≤1）**先计量入账、允许 overflow** | `protocols.py:310-312` | 协议/引用块**先扣钱**，flex 只剩 `1200 − used` |
| flex 按 (prio, 原 index) 选择 | `protocols.py:320` | 同优先级按 append 顺序 |
| **limit < 120 → break（本块及所有更低优先级一起丢）** | `protocols.py:334-335` | 这是「整块消失」的判定线 |
| 超出 limit 则按行/句边界截断 | `protocols.py:336-339`、`:378-389` | 截断从**尾部**开始 |
| 估计器 | `context_builder.py:44-51` | 中文×1.8 + 其他×0.5 |
| 标签包装开销 `(len(label)+14)×1.5` | `protocols.py:373-375` | 关系档案 wrap = 27 |

### 3.1 截断会把契约行切掉（同一实验，生产截断函数）

关系档案块结构（`handler.py:5003-5006`）：

```
第 1 行：你和 {昵称} 的关系档案：{rel_summary}
第 2 行：（这是基于真实聊天记录整理的关系档案。不要编造上面没有的信息。不确定就说记不清。）
```

`_truncate_bg_block` 在 150 字处找最后一个「\n/。/；/，/、/空格」切断（`protocols.py:378-389`），第 2 行永远在尾部 → **先丢**。实测：

| uid | 原文 | 截断后 | 契约行是否还在 |
|-----|------|--------|----------------|
| 2377255095 | 143 字 | 143 字（未触发截断） | ✅ 在 |
| 2524950083 | 381 字 | **131 字** | ❌ **丢失**（末尾停在「…对方称糖糖"糖糖"。」） |
| 3922400700 | 424 字 | 140 字 | ❌ **丢失** |

**这是本轮最坏的发现形态**：预算压力下，系统保留的恰好是「最容易诱导编造的那一段叙事复述」，而丢掉的正是约束它的说明。压力越大，注入越像「事实」。

### 4.1 另一半成因在生产者：材料锚定「最早 10 条」

`relationship.py:76` 每次重合成只取 `store.get_earliest_chats(qq_id, limit=10)`——**最早 10 条聊天**，然后 LLM 按固定 4 项（怎么认识/称呼/偏好不满/梗回忆，`relationship.py:100-112`）复述。于是：

- 一块「只描述最早期交流」的材料，以 p50 471 tok 的体积长期挂在 P9（`relationship.py:26` 每 80 条私聊才更新一次）；
- 它每轮和「每轮实时更新的窗口块（P5）」「每轮 BGE 重选的记忆块（P7）」争同一池预算。

即：**优先级的排序把「最旧的材料」放在「最新鲜的材料」之后——这在语义上是自洽的，问题在于这块最旧材料占的是池子里第二大的位置，而池子本身已经超订。**

## 6. 修复方向（**不落到「改 BACKGROUND_PRIORITY 数字」**）

按「注入上下文管理」的根因层级给方向，数字调整只在最后一条且明确标注为治标：

1. **契约与材料分离（治 C3，收益最直接）**：反编造契约是**块结构**不是材料。应由组装器在截断**之后**重新附加（或把 caveat 提到块首），使任何长度的关系档案都带着「不要编造上面没有的信息」。当前形态等于「压力越大越不设防」。（对照：`knowledge_block` `protocols.py:207-210` 的防编造前言也放在内容**前面**——同一原则，关系档案是唯一把约束放尾部的块。）
2. **给生产者补体积契约（治 C2）**：`relationship.py:120-132` 是目前唯一没有长度上限的合成物写库点。与画像（120 字）、知识块（1500 字）、记忆事实（80 字）对齐，让**生产端**保证 ≤ 预算份额，而不是让消费端每轮兜底截断。
3. **按需注入而非每轮注入（治 C1）**：关系档案是「背景知识」不是「每轮必读」——可参照本仓既有原则「能力数据按需注入」（歌单只随 sing 工具出现，CLAUDE.md 六节）与 World Info 绿灯原则：只在涉及「怎么认识的/称呼/以前的事」的回合进池。不改变单脑架构（决定权仍在 LLM，由工具/条件触发材料提供者）。
4. **补观测（治 C5）**：把「每块 est + 是否被裁 + 裁掉比例」落进日志（当前只有淘汰行、且只记标签）；否则「契约行有没有进上下文」永远只能靠复刻实验倒推。注意这不是加噪声——`protocols.py:362-363` 已经确立了「正常回合不记」的取舍，可以只记「被裁过的块」。
5. **（治标，不推荐单独使用）**调优先级/预算数字：本轮**没有**采用这条——§3 已证明问题是总量超订（1455 > 1200），把关系档案提到 P8/P7 只会把同等体积的窗口/记忆挤下去，是池内搬运而非扩大池子；真要动，也应是「保护块是否该占公共池」这一结构问题（§2.3：协议块最多吃掉 84%）。
