# 记忆提取积压调查 — 成因与机制判定

> 只读调查。**未改任何业务代码**，未跑 pytest，未碰 bot。
> 采样时刻：2026-10-15 19:25–19:55（bot 在跑；DB 以 `file:...?mode=ro` 只读连接查询）。
> 证据来源：`memory.db`（只读 SELECT）、`日志/tangtang.log` 及 `tangtang.log.YYYY-MM-DD`（10-01…10-14）、`状态/.extraction_state.json`、`agent/*.py` 源码。

## 0. 结论先行

**「积压这么多」的成因不是门槛高，是三条机制缺陷叠加；而且积压本身没有在增长。**

1. **积压没有增长，它是稳态池。** 两周内存量 691 → 620 → 703 → 674~1009 → 688 → 600 → **517**（今日），非单调、且低于 10-01。它不是一个在膨胀的队列。
2. **517 条里 44.3%（229 条）是 `（发了张图片）` 占位符**，另有 16 条空串、30 条 ≤2 字。**门槛按「消息行数」计数，无内容消息也能把计数灌满并触发准入。** 这是计数口径缺陷。
3. **准入放行了，提取却没产出。** 10256 个提取任务里 **82.1% 产出为 0**（`result_json.stats.raw_length = 2`，即 LLM 原样返回 `[]`）。近 7 天 710 个任务、窗口内 6631 条消息，产出 0 的占 83%；其中「窗口里一条占位符都没有」的纯文本任务 62 个，**57 个（91.9%）仍然产出 0**。
4. **回填兜底通道完全失效**：319 个 backfill 游标**全部 ≤ forward 游标**，可用候选 0 人 / 0 条。
5. **健康检查在「零到期」时把状态强制改写为 normal**（`agent/health_check.py:400-401`），且 `unhealthy` 要求 `eligible_messages > 0`（`:407-413`）——**「整池无人可准入」这一最需要报警的状态，恰恰被报成 normal**。

**判定：是机制问题。** 但主因不是「门槛 10 太高」，而是 ②计数口径把无内容消息当有效消息、③回填通道名存实亡、④提取产出率为 0 却按成功记账。降门槛到 3 只解决「等 7 天」这一半，救不了只有 1–2 条消息的 93 个人。

## 1. 这 517 条积压到底是什么

**SQL（与生产 `store.get_extraction_backlog_snapshot` 同口径，`agent/store.py:12984-12995`）：**

```sql
SELECT c.qq_id, COUNT(*), MIN(c.id), MAX(c.id), MIN(NULLIF(c.timestamp,''))
FROM chat_log c
LEFT JOIN extraction_cursors e ON e.pipeline='memory' AND e.direction='forward' AND e.qq_id=c.qq_id
WHERE COALESCE(c.is_bot_reply,0)=0 AND COALESCE(c.quarantined_at,'')=''
  AND c.id > COALESCE(e.cursor_chat_id,0)
GROUP BY c.qq_id
```

**结果：161 人 / 517 条**（与任务书给的 164/524 同量级，差值来自这几小时的新增与消化）。

| 人数 | 53 | 40 | 11 | 9 | 14 | 14 | 5 | 9 | 6 | **0** |

## 2. 为什么这些人一条都进不了队

### 2.1 判定逻辑（`agent/extraction_policy.py:11-33`）

```
IMMEDIATE_MESSAGES = 10        # ① n >= 10            → 立即
STALE_MESSAGES     = 3         # ② n >= 3  且 age >= 7 天
STALE_AFTER_SECONDS = 7d
ONE_OFF_AFTER_SECONDS = 21d    # ③ n >= 1  且 age >= 21 天
```

把 161 人逐个代入（本次实测脚本复现同一函数）：

| 分类 | 人数 | 说明 |
|---|---|---|
| ① n ≥ 10 | 0 | — |
| ② n ≥ 3 且最老 ≥ 7 天 | **0** | 68 人满足 n≥3，但**最老的那条都不满 7 天** |
| ③ n < 3 且最老 ≥ 21 天 | **0** | 93 人 n<3，但最老 20.8 天 < 21 |
| **到期合计** | **0** | `eligible_messages = 0` |

### 2.2 两条时间线都精确卡在阈值上 —— 这说明规则在生效

- n ≥ 3 的 68 人里，最老的天数是 **6.88 / 6.47 / 6.31 / 6.20 / 5.99 / …**，**没有一个人 ≥ 7 天**。
- 全池最老是 **20.8 天**，**没有一个人 ≥ 21 天**。

两个上界都紧贴阈值下方，只能解释为：**越过阈值的用户已经被老化规则放行并消化掉了**。日志侧吻合：
- 「🧠 积压准入」逐日：10-01 162 / 10-03 214 / 10-05 368 / 10-08 42 / 10-11 117 / 10-13 49 / 10-14 33 / **今日 16**（`agent/handler_autonomy.py:1943-1946` 是这条日志的唯一来源）。
- 一批存活样本：job#70394（10-14 15:19 创建，窗口 9 条全是 **10-07** 的消息）、job#70378（10-14 11:52，窗口 5 条全是 10-07）——**正是 7 天老化规则到点放行的形状**。

### 2.3 「差 1 条到 10」的 6 个人为什么没继续攒

不是被 `_high_freq` 跳过，也**不是计数器重启清零**：

- 规则① 走的是 **DB 口径**（`agent/store.py:12984-12995` 的 `COUNT(*)`），与内存里的 `_extraction_counter`（`agent/handler.py:3373-3381`）**是两套独立计数**。内存计数被跳过只影响「提前量」，到 10 条时 DB 侧照样放行。
- 实测这 6 人的窗口（例：qq=2656840563 n=9，最老 10-10 22:07）：9 条里大部分是 `（发了张图片）` 与短句，**是他们自己没再发**——不是计数丢了。
- 反证：**全池 n 的最大值恰好是 9，没有 10、11、12**。若计数会丢，就会出现一堆卡在 ≥10 却进不了队的人。没有，说明 10 处是通的。

### 2.4 「等什么」的一句话总结

| 人群 | 人数 | 条数 | 在等什么 |
|---|---|---|---|
| n ≥ 3 | 68 | 384 | 等最老那条满 **7 天**（最近的一个还差 ~0.1 天） |
| n = 1–2 | 93 | 133 | 等最老那条满 **21 天**（最老的还差 ~0.2 天） |

## 3. 机制判定：逐条成立与否

### ① 「门槛与『人不说话了』冲突：攒不满阈值的人永远不提取」——**部分成立（措辞要改）**

不是「永远」：rule ③（`extraction_policy.py:33`）保证再稀疏的人也会在 **21 天** 后被放行，实测最老 20.8 天正卡在门口。
但代价是真实的：**一个只说过 1–2 句话的人，记忆要等 21 天才入库**——等到那时，这句话的语境早就冷透了。
规模：**93/161 人（57.8%）、133/517 条（25.7%）** 属于这一类。
定性：**设计取舍 + 未被看见的代价**。不是崩溃，是「等于没记」。

### ② 「7 天/21 天老化门槛从来没生效过」——**不成立**

反证三条（见 2.2）：n≥3 组最大年龄 6.88 < 7；全池最大 20.8 < 21；两类样本任务的窗口时间戳精确落后 7 天。
worker 的 `idle_reason=no_open` 只说明**采样那一刻没有到期用户**，不等于老化没生效（`agent/handler_autonomy.py:2142-2143`）。
逐日 idle 分布也显示准入确实在跑：10-05 `active` 473 次、10-10 `active` 1349 次（`idle_reason=active` 包含 `admitted>0`）。

### ③ 「本该由回填兜底、但回填通道停摆」——**成立（确凿）**

回填入口要求「跨越 forward 与 backfill 游标的未处理消息 **≥30 条**」（`agent/handler_autonomy.py:1781`，主人 10 条）。

**SQL：**

```sql
SELECT qq_id, cursor_chat_id FROM extraction_cursors WHERE pipeline='memory' AND direction='forward';
SELECT qq_id, cursor_chat_id FROM extraction_cursors WHERE pipeline='memory' AND direction='backfill';
```

**结果：** forward 游标 510 个，backfill 游标 319 个；**backfill > forward 的用户数 = 0**（319/319 都 ≤ forward）。
把 forward < id < backfill 的消息数逐人相加 → **可用候选 0 人 / 0 条**。

→ 第二条兜底通道**名存实亡**：forward 游标一直追平，永远不会出现「跨越 ≥30 条」的用户。这正是教训 #14 那一类（引擎在转，离合器没接上）。

### ④ 「`_high_freq` 让活跃群的提取计数长期被跳过」——**机制存在，但不构成根因**

代码事实（`agent/handler.py:3244-3248`）：

```python
self._msg_burst_count = self._msg_burst_count + 1 if now_t - self._last_msg_time < 2.0 else 0
_high_freq = self._msg_burst_count >= 6
```

- 计数是**实例级、跨群共享**（`self._last_msg_time` 没有按群分）：任意群刷屏 6 条/2 秒，**所有群**的计数一起停摆。
- 群聊触发在 `agent/handler.py:3372-3381`：`if not self._high_freq:` 整段跳过计数；而消息入库（`agent/handler.py:3355-3359` `persist_inbound_message`）**在此之前且无条件** → **DB 涨、内存计数不涨**。
- **但被 DB 侧规则① 兜底**：DB 计数到 10 照样经 `_maybe_extract_stale` 准入（`handler_autonomy.py:1868-1957`）。实测 n 的上界恰为 9，无 ≥10 滞留者，说明这条路是通的。

→ 判定：削弱「提前量」，不造成永久遗漏。**不是积压成因**。（但记一笔：跨群共享 burst 计数是隐患，待验证假设见 §6。）

### ⑤ 「提取成功但游标没推进/推进错导致重复积压」——**不成立**

**SQL：**

```sql
SELECT COUNT(*) FROM extraction_jobs;                                        -- 10256
SELECT COUNT(*) FROM (SELECT DISTINCT qq_id,range_start,range_end FROM extraction_jobs);  -- 10256
SELECT COUNT(*) FROM (SELECT qq_id, range_end FROM extraction_jobs GROUP BY qq_id, range_end HAVING COUNT(*)>1);  -- 0
```

- 任务窗口 **(qq_id, range_start, range_end) 全库无一对重复**；510 个用户里**没有任何一个 range_end 重复**——游标单调推进。
- `extraction_jobs` 10256 条全部 `status='done'`，无 pending/leased 残留 → 准入容量门（`max_open=8`，`handler_autonomy.py:1878-1883`）不会因为队列堵死而空转。
- 结论：**不存在「重复积压」。** 但这条排查顺带炸出一个更严重的问题，见 §4。

## 5. 结论（对主人三问的直接回答）

### 5.1 这是不是机制问题？

**是。** 一句话定性：**积压不是「门槛太高攒不下」，而是「计数口径把无内容消息当有效消息 + 回填兜底通道完全失效 + 提取产出率为 0 却按成功记账」三条机制缺陷，叠加在一个本来就有不可压缩下限（7 天 / 21 天老化窗口）的设计之上。**

补充一条：**积压没有在增长**（517 条为两周最低）。若把它当成「越来越严重的问题」去降门槛，方向是错的。

### 5.2 降门槛到 3 会救回多少、多花多少次 LLM 调用

用实测数据模拟（同一 policy 函数，只改 `IMMEDIATE_MESSAGES`）：

| 参数 | 立即可准入 | 条数 |
|---|---|---|
| 现状 IMMEDIATE=10 | 0 人 | 0 条 |
| **IMMEDIATE=3** | **68 人** | **384 条** |
| IMMEDIATE=5 | 48 人 | 315 条 |
| IMMEDIATE=3 + STALE 2/3天 + ONE_OFF 7天 | 127 人 | 471 条 |

- **一次性**：68 次额外提取调用（每个用户 1 个 job）。
- **稳态增量**：按「每天有 ≥3 条消息的 (用户, 天) 组合」近 14 日均值 **56.4/天**，日均准入从当前 ~35 次升到 ~56 次，即 **日均多约 20 次调用**。
- 按 82% 空产出率，**这 20 次里约 16 次是白打**（除非同时修 §4 的产出问题）。
- **救不了**只有 1–2 条消息的 **93 人 / 133 条**——他们仍要等 21 天。

**结论：降门槛可以顺手做（代价小），但它不是主要矛盾。**

### 5.3 更该修的是哪一处（按性价比排序）

**P0 — 准入计数排除「无内容消息」（一行 SQL，最小改动，收益最大）**
位置：`agent/store.py:12984-12995`（`get_extraction_backlog_snapshot`），另 `agent/store.py:12970-12978`（`get_persisted_unprocessed_backlog`）同步。
方向：`COUNT(*)` 改为只计内容消息（`TRIM(COALESCE(c.message,'')) <> ''` 且非 `（发了张图片）`/`[图片…` 类占位）。
效果：229+16+6 = **251 条噪声（48.6%）** 不再把计数灌满、不再触发空转 LLM 调用。
注意：**窗口（喂给 LLM 的 20 条）保持不动**——占位符仍是语境，只是不再当「有效条数」计数。

**P1 — 修回填通道的死亡条件**
位置：`agent/handler_autonomy.py:1781`（`count >= (10 if qq_id == owner else 30)`）。
现状下 forward 游标永远追平，`30` 这个条件永不成立（实测候选 0 人/0 条）。

**P2 — 健康检查要能报出「到期恒为 0 且存量 > N」**
位置：`agent/health_check.py:400-401`（`if eligible_messages == 0: state = "normal"`）与 `:407-413`（`unhealthy` 要求 `eligible_messages > 0`）。
现状：**最该报的「整池无人可准入」被强制改成 normal**；10-10 时池子同时在涨、到期 21–55、state=degraded/stopped，才是它唯一会响的形状。属教训 #30 家族（检查器从设计上不会报这个故障）。

**P3 — 修 `agent/memory.py:1261-1262` 的 `f` 前缀**
一行改动、零风险；即便模型忽略字面量，也不该把未替换的模板变量发给 LLM。

SELECT c.qq_id, COUNT(*), MIN(c.id), MAX(c.id), MIN(NULLIF(c.timestamp,''))
FROM chat_log c
LEFT JOIN extraction_cursors e ON e.pipeline='memory' AND e.direction='forward' AND e.qq_id=c.qq_id
WHERE COALESCE(c.is_bot_reply,0)=0 AND COALESCE(c.quarantined_at,'')='' AND c.id > COALESCE(e.cursor_chat_id,0)
GROUP BY c.qq_id;
