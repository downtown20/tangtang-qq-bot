## 〇、一句话结论

- **方案A**：会把私聊主路径（实测占 bot 回复 23/81 ≈ 28%，文档记私聊 64.4% 含分段）的账本从「handler 逐段写 chat_log」换成「平台确认投影」，但**轨①不会自动消失**——不拆掉它就是每句回复在 chat_log 里出现两次，这是唯一的不可逆风险。收益不是新功能，是单一事实源。
- **ADR-006 接入**：技术上落点清楚（_call_api 注入 echo、发送前持久化 transport_request_id、_event_route 收 message_sent），但按 ADR 自己写的启动条件（真实适配器 echo + WS 鉴权 + 群/私 canary）**今天一条都不满足**；硬接最可能的后果是确认率**下降**（fail-closed 到 uncertain，而 uncertain 禁止重发）。

### 1.2 为什么轨②对回复是 0（两个独立的门，缺一不可）

1. **门一｜多段直接丢模板**：agent/reply_pipeline.py:485-486 `multi_part = len(parts) > 1` / `transport_template = receipt_template if not multi_part else None`；:509-513 记 warning。docstring（:458-466）自己写明这是等 ADR-003:23 的 receipt.parts 聚合。
2. **门二｜成功路径不入队**：onebot/ws_client.py:347-366 `_enqueue_retryable_send_async` 的首行判据 `if not self._outbox_store or not allow_enqueue or not result.retryable: return`（:353）；调用点在 `:1541-1545`（群）与 `:1695-1699`（私），都在 **POST 之后**。成功发送的 `SendResult.retryable` 为 False（`_classify_send_error` 只在 NETWORK/HTTP_5XX/无细节 failed 时给 True，:96-115）⇒ **成功的回复永不入队**。

⇒ 这解释了 2026-10-13 台账 T2.4「❌ 未达完成标准」为何到今天仍未变：**根因不在模板传递，在入队门槛**。

### 1.3 多段不是边缘情形，是主路径

- agent/protocols.py:551 注释（既有实测）：私聊近 30 天 **64.4%** 的回复含空行分段、**平均 2.15 段**；2026-10-14 T32 起空行与 `[分段]` 等价（protocols.py:570-607）。

### 1.4 身份与幂等机制（决定方案A 要不要改 ID）

- agent/action_contract.py:196-224 `derive_action_id`：canonical JSON **已包含 ordinal 与 payload** ⇒ 逐段不同文本天然得到不同 `act-*`。**方案A 不需要改 ID 算法。**

### A2｜账本语义怎么变

**今天的形态（实测）**

| 场景 | chat_log | conversation_window_events | confirmed_action_facts |
|------|----------|----------------------------|------------------------|
| 单气泡回复（绝大多数） | **1 行**，`event_key=''` | **0 行** | **0 行** |
| 多气泡回复（私聊 ~28%） | **N 行**，`event_key='delivery:<源消息id>:<i>'` | **0 行** | **0 行** |
| 定时任务发送（task:*） | 1 行，`event_key='action:<aid>:chat'` | 1 行 | 1 行 |

`_account_confirmed_prefix` 的两条分支差别的**唯一实测差别**就是这个 event_key：单段不传 event_key（走 `chat_log` 唯一索引的 `WHERE event_key != ''` 豁免，store.py:506-509），多段传 `delivery:<源消息id>:<i>`（handler.py:13696-13697），从而**已经**恢复了「条」的边界。

**方案A 之后的形态（若只加不拆）**：

- 多段回合会**同时**得到轨① 的 `delivery:<src>:i` 行与轨② 的 `action:<aid>:chat` 行 ⇒ **同一句话在 chat_log 出现两次**。
- `idx_chat_log_event_key`（store.py:506-509，唯一索引 + `WHERE event_key != ''`）**只保证同一个 key 不重复，不保证两条轨互不重复**——这是硬约束级的漏口，不是概率问题。
- 连带翻倍的读者：上下文历史注入、记忆提取（按 chat_log 增量扫）、`self_check.record_sent`（handler.py:13511）、`memory.add_to_buffer`（handler.py:4363）、自忆锚点的文字兜底 `validate_self_memory_source`。
- 另一个**净新增**的语义：轨②会写 conversation_window_events ⇒ 回复首次产生窗口事件。今天回复路径窗口事件 0 行，所以**重启后私聊窗口不含任何回复**；接入后 `_sync_durable_events` 会在重启时把已确认回复回放成窗口。这是新行为，需要显式决定是否期望（今天的行为可能是有意的，也可能只是没人注意）。
- ⇒ **方案A 必须自带一条设计决定：挂模板的回合，轨①不再写 chat_log**（或轨②只写事实不写 chat_log）。ADR-003 没有写这一条。

### A3｜风险

1. **ordinal 没有来源（必须解决，否则会真冲突）**：handler.py:569 读 `turn_actions['text_ordinal']`，全仓零写入 ⇒ 恒 0。若只靠 payload 不同来区分段，**两段文本相同**时 `derive_action_id` 会给出**同一个** action_id，随后 `enqueue_send_outbox` 抛 `domain action conflict in outbox`（store.py:7238-7240）。「短回复拆两条且内容相同」（例如两条都是「嗯」）在生产里会发生。⇒ 必须给 ordinal 赋真值（顺带满足 ADR-004:20「children 各有 ordinal」）。
2. **已持久化记录会不会认不出自己**：**今天不会。** send_outbox 仅 3 行（2 行 legacy 无模板、1 行 dead）；confirmed_action_facts 23 行 `source_id` 全是 `task:*`，而回复的 source_id 形如 `<scope>:<message_id>`（handler.py:10261-10277）⇒ **命名空间不重叠，零存量冲突面**。代价是：这次不改，以后改会更贵。
3. **derive_action_id 的 payload 契约被谁依赖**：`ActionEnvelope.__post_init__`（action_contract.py:267-279）与 `finalize_action_receipt_template`（:455-467）都会**重算并比对** action_id，不符抛 `receipt action_id does not match frozen source identity`。落到 settle 侧就是 `RECEIPT_TEMPLATE_INVALID` 分支（store.py:9111-9152）：confirmed 被降级为 `confirmed_unaccounted`（:9128-9140）+ logger.error + DB-only 修复入口 `repair_confirmed_projection`（:9298）。⇒ 改契约的代价是**冻结而非丢账**，方向安全，但必须写进迁移步骤并留 `transport_request_id` 类兼容读取。
4. **outbox 重试语义会被改变**：今天 outbox 的语义是「失败后的重试队列」（入队在 POST 后、且只在 retryable 时）。ADR-006 要求**发送前**持久化 transport_request_id ⇒ 行会在每次发送前插入。逐段后每回合可能插 N 行，且 confirmed 后被立刻 `DELETE`（store.py:9190-9193）。net 效果是**每回合 N 次 INSERT + N 次 DELETE，且包在 BEGIN IMMEDIATE 里**（store.py:9077、:7215）——写放大是确定的，是否影响事件循环**无测量证据（待验证假设）**。
5. **部分送达的语义边界**：`settle_send_outbox` 对 task_attempt_id 非空的行要求「confirmed 必须带 message_ids」，否则强制降级 uncertain + `MESSAGE_ID_UNCONFIRMED`（store.py:9086-9091）。逐段投影时若某段 message_ids 缺失，会走进同一个降级口——这是**已有防线，接入时要复用它而不是绕开**。

### A4｜谁消费 parts 聚合产出的事实

- **逐段 chat_log 行**：消费者已存在（上下文注入、记忆提取、窗口续期、自忆文字锚点）。轨①今天已经在产，所以**这部分收益已经拿到**——方案A 不会在这条上新增任何消费能力。
- **confirmed_action_facts**：功能消费者只有 1 个（`validate_self_memory_action_anchor`，store.py:5970），且 2026-10-12 已被文字锚点兜底绕开（handler.py:11816-11840）。窗口事件表的消费者是 conversation_tracker 的重启回放（conversation_tracker.py:94-131）。其余是计数器（health_check.py:217-241）。
- ⇒ **「没人读就只是多写几行」这个担心成立一半**：facts 的**新增**消费≈0；真正的收益是「传输层确认 → 账本单一事实源 → 消除双写风险」，不是解锁新功能。这条应当写进实现目标的表述里，否则会被误当成功能开发。

### A6｜最大的三个后果（一句话版）

1. **主路径换账本，且必须同时拆掉轨①**：私聊 28%（实测）~64.4%（文档）的回复目前靠 handler 逐段写；换成轨②后若不拆轨①，**每句话在 chat_log 出现两次**，直接污染历史注入、记忆提取与自忆锚点。这是唯一的不可逆风险（重复行一旦落库就要手工清）。
2. **outbox 从「失败重试队列」变成「每次发送的传输记录」**：成功路径必须开始入队，每回合 N 次 INSERT+DELETE 包在 BEGIN IMMEDIATE 里，ADR-005 的 attempt/重试所有权语义要重新对齐（今天 `attempts`/`next_retry_at`/`retry_owner` 三列的含义是为「失败后重试」设计的）。
3. **收益是「单一事实源 + 自忆动作锚点恢复真实语义」，不是新功能**：facts 的功能读者只有 1 个且已有文字兜底；窗口事件这条今天几乎无消费收益。若按「补全功能」来排期，会期望落空。

## 三、ADR-006 接入会怎么样

### B1｜接入形态（file:line 落点）

| # | 落点 | 现状（证据） | 接入要做什么 |
|---|------|--------------|--------------|
| ① | onebot/ws_client.py:1437 `_call_api` | 只发 headers + json=params（:1448-1452），**没有任何 echo**；返回 `parsed`（:1474） | 给 send_* 注入 `echo=<transport_request_id>` 并把响应里的 echo 校验回来（ADR-006:9-14 指的就是这件事） |
| ② | onebot/ws_client.py:1524 `send_group_message` / :1678 `send_private_message` | 入队在 **POST 之后**（:1541-1545 / :1695-1699）且只在 `result.retryable` 时 | 改为 POST **之前** `enqueue_send_outbox`（store.py:7174）拿 outbox_id 并持久化 transport_request_id（ADR-006:23「发送前持久化」） |
| ③ | onebot/ws_client.py:881 `_event_route` | 只映射 message / notice / request / meta_event（:889-901），`message_sent` 落 `return None`（:901），事件被丢 | 增加 message_sent 分支——**ADR-006:33-34 明文警告不许在鉴权/canary 前动这里** |
| ④ | 新消费者接线 | `agent/platform_receipts.py` 在 agent/ 与 onebot/ 的生产消费者 = **0**（grep 命中仅 platform_receipts.py 自身 + tests/test_platform_receipts.py 14 处 + tests/test_integration_contract.py:169/:221） | `validate_platform_receipt`（:202-213）→ `to_evidence()`（:184-199）→ Store 私有入口 `settle_send_outbox`（store.py:9062）/ `mark_send_outbox_confirmed_unaccounted`（store.py:8072） |
| ⑤ | config.yaml | **没有** platform receipt 相关 flag（ADR-006:38-40 承诺的 feature flag 不存在）；现有 `tasks.*` 四个 flag 是**定时任务领取**开关（main.py:290-312；控制台:2968-2970） | 新增 1 个 flag，并同步糖糖控制台_qt.py（教训 #4） |

### B2｜会带来什么

**新运行时行为**

- 反向 WS 要接收 `message_sent`（今天不接，:881-901）。
- `_call_api` 要带 echo 且校验回显；这是**所有** API 调用共用的函数（get_login_info / delete_msg / set_group_ban … 共 26 处调用），改它等于给全部 API 加一层回执绑定 ⇒ 影响面是 ws_client 全量，不是 send_* 局部。
- 发送前多一次 BEGIN IMMEDIATE 的 DB 写（store.py:7214-7215）。

**新数据**

- `send_outbox` 从 3 行变成「每回合 1 行（或逐段 N 行）」，且 confirmed 后立即 DELETE（store.py:9190-9193）⇒ **净增是每回合一次 INSERT+DELETE**。
- 需要一个**新列**存 transport_request_id：send_outbox 现有 19 列（action_id/target_type/target_id/group_id/message/status/attempts/next_retry_at/last_error/created_at/updated_at/receipt_template/domain_action_id/confirmed_message_ids/confirmed_at/projection_error/task_attempt_id/ordinal/retry_owner）里**没有**。迁移要走既有幂等列迁移模式（store.py:500-503 `try: ALTER TABLE ADD COLUMN except OperationalError: pass`）。

**与 send_outbox 的关系：不是冲突，是同一张表**

- ADR-006 的回执本来就是喂给 `settle_send_outbox` 的（同一个终局入口），不存在第二套发送状态机。
- 真正的张力在两套**错误判定**之间：`platform_receipts.validate_context` 失败一律 fail-closed（:167『失败时调用方必须 fail-closed』；:175-181 synthetic/时间窗拒绝）vs 现有 `_classify_send_error` 的 retryable 分类（ws_client.py:96-115）。**接入后必须指定谁说了算**，否则同一失败会有两个处置（一个不重发、一个允许重试）。

**与 _last_checked_send_* 的关系：会冲突（无证据部分已标待验证）**

- handler.py:13488-13526：`confirmed = is_send_confirmed(sent_ok)`（**内存**、同步）→ 决定本回合 ok、写 `_last_checked_send_payload`、`self_check.record_sent`、回复遥测（:13531-13555）。
- 回执路径是**DB、异步、事后**。同一事实两个判定源。若要 DB 当权威，handler 的 `return confirmed` 同步语义需要改成「待回执」——这是 handler 主流程语义级的改动，**不是接线级**。

### B3｜风险

1. **两个事实源——是，但已有部分防线（可检测，不静默）**：今天「送达」由 `SendResult.delivered`（来自 HTTP 响应里的 int32 message_id，ws_client.py:54-74、:87-93）判定；接入后由 `PlatformReceipt.payload_sha256 + message_ids + 时间窗` 判定。重复写入时：`_commit_confirmed_action_conn` 对同 domain id 返回 `confirmed_duplicate`（store.py:8276-8277）或抛 `ConfirmedProjectionConflict`（:8291-8296）；`settle_send_outbox` 要求行仍为 `status='sending'`，先到者赢、后者返回 `missing`（:9078-9084）。⇒ **不会静默双写**，但会留下「谁是权威」的口径问题（ADR-003 的单一事实源精神要求定一个）。
2. **对已持久化 outbox 的影响**：存量 3 行全 dead，新增列后该列为空字符串。`PlatformReceipt.__post_init__`（:99-104）要求 transport_request_id 非空 ⇒ **存量行不能直接喂进契约**，必须允许「空值 = 无回执能力」的路径（ADR-006 未写这一条）。**待验证假设**：是否存在非 dead 的历史行（本次查库：无，仅 3 行且 status='dead'）。
3. **ADR-006 自己列的启动条件今天一条都不满足**（:33-34）：需要「真实适配器 echo、WS 鉴权和群/私 canary」三者齐备才允许改 `_event_route`/`_call_api`。实测：`_call_api` 无 echo；反向 WS 只校验 localhost、**无连接级鉴权**（ADR-006:13-14）⇒ 一旦开口接 message_sent，伪造回执从「理论」变成「可注入」，而回执能直接驱动 `settle_send_outbox` 写**永久不可变事实**（confirmed_action_facts 有 immutable 触发器：store.py:790/:795）。这是本部分**最高风险**的一条。
4. **fail-closed 的代价方向**：platform_receipts 的设计是「校验失败保持 uncertain，不得重发、不得改写 current attempt」（ADR-006:28-31），而 ADR-005:19-20 又规定 uncertain/partial/cancelled 在行为 canary 前**禁止重发** ⇒ 接入后一旦回执链不稳，会出现「消息实际已发出、账本记 uncertain、且不允许重发」的静默堆积。

### B4｜代价

- **规模**：ws_client.py +40 ~ +80 行（echo 注入/校验、message_sent 路由、发送前入队）；`_event_route` +5 ~ +10 行；新消费者接线 +20 ~ +40 行；store.py 新列迁移 +20 ~ +40 行；config.yaml +1 flag；糖糖控制台_qt.py +2 处（预设字典 + 字段表）。**≈5 文件 / +90 ~ +190 行**（比方案A 小）。
- **测试**：`tests/test_platform_receipts.py` 已有 14 处引用可复用；需新增「echo 不匹配 → uncertain 且不重发」「message_sent 默认 fail-closed（allow_synthetic=False）」「回执与 SendResult 争同一 outbox 行时先到者赢、后者 missing」三条。另：`tests/test_integration_contract.py:221` 那行 `('agent/platform_receipts.py','to_evidence'): '仅测试引用…当「待接线」留着'` 的注释与白名单语义要同步改，否则闸门会与实现打架。
- **是否改 config：要**。ADR-006:38-40 承诺的 feature flag 今天不存在——这本身是「文档与代码分家」（C-5）的一个实例。改 config 同时必须同步 `糖糖控制台_qt.py`（教训 #4；同型闸门 tests/test_task_action_phase2a_commands.py:201-212 会检查字段表与 config 一致）。

### B5｜接入后最可能的三件事 + 维持现状的损失

**最可能的三件**

1. **确认率不升反降**：回执要求同时命中 outbox_id / self_id / channel / target / 正文 SHA-256 / 合法 int32 唯一 message_ids / 时间窗（platform_receipts.py:99-125、:164-182），而 OneBot 侧 `message_sent` 无 echo、反向 WS 路由今天不接收该事件（ADR-006:9-14）⇒ 一旦校验失败就 fail-closed 到 uncertain，而 uncertain 在行为 canary 前禁止重发（ADR-005:19-20）。净效果是把今天「HTTP 响应即确认」（15 条 task 事实走的就是它）的路径**变窄**。
2. **outbox 变热表**：每回合一次 INSERT + 一次 DELETE，都在 BEGIN IMMEDIATE 里，且 send_outbox 上有锚点触发器与唯一索引（store.py:813 / :1600 / :1641）。是否拖慢事件循环**无测量证据——待验证假设**（需要真实并发压测，本报告不做效率结论）。
3. **反向 WS 的鉴权缺口从「理论」变「入口」**：一旦 `_event_route` 接 message_sent，无连接级鉴权的反向通道就能伪造回执；而回执的唯一去向是写**不可变**的 confirmed_action_facts。按 ADR 自己的顺序要求，**先鉴权后接线**。

**维持现状的损失**

- 出站送达的**权威证据链缺一环**：只有 HTTP 响应，没有请求级关联（ADR-006:9-14）⇒ 重试/并发/重启窗口里 message_id 与「哪一次请求」无法对应，异常时只能人工推断（send_outbox 里那 3 行 dead 就是这种推断的产物）。
- `payload_sha256` 类校验完全没机会参与 ⇒ **「平台确认的是不是她原话」没有任何自动防线**。
- 契约代码（213 行）+ 14 处测试 + 台账「待接线」条目长期悬空，成为 C-4 那种「已知不修」的重复问题（task-6 已记 ≥3 次重提）。
- 反向 WS 不接 message_sent ⇒ 群/私 canary 无从谈起，ADR-002 B2 的贴图统一被同一根链卡住。
