## 第三部分 · P1-a：驱动力消费点 `reply_commitment`

### 取证（先取证再改）

审计 P0-1 说 `release_by_action("reply_commitment")` **零调用**。取证确认，并且
真实缺陷比审计写的更深一层：

| 证据 | 值 | 来源 |
|---|---|---|
| `release_by_action("reply_commitment")` 生产调用点 | **0** | `grep release_by_action agent/*.py` |
| 兑现承诺时的实际释放 | `release("commitment", 0.2)` ——**写死魔法数**，两处 | `handler.py:11472`、`self_state.py:279` |
| 自忆 `promise` = 今天真正的承诺来源 | **175 条 active** | 查库 `origin='self' AND key='promise'` |
| `accumulate_commitment()` 生产调用点 | **0** | `unfinished_add`/`unfinished_remove` 两个参数都只有定义、无调用方 |
| 结果 | 承诺压力只靠 tick 的固定 alpha（0.10/h）累积，**与她实际攒了多少承诺毫无关系** | `.tangtang_self.json`：commitment **0.976**、express **1.0**、curiosity_info 0.987 |

→ **真实的主要矛盾不是「一个名字没人调」，是「承诺压力与她的承诺账本两端都脱钩」**：
写入端不升压、兑现端走魔法数。只把 `reply_commitment` 接上而不补写入端，
等于修了表没修根。

### 改了什么

| 位置 | 改动 | 理由 |
|---|---|---|
| `handler.py` `_extract_self_memories_llm` | 新承诺自忆写入成功后 → `drives.accumulate_commitment()`（走 `getattr` 可选依赖） | 补**写入端**：承诺入账 → 压力升 |
| `handler.py` 同上（结算分支） | `release("commitment", 0.2)` → `release_by_action("reply_commitment")` | 数值唯一来源 = `drives` 的 mapping |
| `self_state.py` `update_relationship`（unfinished_remove） | `release("commitment", 0.2)` → `release_by_action("reply_commitment")` | 同上；消灭第二处写死的 0.2 |
| `drives.py` docstring | 写明 mapping 是数值唯一来源、0.2→0.30 的行为增量已实测知情 | 让分叉的成因可被下一个人看见 |

### ⚠ 一个**显式行为改变**（不是「保持现状」）

`reply_commitment` 表里原本就写着 `[("commitment", 0.30)]`，而实际结算用的是写死的
`0.2`。改走表之后：

- 净释放：`0.2 × 1.1 = 0.22` → `0.3 × 1.1 = 0.33`（**+50%**）
- 按 commitment alpha 0.10/h 计，压制时间 **2.2h → 3.3h**
- 方向与审计 P0-1「消费点要压得住积累」（承诺压力长期 0.976 贴顶）一致

我在代码注释里写明了这是**知情的**行为增量，不是「顺手调参」。若主人认为应保持
0.2，改 `drives.py` 的 `"reply_commitment": [("commitment", 0.3)]` 一处即可
（这正是「单一来源」的好处——改一处，两个消费点同时生效）。

### 新增闸门（防复发）

`tests/test_integration_contract.py::TestActionVocabularyGate`：

1. **`test_every_action_name_has_a_production_call_site`** —— 从 `drives.py` 的
   mapping **解析出全部键**，再扫生产代码里真实的 `release_by_action("<name>")`
   调用点，每个键都必须有调用点。名字**不写死在测试里**（写死就会漂移）。
2. **`test_checker_sees_a_planted_call_site`** —— 阳性对照：种一个调用点必须被看见。
3. **`test_settlement_amount_has_a_single_source`** —— 用 **AST**（不是正则）
   找写死的 `release("commitment", <数字>)`，出现即红。
4. **`test_hardcoded_release_checker_sees_a_planted_call`** —— 阳性对照 +
   **阴性对照**（注释里的旧代码不算）。

> [!] 这两条闸门的第一版我都写错过，记在附录 B。

### 回归测试

`tests/test_memory_grounding.py`：

## 第四部分 · P1-b：情绪正向自报回灌

### 取证

| 结论 | 证据 |
|---|---|
| 5 个正向事件（被夸/被感谢/被想念/亲密聊天/帮到别人）**零发射点** | `grep MoodEvent agent/*.py`：只有 BEING_AT×2 / INTERJECTED / SENT_LONG_REPLY / SENT_REPLY / LATE_NIGHT / BEING_SCOLDED / BEING_IGNORED |
| 心情没有任何正向输入 | `mood.py::_apply_decay` 每半小时把心情拉回中性 70 |
| **她从来不自报情绪标签** | 查 `chat_log`：18397 条 bot 行中，以 `[` 开头的 **0 条**；含 `[SING` 4 条、`[分段]`/`[引用]`/`[不说话]` 各 0 条 |
| 现有情绪标签是**说话语气**不是她的心情 | `handler.py:10345-10351` 明确写「语气不是话题情绪」；`EMOTION_SPEED` 只服务 TTS 选音色 |

→ 所以「接现成的情绪标签」这条路**不成立**（那是语气，且文本路径根本不产出）。
审计给的方案是「回复 LLM 自报标签回灌，约 25 token、零额外调用」——按这个做。

### 为什么不能做成常驻注入

审计「不要动」第 11 条：**不加无条件常驻的「近况叙事」摘要**——同形注入在
2026-08-17 瘦身时被**实测有害**（诱导模型「汇报状态」而不是「带着状态说话」）。
所以本实现的核心不是标记本身，而是**闸门**：

```
_mood_report_turn = bool(feedback_candidate)
```

只有「她刚说完、**这个人接着回**」的回合才注入协议（`_take_feedback_candidate`
已有的判定，群 60s / 私聊 120s 窗口）。没有真实交流发生的回合不注入，
也就没有这 ~180 token。

### 改了什么

| 位置 | 改动 |
|---|---|
| `mood.py` | 新增 `SELF_REPORTABLE_EVENTS`（5 个正向事件）与 `MOOD_REPORT_EVENTS`（中文名 → 事件，键**就是** `event.value[0]`，不另起一套命名） |
| `protocols.py` | 新增 `parse_mood_report()`（返回 `(标签, 正文)`、无标记时正文逐字相同）、`strip_mood_report()`、`MOOD_REPORT_PROTOCOL`；`strip_protocol_markers()` 接入兜底 |
| `handler.py` | 群/私两条路径：`feedback_candidate` 处记 `_mood_report_turn`；注入协议（挂在闸门后）；**clean 之前** `parse_mood_report(reply)`；`if ok:` 里 `_apply_mood_report(_mood_report)` |
| `handler.py` | 新增 `_apply_mood_report(label)` —— 白名单 fail-closed + 白名单外**记日志**（不许静默，审计 RC5） |

### 设计边界（写清楚，免得下次凭感觉重提）

- **只有 LLM 能报**：这五个事件的语义是「他人指向她」——「ta 那句话到底是在夸
  还是在客套」只有读懂那句话的模型知道。系统按关键词或按冷热判定去映射，
  等于给状态机编造体验（教训 #9/#19；这也是 2026-10-12 M3 刻意不把
  `warmly_received` 硬塞进事件表的理由）。
- **不做关键词检测**：`mood.py:220-221` 的关键词检测退役是决定不是遗漏
  （审计「不要动」）。闸门 `test_no_keyword_emotion_detection_came_back` 钉住。
- **回灌必须在确认送达之后**：没发出去的话不算一次真实交流（与 `SENT_REPLY`
  同一口径）。闸门 `test_mood_report_is_backfilled_only_after_confirmed_delivery`。
- **解析窄、兜底宽**（沿用 `[分段]`/`[引用]` 的失败方向）：只取第一个标记作事件
  （防刷数值），但正文里**所有**标记都剥掉（漏出标记她会当众穿帮）。
- **词表只有一份**：协议里列给她的词 = `mood.SELF_REPORTABLE_EVENTS` 的中文名。
  闸门 `test_whitelist_matches_mood_engine_events` 双向断言。

### 回归测试

- `test_mood_loop.py::TestMoodReportBackfill`（5 条）：白名单词真的能推动引擎、
  **穷举**每个词都真的生效且正向、白名单外 fail-closed **且有日志**、
  空标签 no-op、引擎缺失不炸。
- `test_protocols.py::TestMoodReportProtocol`（10 条）：解析契约、
  无标记时逐字相同、全角冒号、只取第一个但剥全部、未闭合括号不算标记、
  解析层不做白名单、统一出口覆盖、clean 兜底。
- `test_integration_contract.py`（4 条）：两路径都在 clean 前读、
  协议**挂在闸门后**（防改成常驻）、回灌在 `if ok:` 内、无关键词检测复活。
- `test_autonomy_boundaries.py` 既有 2 条（负向事件）保持绿——本轮没动负向路径。
