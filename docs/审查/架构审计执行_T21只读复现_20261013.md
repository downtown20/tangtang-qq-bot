## 三、复现时发现的独立缺陷：单段确定失败时失败原因被吞掉

### 现象

场景 C（脚本只给 1 个 failed 结果）：`aggregate.error == ""`，
而 `SendResult(False, False, error="BOT_ERROR")` 明明带着 `error="BOT_ERROR"`。

### 定位

```
agent/reply_pipeline.py:522   else (first_problem.error if first_problem else "")
agent/reply_pipeline.py:524   retcode=(first_problem.retcode if first_problem else None),
agent/reply_pipeline.py:510   first_problem = next((r for r in results if not r.delivered), None)
```

`first_problem` 存在（不是 `None`），但 `if first_problem` 走的是**真值判断**，
而 `SendResult.__bool__` **故意**只返回 `ok`：

```
onebot/ws_client.py:49-52   def __bool__(self): return self.ok
onebot/ws_client.py:50-51   # 兼容旧调用点：bool 只表示 API 接受了请求，不代表已送达
```

`first_problem` 的定义是「**没有** delivered 的第一段」⇒ 它**恒为假值**
（`delivered=False` ⇒ `ok` 也基本为 False）⇒ 两个三元一律走 else 分支。

### 最小验证（`.trash/20261013-stage2/verify_boolbug.py`）

```
failed = SendResult(False, False, error="BOT_ERROR", retryable=False)
bool(failed)                      -> False
failed.error if failed else ""    -> ""        # 实测
                                      "BOT_ERROR"  # 预期
f2.retcode if f2 else None        -> None      # 同型风险：retcode 一起被吞
```

### 根因

**对「可能为假值」的对象用真值判断来区分子类型**——这不只是「少个日志」，
它让聚合结果**丢掉了失败原因与错误码**：

- 上层（`handler.py:13140-13145`）拿 `last_send_result` 只能打出 `state=failed`，没有原因；
- `channel B`（发送路径）里**已经有** `== "failed"` 的显式判定（`:456`，作者显然知道），
  却在 `:522-524` 用了真值判断 ⇒ 同一文件内两种判定方式并存。

### 为什么**不**合进 T2.2

T2.2 的完成标准（规划 4.3）是「`chat_log` 只含已确认前缀 + `status=uncertain` 且
`error_code=PARTIAL_DELIVERY`」，**不覆盖 `status=failed` 的单段失败路径**。
顺手改会**扩大 T2.2 的变更面**——违反规划第五部分第 1 条（未达完成标准不得标完成）与
「一次只验证一个假设」。

⇒ **处置建议**：新增 **T2.2b**（与 T2.2 同批但独立核对），改造点只有两行：
`if first_problem is not None`；门禁用「单段确定失败时 `aggregate.error` 必须非空」+ 阴性对照。
**本文件只记录，不做决定。**

### 影响面（未逐条判定，标注为粗筛）

`agent/` 下「裸变量名作真值条件」的三元表达式共 **366** 处（AST 口径，未逐个判定变量
是否可能为永远真值的对象）。本缺陷是其中**已证实的一处**，其余仍是假设。

## 五、顺带核验：审计附注的「反向事故」已不再成立

审计附注（`:146`）提到 08-30 的真实事故：段 2 明确失败（`retcode=100 image source is empty`）时，
Handler 仍打 `📤 已发送`。**这是「过度记账」的另一边，也是修复必须避开的方向。**

本轮实测：`📤 已发送` 在 `agent/handler.py:5174`，被 **`if ok:`（`:5173`）** 门控，
并有对称的 `else: ❌ 私聊回复发送失败`（`:5180-5181`）。
群路径 4126 也同样是 `ok = await self._checked_send(...)` 之后才进 `if ok:`。

⇒ **该反向事故在审计之后已经被修掉了**（本次未复现）。所以 T2.2 的修法边界是：
**只记平台已确认的那几段**，既不回到整条入库，也不引入新的过度记账。

## 六、对 T2.2 的输入（不是设计，只是复现带出来的约束）

1. `chunk_ids` 已经在聚合结果里——按确认粒度归账**不需要新的传输层信息**。
2. `last_confirmed_payload` 的「只有全部确认才写」不能**只**放宽成「有确认就写」：
   它是无边界拼接，放宽会立刻制造 ②。**②与①必须同一次改**（这正是 T2.2/T2.3 相邻的原因）。
3. 语义边界仍由既有测试钉死，不能动：
   `tests/test_reply_send.py:163-181`（前段未确认不发后段）、
   `:183-199`（PARTIAL_DELIVERY 标记）、
   `tests/test_send_commit_boundary.py:164-199`（部分送达不是成功提交）。
4. 「确定失败」与「不确定」要分开：A 是 `BOT_ERROR`（确定失败），D 是 `NETWORK_UNCERTAIN`（可能已送达）。
   T2.2 的 `status=uncertain` / `error_code=PARTIAL_DELIVERY` 要能同时表达这两种；
   在这条没写清之前，缺陷 ④（把 `error` 吞成空串）会**直接抵消**这个能力。
