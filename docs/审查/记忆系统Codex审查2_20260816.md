# 记忆系统治理与运行时修复审查（2026-08-16）

## 审查结论

**结论：Request Changes，不建议按当前状态上线。**

本轮发现 3 个 Critical、8 个 Important、3 个 Minor。最主要的风险不是 schema 或工具是否存在，而是治理契约在出口和失败路径上没有闭环：`notes_dirty` 仍有多个旁路，纠正后的重合成会把已知错误的旧画像重新喂给 LLM，事实簇提取失败又会被误判成“成功但无事实”并永久推进游标。另有 `_engaged` 元组键迁移遗漏、全局记忆搜索漏过滤 `status`、CQ@ 校验绕过和并发识图错写等运行时问题。

审查范围以源码中的 `2026-08-16` 注释为变更标记，覆盖题目列出的重点文件、相关调用点、裸 SQL 读写点及新增测试。项目无 git 基线；GitNexus 索引时间为 2026-08-15，早于本轮改动，且当前会话未暴露 GitNexus MCP 资源。为遵守“只写报告文件”，未重建会修改 `.gitnexus` 的索引，改用源码级调用点和 SQL 全量追踪。已用项目内 Python 3.10 对 `agent/`、`napcat/`、`tools/`、`tests/` 共 177 个 Python 文件做 AST 语法解析，全部通过；完整 pytest 未执行，因为可用解释器均未安装 `pytest`（`python310\python.exe -m pytest` 返回 `No module named pytest`）。下述关键问题均有源码证据，其中 C1/C2/C3/I1 已做独立最小复现。

## Critical

### C1. `[agent/memory.py:1140]` dirty 旧画像被纠正后的重合成再次作为真值输入，可能复活刚撤销的错误事实

**证据：** `correct_memory()` 在命中旧画像时把 `people.notes_dirty` 置 1（`agent/memory.py:183-187`），后台纠正路径随后调用 `synthesize_profile(..., bypass_cooldown=True)`（`agent/handler.py:6768-6777`）。但 `synthesize_profile()` 无条件读取 `person.notes`，并在 user prompt 中加入 `已有画像：{existing}\n\n请增量更新`（`agent/memory.py:1140-1162`），完全没有检查 `notes_dirty`。最小复现中，`notes_dirty=1` 且 notes 为“旧画像：喜欢特摄”时，该文本仍出现在重合成 prompt。于是模型同时看到 corrected 事实和已知错误的旧画像，可能保留、折中或重新生成被撤销内容。

**为什么是问题：** dirty 的语义应是“旧画像不可信，禁止参与任何真值消费”，不仅是“不注入聊天”。当前实现让纠正闭环在最关键的重建步骤自我污染。

**建议修复：** 在合成入口统一处理：`existing = "" if person.get("notes_dirty") else person.get("notes", "")`；纠正重合成只使用 active、满足置信度门槛的原子记忆。补一条端到端测试：旧 notes 含错误事实、置 dirty、写 corrected 事实后，捕获 LLM prompt，断言旧 notes 不出现而 corrected 事实出现。

### C2. `[agent/handler.py:2610]` `notes_dirty` 并非所有画像出口的强制门，已知错误画像仍能进入 LLM/tool 结果

**证据：** dirty 门只在部分路径生效（如 `agent/memory.py:467-470`、`agent/handler.py:2651-2658`、`agent/handler_autonomy.py:704-707`），但至少以下实际消费出口未检查：

- 私聊第三人交叉上下文：`agent/handler.py:2608-2623`
- 群人物关系图：`agent/handler.py:5843-5864`
- 群聊紧凑记忆块：`agent/memory.py:554-566`
- `get_person_profile` 类工具结果：`agent/handler.py:7516-7526`
- people 搜索工具：`agent/store.py:647-655` 返回值甚至不包含 `notes_dirty`，`agent/handler.py:7534-7550` 因而无法过滤

这些路径虽统一加了截断和 caveat，却仍会把 dirty 内容交给 LLM。`tests/test_protocols.py:302-315` 只做“源码中存在 caveat 常量”的静态断言，没有验证 dirty 时的运行结果，因此是假绿面。

**为什么是问题：** 纠正后用户可能在私聊工具查询、群人物图或交叉上下文中立刻再次看到旧错误；caveat 只能声明不确定性，不能替代“已知错误禁止消费”的真值门。

**建议修复：** 不要在 5 个调用点重复补判断。让 Store/Memory 提供唯一的 `active_profile(person)`/`profile_text_for_person()`，dirty 时返回空；所有 8 个出口只通过该接口取画像。`search_people()` 应返回 `notes_dirty` 或直接将 dirty notes 投影为空。为每个出口做参数化行为测试，而不是搜索源代码字符串。

### C3. `[agent/memory.py:1329]` 事实簇 LLM 失败与合法空结果不可区分，调用方会永久推进 `fact_cluster_last_chat_id`

**证据：** `extract_fact_clusters()` 对无 JSON 方括号、JSON 解析异常、LLM 异常以及合法 `[]` 都返回完全相同的 `{"new_clusters": 0, "new_facts": 0, "updated_clusters": 0}`（`agent/memory.py:1329-1342`）。调用方把任何正常返回都视作“成功（含明确空结果）”，无条件把游标推进到本批最大 chat id（`agent/handler.py:6957-6969`）。最小复现中让 LLM 返回非 JSON 上游错误页，函数返回零结果字典，按调用方逻辑会推进到批次末尾。

**为什么是问题：** 一次瞬时超时、空回复或格式漂移会使最多 30 条消息永久越过事实簇提取；重启后持久游标仍在新位置，无法重试。这直接违背注释声明的“失败不推进”。

**建议修复：** 返回带显式状态的结果（如 `ok: bool, explicit_empty: bool`），或解析/LLM 失败直接抛异常；仅 `ok=True` 时推进游标。合法 `[]` 必须与异常路径分别测试，并加重启后游标未推进的契约测试。

## Important

### I1. `[agent/store.py:1110]` 全局关键词/语义搜索绕过 `status`，撤销事实可重新进入 LLM 上下文

**证据：** `query_memories()` 和 `get_cluster_facts()` 默认过滤 active，但 `search_memories_by_keyword()` 的外号分支和 LIKE 分支都直接读取 `memories`，没有 `COALESCE(status,'active')='active'`（`agent/store.py:1120-1137`）。该函数经 `MemorySystem.search_memories()`（`agent/memory.py:1744-1750`）进入 `/记忆搜索`/话题联想等真实消费路径。最小复现插入一条 importance=9 的 retracted 事实和一条 active 事实后，关键词搜索同时返回两条。

同类遗漏还形成“embedding 复活链”：`get_memories_without_embeddings()` 会把非 active 行选入（`agent/store.py:1686-1697`），`get_memory_by_id()` 不验 status（`agent/store.py:1099-1107`），后台填充会给刚删除 embedding 的 superseded/retracted 行重新建向量；`search_similar_memories()` 又不验 status（`agent/store.py:1777-1798`）。

**为什么是问题：** status 不再是全局真值单一来源。用户刚 forget/correct 的事实能从搜索工具或未来语义路径重新出现。

**建议修复：** 所有业务读方法默认 active，只有名称明确的 audit/diagnostic API 才允许 `include_retracted=True`。为 `search_memories_by_keyword` 的普通与 alias 两分支、embedding 填充和语义搜索补 retracted/superseded 回归测试。

### I2. `[agent/handler_autonomy.py:203]` `_engaged` 改为 `(group_id,user_id)` 后仍有两个旧访问点

**证据：** 自治路径遍历 `_engaged` 时把整个 tuple 当成 `user_id` 再传给 `is_engaged()`（`agent/handler_autonomy.py:203-207`），生成的查找键实际是 `(target_group, "('group','user')")`，因此已有活跃窗口时 `has_active_window` 仍为 False。群回复路径的深度对话日记判断仍用 `_engaged.get(user_id,{})`（`agent/handler.py:2032-2038`），永远取不到元组键。最小复现确认真实窗口 `('g','u')` 存在且公共接口返回 True，但旧遍历判定返回 False、旧直接查找为空。

**为什么是问题：** 糖糖可能在已有活跃对话时插入自治发言；3 轮以上窗口的日记背景则永久失效。`tests/test_nickname.py:110-138` 只验证 tracker 自身公共方法，没有覆盖两个跨模块消费者。

**建议修复：** 禁止外部模块直接读取 `_engaged`。新增 `has_active_window(group_id)` 和 `get_window_state(user_id,group_id)` 公共接口；替换两个访问点并补自治/日记集成测试。

### I3. `[agent/reply_pipeline.py:245]` CQ@ 校验并非 fail-closed，跨群 QQ 和变体标签仍可绕过

**证据：** 回调只匹配精确的 `[CQ:at,qq=(\d+)]`（`agent/reply_pipeline.py:263`）；带额外参数、空格、`qq=all` 或其他 CQ@ 变体不会进入校验，会原样发送。对精确数字标签，`person_exists(qq)` 即放行（`agent/reply_pipeline.py:258-259`），但 people 是跨群全局表，不代表该 QQ 在当前群。`@昵称` 的 DB 回退同样用全局 people/aliases（`agent/reply_pipeline.py:229-233`），可能解析到别群同名成员，随后又因 person_exists 被保留。

**为什么是问题：** 目标不在当前群时仍可能触发 SnowLuma/NapCat 发送失败，复现“一个坏 @ 让整条回复丢失”；恶意/幻觉 CQ 变体也绕过安全清洗。现有测试 `tests/test_reply_pipeline.py:112-163` 只覆盖精确格式和短号，不覆盖跨群或变体。

**建议修复：** 先匹配所有 `[CQ:at,...]`，只允许严格解析成功且属于当前群成员（active buffer 或 `group_members(group_id,qq)`）的目标；其余 fail-closed 删除标签、保留正文。people 存在性不能作为群成员校验。

### I4. `[agent/relationship.py:65]` 关系档案异常路径既不退避，也以裸 `create_task` 泄漏异常，并缺少同用户单飞

**证据：** `_mark_failure()` 只处理“无 earliest/空输出/全未知”（`agent/relationship.py:55-57,78-92`）；`await self._llm(...)` 抛异常时没有 try/except，因此不会写 `rel_syn_fail_until:*`。调用方用裸 `asyncio.create_task()`（`agent/handler.py:2931-2934`），未走已有 `_safe_task()`，异常会成为 `Task exception was never retrieved`。此外 `maybe_update()` 在 await 前没有 per-user in-flight 锁，多条私聊可同时越过阈值检查，排队重复合成并覆盖档案。`tests/test_relationship.py:68-79` 只让 mock 返回空串，没有测试抛异常或并发。

**为什么是问题：** 真正的网络/API 故障恰好绕过“失败退避”，造成每条私聊重试、日志风暴和 LLM 空耗；并发任务还可能重复写。

**建议修复：** 在 manager 内部捕获 LLM 异常、记录日志并 `_mark_failure()`；增加 per-user single-flight；调用侧用 `_safe_task(..., name=...)`。测试 AsyncMock `side_effect=TimeoutError`、同用户并发两次只调用一次。

### I5. `[agent/store.py:1014]` 识图写回按“最近占位符”定位，在并发消息下会把描述写到错误图片

**证据：** ws 层对每条群消息独立 `create_task`（`napcat/ws_client.py:137-145`）；视觉调用有不确定延迟。写回时 Store 仅按 `(qq_id,group_id)` 查最新占位符（`agent/store.py:1018-1028`），buffer 侧也倒序找该用户最近占位符（`agent/memory.py:612-628`）。同一用户快速发两张图时，两次识图可能乱序完成并都命中第二张；第一张仍是占位符，第二张可能被旧描述覆盖。现有 `tests/test_reply_pipeline.py:195-213` 都是单图串行。

**为什么是问题：** 持久聊天史会把视觉描述绑定到错误消息，后续记忆提取可能把另一张图的内容当成当前证据。

**建议修复：** 入口记录 chat row id/buffer entry token（优先直接使用 QQ `message_id`），识图完成后按精确 id CAS 更新；若目标已非占位符则拒绝覆盖。加两张图逆序完成的异步测试。

### I6. `[agent/memory.py:1198]` “合成快照事务化”实际只做到单 key 事务，notes/profile/facts 仍会出现半世代

**证据：** 合成成功后先独立事务更新 `people.notes` 并清 dirty（`agent/memory.py:1198-1201`），再分别调用两次各自提交的 `replace_synthesis_memories()` 更新 profile 和 facts（`agent/memory.py:1204-1209`；提交点 `agent/store.py:965-999`）。三次事务之间崩溃或第二次失败时，读者可看到“新 notes + 旧事实”或“新 profile + 旧 fact 集合”。

**为什么是问题：** 注释承诺“完整旧集合或完整新集合”，但跨表/跨 key 的真实画像世代不原子；恰在纠正场景中可能让 dirty 提前清零，而旧合成事实仍可见。

**建议修复：** 在 Store 提供一个 `replace_profile_snapshot(qq_id, profile, key_facts, ...)`，单连接单事务完成 notes、dirty、两类旧行 supersede、新行插入；embedding 可事务后补，但业务读只在 active 新世代完整落库后开放。加入中途故障回滚测试。

### I7. `[agent/handler_autonomy.py:772]` 主动私聊回复以 `bot_qq` 作为 chat_log 所属人，新增 `include_bot_replies` 看不到它

**证据：** 正常私聊 bot 回复使用 `log_chat(user_id, reply, is_bot=True)`（`agent/handler.py:2921`），因此 `get_unprocessed_messages(qq_id,...,include_bot_replies=True)` 能取到上下文。主动私聊却写成 `log_chat(self.bot_qq, reply, is_bot=True)`（`agent/handler_autonomy.py:772-779`）。Store 查询始终先限定 `chat_log.qq_id = 目标用户`（`agent/store.py:1207-1228`），所以主动开场既不进入该用户的提取语境，也不进入 `get_recent_dialogue(qq_id)`；重启后 buffer 消失，持久史表现为糖糖没说过这句话。

**为什么是问题：** 注释宣称“主动说的话补记录”，但接线对象错误；恰好削弱本轮为玩笑/引用判断新增的 bot-reply 语境。

**建议修复：** 私聊按对话归属写 `qq_id`，`is_bot=True` 表示说话者；群自治若无法归属个人，应使用单独 group conversation schema，不能拿 bot_qq 冒充对话 owner。补“主动私聊后 include_bot_replies 可读”的集成测试。

### I8. `[tools/cleanup_memory_mechanical.py:46]` 去重实现保留最旧行，和文档承诺的“保留最新”相反

**证据：** 注释与模块说明均称重复 active 记忆“只留最新一条”，SQL 却用 `MIN(id) as keep_id`，随后 supersede `id != keep_id`（`tools/cleanup_memory_mechanical.py:46-55`）。

**为什么是问题：** 最新行可能带更高 confidence/importance/origin 或更准确时间；脚本会保留旧元数据并退役新版。当前无对应测试。

**建议修复：** 至少改为 `MAX(id)`；更稳妥是定义明确优先级（corrected > extracted、confidence、importance、timestamp、id）并测试不同元数据的重复组。dry-run 输出应显示保留 id 和将退役 id。

## Minor

### M1. `[napcat/ws_client.py:743]` @ 段在 name 分支丢失 QQ，handler 又依赖 raw CQ 才能建立身份映射

**证据：** `_extract_text()` 有 name 时只输出 `@name`，仅无 name 时输出 `@QQ{qq}`（`napcat/ws_client.py:743-753`）；handler 的 QQ→昵称替换只识别 `@QQ数字`（`agent/handler.py:1937-1942`），身份映射则从 `raw_message` 中重新找 CQ（`agent/handler.py:1943-1947,7569-7589`）。若上游事件没有 raw_message 或 raw 格式不是 CQ，name 分支把 QQ 永久丢掉，LLM 看得到名字却无法得到工具所需 subject_qq。现有 `tests/test_at_mentions.py:19-36` 分别测 ws 和 handler helper，没有覆盖完整事件。

**建议修复：** ws 事件保留结构化 `mentions=[{qq,name}]`，handler 直接消费；不要从展示文本或 raw 字符串反推身份。补 raw 缺失的端到端测试。

### M2. `[agent/store.py:923]` 新真值生命周期下，旧清理/统计 SQL 仍把审计行当业务行

**证据：** `delete_stale_memories()` 不看 status，会物理删除低 importance 的 retracted/superseded 行且未同步删 embedding（`agent/store.py:923-935`）；`get_people_with_memories_gt()`、`count_memories_for()`、`get_global_stats()`/embedding coverage 等统计也计入非 active 行（如 `agent/store.py:2220-2233,2288-2301`）。这会让每日播报“记住了 N 件事”虚高，并让只有撤销记忆的空画像用户反复进入补全扫描。

**建议修复：** 明确区分 active 业务统计与 audit 总量；清理审计历史只走专门 retention 策略，并成对清 embedding。

### M3. `[agent/handler.py:624]` feedback 健康检查可在零反馈、未成功播报时假绿

**证据：** `_report_stats_with_feedback()` 无论 `feedback.total` 是否为 0 都写 `feedback:last_consumed`（`agent/handler.py:624-640`），而该函数在 LLM 生成和群发送之前被调用（`agent/daily_report.py:186-215`）。健康检查只看 key 是否存在（`agent/health_check.py:278-288`），所以一次失败播报或空表查询也会显示“feedback 已消费”。`tests/test_read_side_quality.py:82-89` 只断言 key 被写入，固化了假绿。

**建议修复：** 若“消费”指确实用于播报，应在至少一群发送成功后记录，并保存所覆盖的时间窗/最大 feedback id；健康检查验证进度而非时间戳存在性。若这里只是“查询过”，应改 key 和健康文案，避免夸大管线闭环。
