# 记忆系统 Codex 独立复审（2026-08-16）

## 一、结论摘要

本次只读复审覆盖 `agent/memory.py`、`agent/store.py`、`agent/handler.py` 的记忆注入/工具/执行/提取段、`agent/protocols.py`、`agent/relationship.py`、`agent/context_builder.py`、`agent/handler_autonomy.py`、`agent/perception.py`、`agent/health_check.py`、相关测试，以及 `memory.db` 与 `tangtang.log`。

简报的主要结论成立：事故根因不是单个错误事实，而是“低质量提取可晋升为画像、合成物反复自证、画像被高信任注入、用户纠正没有数据库写回”形成的闭环。20 项中，15 项成立，4 项部分成立/表述需修正，1 项证据范围需要收窄；没有一项应完全撤销。

需要优先补充三个比简报更关键的结构性问题：

1. **P0：关系档案更新游标读回缺失。** `Store.get_or_create_person()` 没返回 `relationship_updated`，`RelationshipManager.maybe_update()` 永远把它读成 0。用户聊天数超过 80 后，几乎每轮私聊都会重新合成并覆盖关系档案。事故时日志在 17:39:03、17:40:09、17:40:35、17:42:02、17:42:28、17:46:32、17:49:27、17:50:46 连续记录同一人的关系档案更新。这是明确的 `_save/_load` 不成对。
2. **P0：事故纠正句根本没有进入“纠正信号”链。** “我不爱特摄也不迷时政……”不包含现有 `CORRECTION_SIGNALS` 的任何短语，因此本轮连理解协议都没触发；当前协议只覆盖“你理解错了”型元纠正，不覆盖“旧事实是 X，正确是 Y”型事实纠正。
3. **P1：事实簇提取共用语义提取游标且提前推进调度进度。** 主提取先推进 `_last_extracted_id`，随后事实簇任务再用同一 `get_unprocessed_messages()` 取数；任务还在成功前就写 `_last_fact_extraction`。结果是事实簇批次依赖竞态，忙锁/样本不足/空批次后也可能再等 50 条消息才重试。事实簇不是完全死代码（库中有 1,850 簇、5,296 条事实），但接线不可靠。

数据库为运行中主库，审查读取点附近统计为：`memories=13,718`、`profile_synthesis=365`、`fact_synthesis=1,770`、`fact_clusters=1,850`、`cluster_facts=5,296`、`feedback=2,701`、`episodes=241`。主人 `2524950083` 有 150 条记忆，其中画像 15 条、画像事实 63 条。简报中的 13,711 是更早快照，不是错误。

GitNexus MCP 在本会话未暴露，改用仓内 CLI。CLI 能返回符号上下文，但索引行号明显落后于当前源码（例如 `synthesize_profile` 索引为 1069 行，当前源码为 940 行），且项目不是 Git 仓库，无法用 `status` 判断增量；下表行号均以本次直接读取的当前文件为准。

## 四、简报遗漏的问题

按严重度列出：

### P0

1. **[agent/store.py:455-466 + agent/relationship.py:26-34] `relationship_updated` 写入后读不回。** 为什么是问题：关系档案在 80 条后每轮私聊重算，持续付费、覆盖、放大“未知”元评论；日志已给出连续调用证据。建议：Store 返回完整持久字段，并新增真正的“游标往返 + 80 条边界 + 失败不推进”测试。
2. **[agent/protocols.py:24-53] 事实纠正与元纠正混为一个不完整信号表。** 为什么是问题：事故原句不命中，系统没有机会要求写回。建议：不要继续堆中文关键词；由工具协议要求模型在识别到事实否定/替换时调用 correction tool，并用事故原句做端到端闸门。现有高精度元纠正信号只负责模型升级/理解协议。
3. **[agent/store.py:935-940] 拟议 importance=0 路线与现代码冲突。** 为什么是问题：setter 强制最小 1，而且所有查询都不排除 0/1；即使直接 SQL 写 0，也仍会被 recall。建议：使用独立 truth status，或在不保留审计历史时硬删除；不要复用 relevance 权重表达“已否定”。

### P1

4. **[agent/handler.py:6477-6483,6698-6728] 事实簇任务没有独立消息游标，且调度进度先于成功写入。** 为什么是问题：任务取到的不是触发它的那批消息，失败后长时间不重试。建议：独立 `fact_cluster_last_chat_id`，把 batch/最大 id 显式传给任务，只在成功或明确空结果后推进。
5. **[agent/store.py:255-272,1748-1775] `evidence_ids` 字段从未写入。** 为什么是问题：事实簇无法回溯是哪条聊天支持它，纠错工具只能靠文本相似度猜，无法可靠撤销一条来源。建议：提取输入保留 chat id，LLM 输出或批次映射写 evidence_ids；纠正优先按证据和 subject 匹配。
6. **[agent/memory.py:953-971] 画像合成输入包含旧 `profile_synthesis`/`fact_synthesis`。** 为什么是问题：不仅 notes 会回喂，旧合成记忆也会进入 recall 前 50 再合成，形成第二条自我复制通道。建议：合成只读 active 的原始/人工/纠正事实，排除 `origin=summarized` 和 singleton profile。
7. **[agent/memory.py:620-680] 去重缓存和语义合并不更新完整元数据。** 命中进程缓存会直接 return，后续更高 importance/confidence 不生效；语义合并只改 value/importance/embedding，不改 confidence、origin、cognitive、timestamp，且 `update_memory_value()` 额外 +1 并截成 100 字。建议：统一成 Store 原子 merge API，明确每个字段的胜出规则；合成画像不要走普通 100 字记忆 merge。
8. **[agent/memory.py:308-321] 统计接口用 top-1000 查询代替 COUNT。** 为什么是问题：至少两名用户已有 1,000+ 记忆（最高 1,440），触发计数会封顶，后续新事实可能不再合成/整合。建议：Store 提供带 active/origin/key 过滤的 SQL COUNT。
9. **[agent/memory.py:1161-1243,1258-1297] 事实簇后处理缺少与主提取一致的质量校验。** confidence 默认 0.7 仍直接入库；分类不校验；重复 INSERT OR IGNORE 后 `new_facts` 仍无条件 +1；摘要把低置信和矛盾事实全部再写一遍。建议：共享结构 schema/validator，只按实际 insert 结果计数，摘要前做 active/confidence 过滤与冲突标注。
10. **[agent/handler.py:7263-7277] `_get_profile_and_recent()` 是简报漏列的裸画像出口。** 它截 150 字但没有 caveat，且可能与 `_search_people()` 交替返回。建议纳入统一 `profile_line()` 调用点和闸门测试。

### P2

11. **[agent/store.py:455-466 + agent/handler.py:6743-6756] `last_bonus_date` 同样没有从 person dict 返回。** 每次调用都像“今天尚未加分”，虽然 intimacy 上限掩盖了结果，但违反持久化成对性并制造无意义写入。
12. **[tests/test_protocols.py:302-315] caveat 闸门是假覆盖。** 测试只检查函数体中出现常量，没验证每个输出路径；因此 PM `recall_formatted()`、`_search_people()`、`_get_profile_and_recent()` 漏 caveat 仍全绿。建议对真实 formatter/工具输出做行为断言，不做源码包含断言。
13. **[agent/memory.py:145-160] BGE 粗筛在“部分有 embedding”时会完全丢弃无 embedding 记忆。** 手工/刚纠正的记录若向量尚未生成，可能在最需要时不可见。建议把无向量的高优先级 corrected/manual 项加入 fallback 候选，或保证纠正事务同步写 embedding。
14. **[agent/memory.py:603-605 + store 查询] 多个检索/格式化接口对合成、原始、人工、纠正来源没有统一类型契约。** 每个调用点自行决定 caveat，必然继续漏口。建议在 Store/Memory 层返回统一的 `source_kind/truth_status/display_label`，上层只格式化。

## 五、修复集 A-F 评审

### A. correct_memory / forget_memory

方向正确，是最高优先级，但当前方案还不够原子，也低估了多存储面的纠错。

- **status 列优于 importance=0。** importance 是相关性/显著性，不是真值；0 目前还会被 setter 钳到 1，查询也不排除。建议最小字段为 `status active|retracted|superseded`，可选 `superseded_by`、`corrected_at`。若不需要保留审计历史，直接硬删除比 importance=0 更简单可靠；但主库事故审计价值高，推荐 status。
- status 不能只加在 memories。至少 memories 与 cluster_facts 要统一 active 过滤；fact_clusters 的 summary 必须在撤销事实后重算或标 dirty。people.notes 是派生缓存，不应逐字文本替换。
- **不要直接让 correction 工具“编辑 notes 中的一句话”。** notes 是无结构 LLM 文本，局部替换容易残留同义错误或破坏句子。正确流程是：事务内撤销命中原子事实/合成行，写入 `origin=corrected, confidence=1.0` 的纠正事实，标记 profile dirty，立即停止注入旧 notes；主工具调用结束、LLM 锁释放后后台重合成，再原子替换 notes。纠正触发的重合成应绕过日常冷却一次。
- 需要覆盖 `profile_synthesis`、`fact_synthesis`、cluster_facts、cluster summary、notes；必要时关系档案也标 dirty。当前 A 只说“触发重合成”，在异步完成前仍会继续注入错 notes，应补“dirty 时不注入”。
- 工具可以简化为一个 `correct_memory(subject_qq, wrong_fact, corrected_fact='')`：corrected_fact 为空就是忘记。若保留两个工具，执行层也应共用一个事务服务，避免两套权限/匹配逻辑漂移。
- 权限设计基本正确：本人可纠正关于自己的事实；第三人仅 owner。执行侧必须复验，不能只靠 schema 是否注入。
- BGE 匹配应保守返回命中摘要和数量；没有证据 id 时不要批量撤销低相似项。新增 evidence_ids 后优先按来源定位。

### B. 合成冷却 + 排除合成计数

方向正确，但 `synth_done:{qq}` 固定 24 小时过粗：活跃用户一天内的明确新事实可能需要更新，纠正更不能等 24 小时。

建议使用统一的 `profile_last_success` 与 `profile_dirty`：日常计数/整合触发共享 6～24 小时成功冷却；纠正置 dirty 并允许一次绕过。计数用 SQL `COUNT`，只计 active 且非 summarized 的输入事实，不计 profile/fact synthesis，也不受 1,000 行上限。只有合成成功并原子换入后才更新 success；attempt 只用于失败退避。

### C. 合成行替换式写入

“替换快照”是正确语义，但不能笼统选 DELETE+INSERT 或 UPSERT：

- `profile_synthesis` 每人只有一条，是 singleton，适合 partial UNIQUE `(qq_id,key) WHERE key='profile_synthesis'` + UPSERT；稳定 id 也便于 embedding 与引用。
- `fact_synthesis` 每次是 2～5 条集合，不能对 `(qq_id,key)` 做唯一约束。应在**一个 Store 事务**里删除/撤销旧集合并 bulk insert 新集合，或用 generation id 切换 active generation。最小实现是事务化 DELETE+INSERT。
- 不能由 Memory 层逐条调用现有方法完成替换，因为每个方法各自 commit，崩溃时会留下“已删未写”或半套事实。
- Phase 2b 应按 `(qq_id,key,status)` 查全量或向量索引，不再用 top 100。普通记忆的语义合并和合成快照替换应是两个 API。

### D. 输出契约与清洗

必要，但“常见前缀正则剥离”只能做兜底，不能成为主要正确性机制。建议结构化输出（例如 JSON 的 `profile` + `key_facts`）并做 schema 校验；失败就不覆盖旧画像。清洗函数同时用于写入和读旧数据可以接受，但必须保留原始输出日志用于审计。

relationship 不应要求“未知就写未知”，应要求缺证据的字段省略。后处理只丢“整条是未知/不确定”的条目，不能粗暴删除含“未知”的真实复合句。

### E. 提取质量契约

共享规则、补上下文和 speaker role 都正确；**“confidence 恰为 0.7 一律丢弃”会误伤。** 0.7 既可能是模型偷懒默认，也可能是合法的弱证据，事实簇 prompt 还明确把“暗示”定义为 0.7～0.8。用浮点值猜模型意图不稳。

更优方案：

1. 字段缺失/类型非法与“显式输出 0.7”分开处理；缺失可拒绝，显式 0.7 保留为低可信候选。
2. confidence 进入 recall/合成门控：低于 0.75 的 semantic 不进入 notes/事实摘要和自动注入，但可保留供搜索时带 `~` 标记；episodic 可按较低权重保存。
3. 明确自述要求 0.9+；身份/关系/健康等高风险稳定事实要求证据 chat id，并对否定、引用、玩笑、测试做统一 validator。
4. 批次加入相邻糖糖回复并保留 role/chat id；不要再把全部文本统一标成“昵称：”。

这样既不丢失弱线索，又切断弱线索晋升为画像的路径。

### F. 注入侧收口

方向正确，但调用点不止拟议的三处。至少覆盖：私聊全量 notes、交叉上下文、`format_compact_memories()`、`recall_formatted()`、`_search_people()`、`_get_profile_and_recent()`、自治私聊、群人物关系图、工具 `search_memories` 的合成行。

独立警告行比括号 caveat 强。120 字截断是止损，不是正确性方案：若错误恰在前 120 字仍会注入，若正确关键信息在后面反而被丢掉。根治仍是 active/status、派生缓存 dirty、只从高可信原子事实重建、合成行不参与“真实事实”频道。

## 六、P0 是否顺带数据清洗

**需要，而且必须在新读写语义上线后立即做一次针对性清洗；否则代码修好后旧污染仍会继续被 recall/notes/search_facts 使用。** 不建议在修复前直接大范围删库，也不建议用一次 LLM 自动“判断所有真假”。

建议分两层：

1. **事故对象定向清洗（P0 同批）。** 先备份主库并导出待改行；对主人撤销 `id=7736`、`id=8289` 及所有含错误结论的 profile/fact synthesis；撤销“时政兴趣”簇及对应原子事实；将 `id=12478` 的“蓝发小妹”事件标 superseded；写入三条 owner 明确纠正事实（一直是开发者、蓝发小妹就是糖糖、关系是主仆）和两条明确否定（不爱特摄、不迷时政）；将 notes/relationship 标 dirty，重合成后人工验收。15 条旧画像和 63 条旧画像事实应整体退役，只保留一个新 active generation。
2. **全库机械清洗（后续批）。** 只做可证明安全的规则：同一人的多条 profile 只保留最新合格 generation；完全重复行合并；明显元前缀画像标 dirty；修复 fact_count；重建 embedding。近义事实、矛盾事实不要自动删，生成审核清单。

清洗脚本必须支持 dry-run、事务、行数断言、前后导出和可回滚；主库是运行中数据库，应停写或在维护窗口执行。

## 九、最终对齐

### 9.1 纠正回复误入 bot 自忆：成立，纳入批 2

我方补充复核后确认该遗漏成立。当前群聊与私聊分别在 `agent/handler.py:2033`、`agent/handler.py:2757` 对最终回复无条件调用 `_extract_self_memories()`；该方法在 `agent/handler.py:6307-6320` 只缓存回复字符串，累计五条后交给 `agent/handler.py:6322-6355` 的 `_extract_self_memories_llm()`。后者只知道文本来自“糖糖的回复”，提示词没有用户原话、工具调用记录或回复用途，因此“记住了：哥哥不爱特摄”可能被判断成糖糖自己的 opinion，并由 `remember_self(bot_qq=...)` 写进 bot 自忆。批处理还会丢失原回合边界，使事后纠偏更困难。

**最终结论：批 2 必须加入“纠正事实不得重复进入自忆”的闭环。** 这不是单纯补一句 prompt，而应使用回合来源信息做执行侧门控：

1. `correct_memory`/`forget_memory` 成功执行时，在本回合 `turn_actions` 或等价的回合结果对象上记录结构化标志（例如 `memory_correction_applied`），不要通过“记住了”“纠正”等中文子串判断。
2. `_extract_self_memories()` 接收带来源的候选项，而不再只收裸字符串；纠正/遗忘工具后的确认性回复不进入自忆候选。若一个回复同时包含独立承诺，宁可本回合不自动提取，也不要让用户事实跨主体写入 bot 自忆。
3. `_extract_self_memories_llm()` 的输入至少保留 reply id、scope 和用途；提示词补充“复述、确认或总结用户事实不是糖糖自己的观点”，作为第二道防线，但不能代替结构化门控。
4. 批 2 上线时扫描 bot 自忆中由纠正确认话术产生的既有污染，列入定向清洗候选；只凭相似文本不得自动删除，需按事故回合或人工确认撤销。

GitNexus 对 `_extract_self_memories_llm` 的上游影响分析为 **LOW**：1 个直接调用者、4 个受影响符号、1 个业务入口族；但其二级调用者同时包含群聊和私聊主流程，所以验收必须覆盖两种 scope。当前项目非 git 仓库，GitNexus 无法用 git 状态判断索引新鲜度；以上行号和行为以本次直接读取源码为准。

### 9.2 批 1 最终拆法

**拆分，不维持原六文件大批；但不采用“1a 写临时注入止血、1b 再重写 formatter”的边界。** 那会让同一输出路径连续修改两次，并可能留下两套截断/caveat 规则。最终按职责拆为：

- **批 1a：关系游标与重算风暴止血。** 只处理 `agent/store.py`、`agent/relationship.py` 及对应测试，修复字段加载成对性、成功游标、失败退避和 unknown-only 结果。该批可独立部署、独立回滚。
- **批 1b：统一 profile formatter，并一次迁完所有注入出口。** 以 `agent/protocols.py` 为单一格式化契约，再修改 `agent/memory.py`、`agent/handler.py`、`agent/handler_autonomy.py` 及测试。截断、独立 caveat、dirty 时禁注入、合成来源标签都由 formatter 决定；禁止各调用点复制局部规则。

这样每批都有完整行为测试，不把“实现”和“测试”拆开。1a 先阻止持续写放大，1b 再统一读侧止血；若线上事故仍在持续，可在同一维护窗口连续发布，但评审、测试和回滚仍保持两个提交/部署单元。

### 9.3 `fact_synthesis` 集合替换最终选择

**最终选择：事务化 DELETE+INSERT，不采用 generation id。**

理由如下：

- `fact_synthesis` 是可再生的派生快照，不是原始证据；审计历史应保留在 active/retracted 原子事实、纠正记录和清洗导出中，不必靠每代派生文本承担。
- SQLite 同一事务中的 DELETE 与批量 INSERT 对其他连接是原子可见的：读者只会看到旧集合或完整新集合，不会看到空窗和半套结果，已满足本项目当前一致性要求。
- generation id 会把复杂度扩散到所有查询、召回、计数、embedding、清洗和唯一约束；任何一个读路径忘记筛 active generation，旧污染就会重新出现。当前首要目标是收紧真值面，不应新增第二套版本选择语义。
- 集合项没有稳定 id 的业务需求。旧集合删除时应同步清理关联 embedding；新集合的文本和 embedding 可先准备，再由一个 Store 事务完成删除、批量插入及可用 embedding 写入。任一步失败必须整体回滚并保留旧集合。

实现约束：事务 API 必须是单一 Store 方法，按 `(qq_id, key='fact_synthesis')` 替换全量集合；Memory 层不得循环调用会各自 commit 的现有写入方法。若未来出现历史画像回放、跨节点并发合成或无停顿多版本发布的明确需求，再升级 generation id；目前它不是最小且足够的方案。
