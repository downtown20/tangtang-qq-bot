# 语音系统工程调研：可学习的开源项目（2026-08-24）

> 主人判断「当前修改有很多系统性问题」后，三个方向并行深读开源工程：
> ① GPT-SoVITS 官方（我们用的引擎）② xiaozhi-esp32-server（10.4k★ 完整语音对话工程）③ AstrBot（39.5k★）+ LangBot（17.5k★）及其 TTS 插件生态。
> 结论：系统性问题的根因和工程答案都已找到，整改分批次，批 A 是根因级最小改动。

## 一、五大系统性问题的三方答案（交叉验证）

### 1. 短句早停（0.44s）——根因已由官方 issue 定性

**根因**：`prompt_text='你好'`（2字）与 5.7s 参考音频严重不匹配。官方 Issue #1537/#160 明确定性「合成长度 < 参考音频长度 + 文音不匹配 = 参考音频泄露/输出异常高危组合」。短句 12 token EOS 极可能由此引起（模型在 prompt 语义与目标文本长度错位下不稳定）。

**官方两条路**：
- `prompt_text=""` 无参考文本模式（音色不受影响，官方 Issue #1051 确认）——**仅 v1/v2 支持**；v4（use_vocoder）会抛 NO_PROMPT_ERROR
- ASR 精确转写 5.7s 参考音频真实内容作为 prompt_text——v4 必须走这条

**配套发现**：官方默认 cut5 且 contributor 建议「切分拉满」（模型以短句训练）；本地 cut5 丢段（1.28s）可能是 prompt 错位下的表现——修 prompt 后 cut5 值得重测。官方对短文本兜底线是 4 字/6 音素，我们的句子都高于此线。

### 2. 质量检测——自造启发式已被官方社区否掉

官方 Issue #1067（contributor 集思广益帖）结论：**时长阈值只能抓「长空白」一类**，我们已两次因此误判。社区验证过的替代：
- **ASR 相似度打分选优**（Issue #1044 有现成工具思路）：合成 → 本地 ASR 转写 → 与目标文本相似度打分，低分重 roll。糖糖已有本地 ASR 能力，可行。
- **重 roll**：同参数重生成（生成式随机性可救，Issue #2324 承认无法根治）。
- xiaozhi 的 **Silero VAD 双阈值滞回 + 滑动窗口投票**（silero.py:88-105）：高阈值进/低阈值出/N/M 帧投票，「有效语音时长/期望时长」比 RMS 能量门更贴近「有没有真的说话」。

### 3. 进程管理——我们已修，方向与 xiaozhi 一致

xiaozhi：单 provider 内重试 ×5 + tts_timeout 超时 + LLM 层兜底文案，**从不因合成失败杀服务**。我们 got_200 分流后已对齐（截断/静音降级不重启；只有全程 502/连接失败才重启）。

### 4. 音频缓存——xiaozhi 与 AstrBot 两个对立答案

- xiaozhi：唤醒词回复按 `md5(voice)` 磁盘缓存 + 元数据 YAML + **过期后后台异步重建**（refresh_time）+ 15KB 文件大小门槛。
- AstrBot：**不做内容寻址缓存**——「聊天场景命中率低、维护成本高」，用容量上限（默认 1024MB）+ 10 分钟一轮按 mtime 删 30%（TempDirCleaner）。
- 结论：保留糖糖现有 md5 缓存（key 已含 speaker+speed，比 xiaozhi 强），补**容量上限清理**（抄 TempDirCleaner 思路）；高频固定话术可考虑「过期后台重建」（中期）。

### 5. 发送链路——「语音是装饰，文本是事实」

AstrBot/LangBot 共同铁律：TTS 失败/超时/空音频 → **原文本照发**（不拦截）；逐段 try/except 隔离失败；dual_output 可语音+文字同发。糖糖已是「文本正文 + 语音附件」双通道，方向一致；核对：所有 TTS 失败路径必须保证文本已送达（发送链路契约已有闸门）。

## 二、情绪决策——我们已对齐，微调即可

xiaozhi：LLM 回复**首字符 emoji** → EMOJI_MAP 查表（21 映射）+ 提示词硬约束「只能以一个白名单 emoji 开头」。LangBot 插件：LLM 改写文本时产出「(情绪)[细粒度标签]」→ 配置表映射 SoVITS emotion；关键词计分做 fallback。
糖糖现有：LLM 标签→显式参数→关键词→mood→normal + 3 分钟平滑——已是单一决策源链。可微调：协议层（protocols.py）加「回复开头最多一个情绪标签」格式约束。

### 批 B：Silero VAD 语音占比第三道检测

> **2026-08-25 退役说明**：慢速、拖音和角色声线触发了严重 VAD
> 假阴性，并出现 sherpa 环形缓冲状态错误。语音质量门、VAD 运行时代码、
> 专用探针及模型已从活动路径移除；以下内容仅保留为历史取证记录。

- 实现：sherpa_onnx 1.13.6 VoiceActivityDetector + silero VAD 模型（2.2MB，asr_models/silero-vad/）。懒加载单例持 MODEL_LOAD_LOCK；加载失败降级双检。
- 两个 API 坑（实测发现）：一次性投喂大数组只处理首块（任意时长检出固定 0.22s）→ 分块 512 喂；`front` 是属性、segment 时长 = len(samples)/16000。
- **判据修正**：最初用「语音时长 < min_dur」，实测后改为「语音占比 < 0.5 拦截」——正常合成音频占比 80-102%（1.04-7.56s 七样本实测），半截音频骤降 ~30%；占比判据与字数/语速无关，短句不误杀。
- 端到端实证：前 2s 语音+后 5.2s 静音的构造样本 → 拦截；完整音频 → 过；纯静音 → 双检拦。

### 批 C：运行中缓存清理

- xiaozhi「过期后台重建」砍掉——QQ 聊天场景缓存命中率低，属过度工程。

### 批 D 补充：情绪标签误标修复（2026-08-24 深夜，主人反馈触发）

**症状**：97 字温柔陪伴文本（「有人难过的时候……安安静静陪着也挺好的喵～晚上心情软软的」）被标「情绪=难过 音色=丛雨·sad」——难过声线配温柔内容严重打架。

**取证**：日志「97→97字」= 无标签剥离 = **LLM 没有标情绪标签**。真凶是决策链第三层 `classify_emotions` 关键词兜底——`kw in text` 子串匹配（sticker.py:55），文本话题词「难过」命中。这违反教训 #9/#10（关键词替 LLM 做决策），且**话题情绪 vs 说话语气是语义区分，任何关键词工程都修不好**（jieba/否定词过滤都救不了「有人难过的时候」）。

**修复（两处）**：
1. send_voice 描述加语义澄清：「标签是你说话时的语气、不是话题里的情绪——比如对方难过时用[温柔]或[悄悄话]陪伴，只有你自己真的难过才用[难过]」——防 LLM 主动标错。
2. 决策链移除关键词兜底：`LLM 标签 → 显式参数 → 关键词 → mood → normal` 改为 `LLM 标签 → 显式参数 → mood → normal`——LLM 没表态时语气由糖糖自身状态（mood）决定，系统不做文本情绪判断。classify_emotions 保留（表情包选图仍用，handler.py:4961/4964）。注释写明「⚠️ 不要加回」。

**闸门**：TestVoiceEmotionTagContract 新增两条——描述澄清文本断言 + AST 检查 `_send_voice_reply` 内无 classify_emotions 引用（防「好心修复」加回）。

**验证**：523 测试绿（+2）+ pyflakes undefined 清零。需重启 bot 生效。

## 七、QQ 语音识别修复：SILK v3 解码（2026-08-24 深夜）

**症状**：主人发语音，日志 `⚠️ ffmpeg 转码失败: ...xxx.amr.amr`（三次），bot 听不懂语音。

**取证链（不猜，全实测）**：
1. 转码失败路径在 asr.py `_convert_to_wav`——ffmpeg 非零退出。
2. 用 NapCat `get_record` API 重下当天三条失败语音（bot 同款 token/header）——**全部字节头 `\x02#!SILK_V3`**：QQ 语音是 SILK v3，文件名带 `.amr` 后缀但内容不是标准 AMR。
3. 本机 ffmpeg（N-125350 build）**无 silk 解码器**（`-decoders | grep silk` 空），对 silk 转码报 "could not find codec parameters"——转码必失败，不是偶然。
4. 修复路线实测：`pilk`（QQ bot 生态标准 silk 库，pip 可装）`silk_to_wav(rate=16000)` 解码真实语音 → 8.64s 完整转出「最近的话前几天在去旅游去了去深圳看了一下看到我妈然后买了很多东西你可以听到我的说话吗」——端到端全通。

**修复**：
- asr.py `_convert_to_wav`：魔数 `#!SILK_V3` 检测 → pilk 解码（`asyncio.to_thread`，16kHz mono wav）→ 直接走既有 SenseVoice 链；pilk 未安装 → 警告降级返回 None（不炸）。
- handler.py `_transcribe_voice`：修 `.amr.amr` 双后缀——file_id 已含扩展名，直接用 `Path(file_id).name`（防路径注入）。
- 依赖：requirements.txt L2 加 `pilk>=0.2`；tools/体检.py OPTIONAL_DEPS 加 pilk（笔记本同步纪律）。

**验证**：527 测试绿（+4 silk 测试：魔数路由/无 pilk 降级/非 silk 不触发/真实 pilk roundtrip）+ pyflakes undefined 清零。**需重启 bot 生效；笔记本需 pip install pilk。**

## 八、情绪标签强制决策：emotion 必填枚举（2026-08-24 深夜）

**症状**（主人反馈）：「语音质量下降了，主要是情感问题，发的语音都很局促统一」——日志实证：25 字活泼文本「行～那我现在就发一条，你仔细听听这情绪自不自然喵！」情绪=无 → normal 音色。

**根因（上一轮修复的副作用，诚实复盘）**：移除关键词兜底后，情绪决策链 = LLM 文本标签 → mood → normal。但 send_voice 工具无参数，标签协议描述写着「（不写用默认语气）」——**给了 LLM 跳过情绪决策的许可**，LLM 几乎不写标签 → 大量语音兜底 mood（中性居多）→ normal → 全部统一。关键词兜底曾提供色彩（代价是话题词误标），移除后色彩来源断了——主要矛盾从「关键词误标」变成「LLM 没有逐条决策情绪」。

**修复**：
- send_voice 工具 schema：`emotion` 升级为**必填枚举参数**（enum = EMOTION_SPEED.keys() 单一来源）——LLM 每条语音必须决策语气，白名单枚举防自创词（比 prose 约束强得多）。
- 描述保留语义澄清（语气≠话题情绪：对方难过时选[温柔]/[悄悄话]，自己难过才选[难过]）+ 语音模式文本标签白名单。
- `_execute_tool` send_voice 分支：emotion 存入 `turn_actions["voice_emotion"]`。
- 群/私发送路径：注入为文本标签 `[emotion]` 前缀——走 extract_emotion_tag 既有链路，**情绪平滑照常生效**（若走 _send_voice_reply 的 emotion 参数会绕过平滑）；标签在发送前剥离，不泄漏到文本消息。
- 语音模式（/语音 持久模式）无工具调用——走文本标签协议，描述已提示。

**验证**：531 测试绿（+4：turn_actions 存储/漏传不炸/禁用拦截/schema 必填+枚举单一来源闸门）+ pyflakes undefined 清零。**需重启 bot 生效。**

## 四、反面教训（调研中确认的勿抄项）

- xiaozhi 对合成音频零质量校验（我们领先）；缓存 key 不含音色（我们 key 含 speaker ✓）；无多 provider 降级链（我们有 ✓）
- AstrBot GSVI 适配器的 emotion 是配置死值（痛点②的缺口，框架没解决，LangBot 插件层解决）
- 官方无任何重试逻辑——重试是我们客户端的正确保护
