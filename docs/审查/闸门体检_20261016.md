**⑨ 为什么是 B**：`tests/test_ui_anim.py:24-36` 的判据是

它同时在找两个字符串——**只要调用写成 `s.setCurrentIndex(...)`（局部变量持有 stack），两个条件就都不成立，闸门放行**。这正是本仓教训 #36（「经变量或属性链到达的调用全丢」）在**判据侧**的翻版。

## 六、建议的机器化纪律（怎么把「新闸门必须自带阳性对照」变成能自动检查的东西）

### 6.1 已经存在的两条（我实测验证过它们真的会红）

| 组件 | 我做的实测 | 结果 |
|---|---|---|
| `tools/变异对照.py`（T2.11，160 行） | `--spec` 对 `main.py` 做两个变异，靶是 `tests/test_vision_provider_consistency.py` | `R1_rollback_to_local: RED OK` / `G1_comment_only: GREEN 假变异` / `还原核对：sha256 672f919db8539ddf == 改前 OK` / **EXIT=2** ✅ **它会把假变异判成不合格** |
| `tests/test_mutation_harness.py`（98 行自检） | 读源码复核 + 逻辑上它用 `tmp_path` 夹具（**不动持久文件**） | 6 条全是阳性对照：真变异→RED、空变异→退出码 2、锚点歧义→拒绝、`PYTHONIOENCODING=latin-1` 注入→仍工作、基线红→拒绝 ✅ |

**这两条就是「纪律」的机器化主干**，设计是对的：**判据的判据也要有对照**。

### 6.2 但它有三个洞（实测/读码证据）

1. **任何非零 pytest 退出都算 RED**（`tools/变异对照.py:67` `return out.returncode != 0, ...`）。
   实测（临时夹具，不动仓库）：

   `
   M_SYNTAX: SMALL = "small" → SMALL = "small       （制造语法错误）
   → M_SYNTAX: RED OK       ← 这里的「红」只是 mod.py 语法崩了，测试根本没跑到断言
   `

   **建议**：`_run_tests` 解析 `-q` 输出里的 `FAILED <nodeid>` 集合，要求它非空**且**确实是断言失败；纯 collection error 单独报 「INVALID（变异把目标改成了不可导入）」，**不计入 RED**。
2. **它只证明「变异后红了」，不证明「红在对的那条断言上」**。
   **建议**：spec 里加 `expect_fail: ["tests/x.py::test_y"]`，工具核对实际 FAILED 集合 == 期望集合，不等即不合格。这样每个变异都自带「红在哪一行」的声明。
3. **`--allow-green` 是无审计的逃生门**（`tools/变异对照.py:91,145`）。
   **建议**：`--allow-green NAME="理由"`，理由写进 `--json` 结果，CI 里 grep「无理由的 allow-green」。逃生门可以留，**但必须留痕**——否则它会变成「顺手让 CI 绿」的后门（教训 #30 同族）。

### 6.3 真正缺的那一块：**闸门自身的锚点巡检**（针对 B 类的病根）

B-1 的成因不是「变异太弱」，而是**判据引用的字符串在目标文件里出现多次**——`_batched_events` 在 `handle_group_message` 里出现 2 次，判据用 `in` 就永远为真。
**可机器化的一条固定巡检**：

1. 对每个「读源码做判据」的测试函数，用 **AST 提取它断言里出现的字符串字面量**（形如 `assert "..." in body` / `source.count("...") == n`）；
2. 对每个字面量，在**它监视的目标文件**里统计出现次数 n_occ；
3. 规则：
   - **n_occ == 0 → 红**（锚点已腐烂——这就是教训 #30「正则从没匹配过」的字符串版）；
   - **n_occ > 1 且判据语义是 `in` / `count(...) == 1` → 黄（报告，不红）**：「该串在目标文件出现 N 次，判据可能被别处糊过去」——**M1/B-1 会在这一步被提前抓出来**；
   - n_occ == 1 → 通过。
4. 现有例证：`"_batched_events"` 在 handler.py 出现 **4 次**（3283/3495/4756/4895）→ 命中黄灯；`key="promise",` 出现 **1 次** → 通过；`_check_catch_up_query` 出现 **0 次**（这正是「退役短语不得复活」那条判据的正确形态——0 是它的期望，也是它必须带说明的原因）。
5. **它自己的局限（必须先写下来）**：字面量一旦被 f-string 拼接、变量化、或跨行拆开就漏（教训 #36 同族）；也不能判断该串是否出现在**正确的分支**里。**它是报警器，不是判据**——黄灯必须有人看一眼。

### 6.4 把「阳性对照」变成每个闸门的标准件

见第四节末的通用模板。要点：
- **阴性对照 + 阳性对照成对出现**：干净样本必须过，种了违规的必须红。
  阴性对照能抓「锚点腐烂」，阳性对照能抓「判据失效」。**只做阳性对照是半条纪律。**
- 既有范例：`tests/test_integration_contract.py` 的 `test_gate_sees_a_planted_dead_member` / `test_gate_sees_a_planted_dead_method`（用 `agent/__planted__.py`）与 `tests/test_mutation_harness.py`。
- **局限**：夹具是**简化世界**——tmp_path 里的 mini 目标可能丢掉真实文件的复杂度（多重重名、跨行格式）。所以**夹具对照通过 ≠ 真文件对照通过**：夹具对照做 CI 常驻，真文件对照做发布前一次。

### 6.5 扫描面（教训 #31 的机器化）

- **反面教材已修**：发布扫描器只扫 7 种后缀 → 二进制兜底 + 「匹配字节必须整体合法 UTF-8」判别器。
- **正面要求**：凡是「扫某个目录」的判据，必须**打印实际扫描的文件数**（`tools/静态检查.py` 已这么做，且会因 pyflakes 抱怨立刻红灯——这是本项目最好的一条实践），并且要有**「扫描数为 0 即红」的下界断言**。
- 本次实测的数字：设备闸门扫 **161 个 .py**；installer 差集只有 **3 个元素**；songs 闸门 `checked=16`；vision 三文件 stale-local 命中 **0 行**（0 是它期望的结果——**正因为是 0，才更需要阳性对照**）。

## 五、建议的机器化纪律（可落地的那部分）
