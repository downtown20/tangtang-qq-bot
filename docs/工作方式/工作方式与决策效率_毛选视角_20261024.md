# 工作方式与决策效率 —— 毛选视角

> 2026-10-24。回答四个问题：① 如何更高效地工作？② 市面上有没有可学的地方？
> ③ 如何在上下文没爆满时尽量自己决策、减少主人的决策依赖？④ 上下文预算怎么管？
> 用毛泽东的方法论作分析框架——不是套意识形态，是因为它解决的正是我们当下的
> 处境：一个极小的团队（一个人 + 一个 AI）、资源有限（我的上下文、你的注意力）、
> 长期复杂、信息永远不全。

---

## 一、《实践论》：我们的第二次飞跃没有制度化

认识有两次飞跃：**感性 → 理性**（从具体经验提炼规律），**理性 → 实践**
（用规律指导行动，并在行动中修正规律）。

对照我们的实际：

- 第一次飞跃做得不差：37 条教训、口径字典、预测台账、变异对照——规律写下来了。
- **第二次飞跃没有被制度化**：教训写在表里，但下次照样踩。2026-10-24 一天之内
  我犯了三处同族错误（口径混淆 / 漏读既有约束 / 判据与入口不同源），而这三条
  都能在既有教训里找到对应（#18 修复假设先取证、#35 文档与代码分家、
  #37 假绿）。

**结论**：效率问题不是「做得慢」，是**同一个错误没有被机制拦住**。
所以效率的第一条不是提速，是「把已经提炼的规律变成机器闸门」——
能写成测试/闸门/字典的，绝不留在教训表里靠自觉。

毛选的说法：**「抓主要矛盾」**。当前的主要矛盾不是记忆不够多（7,203 条可注入），
而是「同样的判断错误反复出现」。次要矛盾（覆盖率、画像数）可以等。

## 二、三条效率原则（从毛选提炼）

1. **不打无准备之仗**（《论持久战》）
   任何要改生产数据的动作，先小批试点、抽样、再全量。今天四个批次
   （411 → 1,627 → 24 → 23 人）全是这个打法，0 误判。
   反面：不做 dry-run 直接 apply，等于「浪战」。

2. **集中优势兵力打歼灭战**
   一次只推进一件事，做完、验证完、可回滚，再下一件。
   反面：同时开五个半成品——那是「全线出击」，我们没那个兵力（上下文）。

3. **伤其十指不如断其一指**
   宁可把「不确定性注入」做透（测试 + 变异 + 开关 + 观察），
   不要同时铺开「未闭合事件 + 叙事主线 + 分域画像」三条线。
   这也是我这轮把「语义回挂全量」按下的原因——它和不确定性注入抢注意力。

## 三、问题二：市面上可学的东西（按「学什么」分类）

《论持久战》反对两种论调：速胜论（一次重构就完美）和亡国论（这项目没救）。
我们两者都不是：**这是持久战，积小胜为大胜，每阶段有明确目标**。

| 我们可以学的 | 对应我们已有的 | 差距 |
|---|---|---|
| SRE 的事后复盘（postmortem，只谈事实不谈责任） | 37 条教训表 | 我们有「教训」，缺「复盘格式」（时间线 + 触发条件 + 拦住它的闸门） |
| ADR（架构决策记录） | 决策台账 + 口径字典 | 台账刚建，ADR 还没有 |
| **mutation testing**（改坏必须变红） | `变异对照.py` | **已经做了，而且比多数项目做得彻底**——这是我们的强项，别丢 |
| **golden set / eval harness**（记忆质量的评测集） | 无 | **最大缺口**：现在判断「记忆变好」全靠覆盖率，没有「质量」评测 |
| feature flag / 灰度发布 | config 开关 | 机制有，习惯没养成（不确定性注入要用它） |
| ACP（模型驱动的上下文压缩） | DSH 内置压缩（有损） | 见第六节 |

**向谁学的判断**：学**方法论**（复盘格式、ADR、flag），不学具体工具；
学**同类项目的架构**（见第六节），不学它们的实现细节——我们的记忆系统
是自己的资产。

## 四、问题三：如何自己决策，减少你的依赖

这是本轮最重要的一问。直说结论：

> **自主决策的能力不取决于上下文大小，取决于「外部记忆」的质量。**

理由是一个结构事实：**我的上下文每次会话都会重置**。所以「我记得多少」这件事
根本不能靠上下文——把判断依据放进上下文，下次就没了。真正决定决策质量的，
是**磁盘上那四样东西**：

| 外部记忆 | 作用 | 状态 |
|---|---|---|
| 口径字典 | 数字的含义（今天三处错误的根因） | ✅ 刚建 |
| 预测台账 | 我过去的判断偏差（校准） | ✅ 刚建，4 条待回填 |
| 教训表 | 踩过的坑 | ✅ 有 37 条 |
| 测试/闸门/变异 | 机器拦住，不靠自觉 | ✅ 成熟 |

**所以「提高自主决策率」的路径是：把更多判断依据从工作记忆搬到长期记忆。**
每搬一样，我就能多自主一步，因为我不再需要「这次会话记得」才能判断对。

《党委会的工作方法》里有三条正好对应：

1. **「胸中有数」**——对情况和问题要注意到数量方面，要有基本的数量分析。
   → 口径字典。没有口径的数字比没有数字更危险（今天错误 #2 就是这样）。

2. **「安民告示」**——开会要事先通知，让大家知道要讨论什么。
   → 预测台账。我动手前先公开「我预测 X=N、置信度中、依据是 Y」，
     你不需要读代码就能判断我要做什么、值不值得。

3. **「学会弹钢琴」**——十个指头都要动，但要有节奏，不能乱弹。
   → L1/L2/L3 分级。该自主的（技术、工具、测试）我全自主；
     该你拍板的（人格、主动性、花钱量级）一次问清。

**什么时候仍然必须问你**（这不是「依赖」，是分工）：
《关于领导方法的若干问题》说「一般号召与个别指导相结合」。
- **一般问题**（技术债、工具、测试、记忆结构）→ 我自主 + 事后汇报；
- **个别问题**（糖糖应该是什么样的人、她要主动到什么程度、值不值得为某件事
  花钱）→ 只能你拍板。因为这类问题的判据是「你的体感」，不是数据。
  数据能告诉我「发生了什么」，告诉不了我「好不好」。

分工的目标不是「把我变成不需要你」，是**把你从技术决策里解放出来，
只保留价值决策**。你今天的三个决策（陪伴者定位、亲密度满级判据、预算授权）
就是最好的例子——这三个决定方向的判断，我做不了。

## 五、问题四：上下文预算怎么管

**关键认知：指导文档是每轮注入的，它的长度直接吃上下文预算。**
所以「合并 CLAUDE.md / AGENTS.md」不是美化，是省钱——这解释了为什么
billion-context-dsh 的文档里专门有一条：被压缩的注入行会被宿主**立刻重注入**，
形成「压缩→重注→再压缩」的死循环（他们的 issue #71）。

四条规则：

1. **分层**：常驻注入的只放「不看就会做错」的东西；考据放 `docs/`，按需读。
2. **压缩要有标记**：压缩后的是「我写的摘要」，不是原文。billion-context-dsh
   会强制给摘要加 `[Model-written summary — not user words]`——防的就是把摘要里
   的义务句当用户原话执行。这条我们也该学（`<背景·标签>` 已经在做类似的事）。
3. **可恢复**：压缩不是删除。ACP 的 `decompress` / `search_context` 让被压缩的
   内容可检索、可恢复。
4. **别让压缩吃掉规则**：CLAUDE.md 里的铁律如果被压缩掉，我下一轮就不知道了。

## 六、插件调研结论（2026-10-24 实测）

调研对象：你点名的 `billion-context-dsh`、`ds-bot`，以及顺带发现的几个。

### 6.1 billion-context-dsh —— 值得装，但要选时机

[GitHub](https://github.com/Tyan66666/billion-context-dsh) ·
[npm](https://www.npmjs.com/package/billion-context-dsh) ·
[插件目录页](https://dshbase.com/zh/plugins/billion-context-dsh/) · 146 stars · MIT

**它解决的问题，正是我说的「别让上下文吃掉判断力」**：现在的 DSH 压缩是
**自动的、有损的**（内置 `compaction-basic` 在 80% 时自动摘要，我无法干预）。
装上之后变成 **ACP 模式**：

- 给模型四个工具：`compress`（我写摘要替换一段范围）/ `decompress`（恢复原文）/
  `search_context`（在被压缩的块里检索）/ `acp_status`（看上下文构成）；
- **「只建议、不强令」**：到阈值只 nudge 我一句「该压了」，压不压、压什么由我定；
- 摘要由**我自己写**（不额外调一次 LLM 摘要），能保留文件路径、决策、错误信息；
- 压缩范围成为 checkpoint，**原文仍留在 append-only 日志里**，可恢复。

对我们这种「一天跑四个批次 + 大量取证 + 长期多轮」的工作，契合度很高。

**但有三条硬约束，不能无视**：
1. 作者明确标注 **「测试版，请勿用于生产环境」**（v0.2.27，DSH 本身也是 beta）；
2. 装完**必须重启 dsh**——会中断当前会话；
3. 与 DSH 版本有**严格兼容区间**（peer: `>=0.1.5-alpha.1 <0.2.1-0`），
   装前必须 `dsh --version` 核对。

**我的建议**：装。但**不要现在装**——在这一轮工作收尾、准备开新会话之前装。
理由：它替换的是上下文管理器（会话的心脏），装错会让会话起不来；
而现在的会话有价值（正在执行的记忆工程）。回滚方式很清楚：
profile 里禁用 `compaction-acp`、重新启用 `compaction-basic`。

命令（供你执行，我不该自己改 `~/.dsh` 的 profile）：
```bash
dsh --version                                  # 先核对兼容区间
dsh plugin --profile web add billion-context-dsh
# 装完重启 dsh，新会话里让我调 acp_status 自证
```

### 6.2 ds-bot / DeepSeek-Bot —— 参考架构，不直接用

- [Fei2411/DeepSeek-Bot](https://github.com/Fei2411/DeepSeek-Bot)：一队长期存活的
  bot，有主 bot、bot 间消息、群聊。
- [BotHarness/DeepSeekBot](https://github.com/BotHarness/DeepSeekBot)：个人 bot 团队，
  持久记忆 + 身份 + 权限，插件扩展。

**为什么值得看**：它们解决的是「多 bot 长期存在」——与我们「一个 bot 长期存在」
是同一类问题（身份连续性、记忆归属、权限边界）。**值得学的点**：
bot 间消息的协议设计、权限模型；**不值得照搬**：多 bot 的复杂度我们现在不需要
（单脑架构是我们的原则，加 bot 会破坏它）。

### 6.3 顺带发现

- `dsh-context`（[2121 stars, 已验证](https://dshbase.com/zh/plugins/dsh-context/)）：
  记忆/检索层。**不需要**——我们有自己的记忆系统（22,571 条），换掉等于放弃资产。
- `dsh-ctxopt-compaction` / `deepseek-harness-compaction-ui`：压缩的替代/UI 变体。
  前者与 billion-context-dsh 是同类竞争方案，后者只是界面。**先只评估一个**，
  不要同时装两个同类后端（ACP 文档明确警告：同一 realm 两个后端会冲突）。

## 七、文档合并的原则（《反对党八股》）

《反对党八股》前三条罪状，正好是我们的文档病：

1. **「空话连篇，言之无物」**：37 条教训里有重复/过时条目，每轮注入都付一次成本。
2. **「装腔作势，借以吓人」**：技术文档里大量「为什么这样改」的考据——
   对执行者有用，对**每轮注入**有害。
3. **「无的放矢，不看对象」**：`CLAUDE.md` 的读者是「接手的 AI」，`AGENTS.md`
   的读者是「Codex 启动时」，两者对象不同，内容却大量重复。

**合并方案（低风险优先）**：

| 文件 | 处理 | 理由 |
|---|---|---|
| `CLAUDE.md` | **不动结构**，开头加「文档地图」（哪份文档管什么） | 它是核心资产（37 条教训 + 铁律），重写风险 > 收益 |
| `AGENTS.md` | **瘦身到 ~40 行**：删掉重复 CLAUDE.md 的环境/验证/铁律摘要，只留 Codex 独有的审查协议 + 工具清单 + 接手第一步 | 它每轮被 Codex 注入，重复内容是最贵的冗余 |
| `docs/工作方式/` | 新建：本文件 + 工具索引 | 考据和工作方法放这里，按需读，不占常驻预算 |

**为什么不是「彻底合并成一份」**：Codex 启动时自动读 `AGENTS.md`，这个文件名是
硬约定；而 `CLAUDE.md` 是主事实源。强行二合一等于让 Codex 每轮多读一份长文档。
**分层比合并更省**——这是判断，不是懒惰。

## 九、一句话总结

**效率不来自更快的手，来自更少的重复错误；自主不来自更大的上下文，
来自更硬的外部记忆；决策正确率不来自更聪明的判断，来自更诚实的台账。**
