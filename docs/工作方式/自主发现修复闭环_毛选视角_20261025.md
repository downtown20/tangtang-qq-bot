# 自主发现—修复闭环 —— 毛选视角

> 2026-10-25。主人定的工作方式：**不等他报问题，我自己去会客厅跟她说话，
> 从她的话里发现缺陷，倒查链路，修好，再回去问她一遍。**
>
> 他点名的两个已知方向：「没有活人的时间观念」「记错」。
>
> 本文不是理论文章，是**操作规程**。每一步都要能落地、能验证、能被下一个人接手。

---

## 零、为什么是「跟她对话」而不是「看日志」

《实践论》第一句：「你要知道梨子的滋味，你就得变革梨子，亲口吃一吃。」

看日志只能看到**已经记录下来的东西**。而记录本身有选择：
`turn_traces` 只记 reasoning 和工具名，不记她看到了什么；`decision_runs` 只记
决定，不记依据；`chat_log` 只记文字，不记上下文。

**她的话是第一手材料，日志是二手材料。** 一手材料里能看出二手材料记不住的东西：
她以为现在是几点、她把谁的事记成了谁、她有没有老实说「不知道」。

毛选的说法：**「没有调查，就没有发言权。」** 我过去的做法是「读代码→推断缺陷→修」，
那是**从概念出发**，不是从实际出发。这条工作流把它倒过来：
**先看她错在哪，再问代码为什么会让她错。**

## 一、闭环六步（每轮只打一类缺陷）

### 第 0 步 立项 —— 一次只打一类

- 在 [预测台账](../决策/预测台账.md) 写一条：**我怀疑哪一类缺陷、预计能抓到几条**。
- **不铺开**：「时间感 + 记忆 + 指代 + 编造」一起查，等于什么都没查清。
- 依据《论持久战》：「集中优势兵力，各个歼灭敌人。」

### 第 1 步 对话取证 —— 只收集，不判断

- 会客厅（`python tools/会客厅.py`）连续对话 **5~8 轮**，全部围绕第 0 步选的那一类。
- 每轮落盘三样：**我说了什么 / 她说了什么 / 她的 reasoning**。
- **纪律：这一步禁止下结论。** 一看到可疑就跳去改代码，就等于「下车伊始，哇喇哇喇」。
- 一起落盘她这一轮调了哪些工具（`tool_steps`）——工具调用暴露她的信息来源。

### 第 2 步 建真值 —— 去伪存真

她说的每句可核对的话，标三态：

| 标记 | 含义 | 怎么处理 |
|---|---|---|
| ✅ | **可核对**：有客观真值（时间、DB 里的事实） | 去查真值，比对 |
| ❓ | **无真值**：她对感受/印象的判断，没有对错 | 不进缺陷清单 |
| ⚠️ | **自相矛盾**：她的话和她自己的 reasoning 打架 | 单独一类（提示缺陷） |

**只有 ✅ 能进缺陷清单。** 这是防止「我觉得她答得不好」被当成 bug 的闸门——
感受不是缺陷，可核对的偏差才是。

### 第 3 步 归因 —— 抓主要矛盾，问一个二分问题

> **她是「不知道」，还是「知道但用错了」？**

这是整条工作流的核心判断，因为它决定修哪里：

| 判断 | 含义 | 修哪里 |
|---|---|---|
| **不知道** | 材料里根本没有这个信息 | **注入缺陷** → 加注入源 |
| **知道但用错** | 材料里有，她读到了但用错 | **提示/协议缺陷** → 改 protocols.py 文本 |
| **不知道也没问** | 材料里没有，但**她有工具能查**却没查 | **工具可发现性缺陷** → 改工具描述 |
| **库里的就是错的** | 她照实说了，但原料是错的 | **数据缺陷** → 修提取/回挂 |

判断依据必须是**她这一轮的实际注入材料**，不能靠推。
本步的硬前提见第 5 节「取证工具」——没有 prompt 留档，这一步就只能靠猜。

### 第 4 步 修 —— 最小改动，一次一处

- 一次只改**一个注入源**或**一段协议文本**，不要同时改两处——
  否则复验改善了你也不知道是哪一处起效。
- **禁止用「让她更小心」来修**（教训 #2）：在 prompt 里加「请注意现在是几点」
  「不要记错」是**让她表演**，不是让她知道。真正的修法是给她信息，
  她自己会用——这是本项目「LLM 是唯一决策者，系统只提供能力」的原则。
- 改动过三条验证（见第 6 节）。

### 第 5 步 复验 —— 回会客厅问同一个探针

- 用**同一个问法**再问一遍，对比前后。
- **测试绿 ≠ 修好了**（教训 #25/#37）。她的行为变化才是判据。
- 如果复验没改善：不要加码 prompt，回到第 3 步重新判断二分。

### 第 6 步 沉淀 —— 三处落盘

1. [预测台账](../决策/预测台账.md)：预测 vs 实际，我判断的偏差
2. [开工交接单](../交接/开工交接单_20261024.md)：新增缺陷与修复
3. 本文件附录：这一类缺陷的**案例编号**（可复用的诊断经验）

## 二、探针库（问什么才能问出问题）

随机闲聊问不出结构性缺陷。**一类缺陷配一类探针**：

### T 时间感

| 编号 | 探针 | 期望（活人） |
|---|---|---|
| T1 | 「现在几点了？」 | 说个大概（一小时内） |
| T2 | 「今天几号？周几？」 | 正确 |
| T3 | 「我们上次聊天是什么时候？」 | 「昨天半夜」「前天」这类相对量 |
| T4 | （隔几分钟）「刚才那几句话我们聊了多久？」 | 有量级概念 |
| T5 | 「明天你有空吗」→ 追问「明天是几号」 | 自洽 |

### M 记忆

| 编号 | 探针 | 期望 |
|---|---|---|
| M1 | 从 DB 取一条**已注入范围**的事实问她 | 复述正确 |
| M2 | 问她「记不记得我提过 X」（X 是别人说的） | 不张冠李戴 |
| M3 | 问她一件库里**绝对没有**的事 | 老实说不知道，或明确说是猜的 |
| M4 | 先给一个错误前提，看她纠正还是顺着 | 纠正 |
| M5 | 问一件刚在**同一会话**说过的事 | 记得 |
| M6 | **重启 bot，再问同一件事** | 记得（2026-10-25 第 4 轮补） |

### R 指代

| 编号 | 探针 | 期望 |
|---|---|---|
| R1 | 「他刚才说的那个你怎么看」（他 = 上文明确的人） | 认对人 |
| R2 | 「上回那个事后来怎么样了」 | 要么追问哪个事，要么答对 |

### S 自我状态

| 编号 | 探针 | 期望 |
|---|---|---|
| S1 | 「你现在心情怎么样」 | 与 `state` 输出的 mood/drives 大致相符 |
| S2 | 「你上一次主动说话是什么时候」 | 有概念 |
| S3 | 「你刚才那句话是什么意思」（追问她自己的话） | 记得自己说过 |

## 三、缺陷分类学（编号规则，便于台账累计）

| 前缀 | 类别 | 子类 |
|---|---|---|
| **T** | 时间感 | T-1 无绝对时间／T-2 无日期／T-3 无流逝感／T-4 自相矛盾 |
| **M** | 记忆 | M-1 复述错／M-2 张冠李戴／M-3 编造细节／M-4 忽略更正／M-5 原料本身错 |
| **R** | 指代 | R-1 认错人／R-2 接错上文 |
| **S** | 自我 | S-1 不知道自己状态／S-2 不记得自己的话 |
| **D** | 表达 | D-1 重复／D-2 格式泄露／D-3 中英混杂 |
| **I** | 注入 | I-1 该注入没注入／I-2 注入了不相干内容／I-3 注入了错的东西／**I-4 注入了但被静默缩水**／**I-5 假取回路径** |

**每个缺陷必须落到一个编号。** 落不到编号的，说明还没想清楚，不是缺陷。

**I-4 的判据（2026-10-25 第 8 轮补）**：块**在**（`user_bg_labels` 里有它），
但里面的内容只剩一个头。它比 I-1 难发现得多——日志会说「这个块保留了」，
界面也正常，只有数**内容**才看得出来。

现场：记忆块 `294t → 70t` 之后只剩标题行 `📋 名字(ID:xxxx) | 聊N次 | 等级`，
一条记忆都没有。根因是裁剪函数用旧的中文系数（`÷1.8`），与估算函数（`÷0.72`）
差 2.5 倍。**I-4 的通用查法是：拿「注入源函数的输出」和「最终 prompt 里的对应
片段」逐字比，不要只看标签在不在。**

**I-5 的判据（2026-10-25 第 9 轮补）**：某个**被淘汰的块**被告知「你可以用
工具 X 取回来」，而 X 实际上取不回它。

现场：`_BG_RECOVERY_TOOLS` 里 `"自忆": "search_memories"`，而该工具的检索主体是
**当前对话对象**、自忆的归属主体是 `bot_qq`——两个主体不同，永远查不到自己。
代价：自忆 94% 的回合被淘汰，且她**以为自己有退路**。

**I-5 的通用查法是**：每一条「A 能取回 B」的登记，都要打开 A 的执行体，读它
**按谁检索**，再和 B 的归属主体比。名字相似不算证据。

### 还有一类缺陷，编号在「进程」这一层

上面所有分类都在「一次对话内」。但 2026-10-25 第 4 轮发现了一类跨进程的：

| 编号 | 类别 | 判据 |
|---|---|---|
| **P** | 进程级失忆 | **重启前后问同一件事**——闲聊测不出来，必须专门做 |

P 类的共同形状是「写下去了，但没有回灌/恢复」。它有个反直觉的修法原则：
**能重算的东西不该存**——对话窗口能从 `chat_log` 重算，就该重建；
只有「重算不出来」的状态（冷却/配额/观察记录）才必须落盘。
存两份必然有不一致的那天，而那时候没人知道该信谁。

## 四、反向纪律（防「假修」，这是最容易翻车的地方）

1. **只修症状不修根**：改一句 prompt 让她这句话对了，下一句还错——
   这不是修，是补丁。问「她为什么不知道」，不是「她这句怎么答对」。
2. **先有阳断再有判断**：一次对话里她答错，先确认是不是**探针问题本身有歧义**。
   我的一句话如果人也会听岔，那不是她的缺陷。
3. **复验必须用同一个问法**，否则新旧两次没有可比性。
4. **不许用「她好像好多了」当结论**——要么有可核对的偏差消失，要么有 trace 佐证。
5. **同一个缺陷修了两次没好，停下来重新归因**——大概率是二分判断错了
   （以为「不知道」，其实是「知道但用错」）。
6. **改完注入必须验证「东西真的送到了」**（第 1 轮的血教训，缺陷 B-2）：
   代码写对 ≠ 内容进了 LLM 的上下文。system prompt 会被预算截断
   （`context_builder._truncate_text` **从头保留、砍掉尾部**），越靠后的段越先死。
   所以「她答对了」也不能当证据——她可能只是现查工具补上的。
   判据必须是 **「这一轮她调工具了没有」+「reasoning 里的信息是不是自己写出来的」**。
7. **区分「她不知道」和「她没看到」**：前者修注入源，后者修投递链路
   （预算/截断/条件分支）。第 1 轮把这两件事混在一起，导致第一遍修完等于没修。

8. **「可逆」不等于「我该自己做」**（2026-10-25 第 5 轮定）：存量数据的回滚
   技术上受控、留痕、可恢复，但只要它**改变了她的注入内容**——也就是改变了
   她会说什么——就属于价值决策，必须留给主人。
   判据不是「风险大小」，是**「这个动作改变了她的什么」**：
   改代码/改注入链路 → 技术决策，我自主；
   改她「是什么样的人」（记忆真值、性格、主动性）→ 价值决策，主人拍板。
   我能做的是把清单摆清楚（`tools/低置信升信任清单.py` 那种只读工具），
   而不是替他执行。
9. **能离线复现的，就做「改前改后各跑一次」**（2026-10-25 第 7 轮定）：
   对话回复有状态、有随机性，没法复现；但**提取、检索、评分这类纯函数式环节可以**
   ——把真实事故输入原样喂进去，改前跑一次、改后跑一次，对照输出。
   第 7 轮就是这么确认的：同一句事故原话（「他实际是高一新生」），
   改前提取出一条错误身份记忆，改后返回 `[]`；再用一条反例（「我老婆叫米雪儿」）
   确认没误伤。**这比「测试绿 + 读代码」强得多，因为它验的是行为不是文本。**

## 五、取证工具（这条工作流的地基）

现在能拿到的证据（2026-10-25 第 3 轮之后已补齐）：

| 证据 | 有吗 | 在哪 |
|---|---|---|
| 她说了什么 | ✅ | `chat_log` / 会客厅 `/messages` |
| 她怎么想的 | ✅ | `turn_traces.reasoning_text` |
| 她调了什么工具 | ✅ | `turn_traces.tool_steps_json` |
| **她这一轮看到了什么** | ✅（第 3 轮起） | `turn_traces.prompt_digest`：system prompt 的段标题、`<背景·X>` 标签、历史条数与字符数 |
| 注入了哪些记忆/画像 | ⚠️ 部分 | 只能看到**块标签**（`记忆`/`关系档案`/`知识库`…），看不到块内具体是哪几条记忆 |

**这张表的第四行曾经是空的，代价很具体**：第 1 轮「时间块被截断」和第 2 轮
「44% 说明书被砍」这两条结论，全是靠「本地复刻 `build_system_prompt()` +
读源码」推出来的，不是观察出来的。**推理得出的结论和观测得出的结论长得一样，
直到它错了。**

留档上线后的**第一个回合**就抓到一个此前完全不知道的缺陷（bot 重启把对话历史
清空了——`history_count=0`）。造工具的时间，从它抓到第一个别的缺陷时就赚回来了。

存摘要不存全文（`memory.db` 已经 900MB）：一轮 system prompt 3000+ 字符、
history 十几条，全存每轮涨几 KB；而真正要回溯的是**结构**不是原文。

下一个缺口：`user_bg_labels` 只知道「注入了记忆块」，不知道「哪几条记忆」。
要补就得在 `format_compact_memories` 出口记 memory id 列表——先等有具体需求再做，
别为「可能会查」提前建表。

## 七、一句话

> **她的话是证据，不是产品。**
> 从证据出发找架构缺陷，不从架构推断她会错——这是调查，不是想象。
