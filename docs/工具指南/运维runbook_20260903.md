# 小糖糖运维 Runbook（2026-09-03）

适用对象：小糖糖 Windows 控制台运行环境。本文把控制台操作、只读观察器和 SQLite 恢复边界收在一起；它不替代发布裁决，也不授权修改 `config.yaml` 或直接修生产数据。

## 1. 启动、重启、停止

### 正常启动

1. 打开 `启动控制台.bat`（或运行 `python 糖糖控制台_qt.py`）。
2. 在仪表盘先点“启动 SnowLuma”，确认 QQ 登录及状态在线。
3. 点“🍬 启动小糖糖”，等待日志中的“`小糖糖已上线`”。
4. 另开终端启动只读观察器；首次可先采一次：

   ```powershell
   .\python310\python.exe tools\runtime_observer.py --once
   ```

   正式观察示例（默认生产库和日志均只读）：

   ```powershell
   .\python310\python.exe tools\runtime_observer.py --duration-hours 2 --interval-seconds 300
   ```

   产物默认进入 `artifacts/production_monitor/`，包含脱敏 JSONL、JSON 和 Markdown。`PASS` 只代表该域有充分正向证据；`INSUFFICIENT` 是未触发/样本不足，不能当作通过。

### 正常停止与计划重启

1. 先让观察器完成一次快照或记录当前产物路径。
2. 控制台点“⏹ 停止”；不要直接删除 `memory.db`、`memory.db-wal` 或进程文件。
3. 等控制台状态变为“● 离线”，再确认无 bot Python 进程继续写库。
4. 需要重启时用控制台“🔄 重启”（先停止再启动），重新执行“正常启动”的第 3–4 步。
5. 观察器若跨越计划重启，使用 `--expected-restarts 1`；普通稳定性观察不要设置它。观察新 boot 后确认 outbox 没有 `sending` 残留、`uncertain/dead` 没有未经处置的增长。

> 每天 06:00 的控制台自动重启也按“计划重启”处理：保留重启前后的观察器产物，不能把跨 boot 的稳定性误报成单实例连续稳定。

### 非正常退出

1. 不立即手工重发任何可能已发出的消息。
2. 启动后优先观察 outbox：`sending` 必须被恢复为 `uncertain`，`uncertain` 不在 due list 中，等待平台回执或走指定的 DB-only repair。
3. 保存对应 boot/cid 的脱敏观察器产物与日志时间范围；再决定是否修复。

## 2. 回滚

### 代码/文档回滚

1. **先停止 bot。** 找到同目录、同批次且确认为改动前的 `.bak-YYYYMMDD-批次` 文件。
2. 不覆盖式检查备份的文件名、时间、大小及（若有）SHA-256；确认它对应目标文件。
3. 先把当前目标复制为新的带时间戳保留副本，再以 `.bak` 覆盖目标。
4. 运行 `python -m compileall -f <已恢复文件>`；由负责人复跑 pytest/pyflakes。
5. 控制台启动 bot，并以观察器记录新 boot。若回滚改变用户可见行为，必须先由主负责人裁决。

### `config.yaml` 回滚

1. 仅在控制台停止 bot 后执行；优先用同目录 `config.yaml.bak*`，不要猜测旧值。
2. 覆盖前留存当前 `config.yaml` 的时间戳副本。
3. 通过控制台检查预设值与文件是否一致；配置不能只回滚一侧。
4. 启动后检查日志中的启动配置告警，尤其是破坏性 boolean 开关。

### 数据库回滚

1. 停止 bot，确认进程不再写入 `memory.db`。
2. 在隔离目录对候选备份运行 `PRAGMA integrity_check`；结果必须为 `ok`。
3. 将当前 `memory.db`、`memory.db-wal`、`memory.db-shm` 移到带时间戳的隔离目录，不删除。
4. 只复制已验证的一致快照为新的 `memory.db`；不要把运行中的主库与旧 `.wal` 混用。
5. 先以 `tools/体检.py` 和只读观察器检查，再启动 bot。发现 schema/checksum 拒绝时停止，不要用 SQL 绕过。

## 3. 数据备份与恢复演练

### 在线一致性备份（SQLite Online Backup API）

运行中数据库处于 WAL 模式，**禁止直接复制 `memory.db`**：最新页可能仍在 `memory.db-wal`。使用下列命令创建一致快照；目标目录要**自己先建好**（脚本不会自动创建），目标名不可覆盖。

> ⚠️ 2026-10-15 清理已删掉旧的 `backups/`（连同它的 8 个记忆快照与 `memory.db.previous`）；需要回滚点请按本节重新生成。

```powershell
@'
import sqlite3
from pathlib import Path

source = Path('memory.db')
target = Path('backups') / 'memory_manual_YYYYMMDD_HHMMSS.db'
if target.exists():
    raise SystemExit(f'拒绝覆盖：{target}')
with sqlite3.connect(str(source), timeout=60) as src:
    with sqlite3.connect(str(target)) as dst:
        src.backup(dst, pages=4096)
with sqlite3.connect(str(target)) as check:
    assert check.execute('PRAGMA integrity_check').fetchone()[0] == 'ok'
print(target)
'@ | .\python310\python.exe -
```

项目同步工具 `python tools/同步记忆.py 打包` 同样使用 SQLite 一致快照（`VACUUM INTO`）。解包/覆盖的机器必须先停止 bot；它的安全检查不应被绕过。

### 恢复演练（先在副本）

1. 对新备份运行上述 `integrity_check`，并记录文件大小和 SHA-256。
2. 把备份复制到临时目录，以临时副本运行 `Store` 启动校验或对应只读查询；不得在原备份上改写。
3. 确认关键表可读、outbox 健康统计可查询、没有 schema/checksum 错误。
4. 只有演练成功后，才允许按“数据库回滚”节在停机窗口覆盖正式库。

## 4. 清理

1. **日志轮转**：先停止或确认日志句柄已关闭；归档 `日志/tangtang.log` 至带日期的目录，保留当前日志与至少一个可用于事故追溯的完整窗口。不要用全文 grep 处理巨型日志；用 Python 流式过滤按 boot/cid 取证。
2. **观察器产物**：保留仍被报告引用的 JSONL/JSON/Markdown；仅清理已确认不再需要的旧窗口。清理前核验路径在 `artifacts/production_monitor/`，避免误删其他验收资产。
3. **`uv-cache`**：仅可删除 `artifacts/uv-cache/` 这类可再生缓存，不能删除 `venv*`、模型、`memory.db` 或备份。清理后由负责人按需重装/复跑门禁。
4. 每次清理先列出绝对目标路径；完成后记录删除/保留范围及可否恢复。

## 5. 观察器报警处置（`FAIL`）

1. 保存报告 JSON、Markdown、对应 JSONL 和时间范围；不要先重启覆盖现场。
2. 在报告 `domains.<domain>.evidence` 定位域，再以 boot/cid 过滤日志和执行只读 DB 查询。
3. 分域处置：

   | 域 | 首先核对 | 不可做的事 |
   |---|---|---|
   | `sending` / `qq_gateway` | `outbox_open`、`uncertain/dead`、平台确认及对应 cid | 对 uncertain 盲重发 |
   | `llm` / `llm_tools` | 429/5xx/timeout、未收尾 token、前后台 p95 | 仅因单窗数字调并发/超时 |
   | `memory` / `background_tasks` | extraction job 状态、lease、cursor、dead/requeue 冷却 | 放宽 deferred 阈值或手工推进 cursor |
   | `knowledge_tools` | tool outcome、retrieval trace、来源和脱敏字段 | 将 `INSUFFICIENT` 写成 PASS |
   | `observer_integrity` / `runtime_logs` | JSONL 连续性、轮转尾部、结构化日志 | 只看 Markdown 忽略原始 JSONL |
   | `local_services` / `voice` / `vision` | 服务心跳、进程退出、模型加载串行日志 | 并行重载模型 |

4. 先写最小临时库/mock 复现；确认根因后再提交最小修复并做定向回归。
5. 负责人复跑 pytest/pyflakes；安全重启后以新观察器窗口复验。没有足够样本时保留 `INSUFFICIENT`，不升级结论。

## 6. 常见事故处置速查

| 症状 | 先取证 | 正确边界 / 下一步 |
|---|---|---|
| 闸门静默 | `turn_actions`、权限/窗口日志、是否实际进入 LLM | 不能用关键词规则抢 LLM 决策；先证明哪个 gate 吞了路径。 |
| 观察器假红 | JSONL、boot 边界、`raw_failures` 与 `recovered_failures` | 恢复过的失败保留审计，不等同未恢复 FAIL；旧窗口不重算、不覆盖。 |
| 结算断链 | outbox、receipt mailbox、confirmed facts、任务 child/attempt 状态 | `uncertain` / `confirmed_unaccounted` 不得重发；已确认只允许 DB-only projection repair。 |
| 持久化缺口 | 重启前后状态、`_save/_load`、SQLite 行 | 重启后必须记得的冷却/观察/配额必须落盘；不能以内存补丁代替。 |
| 发送中或结算中被杀 | `send_outbox.status`、receipt、due list | `sending` 恢复为 `uncertain`，禁止自动 replay；P5-2 已以真子进程终止验证。 |
| SQLite 锁慢 | 临时库 p95/p99、队列/锁等待、事件循环指标 | 区分测试夹具、同步写和 LLM 锁；没有生产证据不改生产并发。 |

## 变更与用户可见行为声明

本 runbook 为文档，不迁移消息、动作、回执或检索算法；对 QQ 用户可见行为**保持不变**。执行其中的恢复/回滚属于运维操作，可能回退到备份时刻的数据状态，必须在操作记录中说明影响时间窗。
