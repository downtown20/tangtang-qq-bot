# legacy 记忆补证据 —— 立项研究

> 2026-10-24 立项。触发：调查「QQ <uid> 没有昵称」时撞到更深的一层——
> 这个人跟糖糖聊了 1886 次、有 252 字画像，但**288 条记忆里 261 条（90.6%）
> 是 `legacy_unverified`，被信任门挡在注入之外**；画像也因同样的原因不可注入。
> 也就是说：糖糖"认识"她 4 个月，实际能用的记忆不到一成。
>
> 这不是个例。全库 `legacy_unverified` 16700/22458（74.4%），118 份画像里
> **59 份被封**。本文件是解决方案的研究，不含实施。

---

## 一、问题：信任门是对的，但只有"门"，没有"路"

### 1.1 现状证据（2026-10-24 查库）

| 口径 | 数字 | 说明 |
|------|------|------|
| `memories.trust_level='legacy_unverified'` | 16,700 / 22,458（74.4%） | 被拒绝进入可信召回 |
| `verified` / `unverified` / `corrected` | 5,515 / 215 / 27 | 真正能用的那一部分 |
| `people` 有画像 | 118 人 | |
| 画像 `notes_trust_level='legacy_unverified'` | **59 人（一半）** | `active_notes()` 返回空 → 不注入 |
| 画像 `verified` | 59 人 | |
| 案例：<uid> | 记忆 288 条，**261 条 legacy** | 名字那条 `#5108「名字是米雪儿」` 证据 0 行 |

### 1.2 门是怎么立起来的（历史，不能简单拆）

`legacy_unverified` 不是"没验证过"，而是**验过但验不过**：

- 2026-08-26 之前的 `evidence_ids` 是逗号字符串，没有外键、没有校验，历史批处理
  曾把糖糖自己的回复、其他用户的消息、甚至不存在的 chat_log id 当成证据。
- `_init_db` 的迁移把这些行保留为审计线索，但降为 `legacy_unverified`，
  并且**把"无原始证据却标了 verified"的摘要也降级**（幂等，每次启动跑）。
- 之后立的规矩：升级必须 `update_memory_evidence(..., allow_legacy_promotion=True,
  reviewer=..., review_reason=..., evidence_quote=...)`——**必须给原文 quote**，
  且 `_validate_memory_evidence` 会校验 quote 真的被那条 chat_log 支持。

**这个门必须留着。** 拆掉等于让"LLM 曾经凭印象写的一句话"重新变成"可信事实"，
那是 2026-08-16 事故的翻版。

### 1.3 缺的那一半：没有"补证据"的通道

门要求"证据 + 原文 + 复核人"，而 74% 的存量数据**证据字段是坏的**（CSV 未校验
或为空）。要让它重新可信，只有两条路：

- 人工复核：`tools/memory_reverify.py` 已经支持，但 16,700 条不可能人工。
- **把证据补回去**：原始聊天记录 `chat_log` 还在（298,657 行），这是唯一可用的
  事实源。问题是——**没有任何批量机制把记忆挂回它的原话**。

于是形成死局：数据在，原文在，但两者之间没有桥。

## 二、不能做的事（先把边界划出来）

1. **不能批量把 legacy 直接改 verified**。这与"验过但验不过"的事实直接矛盾。
2. **不能放宽 `active_notes()` 的放行集合**。CLAUDE.md 已定死：legacy 明确停用
   自动注入，要进注入只能经显式重合成产出 verified 快照。
3. **不能用"相似度够高就算证据"**。`chat_log` 里有几万条消息，任何两条闲聊都
   可能有 0.7 相似度。低门槛会批量造假证据，比现在更糟。
4. **不能改 `memory_evidence` 的语义**。它是"这条记忆由这句原话支持"的关系表，
   一旦掺进推断，整张表的可信度就归零。

## 三、候选方案

### 方案 A：严格子串回挂（零误判，覆盖低）

**做法**：对每条 legacy 记忆，在同 `qq_id`、`is_bot_reply=0`、时间邻近的
`chat_log` 行里找 `message` **原样包含**记忆 `value` 的行；命中则写
`memory_evidence` + 走 `update_memory_evidence(allow_legacy_promotion=True)`。

**优点**：误判率理论为 0（子串关系不需要相似度阈值）。
**缺点**：覆盖面很小。实测过案例：
`#5108「名字是米雪儿」` ← 原话是「我是欧泊搜查官米雪儿呀！」——**不是子串**，
挂不上。记忆提取天然会改写、压缩、归纳，严格子串只能覆盖"原样记录"那一类。

**结论**：可作为**第一批安全样本**，用来建立工具链与基线指标，但解决不了主体。

### 方案 B：LLM 辅助回挂（唯一可规模化）

**做法**：对每条 legacy 记忆，取候选 `chat_log` 行（同人、±时间窗、关键词召回
Top-K），交给 LLM 判断"这条记忆是不是由这句原话得来的"，要求返回 `chat_id` +
**原文引文**。拿回来的东西不直接落库，而是喂给既有的
`update_memory_evidence(..., evidence_quote=...)`——**由它做最终校验**：
引文必须能在那条 chat_log 里被定位，否则拒。

**优点**：
- 能处理改写/归纳类记忆（方案 A 的死角）。
- **信任门不动**：LLM 只是"提出候选"，把关的仍是既有校验器。
- 失败模式安全：LLM 幻觉的引文会被 `_validate_memory_evidence` 拒掉。

**风险**：
- 成本：16,700 条 × 候选召回。必须限量、分批、可中断。
- LLM 可能"合理编造"——引文能被定位不代表**语义真的支持**这条记忆
  （例如记忆说"她养了猫"，引文是"我喜欢猫"）。这是本方案的核心风险，
  需要额外的语义门槛（见 3.2）。

### 方案 C：只补"高价值记忆"（优先级裁剪）

不必全量。按影响面排序：
1. `importance >= 8` 的（画像/名字/关键事实的来源）
2. 被 `notes_source_ids` 引用的（画像谱系）
3. 名字/称呼类（本轮 P1 已归档进 aliases，但那条记忆本身仍是 legacy）
4. 其余按 importance 降序

**优点**：把预算花在会改变行为的地方。
**结论**：不是独立方案，是 A/B 的执行顺序。

### 方案 D：让画像重合成的谱系校验更宽松

**否决**。`replace_profile_snapshot` 要求 `source_memory_ids` 全部 verified 且
逐条有证据——这正是 2026-08-16 之后画像可信的唯一保证。放宽它等于从后门拆掉
整个信任模型。

## 四、推荐路线

**分三期，每期都有独立可验证的产出，且都能回滚。**

### 第一期：工具链 + 严格子串基线（低风险，先建测量尺）

1. 写 `tools/回挂记忆证据.py`：
   - 默认 `--dry-run`，只统计
   - `--mode=substring` 走方案 A
   - 输出：`attempted / matched / rejected_by_validator / landed`
2. 在**生产库副本**上跑一遍，拿到三个基线数字：
   - 严格子串能命中多少条（预估 < 10%）
   - 校验器拒掉多少（应当接近 0，如果高说明工具写错了）
   - 抽样人工核对 20 条，确认零误判
3. 全程走 `memory_revisions`（actor=`backfill:evidence`），每次升级留痕。

**验收**：工具幂等（重跑不重复写）；抽样 20 条零误判；`pytest` 全绿。

### 第二期：LLM 辅助回挂（主体，需先有小规模对照）

1. 只在 `importance >= 8` 的子集上跑（预估几百条，可控）。
2. **双闸门**：
   - 校验器闸门（既有）：引文必须被 `chat_log` 支持
   - **语义闸门（新增）**：让另一个 LLM 调用只回答一个问题——
     「这句原话是否足以支持这条记忆的断言？yes/no」，拿不到 yes 就放弃。
     **两次独立调用**比一次"请判断并给出引文"更不容易自洽地编造。
3. 抽样人工核对 30 条（这一步不能省，也不能用 LLM 代替人工做"最终判定"）。
4. 只有误判率 < 5% 才进入全量。

**验收**：抽样误判率 < 5%；`verified` 占比上升但**不被刷满**（例如从 24.6%
升到 40~50% 就是健康区间，升到 90% 说明闸门失效）；回滚脚本可用。

### 第三期：画像重生 + 让结果可见

证据补齐后，`people.notes` 仍是 legacy。需要：
1. 对证据已齐的人触发一次画像重合成（`replace_profile_snapshot` 的谱系校验
   此时能满足），产出 verified 画像。
2. 在记忆剖面里显示**可注入比例**——现在这一栏根本没有，等于没人知道
   74% 的记忆其实是死的。这是本轮调查暴露的**可观测性缺口**：
   信任门在安静地工作，而"挡掉了多少"从来没有出现在任何界面上。

**验收**：剖面页能看到「可注入 / 被信任门挡住」的数字；主人能自己判断
要不要为某个人跑一次补证据。

## 五、必须一起设计的三件事

1. **可观测性**：`memory_capabilities()` 加 `trusted_injectable` / `trusted_blocked`
   两个数。没有它，这 74% 会一直隐形——本轮就是因为查昵称才偶然发现。
2. **回滚**：每期都要有"撤销这一批"的脚本。做法是给
   `memory_revisions` 记 `actor=backfill:evidence:<批次号>`，回滚按批次把
   `trust_level` 打回 legacy 并删对应 `memory_evidence` 行。
3. **幂等**：同一记忆重复回挂不能产生多条 evidence（`memory_evidence` 有主键
   `(memory_id, chat_id, relation)`，天然幂等，但要注意别让 relation 变化绕过）。

## 六、已知限制（写在这里，避免以后误判）

1. **补证据 ≠ 补真相**。它证明的是"这句话确实被说过"，不是"这件事确实成立"。
   用户说过的错话，补上证据后依然是错的事实——只是它现在**可追溯**了。
2. 老数据的 `event_time` 覆盖率只有 25%，时间窗召回本身可能失效；这类记忆
   只能靠内容召回，误判率会更高，应当单独统计。
3. 第一期的严格子串命中率如果低于 5%，说明"改写幅度"比预期大，
   第二期的语义闸门必须更保守（考虑把门槛提到"必须包含关键实体词"）。

## 七、工作量与优先级建议

| 期 | 内容 | 预估 | 风险 |
|----|------|------|------|
| 一 | 工具链 + 子串基线 + 抽样 | 半天 | 低 |
| 二 | LLM 回挂 + 双闸门 + 抽样 | 1~2 天 | 中（核心风险在这里） |
| 三 | 画像重生 + 可观测性 | 半天 | 低 |

建议顺序：**先做第三期的可观测性**（半天，零风险，立刻让 74% 这个数字可见），
再回来做一期二期。理由是：现在没有人知道这批数据是死的，所以也没有人会给
它排优先级；把数字摆到界面上，这件事自己就会说话。

## 八、执行记录（2026-10-24，本轮落地）

立项时给的建议顺序是「先做第三期的可观测性，再回来做一期二期」。本轮按这个
顺序执行：**第三期完整落地、第一期完整落地（含副本上的回滚闭环）、第二期未启动**。

### 8.1 第三期：可观测性（已落地）

`memory_capabilities()` 新增 7 个数字，剖面页 L5 可见：

| 字段 | 本机实测（2026-10-24 17:00） |
|------|------|
| `trusted_injectable` | 5,041 |
| `trusted_blocked` | 12,127 |
| `trusted_cover` | 0.2936 |
| `memories_with_evidence` | 5,256 |
| `evidence_cover` | 0.3062 |
| `people_profiled_injectable` | 59 |
| `people_profiled_blocked` | 59 |

**口径必须说清**：第一节 1.1 的「74.4%」是**全量**口径（16,700/22,458），
界面上的「70.6%」是**活跃**口径（12,127/17,168）。注入只看 active 行，
所以界面只能按活跃口径算——两个数字不一样不是错，但不写清就会被当成矛盾
（下一次「文档说 74%、界面说 70%」的争吵就是这么来的）。

**单一事实源**：把 `{"verified","manual","corrected"}` 提成
`store.TRUSTED_TRUST_LEVELS`。记忆召回门（`query_memories(trusted_only=True)`
的 SQL 片段）与画像注入门（`Memory.active_notes`）都取自它——三处口径一旦
漂移，「界面说可注入 N 条」和「实际能召回多少」就会变成两个数，而这种不一致
在界面上看不出来。`agent/health_check.py` 里 6 处只读观测 SQL 仍用字面量，
常量 docstring 已写明改常量时要同步。

**单人口径要说清（重要）**：剖面页的 `counts` 是「与这个人相关的记忆」混合口径
（包含 ta 说的话 + 关于 ta 的记忆）。以 <uid> 为例，界面显示 423 条活跃、
199 可注入 / 224 被挡（53%）；而**主体口径**（`qq_id` 严格）是 248 条活跃、
只有 26 条可信——**89.5% 用不上**。复算与立项时一致：该人 288 条总记忆里
261 条 legacy（221 active + 38 superseded + 2 retracted）。

两个数字都对，但**决策要看后者**：它才是「糖糖对这个人真正知道什么」。
界面上那个 53% 会把问题显示得偏轻，这是混合口径的固有代价；本轮刻意没有
拆成两个字段，因为 `counts` 与 `counts.memories` 必须同口径，拆开会让人
分不清哪个数字对应哪张表。

验收：
- `tests/test_memory_trust_visibility.py` 6 条。关键设计：**每个信任等级各造
  一条记忆 / 一份画像，同时问闸门放不放行、统计把它算在哪一侧，两边必须给出
  同一个答案**——只断言「字段存在」等于在测 SQL 能不能跑。
- 变异 6 个全真红（`变异_trust.json` 4 个 + `变异_trust_gate.json` 2 个），
  含「召回门偷偷多放一档」「画像门不认信任等级」「dirty 不再拦注入」
  「被挡恒为 0」。
- 前端 `npx tsc --noEmit` 退出码 0。

### 8.2 第一期：严格子串回挂（工具就绪，未在生产库执行）

`tools/回挂记忆证据.py`。默认 dry-run，`--apply` 才写，作用于仓库根的
`memory.db` 时还要额外 `--allow-production`。

**基线（生产库 dry-run，锚点阈值 6 字符）**：

| 口径 | 数量 |
|------|------|
| attempted（可处理的 legacy 行） | 8,972 |
| matched | 2,038（22.7%） |
| ambiguous（同一句话横跨多个群） | 4（0.04%） |
| unmatched | 6,129 |
| too_short | 710 |
| too_long | 91 |
| **rejected_by_validator** | **0** |

`rejected_by_validator = 0` 是这一轮最重要的一条数字：候选构造与既有校验器
（归属 / 作用域 / 引文支持）口径一致，工具**没有**自己造第二套放行判断。

命中率 22.7%，高于立项预估的 <10%。抽样 20 条（跨 10 个人）逐条核对：
原话确实包含记忆原文，关系全部成立。高于预估的原因是「原样记录」类记忆
比预想的多——提取器大量直接摘原句，而不是归纳。

**敏感度**（阈值 → 命中）：6 → 2,038 / 8 → 1,416 / 10 → 984 / 12 → 689。
阈值每加 2，命中掉约三成，说明大量命中依赖 6~8 字短锚。跨群歧义只有 4 条，
说明短锚并没有撞车（限定「同一个人」的消息后撞车概率很低）。6 可用，但
抽样扩到全量时要再看一次这条曲线。

**副本上的完整闭环验收**（`_probe/apply_acceptance.py`，只在副本跑）：

```
基线      可注入 5041 / 活跃 17166 / 有证据 5256 / 证据关系行 28878
dry-run   matched 2038
apply     landed 2038，校验器拒 0
→         可注入 7079（+2038）、关系行 30908（+2030）
重跑      matched 0 / landed 0            ← 幂等
回滚      rolled_back 2038、删关系行 2030、还原 evidence_ids 2030
→         完全回到基线 5041 / 17166 / 5256 / 28878
再回滚    rolled_back 0                    ← 幂等
```

### 8.3 过程中修掉的三个真实缺陷（验收跑出来的，不是推演出来的）

1. **回滚会误删不属于它的证据行**。`memory_evidence` 主键是
   `(memory_id, chat_id, relation)`，而 legacy 行原本就可能带一条同
   (memory, chat) 的审计线索行（实测 8/2038）。原先按 (memory, chat) 删，
   会把它们一起清掉——那不是「撤销这一批」，是「删掉不属于它的数据」。
   修法：删除条件加 `created_at = 本次复核时间`
   （`update_memory_evidence` 用同一个时间变量写两张表，能精确圈定本批插入行）。
2. **回滚不还原 `evidence_ids`**。`rollback_memory_reverification` 只降
   `trust_level`，于是回滚后留下「legacy 记忆却挂着证据 CSV」的不一致，
   实测 `memories_with_evidence` 停在 7285 而不是 5256。修法：按本批次
   `field='evidence_ids'` 流水里的 `before_value` 精确还原。
3. **幂等的判据写错了**。原以为「重跑候选为 0」，实际重跑候选还有 6,934 条
   ——挂不上的那些（unmatched/too_short/too_long/ambiguous）本来就还在池子里。
   正确判据是「重跑不会产生新的挂载」（matched=0 且 landed=0）。

三条都有测试钉住（`tests/test_evidence_backfill_tool.py` 11 条），
变异 7 个全真红（`变异_回挂.json`）。

### 8.4 一个必须说清的限制：补证据 ≠ 补真相

抽样里出现过 `的还是月光大剑`（原话「老实说1我最喜欢的还是月光大剑」）、
`我习惯用pc版本，` 这类**提取器截断的残片**。严格子串会给它们补上真实证据、
提升为 verified——于是它们进入可信召回，但语义价值很低。

这不是工具的错误（关系成立），是「补证据只证明这句话被说过」的直接后果。
二期做语义闸门时，应把「记忆本身是否是一条完整断言」也纳入判断；
在那之前，跑 `--apply` 的人要接受「可信记忆里会多出一批残片」。

### 8.5 第二期：未启动（需要主人拍板）

不是工作量问题，而是立项时自己写下的前置条件：
1. 一期要求「抽样人工核对 20 条」——本轮做了（20/20 成立），但只覆盖
   matched 明细里的 10 个人；
2. 二期要求「抽样人工核对 30 条，这一步不能省，也不能用 LLM 代替人工做

**一个必须知道的副作用：361 条记忆的作用域被确定下来。**

`update_memory_evidence` 对 scope 为空的 legacy 行会按证据消息的群补上
`source_group_id`（代码注释原文：「作用域随之确定」）。实测 411 条里 361 条属于

影响要看召回路径的实参：
- **群聊召回** `recall(source_group_id=group_id)`（`handler.py:4034`）→ 原本

也就是说这 361 条从「只在私聊能召回」变成「只在对应群能召回」。因为证据消息
就在那个群里，这是**把误挂的作用域改对**，不是副作用性的损失；但它是可感知的
行为变化，必须写明。

**回滚能力已实测**（不是承诺）：把当前生产库复制一份，在副本上跑

再与 apply 前的备份逐字段比对：**411 条 trust_level / evidence_ids /
source_group_id 全部一致，0 处残留**；计数只剩 bot 在两次快照之间的正常写入
（+1 trusted / +1 evidence）。`event_time` 刻意不还原（新值是证据原话时间，
比旧空值更准）。

**B 批次暴露的第四个缺陷：回滚不还原 `source_group_id`。**
前三处（见 8.3）修完后回滚仍会留下「legacy 记忆被钉在某个群里」。修法同
`evidence_ids`——按本批次 `field='source_group_id'` 流水的 `before_value` 还原。
测试 `test_rollback_restores_source_group_id` 钉住，变异 B9 真红。

**质量观察（B 批次真正要看的东西）**：这一批 411 条按 key 是 fact 199 / said 110 /

影响大的），不适合当质量门槛。要按质量筛，得等二期的语义闸门——
这也再次说明「补证据 ≠ 补真相」。

### 8.10 语义回挂：工具落地 + 首批 24 条（第二期）

工具 `tools/语义回挂证据.py`。**三道闸门**（缺一不可）：

1. **引文闸门**：LLM 必须返回 `chat_id` + 一个能在原话里**逐字定位**的 `quote`；
2. **校验器闸门**：`update_memory_evidence` 的 `_validate_memory_evidence` 校验
   quote 真是那条 chat_log 的子串、归属与作用域都对——**工具不自己放行任何一条**；
3. **语义闸门**：另起一次独立调用只问「这句原话是否足以支持这条记忆的断言？」，
   不是 yes 就放弃。两次独立调用比一次「请判断并给出引文」更不容易自洽地编造。

候选压缩：jieba 提实词 → 在该人非 bot 消息里按命中数 + 时间邻近取 Top-5 →
只把这 5 句交给 LLM（不把整个聊天记录塞进去）。

首批（importance=10、每人最多 1 条、60 条候选）：

| 结果 | 条数 |
|---|---|
| 落地 | **24** |
| LLM 自己放弃（找不到能支持的原话） | 23 |
| 语义闸门否决 | 4 |
| 无候选 | 9 |
| 引文编造 / 校验器拒绝 | **0** |

抽样 24/24 逐条核对：「记忆 ↔ 原话 ↔ 引文」支持关系全部成立，**误判 0**。
典型正确案例（正是严格子串的死角）：
- 记忆「刚收到大学录取通知书，专业是动画」← 原话「我刚大学录取通知书下来，专业是动画」
- 记忆「成展，名字为成展」← 原话「叫我成展就好了」
- 记忆「有朋友（哥们）」← 原话「我这边和哥们第一次出远门」

成本与速度：60 条候选、8 并发、两轮调用，**270 秒**。按此推算 6,129 条 unmatched
约需 7~8 小时、API 成本约几元（DeepSeek 输入价量级）。所以全量要分期跑，
建议夜间或提高并发。

**又修出一个缺陷**：回滚只认 `backfill:substring:` 前缀，而语义批次写的是
`backfill:semantic:`——注释里写着「同一套回滚」，代码里只认一种（注释与代码
分家）。已改为两个前缀都认，并加测试钉住。

### 8.11 作用域：私聊注入召回改为跨域（单向）

`handle_private_message` 的注入召回 `source_group_id=""` → `None`（不过滤），
群聊仍 `= group_id`。**单向性**是这条改动的全部前提：

- 私聊召回群记忆**安全**：`memories.qq_id` 是记忆主体，召回的仍是「关于当前
  对话对象」的记忆，只是跨了场景；「你在某个群说过的话」他本人在场，不是泄露。
- 群聊召回私聊记忆**永远不允许**：那是当众复述私聊。`memory_access.py:117`
  已把「私聊中不能查询群聊记录」定成隐私红线。

**为什么不影响画像合成**：`synthesize_profile` 自己调 `recall`（无 scope），
且要求 `len(source_scopes)==1` 才合成，与注入召回是两条独立路径。

**已知限制**：渲染时没有给跨域记忆标注来源群，所以 LLM 可能把「你在某个群
说过的话」当成本次私聊的上下文（场景错配）。这是刻意留到下一步的：渲染格式
改动影响所有记忆注入，风险比召回实参大。
