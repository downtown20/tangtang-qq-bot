# provider 组表：把「连接信息」从每个模型里收上来（2026-10-28）

> 主人原话：「AI模型的设计完全参照 dsh harness（如第二张图），不允许单独配置
> 模型的地方全部到『AI模型』中配置，其他地方只允许下拉选择，下拉做成图库打标
> 选模型的样子。」

## 一、改之前是什么形状

`config.yaml` 的 `llm.models[]` 是**平铺**的：一个档位 = 一个模型 + 一整套连接信息。

```yaml
llm:
  models:
  - id: default
    provider: custom
    base_url: https://buddybackend.cloud/     # ← 每个档位各存一份
    api_key: ${CUSTOM_LLM_KEY}                # ← 每个档位各存一份
    model: deepseek-v4.1-flash
```

同一个中转站挂 3 个模型，地址和 Key 就存 3 份；改地址要改 3 处，改漏一处就
「有的档位能通、有的不能」，而且**哪份生效取决于遍历顺序**。

这正是**教训 #54** 描述的形态：

> 组级属性存成条目级副本（组标题写在每条协议的文件头，同组 6 条 6 份；改哪份
> 生效靠遍历顺序）→ 组级的东西只留**一份定义**（组表文件），条目只写引用。

所以这件事**不是「界面不好用」，是数据层反模式**。只改 UI 不动数据，等于把
副本藏起来，下次谁读 `llm.models` 还是会踩。

## 二、改成什么（对齐 DSH Harness）

DSH 的 `settings.yaml` 是两层：

```yaml
llm-pi-ai:
  providers:
    ollama:
      api: openai-completions
      baseURL: http://127.0.0.1:11434/v1
      apiKeyEnv: OLLAMA_LAUNCH_DSH_API_KEY
      displayName: Ollama
      models:                       # ← 模型只声明能力
        - id: qwen3-vl:8b
          name: qwen3-vl:8b
          contextWindow: 262144
          maxTokens: 262144
          input: [text, image]
```

连接信息只在 provider 上一次，模型只声明**能力**。我们照这个形状：

```yaml
llm:
  providers:                        # ← 组表：连接信息的唯一定义处
  - id: custom
    label: 自建中转（OpenAI 兼容）
    api: openai-completions
    base_url: https://buddybackend.cloud/
    api_key: ${CUSTOM_LLM_KEY}
  models:                           # ← 目录：只写引用和能力
  - id: default
    provider: custom                # ← 引用 providers[].id
    model: deepseek-v4.1-flash
    context_window: 0
    input: [text]
```

## 三、唯一换算点

`agent/model_refs.py::provider_conn(config, profile)` 是**唯一**把「档位」翻成
「实际用哪个端点 / 哪个 Key」的地方（教训 #38：同一个量只许一个换算点）。

它做**逐字段**回退，不是整条记录回退：

| 顺序 | 来源 | 什么时候用 |
|---|---|---|
| 1 | `llm.providers[id == profile.provider]` | 新结构（组表） |
| 2 | `profile.base_url` / `profile.api_key` | 旧结构（每档一份副本） |
| 3 | `llm.base_url` / `llm.api_key` | 更旧（只有单模型的时代） |

为什么逐字段：迁移期必然出现「组表建好了但 Key 还没搬进去」的中间状态，
整条回退会让档位里本来可用的 Key 一夜失效。

消费方（**都不许自己翻 providers**）：
- `agent/handler.py::_get_llm_config`（每轮 LLM 调用）
- `agent/vision_router.py`（识图）
- `agent/image_tagger.py`（打标）
- `tools/desktop_bridge.py`（三个写端点 + 激活）

## 四、写入口只有三个（各管一件事）

| 端点 | 写什么 | 为什么单开 |
|---|---|---|
| `POST /api/providers/save` | `llm.providers` 一组 | 改一处要**同时**把引用它的档位里那份过期副本清掉；并且不让掩码 Key 写回磁盘 |
| `POST /api/models/save` | `llm.models` + `active_model` | 设置页有一份**早于这次改动**的整份配置快照，由它回写会把刚改的模型目录覆盖回旧值（教训 #51 同族） |
| `POST /api/models/activate` | 只切档位（+ 推理档） | 点一下就要生效，不该重写整份配置 |

`POST /api/config` **不让碰** `llm.providers`：前端手上的 `api_key` 是掩码，
经那条路回写会把真 Key 写成 `sk-a…xyz（35 字符）`。

## 五、界面（照 DSH 的 provider 卡）

```
provider 卡（一组一张）
  名称 / API 地址 / API 协议
  API Key：已绑定 .env 的 CUSTOM_LLM_KEY（已填）  ← 写值走 /api/secrets/save
  模型目录（N 个）                    [获取可用模型]
    ┌ 显示名 │ 模型 ID │ 64K │ 可看图 │ ⌄ │ 🗑 ┐
    └ 展开：上下文窗口 / 最大输出 tokens / 温度 /
             思考 / 思考强度 / 输入类型 ☑文本 ☑图片 / 用途 ☑聊天 ☐识图 ☐打标
  [+ 添加模型]
[+ 添加 provider]
```

- **provider 卡失焦即存**（三个字段，改完就走，跟 DSH 一致）；
- **模型行展开后显式保存**（九个字段逐字段写盘会堆一堆备份文件）；
- 「获取可用模型」只发 `provider_id`——真 Key 留在后端解析（界面只有掩码，发过去只会 401）。

## 六、设置页收口

按主人要求「别处只允许下拉」，设置页删掉了这些**手填入口**（config 键仍在，
只是只有一个写入口）：

| 位置 | 删掉的字段 | 现在从哪来 |
|---|---|---|
| `llm` 组 | provider / model / base_url / max_tokens / temperature / thinking / thinking_effort | AI 模型页（provider 卡 + 模型目录） |
| `识图` 组 | `llm.vision.model` / `base_url` / 手填 Key | 选档位（`llm.vision.model_ref`） |
| `图库打标` 组 | `api_base` / `api_model` / `api_key` / `ollama_model` | 图库页的选模型面板 |

每个被删的位置都留了一句说明块（`_llm_models_note` / `_vision_models_note` /
`_tag_models_note`）——**删字段不等于不解释**（教训 #48）。

`llm` 组剩下的四个系统开关（`light_thinking` / `tool_loop_limit` /
`request_timeout` / `user_id`）之前**根本没有界面入口**（`Settings.tsx` 遇到
`section === 'llm'` 直接渲染 `<ModelSettings />`，schema 那组字段没人读）。
本轮把它们渲染在 AI 模型页底部「请求行为」块里——教训 #12：写了 infra ≠ 接进业务。

## 七、闸门与变异

| 闸门 | 防什么 |
|---|---|
| `tests/test_model_providers.py`（14 条） | 逐字段回退、组表优先、映射写法、纯扁平配置、handler 真的走组表 |
| `tests/test_desktop_providers.py`（16 条） | 读不写盘、Key 掩码、掩码回传不落盘、删组被引用时拒绝、模型目录写入剥连接 |
| `变异/provider组表.json` 2/2 真红 | 换算点改成只看副本 / `_llm_of` 不容忍 llm 段 |
| `变异/provider写入.json` 4/4 真红 | 不过滤掩码 / 不清理副本 / 删组不写回 / 不剥连接 |

**变异对照当场抓到过一条假绿**：第一版 `test_save_provider_ignores_masked_key_echo`
拿 `${CUSTOM_LLM_KEY}` 去测「掩码不被写回」——而 `_mask_secret` 对 `${VAR}` 是
**原样返回**的，所以「掩码」就是原文，删掉过滤逻辑它也绿。改成用真明文 Key
作前提之后才真红（教训 #37 的又一次实例：验证尺子自己会骗人）。

## 八、迁移（已执行，一次性）

`config.yaml` / `config.example.yaml` 已迁到组表：`providers` 里一组，
档位里的 `base_url` / `api_key` 两行删掉。用文本插入而不是 `yaml.dump`，
为了保留注释与 CRLF；写完 `yaml.safe_load` 自检（providers 在、档位里那两行真没了）。

老配置就算不迁移也能跑（`provider_conn` 三层回退），迁移只是把「哪份生效」
从遍历顺序变成显式的一句引用。

## 九、还留着的老字段（不是忘了删）

`llm.base_url` / `llm.model` / `llm.api_key` / `llm.max_tokens` /
`llm.temperature` / `llm.thinking` / `llm.thinking_effort` 仍会被
`api_models_save` / `api_models_activate` 从当前档位**同步写出**：
`_get_llm_config` 在有 `models` 时按档位覆盖，这几个扁平字段只服务
「没有 `models` 的老配置」，但状态灯和 `/api/status` 还在读它。
留着是为了让两份口径**一致**，不是留了个第二配置点——它们没有独立写入口。
