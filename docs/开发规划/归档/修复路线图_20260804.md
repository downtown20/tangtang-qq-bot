### C4 — `[贴图:xx]` 在回复开头被正则误剥

**文件**：[reply_pipeline.py:87](agent/reply_pipeline.py#L87)

**根因**：`clean()` 的情绪标签正则 `r'^\s*\[[^\]]{1,5}\]\s*'` 匹配 `[贴图:色色]`（`[贴图:色色]` = `[` + `贴图:色色` = 5 chars + `]`），当贴图标签在回复开头时被剥离。之后 `enrich()` 中的 `"[贴图:" in reply` 返回 False → `had_explicit_sticker = False` → LLM 选择的贴图不解析、随机贴图反而被附加。

**修复**（1 行改动）：
```python
# reply_pipeline.py line 87, 改前:
reply = re.sub(r'^\s*\[[^\]]{1,5}\]\s*', '', reply)
# 改后:
reply = re.sub(r'^\s*\[(?!贴图[：:])[^\]]{1,5}\]\s*', '', reply)
```

**验证**：发送 `[贴图:色色]喵~今天天气真好` 作为 LLM 输出 → 确认 `[贴图:色色]` 被正确解析为 CQ 码，且无随机贴图附加。

### C1 — LLM 调用竞态条件

**文件**：[handler.py:2735-2768](agent/handler.py#L2735-L2768)

**根因**：`_llm_busy` 是布尔标志，不是锁。`_call_llm` 无条件设 `True` 不检查；`_call_llm_light` 检查但不等锁。导致：
1. 后台提取正在调用 LLM → 主消息到达 → `_call_llm` 也调用 → 两道 API 并发
2. `_call_llm_light` 先结束 → `finally` 设 `False` → 第三个调用可进入

**修复方案**：`asyncio.Lock` 替代布尔标志。

```python
# handler.py __init__:
self._llm_lock = asyncio.Lock()

# _call_llm_light (line 2735-2752) 改后:
async def _call_llm_light(self, system_prompt: str, user_message: str) -> str:
    """轻量 LLM 调用——用于后台任务。主回复占用时等待最多 15 秒。"""
    try:
        acquired = await asyncio.wait_for(self._llm_lock.acquire(), timeout=15)
    except asyncio.TimeoutError:
        self.metrics.incr("extract_busy_skipped")
        return ""
    try:
        provider = self.llm_config.get("provider", "deepseek")
        if provider == "deepseek":
            return await self._call_deepseek(system_prompt, user_message)
        else:
            return await self._call_openai_compatible(system_prompt, user_message)
    except Exception:
        return ""
    finally:
        self._llm_lock.release()

# _call_llm (line 2754-2768) 改后:
async def _call_llm(self, system_prompt: str, user_message: str, scenario=None,
                    history_messages: list[dict] = None,
                    tools: list[dict] = None) -> str:
    await self._llm_lock.acquire()  # 主回复必须等——不能静默返回
    try:
        llm_cfg = self._get_llm_config(scenario) if scenario is not None else self.llm_config
        provider = llm_cfg.get("provider", "deepseek")
        if provider == "anthropic":
            return await self._call_claude(system_prompt, user_message, config=llm_cfg)
        elif provider == "deepseek":
            return await self._call_deepseek(system_prompt, user_message, history_messages, tools, config=llm_cfg)
        else:
            return await self._call_openai_compatible(system_prompt, user_message, config=llm_cfg)
    finally:
        self._llm_lock.release()

# _call_llm_with_skills 也需要更新——它目前不设 _llm_busy，但会调用 _call_llm
# 改为也通过 _call_llm 间接获取锁（_call_llm 内部已 acquire）
```

**注意**：此改动涉及面广——`_call_llm_with_skills` 也需要确保不绕过锁。需要全面回归测试。

**验证**：
- 模拟高并发：后台提取 + 主消息同时到达 → 确认只有一个 LLM 调用在执行
- 监控 metrics：`extract_busy_skipped` 在后台等待超过 15s 时正确记录
- 确认主回复不被锁饿死——`_call_llm` 是 `acquire()` 不加超时（必须等）
