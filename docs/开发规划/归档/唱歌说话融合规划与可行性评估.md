# 唱歌说话自然融合 —— 规划与可行性评估

> 2026-08-02 | 跳过 RVC 自训练，基于现有模型推进

---

## 一、目标回顾

糖糖在对话中自然哼唱——不是点歌台模式，是唱歌作为表达方式融入聊天。

**当前状态：** 群友说"唱首歌" → LLM 调 `sing` tool → 放整首歌。唱歌和说话是两个独立模式。

**目标状态：** 群友说"今天下雨了" → LLM 联想到《晴天》→ 引用两句歌词 → 系统放 2 句音频 → 继续说下一句话。

---

## 二、技术拆分

### 改什么

| 改动 | 难度 | 行数 | 说明 |
|------|:--:|:--:|------|
| 歌词注入系统提示词 | 低 | ~30 行 | context_builder.py 新增 song_lyrics 段落 |
| sing 工具升级 | 低 | ~20 行 | 加 section/style 参数 |
| 系统提示词引导 | 低 | ~10 行 | 让 LLM 知道可以自然哼唱 |
| `[SING:歌名,段落]` 解析升级 | 中 | ~30 行 | 支持精确指定歌名+段落 |
| 段落级音频 | 中 | ~50 行 | 用已有翻唱生成段落 WAV |

### 不改什么

- RVC 训练：跳过，用现有模型
- 唱歌基础架构：`sing` tool → `_pending_sing` → `[SING:]` → `_send_singing_reply` 链路不变
- LLM 引擎：DeepSeek V4，不改
- 回复处理：reply_pipeline 已有的 `[SING:]` 清洗不变

---

## 三、可行性评估

### 技术可行性：高 ✅

所有改动都在现有代码路径上。没有新依赖、没有新模块。本质上是一次 prompt engineering + tool design 优化。

### 质量标准

| 维度 | 评估 |
|------|------|
| LLM 能否在对话中引用歌词 | ✅ 歌词注入后自然能做到 |
| 音频能否播放片段 | ✅ 用已有翻唱干声切段落 |
| 唱歌语音质量 | ⚠️ 取决于用的 RVC 模型——hutao 可用但音色要确认 |
| 用户体验 | ✅ 从"点歌机"到"自然哼唱"，体验质变 |

### 风险：中等 ⚠️

| 风险 | 概率 | 影响 | 对策 |
|------|:--:|------|------|
| 歌词注入 token 太多（21首歌每首~80字） | 中 | LLM 响应变慢 | 按相关性筛选注入 5-8 首 |
| LLM 过度使用唱歌 | 低 | 每条消息都唱 | 提示词加频率约束 |
| 段落音频生成慢 | 低 | — | 用已有翻唱干声切分，不实时合成 |
| RVC 唱歌音色不满意 | 中 | 效果打折但不影响功能 | 先 hutao 跑通，后换模型 |

---

## 四、决策：值得做吗？

### 投赞成票

1. **改动量小**——~150 行代码，1-2 个 Phase
2. **不依赖 RVC 自训练**——用 hutao 或找的现成模型即可
3. **解决的是核心体验问题**——唱歌从"表演"变为"表达"，价值观匹配
4. **零新依赖、零新模块**——纯优化，不引入复杂度
5. **最坏情况**——唱歌质量因 RVC 音色不够好，但功能跑通了，换模型即可升级

### 投反对票

1. hutao 音色不是你最想要的（但够用）
2. LLM 自然引用歌词的效果需要调优（但方向对）

### 结论：**值得做。**

改动小、风险可控、解决了真正的体验问题。最坏情况是唱歌音色不够完美，但 LLM 能自然引用歌词、系统能放片段——这个交互框架本身已经有价值。RVC 模型随时可以换。

## 五、实施计划

### Phase 1：LLM 知道歌词（~60 行，1 小时）

1. `context_builder.py`：注入 song_lyrics_snippets——每首歌标题+每段首句
2. 系统提示词新增"自然哼唱"指导
3. `sing` 工具升级：加 `section` 和 `style` 参数

### Phase 2：段落音频 + 标记升级（~80 行，2 小时）

4. 用已有翻唱干声（songs/covers/htdemucs/）切段落音频
5. `[SING:歌名,段落]` 标记支持
6. 端到端测试

### 执行条件

- 需要一个可用的 RVC 唱歌模型（hutao 或找的音色更好的）
- LLM 已接入，tool calling 正常工作

### 暂不启动条件

- 如果 RVC 唱歌模型还没确定音色——先确定，再启动 Phase 1
