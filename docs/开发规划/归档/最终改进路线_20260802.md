## 第一轮：基础夯实（6 项，~350 行）

目标：给记忆和工具系统打上类型标签，让后续改动有数据支撑。

### R1-1：记忆认知类型区分 ⭐

**为什么**：这是后续所有记忆改进的基础——差异化衰减、上下文配额、Episode 聚合都依赖 episodic/semantic 标签。

**做什么**：
1. `extract_semantic_memories()` prompt 加 `cognitive` 字段输出 + 身份锚定句
2. `MemoryEntry` dataclass 加 `cognitive`、`confidence`、`origin` 三个字段
3. `store.py` `memories` 表 ALTER TABLE 加三列
4. `remember()` → `insert_memory()` 链路透传新字段
5. `recall()` 透传新字段到 MemoryEntry

**文件**：memory.py (~40行), store.py (~30行), handler.py (~15行)
**依赖**：无
**验证**：提取新记忆 → memory.db 查看 cognitive/confidence/origin 字段有值

### R1-2：工具方法类型区分

**为什么**：消除 `send_voice` 等副作用操作后的无效 LLM 轮次。借鉴 Nekro 的 TOOL/AGENT/BEHAVIOR 分类。

**做什么**：
1. `@register_skill` 加 `method_type` 参数（默认 "agent" 保持兼容）
2. `Skill` dataclass 加 `method_type` 字段
3. handler 工具执行后根据 method_type 决定是否触发 LLM 再处理

```python
# skills.py
@register_skill("send_voice", "发送语音", {...}, method_type="behavior")
@register_skill("web_search", "搜索互联网", {...}, method_type="agent")
@register_skill("calculate", "计算", {...}, method_type="tool")

# handler.py 工具执行后
if method_type == "behavior":
    # 返回值记录但不触发 LLM 再思考
    return result
elif method_type == "agent":
    # 返回值注入上下文，触发 LLM 消化
    ...
```

**文件**：skills.py (~15行), handler.py (~20行)
**依赖**：无
**验证**：调用 send_voice → 发完语音后 LLM 不再多生成一轮

### R1-3：Jinja2 模板化 System Prompt

**为什么**：当前 prompt 组装跨三个文件（personality.py → context_builder.py → handler.py），加新段落要改三个文件的函数签名。Jinja2 把它变成：模板里加 `{{ new_var }}`，Python 传一个值。

**做什么**：
1. 新建 `agent/prompts/system.j2`——一个模板文件包含完整 system prompt 结构
2. `personality.py` 的 `build_system_prompt()` 改为填充模板变量
3. `context_builder.py` 的 `build()` 改为通过模板变量注入状态层
4. 删掉重复注入的 guard（`"if not already in system_prompt_base"` 那些）

**不管的部分**：`role_card.md` 继续作为人格定义的第一来源，通过模板变量 `{{ role_card }}` 注入。user message 的记忆前缀保持 handler 注入方式（LLM 对 user message 遵从度高于 system prompt）。

**文件**：新增 system.j2 (~80行), personality.py (~30行改), context_builder.py (~20行改)
**依赖**：无（但建议 R1-1 先做——cognitive 字段会出现在 prompt 的记忆段落里）
**验证**：/人格 重载 → prompt 结构正确 → 回复质量不低于迁移前

### R1-4：身份锚定

**为什么**：`extract_semantic_memories` 当前 system prompt 是泛泛的"精确的信息提取助手"。改为显式的身份锚定——"你是小糖糖，一只猫娘。以下是你和{nickname}的对话。"——防止把糖糖自己的话当成群友的信息存储。

**做什么**：
1. 改 `extract_semantic_memories` 的 system prompt 开头
2. 改 `_EXTRACT_FACTS_PROMPT` 同

**文件**：memory.py (~10行 prompt 修改)
**依赖**：无（和 R1-1 一起做）
**验证**：群聊中糖糖说"我最喜欢看悬疑片"→ 群友回复"糖糖也喜欢悬疑片啊"→ 不会把"喜欢悬疑片"存成群友的记忆

### R1-6：防抖机制——接入 @ 消息路径

**为什么**：当前 `MessageBatcher` 只在非 @ 消息路径生效。@ 消息（最频繁触发的路径）直接绕过。多人同时 @糖糖 → 每条独立触发 LLM → 可能产生多条回复在同一个上下文中互相不知道对方的存在。需要把防抖覆盖到全路径，参考 Nekro 的 `debounce_timers` + `pending_messages` 模式。

**当前状态回顾**：

MessageBatcher 已存在且接入 handler，但它做了两件事：
- **内容合并**：窗口内多人消息合并成一个 prompt（"同时有 N 个人找你"）
- **延迟处理**：2 秒窗口

问题有三个：
1. @ 消息路径绕过（`enqueue_group` 对 @消息返回 False）
2. 合并逻辑只适合"非 @ 插话"场景——被 @ 时每个人在跟糖糖对话，不该合并成一段
3. 对 @ 消息没有防抖——3 人同时 @ 产生 3 次独立 LLM 调用

**做什么**：

1. **@ 消息加防抖，不做内容合并**——这是和普通消息合并的根本区别：

```
多人同时 @糖糖的场景：
  收到 @A → 启动 1.5s 防抖计时器
  收到 @B → 取消计时器，重新启动（最新消息时间 + 1.5s）
  收到 @C → 同上
  1.5s 后没有新消息 → 正常处理 @C
  
  结果：糖糖只回复最后一条 @ 消息，不会分别回复 A/B/C 三个人。
  
  对比 Nekro：Nekro 的 debounce 也是"只处理最后一条"——不是"合并多条"。这是对的。
  群聊中被多人 @，回复自然分流——有的人会被别人回复、有的人会说下一句。
  糖糖不需要做所有人的发言人。
```

2. **改造 MessageBatcher**——不改架构，加一个独立于内容合并的防抖层：

```python
class MessageBatcher:
    # 新增：@ 消息防抖（不做内容合并，只防重复处理）
    _at_debounce: dict[str, asyncio.Task] = {}  # {group_id: timer_task}
    
    async def debounce_at(self, group_id: str, msg: dict) -> dict | None:
        """@ 消息防抖：取消前一个等待，返回最终该处理的消息。
        返回 None 表示被取消（前一条被后一条替代）。
        返回 msg 表示计时器到期，正常处理。"""
        ...
```

3. **私聊消息同理**——私聊中对方连发 3 条，当前 batcher 合并成"这是完整的对话链"的 prompt 是对的方向（内容合并）。但防抖也应该覆盖：如果对方在 1.5s 内发了 3 条，不应该触发 3 次内容合并——应该等 1.5s 安静期后只做一次。

**文件**：message_batcher.py (~50行), handler.py (~10行)
**依赖**：无
**验证**：
- 2 人同时 @糖糖（间隔 < 1s）→ 只产生 1 条回复
- 3 人错开 @糖糖（间隔 > 3s）→ 分别回复
- 私聊对方连发 3 条（间隔 < 1s）→ 合并为 1 次 LLM 调用

## 第二轮：记忆体验深化（4 项，~150 行）

目标：让记忆的检索和注入更像人的记忆方式——重要的事不忘、不重要的自然褪色、不同类型各占位置。

### R2-1：上下文注入类型配额

**为什么**：当前 `recall_formatted` 按 effective_weight 排序取前 N 条。如果某人的 fact 类记忆特别多，全是 facts 被注入。Episodic 记忆（"一起经历过的事"）被挤掉——但聊天中 episodic 更能建立连接感。

**做什么**：
1. `recall_formatted()` 开头加配额分桶：最多 3 episodic + 3 semantic-fact + 2 semantic-preference
2. 保持现有的章节结构（速写 → 画像 → 身份 → 核心 → 相关 → 最近）
3. 配额按 effective_weight 在各桶内竞争——不降低整体记忆质量，只保证类型多样性

**文件**：memory.py (~40行)
**依赖**：R1-1（需要 cognitive 字段）
**验证**：查一个熟人 → /记忆 → 输出包含 episodic 和 semantic 两类记忆

### R2-2：记忆休眠与苏醒

**为什么**：当前所有记忆统一衰减。但"存了之后 60 天没被想起"和"最近被回忆了 5 次"的记忆衰减速度一样——这不合理。

**做什么**：
1. `recall()` 终排加休眠检测：60 天未 recall → 降权 0.5x，30 天 → 降权 0.7x
2. `reinforce()` 已实现（+1 importance, 更新 last_recalled）——被重新提起的记忆自动苏醒
3. `cleanup_stale_memories()` 条件微调：importance≤2 且 dormant>180 天才删除（原 90 天）

**文件**：memory.py (~30行)
**依赖**：R1-1（用 last_recalled 字段判断休眠，已有）
**验证**：找一条 60 天前存储从未被 recall 的记忆 → 手动 recall → 它的 effective 明显低于同期但频繁被 recall 的记忆

### R2-3：差异化衰减

**为什么**："上周三喝了奶茶"和"他在北大读书"不该衰减一样快。

**做什么**：
1. `recall()` 衰减计算分支：episodic 半衰 ~30 天，semantic 半衰 ~120 天
2. episodic 在检索时额外 ×1.2 加权（对话中"经历过的事"比"知道的事"更有价值）
3. `reinforce()` 差异化：episodic 命中后 boost=0.3，semantic boost=0.15

**文件**：memory.py (~25行)
**依赖**：R1-1（需要 cognitive 字段）
**验证**：一条 30 天前的 episodic 记忆的 effective < 同期的 semantic 记忆

### R2-4：handler.py 拆分——自治逻辑

**为什么**：自治循环、内在消化、驱动力释放逻辑独立于消息路由。

**做什么**：
1. 新建 `agent/handler_autonomy.py`
2. 移入 `_check_autonomous_action()`、`_internal_digest()`、`_pick_initiative_group()` 及相关方法

**文件**：新增 handler_autonomy.py (~1000行), handler.py (~1000行减)
**依赖**：无，但建议 R1-5 之后做（两个拆分无冲突）
**验证**：自治循环正常触发 + handler.py < 6000 行

### 第二轮完成标志

- [ ] 查熟人记忆时包含 episodic 事件而不只是 facts
- [ ] 两个月没被提的记忆自动降权
- [ ] 被重新提起时苏醒（reinforce 生效）

## 第三轮：故事与主动性（4 项，~280 行）

目标：让记忆从散落的句子变成有结构的故事，让糖糖的主动行为从随机选群变成"想到你了所以想跟你说这个"。

### R3-1：Episode 结构化聚合

**为什么**：当前记忆是散落的句子。"上周三在群里聊火锅"不是一条记忆，是 5 条散落的记忆。Episode 把它们聚合成一个"事件"——有标题、有摘要、有时间跨度。检索时优先注入最近的 episode 而不是零散记忆。

**做什么**：
1. 新建 `memories` 同级表 `episodes`（轻量：id, qq_id, title, summary, time_start, time_end, paragraph_ids）
2. `_aggregate_episodes()` 确定性算法：同一 qq_id 的 episodic 记忆 → 时间差 < 60 分钟 → 聚合成 episode
3. `recall_formatted()` 加"📖 事件"章节（最多 2 条 episode）
4. 利用 conversation_tracker 的对话窗口作为 episode 自然边界（可选优化）

**文件**：memory.py (~80行), store.py (~30行), recall_formatted (~10行)
**依赖**：R1-1（需要 episodic 数据积累）、R2-1（配额制保证 episode 能被看到）
**验证**：和一个群友连续聊某个话题 3 轮以上 → 第二天查记忆 → "📖 事件"章节出现聚合后的 episode

### R3-2：社交关系三元组

**为什么**：糖糖只知道"张三喜欢咖啡"，不知道"张三是李四的室友"。社交关系三元组补这个维度——不是 Nekro 那种完整的知识图谱，是轻量的"这两个人之间有什么关系"索引。

**做什么**：
1. `extract_semantic_memories` 的 relationship 类型中加 `triple` 字段
2. `fact_clusters` 表（已有 `subject_qq` 字段）存三元组
3. 新增 `search_relation_triples(qq_id_a, qq_id_b)` 方法
4. handler 中当对话提到其他人时，自动查询关系

**文件**：memory.py (~40行), handler.py (~20行)
**依赖**：R1-1
**验证**：群里有人说"张三是李四的室友"→ 新消息提到张三时，上下文包含和李四的关系

### R3-3：驱动力 × 记忆交叉

**为什么**：当前自治循环选群是机械的（"最近有活动的群"）。驱动力释放应该有方向——承诺压力高时找承诺对象，社交渴望高时找关系好的人，有 episodic 记忆的人优先（"上次聊到一半的事可以继续"）。

**做什么**：
1. 新增 `_build_initiative_topics_context()` 方法：扫描最近的 episodic 记忆和未完成承诺，生成"你可能想聊的事"列表
2. 注入自治循环的 LLM prompt（像现在的驱动力数值和存在状态一样注入）
3. `_pick_initiative_group()` 加记忆驱动权重——有"候选话题"的人所在的群优先级更高

```python
# 自治循环 prompt 新增段落：
"""
你可能想聊的事（不需要每条都提，选你最有感觉的）：
- 张三（群833475319）上周说想去爬山——可以问ta去了没
- 你答应了李四帮ta查资料——还没查
"""
```

**文件**：handler.py / handler_autonomy.py (~80行)
**依赖**：R3-1（需要 episode）、R1-1（需要 cognitive 字段区分承诺和事件）
**验证**：糖糖主动说话时选择了有"未完成承诺"或"最近 episodic 互动"的人的群

### R3-4：统一工具注册入口

**为什么**：当前 `skills.py` 和 `handler.py` 各维护一半工具定义。如果同一个工具被注册两次，LLM 看到两个定义。

**做什么**：
1. handler 中的记忆/语音/唱歌/表情包/群管理工具统一走 `@register_skill`（用闭包捕获 handler 引用）
2. `build_tool_definitions()` 成为唯一的 Tool Calling 定义来源
3. 删掉 handler 中手工构建的工具定义

**文件**：skills.py (~30行), handler.py (~50行删)
**依赖**：R1-2（方法类型区分已在 @register_skill 中支持）
**验证**：所有工具在 LLM 看来只有一份定义，功能正常

## 风险与回退

每项改动独立可回退：
- **R1-1**：ALTER TABLE 加列，不加不兼容约束。回退 = 删列
- **R1-2**：method_type 默认 "agent" 保持兼容。回退 = 删参数
- **R1-3**：保留旧 prompt 构建代码分支，模板渲染失败 → fallback
