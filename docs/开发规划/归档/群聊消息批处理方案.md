# 群聊消息批处理 —— 消灭刷屏式回复

> 2026-07-31 | 起草

## 两个问题

### 问题一：多人同时 @ → 各回各的

群聊中多人同时找糖糖，每条消息独立调用 LLM，导致：
1. **刷屏**：3 条消息可能变成 6-7 条回复
2. **内容重复**：两条回复可能说同一件事
3. **串台**：回复 A 的末尾不小心提到了 B 的话题
4. **不连贯**：群友看到的是散落的碎片，不是一段对话

### 问题二：同一人连续发 → 逐条回复

同一人在短时间内连续发多条消息（想听歌→换一首→日语的歌），糖糖逐条回复每一条，而不是理解意图链，最终还没发歌：

```
用户：想听歌
糖糖：好呀，我会唱童话、小幸运、起风了...你想听哪首？
用户：换一首
糖糖：那就换一首～童话怎么样？     ← 废话，没意义
用户：日语的歌
糖糖：日语歌呀，我想想...          ← 还是废话，还是没发歌
```

**正确做法**：识别这是同一意图的延续，跳过中间回复，直接发日语歌。

## 根因

当前架构：每条消息 → 一次 LLM 调用 → 一条回复。并发消息之间零协调。

## 方案

### 问题一：多人批处理 → 合并窗口

**核心思路**：在打字延迟窗口内合并消息，一次 LLM 调用处理多个@，生成一段连贯回复。

```
现在：
  msg1 → LLM → reply1 (发)
  msg2 → LLM → reply2 (发)   ← 各说各的

改后：
  msg1 → ┐
  msg2 → ├ 打字延迟窗口 → LLM（看到两条消息）→ 一段回复（发）
  msg3 → ┘
```

### 问题二：同一人连续消息 → 语义去重 + 意图合并

**核心思路**：检测同一人在打字延迟窗口内的连续消息，跳过语义重复的中间回复，只回最终的复合意图。

```
现在：
  "想听歌" → 打字延迟 → LLM → "好呀我会唱童话..."
  "换一首" → 打字延迟 → LLM → "那就童话怎么样？"  ← 废回复
  "日语的歌" → 打字延迟 → LLM → "日语歌我想想..."  ← 还是没发歌

改后：
  "想听歌" → ┐
  "换一首" → ├ 语义去重：这是同一意图的延续，不回"换一首"
  "日语的歌" → ┘ 合并意图：用户想要日语的歌，直接发歌
```

**实现**：复用现有的 BGE 语义去重机制（`_last_reply_per_user`），扩展来判断"是不是同一意图的延续"。如果同一人 10 秒内连续发，且语义相似度 > 0.5（比现有的 0.85 宽松），则取消前一条的回复、合并上下文、重新生成。

### 两个问题共用同一机制

都是"打字延迟窗口 + 消息合并"，区别在于合并对象不同：

| | 问题一 | 问题二 |
|------|--------|--------|
| 合并对象 | 多人消息 | 同一人连续消息 |
| 触发条件 | 窗口内多人 @ | 同一人窗口内连续发 |
| 合并方式 | 一段回复 @ 多个人 | 一段回复回应最终意图 |
| 回复数量 | 1 条 | 1 条（跳过中间废话） |

### 关键参数

| 参数 | 值 | 说明 |
|------|-----|------|
| 合并窗口 | 打字延迟（1-4s）| 复用现有延迟，不额外等待 |
| 最大合并 | 3 条 | 超过 3 条分批处理 |
| 回复上限 | 3 段 | 一段回复不超过 3 小段，对应最多 3 个人 |

### LLM 提示词

合并后的提示词格式：

```
【同时有 N 个人找你，请在一段回复里自然地回应所有人】

@小明 说：糖糖今天天气怎么样
@小红 说：糖糖帮我查一下快递
@小刚 说：喵喵喵

回复要求：
- 一段话回应所有人，像真实群聊一样自然
- 可以按话题合并（比如小明和小红都在问问题→先回答小明的天气再帮小红查快递）
- 不要分开发送 N 段独立回复——这是一条消息
- 如果大家的问法差异太大，回复最多 3 小段，每段 @ 对应的人
```

### 合并判断

以下情况**不合并**（单独回复）：
- 两条消息意图完全不同（命令 vs 聊天）
- 消息包含 `/命令`（命令单独处理）
- 合并后的 prompt 超过 500 字

### 伪代码

```python
# handler.py 群聊入口

# 类级别：当前批次
self._reply_batch: list[dict] = []  # 待合并的消息
self._batch_timer: asyncio.Task | None = None

async def _maybe_batch_reply(self, group_id, user_id, nickname, text, msg):
    """将消息加入批次，打字延迟结束后批量处理"""
    
    # 不合合并条件 → 直接回复
    if text.startswith("/") or len(self._reply_batch) >= 3:
        await self._do_single_reply(...)
        return
    
    # 加入批次
    self._reply_batch.append({...})
    
    # 如果是批次第一条，启动定时器
    if len(self._reply_batch) == 1:
        # 取消已有的定时器（如果有）
        # 启动新定时器：打字延迟后处理
        self._batch_timer = asyncio.create_task(
            self._process_batch(group_id, delay=typing_delay)
        )

async def _process_batch(self, group_id, delay):
    """打字延迟到期，处理批次"""
    await asyncio.sleep(delay)
    batch = self._reply_batch
    self._reply_batch = []
    
    if len(batch) == 1:
        # 只有一条，正常回复
        await self._do_single_reply(batch[0])
    else:
        # 多条合并
        prompt = self._build_batch_prompt(batch)
        reply = await self._call_llm(prompt, ...)
        await self._send_reply(group_id, reply)
```

### 风险

1. **定时器竞态**：批次处理期间新消息到达——需要锁或标记
2. **LLM 质量**：合并后的 prompt 更复杂，LLM 可能回答混乱——需要 prompt 工程调优
3. **延迟增加**：第一条消息也要等打字延迟——实际上和现在一样，打字延迟本来就存在
4. **回退**：如果效果不好，恢复单条处理只需要删除批次逻辑

### 不做的事

- ~~不合并私聊消息~~ → **合并。私聊是问题二最高发场景。**
- 不异步处理（保持现有同步流）
- 不引入消息队列中间件

### 私聊特别说明

私聊只会有"同一人连续消息"，不会有"多人同时@"。所以私聊只需要问题二的逻辑：

```
私聊中：
  "想听歌" → ┐
  "换一首" → ├ 检测到同一意图延续 → 合并上下文
  "日语的" → ┘ 一次 LLM 调用：直接选歌发歌
```

不需要打字延迟——私聊中对方连续发消息，每收到一条重置一个短计时器（2 秒），计时器到期后处理合并后的上下文。
