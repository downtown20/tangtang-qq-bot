# 记忆健康监控系统 — 设计文档

> 目标：让记忆系统的运行状态从"不可知"变为"一眼可见"。
> 原则：不改架构、不加重 LLM 负担、所有指标可自愈可追溯。

---

## 一、为什么需要监控

当前状态：系统跑了两个月，提取效率恒为 2-5%，17 人零记忆——但没有任何人知道。

监控要回答的四个问题（每次打开控制台就能看到）：
1. 记忆系统在正常工作吗？
2. 哪些人在被遗忘？
3. 记忆质量是上升还是下降？
4. 哪里堵了？

---

## 二、指标体系（四层，共 15 个指标）

### 第一层：提取管道（是否在生产记忆）

| # | 指标 | 含义 | 采集点 |
|---|------|------|--------|
| M1 | `extract_attempts` | 今日 LLM 提取触发次数 | `_extract_memories_with_llm` 入口 |
| M2 | `extract_successes` | 今日成功产生记忆的提取次数 | LLM返回JSON数组非空 |
| M3 | `extract_memories_total` | 今日 LLM 提取的记忆总条数 | 统计 valid 数组长度 |
| M4 | `extract_rejected` | 今日被校验拦截的记忆条数 | 后置校验 rejected 计数 |
| M5 | `extract_llm_failures` | LLM 调用失败/返回空次数 | except 分支 + 返回 `[]` |
| M6 | `extract_busy_skipped` | 因 `_llm_busy` 跳过的提取次数 | `_call_llm_light` 入口 |

**健康标准**：
- M1 > 0 且 M2/M1 > 50% → ✅ 正常
- M1 = 0 → 🔴 提取完全没有触发
- M4/(M3+M4) > 50% → 🟡 校验过杀
- M6 > M1 → 🟡 忙线阻塞严重

### 第二层：记忆存储（质量如何）

| # | 指标 | 含义 | 采集点 |
|---|------|------|--------|
| M7 | `self_memories_today` | 今日正则自忆产量 | `_extract_self_memories` 写入后 |
| M8 | `memories_confidence_avg` | 今日新记忆平均置信度 | 每日聚合，按区间分布 |
| M9 | `memories_cognitive_ratio` | episodic/semantic 比例 | 每日聚合 |
| M10 | `dedup_hits` | BGE 去重命中次数 | `_deduped_remember` 去重分支 |

**健康标准**：
- M7 < M3 → ✅ 自忆没有超过 LLM 提取
- M7 > M3 × 2 → 🟡 正则自忆轰炸
- M8 < 0.6 → 🟡 LLM 置信度低（默认值占多数）
- M9 episodic < 10% → 🟡 cognitive 分类失效
- M10/(M3+M7) > 30% → 🟢 去重有效工作

### 第三层：记忆覆盖（哪些人被遗忘）

| # | 指标 | 含义 | 采集点 |
|---|------|------|--------|
| M11 | `users_zero_memory` | 聊>50次但0记忆的人数 | 每日聚合查询 |
| M12 | `users_no_profile` | 记忆>10条但无画像的人数 | 每日聚合查询 |
| M13 | `owner_memory_count` | 主人的记忆总数 | 每日快照 |

**健康标准**：
- M11 = 0 → ✅
- M11 > 0 → 🔴 有人在被遗忘（列出 QQ 号）
- M13 < 10 → 🔴 主人记忆严重不足

### 第四层：系统资源（有没有堵）

| # | 指标 | 含义 | 采集点 |
|---|------|------|--------|
| M14 | `pending_extractions` | 积压的待提取用户数（counter 已到阈值但还未触发） | counter 达到阈值时 +1，提取完成时 -1 |
| M15 | `last_extract_timestamp` | 最后一次成功提取的时间 | 每次 M2+1 时更新 |

**健康标准**：
- M14 > 10 → 🟡 提取管道积压
- M15 距现在 > 6 小时 → 🟡 可能停摆

## 三、存储方案

所有指标存在 `kv_store` 表（已有），不需要新建表。

```
格式：metric:{date}:{name} = <int/float>
例如：metric:2026-08-04:extract_attempts = 12
      metric:2026-08-04:extract_memories_total = 8
      metric:2026-08-04:users_zero_memory = 3
```

同时存一份 `metric:latest:{name}` 作为当前值快照，方便控制台快速读取。

### 为什么用 kv_store 而不是新建表

- kv_store 已存在，零成本
- 按天分区，天然支持趋势查询
- 控制台已有读取 kv_store 的代码路径
- 指标体积小（每天 ~20 条记录，一年才 7000 条）

## 四、采集实现

### 不侵入、不加重

采集代码不超过 3 行插入任何现有函数。用计数器的形式，不阻塞主流程。

```python
# agent/metrics.py (新增，~80行)

class MemoryMetrics:
    """内存指标收集器。所有操作 O(1)，不阻塞。"""
    
    def __init__(self, store):
        self.store = store
        self._counters: dict[str, int] = {}  # 内存缓冲，定期 flush
    
    def incr(self, name: str, delta: int = 1):
        """增加计数器（内存操作，不写磁盘）"""
        self._counters[name] = self._counters.get(name, 0) + delta
    
    async def flush(self):
        """将今日计数器写入 kv_store（每 5 分钟调用一次）"""
        today = datetime.now().strftime("%Y-%m-%d")
        for name, value in self._counters.items():
            key = f"metric:{today}:{name}"
            old = int(self.store.kv_get(key) or 0)
            self.store.kv_set(key, str(old + value))
            self.store.kv_set(f"metric:latest:{name}", str(old + value))
        self._counters.clear()
    
    def get_today(self, name: str) -> int:
        """读取今日指标"""
        today = datetime.now().strftime("%Y-%m-%d")
        return int(self.store.kv_get(f"metric:{today}:{name}") or 0)
    
    def get_latest(self, name: str) -> int:
        """读取最新快照"""
        return int(self.store.kv_get(f"metric:latest:{name}") or 0)
```

### 采集点插桩（4 个位置，共 ~15 行）

**位置一：`_extract_memories_with_llm` 入口**
```python
self.metrics.incr("extract_attempts")
# 在 if self._llm_busy: return 之前
```

**位置二：`_extract_memories_with_llm` LLM 调用后**
```python
# extract_semantic_memories 返回后
if items:
    self.metrics.incr("extract_successes")
    self.metrics.incr("extract_memories_total", len(items))
else:
    self.metrics.incr("extract_llm_failures")
```

**位置三：`extract_semantic_memories` 校验层**
```python
# 后置校验 rejected 计数
self.metrics.incr("extract_rejected", rejected_count)
```

**位置四：`_extract_self_memories` 写入后**
```python
self.metrics.incr("self_memories_today")
```

**位置五：定时 flush（handler 自治循环中）**
```python
# 每 5 分钟 flush 一次指标到 kv_store
if now - self._last_metrics_flush > 300:
    await self.metrics.flush()
    self._last_metrics_flush = now
```

### 每日聚合查询（凌晨 2:00 跑一次）

```python
async def _daily_metrics_aggregate(self):
    """每日聚合：扫描数据库，产生M11-M13等需要SQL的指标"""
    today = datetime.now().strftime("%Y-%m-%d")
    
    # M11: 聊>50次但0记忆的用户
    rows = self.store.query("""
        SELECT p.qq_id, p.nickname FROM people p
        WHERE p.total_chats > 50
        AND (SELECT COUNT(*) FROM memories m WHERE m.qq_id = p.qq_id) = 0
    """)
    self.store.kv_set(f"metric:{today}:users_zero_memory_list", 
                      ",".join(f"{r[0]}({r[1]})" for r in rows))
    
    # M13: 主人记忆数
    owner_mems = self.store.count_memories(self.owner_qq)
    self.store.kv_set(f"metric:{today}:owner_memory_count", str(owner_mems))
```

## 六、实施步骤

### Phase 1: 指标采集（~100 行新代码，1 小时）

1. 新建 `agent/metrics.py` — MemoryMetrics 类
2. handler `__init__` 中初始化 `self.metrics = MemoryMetrics(self.memory.store)`
3. 在 4 个采集点插桩
4. 在自治循环中加 5 分钟定时 flush
5. 在 handler 中加 `_daily_metrics_aggregate`，凌晨 2:00 调度

### Phase 2: 展示（~50 行，30 分钟）

1. 修改 `/状态` 命令的输出，追加记忆健康段
2. 控制台 Settings 页加「记忆健康」卡片（可选，先做命令行版本）

### Phase 3: 验证（实际运行 24 小时）

1. 运行一天后查看 `/状态` 输出
2. 确认指标数字合理
3. 根据实际数据调整健康阈值

## 七、不改的东西

| 不改 | 原因 |
|------|------|
| 不用 Prometheus/Grafana | 单机项目，过度设计 |
| 不加实时推送告警 | 不需要——打开控制台就能看到 |
| 不建新数据库表 | kv_store 够用，减少迁移成本 |
| 不改提取逻辑本身 | 监控和修复分离——先看清再动手 |
