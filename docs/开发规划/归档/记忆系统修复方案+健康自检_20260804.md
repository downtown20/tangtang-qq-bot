## 二、未修复问题及方案

### 🔴 P0：bot_qq 在 people 表中显示为"路人" ✅ 已修复

**现象**：糖糖自己的 QQ（2693914170）→ `_qq_suffix` 截为 "4170" → people 表 nickname 为空、chats=0 → 格式化输出为 `📋 (ID:4170) | 聊0次 | 路人`。糖糖看到自己的档案写着"聊0次的路人"，推理出"这是系统把我的档案搞串了"——推理完全正确。

**根因**：
1. bot_qq 在 people 表中 nickname 为空——`get_or_create_person` 创建记录时没设
2. `_get_self_memory_context` 用 `format_compact_memories(bot_qq).replace(魔术字符串)`——两个 replace 都不匹配实际输出，静默失败（CLAUDE.md 错误十三再现）

**修复（不入侵公共方法契约）**：
1. `handler.py __init__`：`update_person(bot_qq, nickname="小糖糖")` ——**修数据**
2. `handler.py _get_self_memory_context`：不再用 `format_compact_memories/.replace` 和 `recall_formatted/.replace`，直接用 `_format_self_memories(selected)` ——**修调用方**
3. `memory.py`：新增 `_format_self_memories()` 私有方法——第一人称自我叙事格式
4. `recall_formatted` 和 `format_compact_memories` 保持不变——**不入侵公共契约**

**自审通过**：无魔术字符串、无契约变更、无静默失效路径。旧代码的 `.replace("📋 {bot_qq}", ...)` 和 `.replace("关于 {bot_qq} 的记忆", ...)` 从来不匹配——这次直接消除了 replace 而不是修 replace 的匹配字符串。

### 🟡 P1：浪浪（1743800785）intimacy=100 但 chats=0

**现象**：owner 的小号 intimacy=100，但没有任何聊天记录。

**根因**：intimacy 可能来自场景绑定（`scenario_targets`）或被手动设置，与 chat_count 不同步。两个数据源独立更新，没有一致性检查。

**方案**：暂不修——这是设计层面的问题。intimacy 和 chat_count 本来就是两个维度（一个是关系质量，一个是互动数量）。100 intimacy + 0 chats 在场景绑定场景下是合理的。只需确保格式化输出时，chat_count=0 不会让 intimacy=100 看起来像 bug。

#### P2.1 `cleanup_stale_buffers` — 含 bug，先修再接

**问题**：第 298-299 行的裁剪逻辑：
```python
if len(self._last_extracted_id) > 100:
    self._last_extracted_id = dict(list(self._last_extracted_id.items())[-50:])
```
这会静默丢弃 50 个以上用户的提取进度——被丢弃的用户下次提取从消息 ID 0 开始。而且没有任何日志、没有告警。

**修复后接入**：自治循环每天一次。同时把裁剪改为只丢弃 30 天以上未活跃的用户（而非简单取后 50 个）。

#### P2.2 `merge_similar_clusters` — 直接接入

**调用链**：`_extract_fact_clusters_task` 末尾 → `merge_similar_clusters(user_id, llm_call, embed_engine)`。每次提取新事实簇后检查是否需要合并。LLM 调用量极小（只在 BGE > 0.7 时触发）。

#### P2.3 `get_topic_context` — 需升级实现

**当前实现是关键词子串匹配**——`"想你" in "不要想你"` → 命中。这违反 CLAUDE.md 第七条（jieba 原则）。接入前应改为 BGE 语义匹配：用当前消息的 embedding 搜索全库记忆，返回跨用户的相关内容。

**不做的事**：不按当前实现接入——关键词匹配会引入噪音和误匹配。

#### P2.4 `_aggregate_episodes` — ⭐ 最有价值，最易接入

**为什么最有价值**：
- 纯确定性算法，不调 LLM，零 API 成本
- `insert_episode` 的唯一调用方——接上后 episodes 表从空变活
- `recall_formatted` 的"📖 往事"段（第 426-432 行）就能输出糖糖记得的事件
- 糖糖能说"上次你跟我说过……"——这是记忆系统最直观的用户体验提升

**接入点**：`_extract_memories_with_llm` 尾部，每次有新 episodic 记忆入库后触发。只对新提取的用户运行（不扫描全库）。每次耗时 <100ms。

#### P2.5 `search_relation_triples` — 暴露为工具

**注册为 tool calling**：`search_relations(name: str)` → LLM 需要了解人际关系时自主调用。实现是关键词匹配，但关系类关键词（室友/朋友/同学/对象/一起）覆盖面还行——够用。

#### P2 实施优先级

```
优先：P2.4 (_aggregate_episodes)  → 零成本，最大体验提升
其次：P2.2 (merge_similar_clusters) → 防止事实簇无限增长
然后：P2.5 (search_relation_triples) → 暴露工具
最后：P2.1 (cleanup_stale_buffers)  → 需先修 bug
暂缓：P2.3 (get_topic_context)      → 需先升级为 BGE
```

## 三、系统健康自检机制

### 设计原则

1. **自报家门，不等用户问。** 糖糖应该在启动时、每天定时、以及 `/状态` 命令中主动报告系统健康。
2. **对比"宣称"和"实际"。** 不只是报告指标数值——要对比：这个功能宣称在跑，实际跑了吗？
3. **静默失败 = 告警。** 任何组件如果应该产出但没有产出，必须被报告。
4. **糖糖是最终消费者。** 健康报告用自然语言生成，糖糖能读懂、能转述给主人。

### 架构

```
                    ┌─────────────────────┐
                    │   HealthCheck 注册表 │
                    │   每个组件注册一个    │
                    │   check 函数         │
                    └────────┬────────────┘
                             │
           ┌─────────────────┼─────────────────┐
           │                 │                 │
    提取管道检查        存储层检查         记忆质量检查
    (extraction)      (store/memory)     (quality)
           │                 │                 │
           ▼                 ▼                 ▼
    ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
    │ 今日提取次数  │  │ embedding覆盖│  │ 重复记忆数   │
    │ busy跳过率   │  │ 去重命中数   │  │ 推理泄露数   │
    │ 零记忆用户   │  │ 清理执行状态 │  │ confidence分布│
    │ 兜底触发次数 │  │ episodes产出 │  │ 截断碎片数   │
    └──────────────┘  └──────────────┘  └──────────────┘
                             │
                             ▼
                    ┌─────────────────────┐
                    │   HealthReport      │
                    │   自然语言摘要       │
                    │   → 糖糖的自我感知   │
                    └─────────────────────┘
```

### 模块：`agent/health_check.py`

```python
class SystemHealth:
    """系统健康自检——每个组件注册一个 check 函数。
    启动时跑一次完整检查，之后每小时跑一次轻量检查。
    结果写入 self_state，让糖糖能感知自己的系统状态。"""

    def __init__(self, handler):
        self._checks: dict[str, callable] = {}
        self._last_results: dict[str, dict] = {}

    def register(self, name: str, check_fn, schedule: str = "hourly"):
        """注册检查项。schedule: 'startup' | 'hourly' | 'daily'"""

    async def run_startup_check(self) -> dict:
        """启动时全量检查。输出给日志 + /状态。"""

    async def run_hourly_check(self) -> dict:
        """轻量检查。只跑 hourly 和 daily（如果到期）。"""

    def health_summary(self) -> str:
        """生成自然语言摘要，注入糖糖的自我状态。
        糖糖能在 /状态 中看到，也能在对话中感知。"""
```

### 首批检查项（12项）

| 检查项 | 频率 | 判断标准 | 异常时做什么 |
|--------|------|---------|------------|
| 提取管道是否在跑 | hourly | `extract_attempts > 0`（过去1小时） | 告警：管道可能阻塞 |
| busy 跳过率 | hourly | `busy_skipped / attempts < 30%` | 告警：LLM 资源竞争严重 |
| 零记忆用户数 | daily | `users_zero_memory < 5` | 告警：有人在被遗忘 |
| 主人记忆数 | daily | `owner_memory_count > 10` | 告警：主人档案空白 |
| 去重是否生效 | daily | `dedup_hits > 0` | 告警：可能有重复入库 |
| 推理泄露 | daily | `memories LIKE '%SKIP%' = 0` | 告警+自动清理 |
| 重复记忆 | daily | `同qq+同value > 1 = 0` | 告警+自动合并 |
| embedding 覆盖率 | daily | `有embedding的记忆/总数 > 95%` | 告警：去重和语义搜索降级 |
| 陈旧清理是否执行 | daily | `cleanup_stale_memories 调用过` | 告警：数据库持续膨胀 |
| reinforce 冷却是否失效 | daily | `recall_count 最高值未增长` | 告警：滚雪球恢复 |
| episodes 表是否为空 | weekly | `COUNT(*) > 0` | 提醒：事件聚合未接入 |
| confidence 分布 | daily | `>=0.8 占比 > 40%` | 提醒：提取质量下降 |

### 与 metrics.py 的关系

`metrics.py` 是**数据采集层**——15 个计数器，只采不判。
`health_check.py` 是**判断层**——读 metrics 数据 + 数据库查询 → 判断健康/异常 → 生成自然语言。

```
metrics.py (采集)  →  health_check.py (判断)  →  self_state (糖糖感知)
                         ↓
                    /状态 命令输出
                    糖糖的自然语言表达
```
