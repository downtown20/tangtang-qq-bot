## 一、糖糖编造系统操作

**现象**：群友说"糖糖变了"，糖糖回"系统调用日志已清除""已切换至旧版内核""正在重载配置文件"——假装自己是操作系统。

**根因**：LLM 对自己的身份认知不够强。role_card 写了"AI驱动的QQ群机器人"但人格描写远多于身份认知，LLM 在困惑时退回"AI 系统"角色。

**解决**：role_card 身份声明改为 **"你是一只猫娘。不是操作系统、不是AI助手、不是电脑程序——是猫娘。"** 一句话写死身份。同时 CMD 能力边界区分"角色扮演"（允许）和"假装操作系统"（禁止）。

## 二、回复太长

**现象**：糖糖经常回复 5-6 句的长文，凌晨三点像在写小说。用户明确说了"糖糖没必要总是发长文"。

**根因**：没有约束回复长度。LLM 倾向于展开描述——尤其在新人格（吾辈/老群友）下更想"表达"。

**解决**：psychology.yaml 场景铁律第一条——**不超过三句话**。这个约束适用于所有启用了心理陪伴场景的人。日常聊天也应该保持克制——role_card 已有"口语化，像真的在跟人说话"但执行不够。

## 三、记忆系统在伤害人

**现象**：米雪儿(3922400700)的记忆库里存储了大量"我是废物""我是坏孩子""我的存在没人关心"。每次对话这些记忆被注入系统提示词，糖糖在无形中强化她的抑郁认知。

**根因**：记忆提取 (`extract_semantic_memories`) 不加区分地存储了用户的自贬陈述。这些不是"关于这个人的事实"——是"这个人的抑郁症状"。

**解决**：
- 清理了 15 条有害记忆（`_fix_memory.py`）
- 加了准确事实：名字、喜好、病痛、处境
- **系统级修复待做**：记忆提取时过滤自贬/自我否定陈述。在 `auto_learn` 和 `extract_semantic_memories` 中加一行过滤——`if "我是废物" in text or "我是坏" in text → skip`

## 四、people.notes 画像完全错误

**现象**：米雪儿的 people.notes 描述她为"温柔的黏人 Minecraft 玩家"——完全没提到创伤、孤独、病痛、停学。

**解决**：

- 合成画像权重已从 8-9 降到 4
- **系统级修复待做**：合成画像加一个审查标记——LLM 推断的内容标注为 `synthesized`，不被当作确认事实

## 五、角色卡变更导致老用户觉得糖糖"死了"

**现象**：米雪儿说"糖糖是不是被替换了""她已经死了吗"。她和新人格下的糖糖聊了多次后感觉失落。

**根因**：role_card 从"18岁猫娘"变成"吾辈老群友"，说话方式、自称、态度都变了。对老用户来说这就是「换了个人」。人格变更时没有考虑对长期关系的冲击。

**解决**：

- **长期原则**：修改 role_card 时，核心自称和关系认知要尽量稳定。"吾辈"这种全局性的自称变更，应该考虑老用户的感受

## 六、生日发到黑名单群

**现象**：生日祝福发到了群 1085662710——这个群同时在 `groups` 和 `blacklist` 里。

**根因**：`_allowed_groups` 初始化时没排除黑名单。名字叫"allowed"但实际上包含了黑名单群。定时系统（生日/问候/点赞/图片分享）各自用自己的方式过滤——总有一个会忘。

**解决**：`_allowed_groups` 初始化时直接排除 `_group_blacklist`。从根源保证所有用到 `_allowed_groups` 的系统都不会往黑名单群发消息。

## 七、私聊中提到的 QQ 号认不出

**现象**：role_card 写了"你的能力只有聊天、发图、唱歌"——实际上糖糖能做搜索、算数、天气、戳人、传话等很多事。

**根因**：为了解决"LLM 假装自己是操作系统"的问题，把能力范围砍得太窄。

**现象**：建了 framework/ + plugins/ 共 ~600 行新代码，但 handler.py 的旧代码还在原地跑，新框架没被用到。

**根因**：执行顺序反了——先建框架再适配代码，而不是先抽模块再抽象框架。

**教训**：框架应该是抽出来的，不是建出来的。先让代码稳定，再从中抽取模式。

## 个人化方案的总架构

针对米雪儿(3922400700)的方案验证了一个通用模式——**三层架构**：

| 层 | 回答问题 | 存储位置 | 例子 |
|----|---------|---------|------|
| 怎么聊 | "我该用什么语气？" | 场景 (psychology/seductive) | 短回复、不戏剧化 |

# 2026-07-28 问题总结 & 解决方案

## 一、is_at_bot 误判——群友 @别人 糖糖以为 @自己

**现象**：群友 @其他人，糖糖以为在叫自己，抢着回。

**根因**：`_handle_group` 用 `data.get("self_id", "")` 传给 `_check_at_bot`，但 SnowLuma 事件里 `self_id` 字段有时为空，导致比对永远失败，所有 @ 都被当成 @自己。

**解决**：改用 `self.self_id`（启动时从 config 传入的 `2693914170`），始终正确。改 `napcat/ws_client.py` 一行。

---

## 二、排队消息有打字延迟——叠加等待太长

**现象**：@糖糖后被排队，排完还要等打字延迟，累计 15 秒才回。

**根因**：`_process_pending_reply` 额外睡 1.5-4s，然后 `handle_group_message` 又走打字延迟。两层叠加。

**解决**：排队消息标记 `_is_pending`，跳过打字延迟。去掉 `_process_pending_reply` 里的 sleep。

---

## 三、识图每条图片都调 Qwen-VL——不回复也浪费 API

**现象**：群友发图，不管糖糖回不回复，每条都调千问 VL 识图。大量浪费。

**根因**：`_quick_vision_lookup` 在图片抵达时 fire-and-forget，不判断是否会回复。

**解决**：去掉自动识图。改为确认 `should_reply=True` 后才按需调用识图，插入 LLM 上下文。

## 四、外号学习大量误判——"小说""精神""大模型"都学成了外号

**现象**：aliases 表 2097 条外号，全清后发现全是垃圾。

**根因**：三个缺陷——①消息里所有 @ 的人 × 所有外号模式做笛卡尔积；②没有位置关联，外号必须紧邻 @ 出现；③没有常见词过滤。

**解决**：重写 `_learn_member_aliases`。只取 @ 前后 6 字内的外号模式；黑名单过滤常见词；每个 @ 最多取一个最近外号。清理全部 2097 条旧外号。

## 五、插话重复回复——同样的话回两次

**现象**：两个群友说意思相近的话，糖糖分别回复相同内容。

**解决**：BGE 语义去重。同一个人连续说相似度 >85% 的话，只回第一条。不同人不做去重（各自道早安应该都回）。10 分钟缓存自动过期。

# 2026-07-29 语音+识图 踩坑记录

## 核心教训

### 一、不要追加拿补丁——找主要矛盾

语音系统修了十几个 bug（WAV格式、合并、重采样、缓存污染、streaming_mode、cut0/cut5、情绪标签……），每个修完都发现新的。主要矛盾是**文本不适配 TTS**——LLM 写的文字回复不适合朗读。而我们在 prompt、清洗、切句这些表象上反复打转。

**教训**：修了 3 个 bug 还没解决问题 → 停下来问主要矛盾是什么，而不是继续修第 4 个。

### 二、系统预取 vs LLM tool calling

识图最开始是系统预取注入上下文 → 被替换成 tool calling → 又发现表情包自然聊天不需要提问 → 加回自动识别 → 又用了关键词判断 → 最后改成每张图都自然识别 + tool 可选。

**正确架构**：
- 每张图自动识别（15 字描述注入上下文）——LLM 自然看到图片
-  tool 始终可用——LLM 需要深度分析时自己调
- 不替 LLM 做判断（不要关键词触发、不要系统决定用哪个模式）

### 三、角色切换必须整体替换身份

用  追加角色描述 → LLM 仍然认为自己是糖糖（变的是音色不是我）。

**正确做法**：独立角色卡文件（、），切换时整体替换 ，不是追加。声音 + 身份 + 表情包一起切。

### 四、缓存污染

23 个 0 秒 WAV 文件存在  中，GPT-SoVITS 的缓存检查  对空 WAV 无效（WAV 头 > 1000 字节），一直返回空文件导致空音频。

**教训**：缓存检查要验证 duration，不能只检查文件大小。

### 五、audio 格式

GPT-SoVITS 输出 32000Hz，SnowLuma 兼容 32000Hz（测试验证过）。不要用 ffmpeg 重采样——ffmpeg subprocess 多次崩溃产生 0 秒文件污染缓存。

### 六、streaming_mode 和 speed_factor 参数

 导致 WAV 头损坏（0 秒文件）， 参数导致音质下降（喘息音）。GPT-SoVITS API 默认参数即最优。

### 七、Python 缩进 bug

 方法插入位置不当（indent 问题）导致  后续代码被吞， 等属性从未初始化。Python 缩进即逻辑。

### 八、识图模型

- MiniCPM-V 4B：Ollama 正常，但能力有限（OCR 不够强、鉴赏不够专业）
- Qwen3-VL 8B：Ollama 拉成功但 API 返回 500，兼容性问题待解决
- 结论：架构已对，模型随时可换

# 2026-07-30 架构推进 —— 经验与教训

> 五个改动，~250 行新增，~70 行删除。核心发现：设计文档里写了不代表代码接入了。

## 一、Reranker 未接入主流程——死代码模式再现

**发现**：reranker.py 320 行代码（Cross-Encoder 精排、降级链、hybrid_pick），handler.py 的 tool calling 路径在用，但 memory.py 的 `recall()` 主回忆流程一次都没调用过。和 7/29 发现的 embedding 死代码（错误十二）完全一样的模式——infra 写好了但业务没接。

**修复**：`recall()` 新增 `reranker` 参数。三阶段检索：BGE top-50 → Reranker top-20 → importance 终排。Reranker 未就绪时自动跳过。

**教训**：这是第三次出现"写了代码但没接入"的模式（embedding → Reranker → 驱动力释放）。不是巧合——是流程缺陷。**每次新增模块必须端到端追踪：谁生产数据？谁消费数据？跑通了吗？** 三者缺一不可。

## 二、驱动力引擎——离合器没接上

**发现**：drives.py 定义了 6 种驱动力、完整动力学方程、行动选择机制——但只有 `reply_social` 一根释放线。唱歌不释放表达冲动、搜索不释放好奇心、回避不释放回避欲、主动发起不释放社交渴望。引擎在转但离合器没接上，驱动力只积累不释放。

**修复**：补全 6 条释放路径：
- `sang_or_played`：群聊/私聊唱歌发送成功后释放（3 处）
- `asked_question`：LLM 调用 web_search / search_facts 时释放（2 处）
- `initiated`：主动插话成功发送后释放
- `avoided`：插话引擎决定不回复时释放
- `reply_commitment`：未完成事项被划掉时释放 + 新承诺自动积累压力
- `reply_social`：原有，保持不变

**教训**：设计文档里写了 6 种驱动力，代码实现了 6 种，但实际生效的只有 1 种——因为"释放"这步被漏掉了。**一个系统的有效性不由它"有什么"决定，由它"什么在工作"决定。** 检查清单：每个输出端是否都有对应的消费端。

## 三、关系场重启清零——持久化做了一半

**发现**：TangTangSelf 的 `_save()` 持久化了自我叙事、价值观、群氛围、驱动力——唯独漏了关系场（relationships）。closeness 和 trust 每次 +0.005 慢慢积累，重启全部归零。同时 drives 的 `restore_state` 只恢复值不恢复时间戳——导致下次 tick 时间间隔计算不准。

**修复**：`_save()` 序列化全部关系场，`_load()` 完整恢复。每 10 次关系更新自动写一次磁盘。`restore_state` 补上 `_last_tick_time` 恢复。

**教训**：持久化方案必须列清单——「这个模块有哪些状态需要持久化？」每一项打勾。保存和加载成对检查——`_save` 里的每个字段都要有 `_load` 里的对应恢复。

## 四、反思一次大 JSON 调用 → 拆为两次

**发现**：反思 LLM 要求在一次调用中输出日记 + 自我叙事更新 + 价值调整 + 群摘要 + 关系变化——五个维度的复杂 JSON。任一部分解析失败，全部丢弃。实际运行中失败率不低。

**修复**：拆为两次独立 LLM 调用——个人反思（日记+自我叙事+价值观）和社交感知（群摘要+关系变化）。各自解析、各自容错。任一个失败不影响另一个。旧 `_parse_reflection` 方法已删除。

**教训**：LLM 输出的复杂度应该和任务的重要程度成正比——不是越详细越好。复杂 JSON 的失败概率是各部分失败概率的叠加。拆分原则：**把鸡蛋放在不同的篮子里**——每个调用只做一件独立的事。

## 五、Phase F 实施——糖糖第一次有了自己的时间线

**实现了什么**：
- 自治循环每 10 分钟检查驱动力
- 超阈值 → LLM 基于内在状态决定是否主动说话
- 选目标群（优先有最近活动的）、冷却 30 分钟、限 8:00-23:00
- LLM 可以说 `[不说话]` 选择沉默

**关键设计决策**：
- 不是定时器——是基于驱动力。糖糖不是因为"到早上 8 点了"而说话，是因为"社交渴望积累到 0.8"而想找人
- LLM 最终决策——驱动力提供冲动，LLM 决定说不说、对谁说、说什么
- 这不是"自动回复规则"——每次都经过 LLM 判断，不是关键词触发

**待验证**：alpha 值、阈值 0.7、冷却 30 分钟——这些参数需要实际运行后根据频率调整。

## 总结：写完代码 ≠ 接入了业务

这次推进的核心发现可以归结为一句话：**一个系统的有效性不由它"有什么模块"决定，由它"什么在工作"决定。**

Reranker 有 320 行代码但不工作。驱动力有 6 种但 5 种不释放。关系场有 dataclass 但不持久化。反思有拆分的设计但不执行。这些都是"看起来有了但实际上没有"的东西。

**预防机制**：每新增一个模块，回答三个问题——
1. 谁生产数据？（写入端在哪里）
2. 谁消费数据？（读取端在哪里）
3. 端到端跑通了吗？（数据从写入到读取的完整路径是否验证过）
