# 昵称与称呼——P0 昵称同步 + P1 自称归档

> 2026-10-24。触发：主人问「为什么 QQ 3922400700 这位用户还没有昵称？之前不是叫他
> 米雪儿吗？现在就没有了？」。调查结论见下，本文件记录**已实施**的 P0/P1 与
> **未实施**的 P2 立项（P2 单独一份：`legacy信任门补证据_立项研究_20261024.md`）。

---

## 一、调查结论（先纠正一个前提）

**`people.nickname` 从来没有过值，不是"有过后被删"。** `first_met=2026-06-26 20:10`
精确对上她第一条聊天记录（`chat_log id=129, 20:10:21`）——档案就在那一刻创建，
创建时写的昵称就是空串，之后 1886 次对话、5710 条消息，一次都没更新过。

**「米雪儿」不是她的名字，是她的角色扮演。**

| 时间 | 证据 |
|------|------|
| 2026-06-29 | 她自己说「我可是欧泊最年轻的搜查官米雪儿！」「我的鼎鼎大名就是米雪儿喵！」——这是《卡拉彼丘》的角色设定 |
| 2026-08-26 | 主人发 `/角色 米雪儿`——这是把**糖糖**切到米雪儿角色/音色，不是给她命名 |
| 2026-08-27 | 成展说「哈哈，其实是**自称**米雪儿的人」——旁人明确认定是自称 |
| 2026-07-27 | 糖糖叫了她很多次「米雪儿」，她回「几乎都错了」 |
| 2026-10-17 | 糖糖自己复盘：「7月27凌晨我说『你是米雪儿』，你当场说几乎都错了。**那次是我编的，我认**」 |
| 称呼曲线 | 7 月 80 次 → 8 月 29 次 → **9 月 0 次** → 10 月 2 次（且是"谈论这个名字"） |

所以"现在没有了"＝上下文窗口滚走之后，那个只活在对话里的称呼自然消失。
系统层面从来没存过。

**为什么一直没存进去（三层同时失效）：**

| 通道 | 机制 | 她的状态 |
|------|------|---------|
| `people.nickname` | **只在档案创建时写入一次，永不更新**；17 个 `get_or_create_person` 调用点里只有群关系图（`_build_cast_context`）传昵称，其余全传空 | 空 |
| `group_members.card` | 群事件实时采集群名片 | 空（她是群管理员但没设名片） |
| `aliases` | 全库只有 2 个写入点 | 0 条 |
| `memories` | 存了 17 条含「米雪儿」 | **90.6%（261/288）是 legacy_unverified，被信任门拒绝注入** |

昵称"只写一次"的规模证据：全库 538 人，**27 人昵称为空**（5.0%），
另有 **71 人昵称已过期**（例：现群名片「马斯克」，档案里还是「冷脸大鹅」）。

## 二、P0：昵称同步（只补空，不覆盖）

### 改了什么

| 位置 | 改动 |
|------|------|
| `store.get_or_create_person` | 行已存在且库内昵称为空、传入昵称非空时**补写**（带 `memory_revisions` 流水） |
| `store.touch_person_nickname`（新） | 消息入口专用：只补空、带进程内缓存挡重复查询、**不创建档案** |
| `handler._handle_group_message` | 在全部早退（黑名单/重放）之后调 `touch_person_nickname(user_id, nickname)` |
| `handler.handle_private_message` | 同上，放在 `testing_mode` 之前（补昵称是数据修复，不是 LLM 交互） |

### 三个刻意的设计决定

1. **只补空、不覆盖**。`people.nickname` 的语义是「跨群稳定身份」（既有设计：
   people 用 QQ 昵称、不用群名片），而群名片会随时改；自动覆盖会让身份跟着名片漂移。
   昵称的历史版本由 `memory_revisions` 承载。
2. **用 QQ 昵称，不用群名片**（`display_nick`）。保持既有设计，不引入跨群漂移。
3. **两层保护，职责不同**：
   - 提前 `return`（库里已有昵称就跳过）→ 省掉多余写
   - `UPDATE ... AND COALESCE(nickname,'')=''` → **并发安全**（两个进程同时补只有一个成功）

   ⚠️ 变异对照的 M5 曾试图验证第二层，被判**假变异**——因为去掉任一层行为都不变。
   这不是测试缺口，是纵深防御：两层管的是不同的事（性能 vs 正确性）。

### 已知限制

**补写发生在消息入口，所以存量 27 人需要「下一次有机会」才会补上**：她下次发言，
或者她在群关系图（`_build_cast_context`）里被传进来。不会凭空自动出现——
`chat_log` 里从来没持久化过发送者昵称（只有消息正文），没有第三个数据源可回填。

## 三、P1：自称归档（进 aliases，绝不进 nickname）

### 改了什么

| 位置 | 改动 |
|------|------|
| `aliases` 表 | 新增 `memory_id INTEGER DEFAULT 0`（证据指针：这个外号依据哪条记忆） |
| `store.add_alias` | 支持 `memory_id` |
| `store._self_name_from_text`（新） | 从一句记忆里抽自述名字（纯函数，无 IO） |
| `store._promote_self_declared_names`（新） | 扫描该用户的 active 记忆，把自述名字写入 `aliases(source='self_declared')` + 流水 |
| `store.complete_extraction_job` | 提取完成后在同一事务里调一次归档 |
| `store.get_alias_records`（新） | 带 source/证据/时间的别名读取（供档案页分层展示） |
| `console_api.memory_profile` | 新增**顶层** `addresses: {nickname, nickname_missing, aliases}` |
| `tools/补自称名字.py`（新） | 一次性回填脚本，默认 dry-run |

**为什么放顶层、而不是塞进 `person`**：前端 `MemoryProfile.person` 的声明是
`Record<string, string | number>`，而这里一个字段是 boolean、一个是数组——
塞进去会让声明与运行时自相矛盾。第一版就是塞进 `person` 的，前端只能靠
`as` 断言骗过编译器（**类型骗过编译器，正是"假绿"**），构造测试数据时 TS
直接报 `Property 'nickname_missing' is incompatible with index signature`。
已改为顶层独立块：`person` 代表 `people` 表的列（全是 string|number），
称呼是派生视图，本来就不属于它。这样声明和数据真正一致，不需要任何断言。

### 识别规则（刻意窄）

只认四种句式：`名字是X` / `我叫X` / `叫我X` / `X是我的名字`。

**刻意不认「我是X」**——它绝大多数是身份词：实测库里 `我是中国人`、`我是大二学生`、
`我是欧泊搜查官米雪儿呀！` 都会命中。允许的字符集也收窄到中日文/拉丁字母/间隔号，
再加虚词阻塞（`就没不是了吗呢…`）。

判据是：**宁可漏认，不可错认**——漏认只是少一个待确认的称呼，错认会污染档案。

这条判据是 dry-run 时抓出来的：第一版把 `叫我尾大狐酱就没问题` 抽成了
`尾大狐酱就没问题`（把语气尾巴吞进了名字）。加虚词阻塞后改为整条拒绝，
并把这条固化成回归测试。

### 三条不能让步的边界

1. **绝不写 `people.nickname`**。自述可能是角色扮演（「米雪儿」正是），
   写进身份字段等于替她认定一个假名字，比没有名字更糟。
2. **每条外号带 `memory_id`**，可回溯、可撤销。
3. **只认 active 记忆**——被推翻的记忆不能再提供名字，否则纠正过的错名会从旁路回来。

### 回填结果（2026-10-24 已执行）

```
qq=  2256983956  自称='穷到吃外卖'  依据记忆 #1808
qq=  2470404655  自称='李火旺'      依据记忆 #5819
qq=  2959482956  自称='秋华令音'    依据记忆 #24591
qq=  3922400700  自称='米雪儿'      依据记忆 #5108   ← 本次的主人公
```

四条都写进了 `aliases`（source=`self_declared`）与 `memory_revisions`
（actor=`extract:self_declared_name`，这是流水表上线后第一批真业务流水）。
**四人的 `people.nickname` 一个都没变**，其中 QQ 3922400700 仍是空串——
自称没有污染身份字段。

## 四、验证

- `tests/test_nickname_sync.py`（10 条）+ `tests/test_self_declared_names.py`（10 条）
- 变异对照：**6 个变异 6 真红 / 0 假变异**
  - P0：去掉昵称补写 / 去掉补写留痕 / 去掉净化
  - P1：去掉虚词阻塞 / 去掉证据指针 / 放开「我是X」句式
- 接线闸门：`promote_self_declared_names` 公开包装曾零引用 → **删掉包装**（归档已在
  `complete_extraction_job` 内接线），没有去扩大零引用基线
- 全量测试第一轮抓到 1 个真问题：`test_frontdoor_io` 的极简 mock `SlowStore`
  没有 `touch_person_nickname` → 群入口 `AttributeError`。修的是 **mock**
  （让它跟上真实接口），**不是**在生产代码里加 `getattr` 兜底——那种兜底会把
  "mock 与真实接口脱节"永久藏起来（与上一轮 `update_cluster_summary` 同一类）。
- 端到端（重启后查接口）：
  ```
  person 里已无异构字段（nickname_missing / aliases_detail 均已移出）
  addresses = {「nickname」: "", 「nickname_missing」: true,
               「aliases」: [{alias:'米雪儿', source:'self_declared', memory_id:5108}]}
  capabilities.revisions = 4
  ```
- 前端 `npx tsc --noEmit` exit 0，且**新类型的声明与结构完全一致**（不再需要断言）
- 静态检查 undefined = 0

### 顺带发现的一个既有 flaky（不是本次引入）

`test_force_engage_cleanup_does_not_block_event_loop` 在一次全量跑里红过：
它的判据是 `assert ticks >= 20`——在 `await asyncio.sleep(0.3)` 期间数 event loop
心跳次数，理论上 ~300，阈值 20。单跑 **6/6 全过**，且它只用
`ConversationTracker` + `SimpleNamespace`，跟昵称/store 没有任何调用关系。

判定：**时间敏感判据测的是环境而不是行为**（CLAUDE.md 教训 #37 的第 ② 种形态）。
全量连跑 3272 个测试时机器负载高，asyncio 调度被推后就会偶发。本次没有改它——
改判据属于另一件事，但记在这里，免得下次有人把它当成自己改动引入的回归。
**同一份代码随后重跑全量：3272 passed, 0 failed（16:48）**，坐实了 flaky 判定。

## 五、没做的事（留给 P2）

`#5108「名字是米雪儿」` 这条记忆本身仍是 `legacy_unverified`（证据 0 行），
**它进不了注入**——也就是说糖糖现在能看到「她自称米雪儿」这个档案标签，
但记忆正文仍然拿不到。这是 74% 存量 legacy 数据的问题，不是称呼问题，
单独立项：`legacy信任门补证据_立项研究_20261024.md`。
