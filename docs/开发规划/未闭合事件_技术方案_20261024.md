# 未闭合事件（`open_loops`）—— 技术方案（待实施）

> 对应 `糖糖的存在方式_战略与设计_20261024.md` 设计一 / 判据 1。
> 状态：**方案已定，未实施**。本文是施工图，照做即可，不要重新设计。
> 上游依赖：不确定性三档注入（2026-10-24 已落地，开关已开）——它让「记得但没证据」
> 的事能带保留地说出来，正是未闭合事件需要的那种语气。

---

## 一、要解决什么

**判据 1（主人原话）**：她能不能说出「你上次说的那件事，后来怎样了」？

现在不能。她**有**相关记忆（`event` 类型的「她说要去面试」），但没有任何东西把
「那件事还没结」这件事本身表示出来。记忆只能被检索，**不会主动来找你**。

一个完整的人身上永远有几件没结的事。陪伴者不是「知道这些事实」，而是**这些事
在她那儿也悬着**——她会在合适的时候问一句「后来呢」。

**已取证的三件事**：

1. 全库没有 `open_loops` 或等义表（`store.py` 的 40 张 `CREATE TABLE` 里没有）。
2. 已有一个 `key='promise'` 的记忆类型，但它是**糖糖自己**的承诺
   （`remember_self(bot_qq, ..., key="promise")`，要求 `target_qq` + `evidence_ids`，
   由 `fulfill_self_promise` 结算）。**不是**「对方的未闭合事件」——方向相反，
   不能复用。
3. 驱动力 `commitment`（承诺压力）已经存在，且**消费点稀缺**（2026-10-13 P1 才补上
   新承诺升压/兑现释放）。方波会接这一层，但不能拿驱动力当事件对象——
   驱动力是「她此刻多在意」，不是「哪件事没结」。

## 二、设计

### 2.1 表结构（新表，不动 `memories`）

```sql
CREATE TABLE IF NOT EXISTS open_loops (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    qq_id         TEXT NOT NULL,              -- 这事悬在谁身上（对方）
    topic         TEXT NOT NULL,              -- 一句话说清「什么没结」
    kind          TEXT DEFAULT 'plan',        -- plan|promise|worry|request|deadline
    expected_at   TEXT DEFAULT '',            -- 预计发生/到期日 YYYY-MM-DD；空=不晓得
    source_memory_id INTEGER DEFAULT 0,       -- 来源记忆（可回溯证据链）
    source_group_id  TEXT DEFAULT '',         -- 作用域（与 memories 同口径）
    status        TEXT DEFAULT 'open',        -- open|resolved|dropped|expired
    asked_count   INTEGER DEFAULT 0,          -- 已经追问过几次（防骚扰）
    last_asked_at TEXT DEFAULT '',
    resolved_at   TEXT DEFAULT '',
    resolution    TEXT DEFAULT '',            -- 「问了、知道了、或者放弃」的说明
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_open_loops_open ON open_loops(qq_id, status);
```

**为什么是独立表而不是 `memories.key='open_loop'`**：记忆是**可检索的历史**，
未闭合事件是**有状态、会被改写的对象**（`asked_count` / `status` 每次追问都变）。
塞进 memories 会让「记忆变更流水」被高频状态改动淹没——那正是
`store.py` 里明写的「不记纯计数」边界。

### 2.2 提取识别（写侧）

在 `memory.extract_semantic_memories` 的 prompt 里加**一类输出**，而不是加一个
新的提取器（避免两套 LLM 调用、两套口径）：

- 新增 `type: "open_loop"`，字段：`topic`、`kind`、`expected_at`、`evidence_quote`、
  `evidence_ids`。
- 规则（写进 prompt）：
  - ✅ 「明天要去面试」「下个月体检」「说了要写但还没写」「想跟某人道歉」——
    有**将来时/计划/承诺/担忧/截止日**
  - 🚫 已经完成的事（「面试完了」）——那是普通记忆
  - 🚫 糖糖自己的承诺——那条路已有 `remember_self`
  - 🚫 无时间指向的空泛愿望（「以后想环游世界」）——不是「没结的事」
- 落库：`store.upsert_open_loop(...)`，按 `(qq_id, topic 归一化)` 去重；
  同一件事重复提到 → 更新 `expected_at`，**不新建行**。
- 证据：`source_memory_id` 指回提取出的那条记忆；记忆本身走既有证据校验。

**关键约束**：提取是 LLM 的决策域，系统**不做关键词门控**（反模式 #9/#10：
「后天」「下周」这类中文时间词枚举不完，2026-08-16 已定「意图解析单一决策源」）。

### 2.3 注入（读侧）——只报告事实，不问「该不该问」

每轮对话开始时（群/私聊都算，但**私聊优先落地**），查这个人的 `status='open'` 行：

```
到期/超期优先（expected_at <= 今天），其次最近创建的
至多 3 条；已追问过 2 次以上的不再浮上来（防骚扰）
```

注入形态（`protocols.py` 统一文本，不在这里硬编码）：

```
<背景·悬着的事>
- 她说过要去做 X（预计 10-28，已过 2 天）——已经问过 1 次
- 她提过想跟某人和好，没说时间
</背景·悬着的事>
```

**绝不做** `if 该追问: 追问`（反模式 #9/#10）。系统只提供「有这两件没结的事」这个
事实，**说不说、怎么说由她定**——她可以在对方提到相关话题时顺一句，也可以这轮不说。

### 2.4 收尾工具 `resolve_open_loop`

给 LLM 一个工具（`@register_skill`，`method_type="behavior"`）：

- 参数：`loop_id`（必填）、`outcome`（`asked`=问过了/`resolved`=已知结果/`dropped`=不再跟进）、
  `note`（可选，一句话说明）
- 行为：
  - `asked`：`asked_count += 1`、`last_asked_at = now`，状态仍 `open`
  - `resolved`：`status='resolved'`、`resolution=note`
  - `dropped`：`status='dropped'`
- **只允许操作本轮的 `qq_id`**（防跨人改写，同 `correct_memory` 的主语闸门）

工具描述里必须写明：「对方提到那件事的后续时，如果你已经从对话里知道结果，
调用它收尾；不确定结果就不要猜着收尾。」

### 2.5 过期与清理

- `expected_at` 过 30 天且 `asked_count >= 2` → `status='expired'`（不再占注入位）
- `status != 'open'` 的行永不再注入（读路径只认 `open`）

## 三、分批落地（不要一次做完）

| 批 | 内容 | 验收 |
|----|------|------|
| **L1** | 表结构 + `store` 读写方法（`add_open_loop` / `list_open_loops` / `resolve_open_loop` / `expire_open_loops`） | 单元测试：状态机边界（open→resolved 不可逆、跨人拒绝） |
| **L2** | 提取识别（prompt 加 `open_loop` 类型）+ 落库 | 用真实历史消息重跑一批，人工抽样 20 条判定对不对 |
| **L3** | 注入（`protocols` 文本 + handler 每轮查询） | 闸门：只有 `open` 且未超次数上限的才注入 |
| **L4** | `resolve_open_loop` 工具 | 端到端：问了→`asked_count` 增→不再重复浮上来 |
| **L5** | 过期清理 + 观察指标 | 3 天观察：她主动提旧事的次数、误报（把已结的事当没结） |

**第一版只开私聊**（与不确定性注入同一条边界）——群里把甲的未闭合事件说给全群，
错配影响面是全场。

## 四、验收

1. **闸门测试**：状态机不可逆（resolved 不许回 open）、跨人越权拒绝、
   `asked_count` 上限后不再注入、过期行不注入。
2. **变异**：
   - M1 去掉「只查 open」条件 → 红
   - M2 去掉跨人校验 → 红
   - M3 注入时把「已问过 N 次」当未问过 → 红
3. **端到端**：构造「面试」事件 → 到期 → 注入块出现 → 调 `resolve_open_loop(asked)`
   → 下一轮不再出现（未超上限时降级为「已经问过」）。
4. **观察指标**（主人体感，预测台账 #9）：主人主动提起「她记得我上次说的事」
   ≥1 次/周（截止 2026-11-30）。

## 五、风险与缓解

| 风险 | 缓解 |
|------|------|
| 变成骚扰机器（每轮都问「那件事怎样了」） | `asked_count` 上限 2 + 冷却 + **由 LLM 决定说不说** |
| 把已结的事当没结 | 提取时明确「已完成的不算」；`resolve_open_loop(resolved)` 收尾 |
| 误提别人的事（群里转述） | 提取只认「发言人本人的将来时」；跨人越权闸门 |
| 提取成本上升 | 复用既有提取调用（同一次输出多一类），不新增 LLM 调用 |
| 表结构写错难回滚 | 新表独立，`DROP TABLE open_loops` 即完全回滚，不碰 memories |

## 六、回滚

```sql
DROP TABLE IF EXISTS open_loops;   -- 全部回滚，不影响任何既有记忆
```

代码侧：注入点用 `if not enabled: return ""`，开关 `memory.open_loops_injection`
（默认 `false`，与不确定性注入同款）。

## 七、为什么不在这轮一次做完

工程最大（设计文档判「1 周」），而且它改的是**每一轮对话的注入内容**——影响面
比数据批次大。按 L1→L5 分批，每批可独立验证、独立回滚；仓促合并等于拿线上
对话做实验（教训 #6/#14 都是「框架先行、接线没做完」）。
