# 桌面端：「她怎么想的」参数化 + 预警体系（2026-10-25 第 47 轮）

> 起因（主人原话）：「后端还有很多参数可以调节，把必要的参数放到前端，比如各环节的
> token 预算等等，这部分需要先调研后端；『她怎么想的』这部分展开需要的完整流程、
> 她做了什么、她决定了什么这三个部分的有效信息太少了……作为运营者我需要更多的参数
> 显示，以及有效的预警，作为一个取代日志的存在；作为用户我需要她的运作方式，
> 信息是否有效等。同样多视角给出方案。」
>
> 本文先给**调研事实**（全部实测，不猜），再给**四视角方案**，最后给实施分级。

## 一、调研：后端到底有多少可调参数

参数分**三层**，性质完全不同，混在一起谈就会得出错误结论（教训 #38：同一个量两个换算点）。

| 层 | 存哪 | 数量 | 谁能改 | 前端现状 |
|---|---|---|---|---|
| **L1 配置参数** | `config.yaml` | **120 个叶子键** | 运营者（设置页） | 设置页覆盖 **63 个**，缺 **~33 个** |
| **L2 代码常量** | `agent/*.py` 模块顶部 | **45 个**（预算/阈值/上限） | 只能改代码 + 重启 | **0 个有出口** |
| **L3 每回合实测** | `turn_traces.prompt_digest` | **26 个字段** | 只读观测 | **0 个显示** |

### 1.4 三缺矩阵：后端有 → API 出 → 前端显示

| 数据 | 后端采集 | `/replay` 出 | 前端显示 | 缺口 |

| 工具调用 name/args/result/ms | ✅ 23% 轮次 | ✅ | ✅ 折叠 | **无效性判定** |
| 决策 decision/status/tool_calls/耗时 | ✅ 2261 条 | ✅ | ✅ 5 个 KV | **理由、error_code** |
| 反馈 sentiment/confidence/reply_ms | ✅ 6483 条 | ✅ | ✅ | **direction_verified** |
| **token 四段账本** | ✅ | ❌ | ❌ | **全缺** |
| **背景块预算 + 每块命运** | ✅ | 部分（仅流程图 2 站） | ❌ | **全缺** |
| **系统提示词 10 个小节** | ✅ | ❌ | ❌ | **全缺** |
| **记忆标记计数（✏️/💭~）** | ✅ | ❌ | ❌ | **全缺** |
| **缺口告知是否注入** | ✅ | ❌ | ❌ | **全缺** |
| **错误码** | ✅ `decision_runs.error_code` | ❌ | ❌ | **全缺** |
| **预算常量本身（1100/6000/240…）** | 代码里 | ❌ | ❌ | **全缺** |

**结论：这不是「后端没数据」，是「投影层只挑了最粗的 5 个字段」。**
`turn_replay()` 把 digest 交给了流程图构建器，自己没往外吐——数据在库、在内存、
在 trace 里，死在最后一次投影上。这是教训 #47 的变体：**内容看得见（流程图有 9 站），
掩盖了投影层丢字段（账本没出）**。

## 二、发现的三个真实异常（有证据，可预警）

### 异常 1：工具定义 5954 tokens ≈ 总预算 6000 的 99%

```
token_sections = {tools: 5954, system: 2386, history: 318, user: 1042}   → 合计 9700
token_total    = 9240（report.total 实际值，含 user）
BUDGET_TOTAL   = 6000（context_builder 的「上下文预算」）
```

⚠ **口径必须先钉死**（否则又是上次那个「假超支 54%」的坑）：
`BUDGET_TOTAL=6000` 约束的是 `_truncate_text` 对 **system_prompt** 的裁剪，
而 `token_sections.tools` 是**工具定义**（请求里另一块），两者**不是同一个分母**。

真实可说的话只有一句：**工具定义 5954 tokens 是每轮固定开销，比上下文预算本身还大。**
这不需要「超支」这种刺眼词，但运营者应该看得见——因为它直接决定
「她还有多少余量装记忆」。**显示时必须标清分母，禁止算百分比混比。**

### 异常 2：背景块 1033 / 1100 = 94%，逼近上限

同一轮 6 个块全在，但「记忆」块被从 **297 裁到 217 t**（`status: truncated`），
且 `gap_notice: true` 说明**已经触发了「缺口」告知**——她被明确告知材料不全。
这是健康的降级，但运营者应该看见「这一轮她拿到的记忆被砍了 27%」。

### 异常 3：`turn_traces` 只有 253 行 / 2 天，`feedback` 有 6483 行

trace 采集覆盖率低（trace 功能 2026-10-24 才上线，且只记「触发消息」）。
→ 界面必须能区分「**没有痕迹**」和「**痕迹里没问题**」，不能都显示成一片绿。
这是四态里 `skip` 的语义，也是主人说的「哪个环节没有坏、哪个环节出了问题」。

## 三、四视角方案

### 3.1 产品经理视角——这一栏到底要回答什么问题

「她怎么想的」不是日志浏览器，是**决策辅助界面**。日志回答「发生了什么」，
它必须回答「**这条回复可靠吗、要不要动什么**」。所以三段各给一个**结论句**开头：

| 段 | 结论句（一句话判定） | 支撑证据 | 可操作项 |
|---|---|---|---|
| 完整流程 | 「9 站全通」/「第 4 站记忆被裁了 27%」 | 每站四态 + 参数 | 跳设置（预算/优先级） |
| 她做了什么 | 「查了 3 次记忆，2 次有料 1 次空手」 | 工具分类 + 结果有效性 | 重跑检索 |
| 她决定了什么 | 「决定回复，因为她判断你在等她」 | 决策 + 理由 + 耗时 | 看决策依据原文 |

**信息分层**：结论句永远可见 → 数字永远可见 → 解释文字进「讲解模式」开关。
这条已经在第 45 轮立好（`.explain-only`），本轮继续遵守。

**反目标**：不要做成「把所有字段平铺」。教训 #48——参数全摆出来 ≠ 人看得懂。
每个数字必须带三件套：**分母、来源、阈值**。

### 3.2 前端分析师视角——怎么落地

1. **一次请求拿全**：仍只调 `/replay`，新增字段而不是新端点（省往返、向后兼容）。
   老后端没新字段 → 前端按 `undefined` 隐藏该块，不报错。
2. **组件拆分**（不新增页面，只新增块）：
   - `TokenLedger`——四段横条 + 背景块命运表（新）
   - `ToolEffectList`——在「她做了什么」里替换 `ToolStepView` 的头部（改造）
   - `DecisionCard`——「她决定了什么」从 5 个 KV 升级为带理由的卡片（重写）
   - `ParamChip`——参数小签（值 + 分母 + 来源 tooltip），复用现有 `fg-param` 样式
3. **密度开关**：讲解模式控制「解释段」，**数字不折叠**；详细 JSON 仍折叠。
4. **四态不塌缩**：`ok/warn/error/skip` 四色，`skip` 用灰不用绿（否则「没痕迹」被当成「健康」）。
5. **性能**：digest 最大 ~2KB，`/replay` 本来就在抽屉打开时调一次，无压力。

### 3.3 运营者视角——我打开它想做什么决定

我会问六个问题，界面必须都能答：

1. **这轮正常吗？** → 顶部一句话 + 四态计数
2. **token 花在哪了？** → 四段账本（工具/系统/历史/用户），带绝对值和上限
3. **她的记忆够用吗？** → 背景块用了几成、哪块被裁、缺口告知有没有触发
4. **她查了但没查到什么？** → 工具「空手率」，这是「她不知道」的直接证据
5. **她为什么沉默/为什么回复？** → 决策理由原文（skip_response 的 `reason`）
6. **哪个参数我可以调？** → 每个数字旁标「来源：常量 / config / 固定」

**预警规则（我要的「取代日志」）**——只有三条，宁可少不要吵：

| 级别 | 触发条件 | 文案示例 |
|---|---|---|
| 🔴 异常 | 工具报错 / decision failed / error_code 非空 | 「检索工具报错了，这轮她没查到记忆」 |
| 🟡 打折 | 任一块 `truncated` / `dropped` / 预算 ≥90% | 「记忆块被裁 27%（297→217t），背景预算用到 94%」 |
| ⚪ 无痕迹 | 没有 trace / 没有工具 / 她决定沉默 | 「这一轮她没调工具」「这一轮她选择不说话」 |

### 3.4 聊天对象视角——我怎么知道她真的在听

我不关心 token 数字，我关心三件事，所以要有一句话翻译：

1. **她看到我说的话了吗？** → `user_bg_labels` 里有「窗口」「提及」= 看到了；
   `history_count=14` = 记得前面 14 条。
2. **她记得我是谁吗？** → 「关系档案」块在且 `kept`；`memory_marks.corrected=1`
   = 有一处是她被我纠正过的（✏️），`uncertain=2` = 两条模糊记忆（💭~）。
3. **她的回答是不是编的？** → 工具调用里有 `search_facts` 且结果非空 = 基于事实；
   结果为空 = 她在凭印象说。

这三点用**一句人话**放在三段顶部（进讲解模式），不塞数字。

## 四、方案（按主人两句话拆）

### 4.1 「把必要的参数放到前端」

**P0 — Token 账本（新增 `prompt_ledger`）**
`/replay` 增加字段，后端做投影 + 判定（判据只有一处，第 47 条教训）：

```jsonc
"prompt_ledger": {
  "sections": [                       // 四段，各自带分母与来源
    {"key":"tools",  "label":"工具定义", "tokens":5954, "limit":null,
     "note":"每轮固定开销，不计入上下文预算"},
    {"key":"system", "label":"系统提示词","tokens":2386, "limit":1800,
     "note":"超出核心层预算，按句边界裁过"},
    {"key":"history","label":"历史对话","tokens":318, "limit":null},
    {"key":"user",   "label":"本轮消息","tokens":1042, "limit":null}
  ],
  "context_budget": 6000,             // BUDGET_TOTAL，只约束 system+history+user
  "context_used": 3746,
  "measured_total": 9240,             // 与上面不同分母，单列，禁止混算百分比
  "background": {
    "limit": 1100, "used": 1033, "left": 67,
    "protected_overflow": false, "evidence_reserve_used": false,
    "gap_notice": true,
    "blocks": [{"label":"记忆","priority":7,"tokens":217,"before":297,
                "status":"truncated","cut_pct":27}]
  },
  "system_sections": ["你是谁", "…"],
  "memory_marks": {"corrected":1, "uncertain":2},
  "warnings": [{"level":"warn","key":"bg_budget",
                "text":"背景预算用到 94%（1033/1100），记忆块被裁 27%"}]
}
```

**P1 — 参数来源面板**：把 45 个常量 + 关键 config 键做成只读清单
（值 + 文件:行 + 能否在设置页改）。目的不是让运营者去改代码，是让他知道
**「这个数是谁定的」**——现在他只能猜。

**P0.5 — 设置页补 18 个真缺口键**（`catch_up` 整组优先）。

### 4.2 「三块的有效信息」

| 段 | 现在 | 补什么 |
|---|---|---|
| 完整流程 | 9 站 + 参数 | 顶部账本摘要条；第 2 站（组装）挂 `TokenLedger`；第 4 站（记忆）挂每块命运 |
| 她做了什么 | 工具名 + 耗时 + 折叠 JSON | 工具**性质分类**（检索/动作/决策）、**结果有效性**（空/报错/有料）、**空手率**汇总、决策类工具提取 `reason` 原文 |
| 她决定了什么 | 5 个 KV | 决策**理由**（从 skip_response/工具 args）、`error_code`、耗时分解、四态徽章、一句话结论 |

## 五、实施分级

| 级 | 内容 | 风险 | 验收 |
|---|---|---|---|
| **P0** | `prompt_ledger` 后端投影 + 判定；前端 `TokenLedger` + 预警条；三段结论句 | 低（只加字段，老字段不动） | pytest 闸门 + 变异对照 + 真实数据渲染 |
| **P0.5** | 设置页补 `catch_up` 等 18 键 | 低（schema 加行） | 保存后 config 落盘复核 |
| **P1** | 工具有效性判定 + 决策理由提取 | 中（要解析 args/result 语义） | 用真实 253 条回放逐条核对 |
| **P2** | 参数来源面板（45 常量清单） | 低 | 数字与代码一致（脚本生成，不手抄） |

**不做**：把常量搬进 config.yaml 让运营者热调。理由：预算类常量改错会静默改变
她的记忆容量，且需要重启才生效，收益低于风险；先让他**看见**，再谈**能调**。
（这条写进立项文档的「不做」清单，避免下轮又被提出来。）

### 7.2 顺带修掉的三个真实缺陷（都不是计划内的）

这一节是这轮最有价值的产出——**计划只想到「加参数」，验证过程挖出了三个界面在撒谎的地方**。

| # | 现象（真实数据） | 根因 | 修法 |
|---|---|---|---|
| 1 | 实测 8 条 trace 里 6 条 `token_sections` 缺失，账本会显示 `context.used=0` 再判 **ok** —— 等于告诉运营者「这轮没花钱」，实际 9265t | `_last_token_report` 那一刻是 None（handler.py 20:13 才补的分账落库） | 新增 `partial` 标记 + `ledger_partial` 预警；**无分账时不许说「材料齐」** |
| 2 | 第 4 站（背景注入）写「**0 块**进了 prompt」，同一站下面又列着 7 个注入过的标签 | `in_prompt` 只数 `backgrounds.blocks`，老 trace 没有这个字段（当天才落库），但 `user_bg_labels` 是有的 | 有标签时用标签数兜底并**注明口径**（「按注入标签统计，逐块用量这次没采到」）；站态判 `warn` 不是 `ok` |
| 3 | 第 5 站（记忆召回）items 写「记忆块：**已注入**」，did 却写「记忆块**没进** prompt」 | 同上：`memory_status` 是空串 → 走进最后的 `else`；而 items 的默认值走的是 `memory_injected` | 补 `elif memory_injected:` 分支，判 warn 并说明「看不出有没有被裁」 |

**教训（已进教训表 #51）**：*同一站内自相矛盾比信息少更糟*——信息少时运营者
知道自己不知道；自相矛盾时他不知道该信哪一行，会去查一个不存在的故障。

### 7.5 顺手删掉一条自己造的噪音

第一版有一条「背景预算 ≥90% → warn」。端到端一看：`fit_backgrounds` 的设计
就是**把预算按优先级填满**（实测连续两轮 1033/1100、992/1100），所以它每轮
都会响。**每轮都响的预警等于没有预警**——运营者会学会无视整个面板。

改为「只报真的丢了东西」：有块被裁 / 被淘汰 / 注入链断了。预算用量仍然显示
在账本顶部，只是不弹预警。同一天在同一份代码里先删过一条 `tool_many`
（工具调用 ≥4 次就报警，而 `tool_loop_limit` 默认就是 4），同一个错误犯了两次
——**判据要问「这个量会不会每轮都为真」**。
