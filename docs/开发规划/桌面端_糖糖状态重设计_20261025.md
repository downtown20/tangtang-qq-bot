> 主人原话：「现在的前端仍然存在可视化低、可操作性低等问题，主要集中体现在
> 『她怎么想的』和『糖糖状态』这两个栏目上，因为这两个栏目本来就是用来显示状态的。
> 『她怎么想的』已经优化过一下，有改进；但『糖糖状态』这部分一直没动。
> 请分别以产品经理、前端分析师、用户、项目经理等不同角色的视角，

## 1. 取证：现状是什么样的

### 1.1 「糖糖状态」到底在哪

| 位置 | 组件 | 内容 |
|---|---|---|
| 会客厅右栏 | `Console.tsx` 的 `.cs-panel`（标题就叫**糖糖状态**） | 9 个 section：情绪 / 驱动力 / 主导 / 自我叙事 / 价值倾向 / 关系场 / 记忆 / 模型 |
| 导航「概览」 | `Dashboard.tsx` | **4 个数字卡**（认识的人/记忆条数/对话记录/表情包）+ 进程开关 + 模型 + 快捷入口 |

主人说的「一直没动」是**右栏那个 panel**：它是从 v1 沿用下来的，
自 2026-10-24 会客厅改版后再没被设计过。

### 1.3 现状的五个具体问题

| # | 问题 | 证据 |
|---|---|---|
| 1 | **没有结论层**：打开先看到「情绪」标题和一根细条，要自己汇总 | 9 个 section 等权重平铺，没有「她现在怎么样」 |
| 2 | **数字无锚**：「精力 31」算低吗？和她自己比呢？ | `cs-gauge` 只给进度条，不给档位词与后果 |
| 3 | **无趋势**：只有当前值 | 没有「1 小时前 → 现在」 |
| 4 | **不可操作**：289 人只显示 5 个，点不动；记忆 22669 条点不动 | `cs-rel` / `cs-memo` 都是纯展示 div，无 onClick |
| 5 | **长文本裸奔**：叙事 130 字、价值观 60 字，挤在细栏里 | `cs-quote` 无折叠、无来源 |

### 1.4 「注释很密集」的现状

第 17 轮为了「小白也能看懂」，在「她怎么想的」里加了大量解释：
`role`（这站干什么）、`logic`（判断依据）、`param-doc`（每个参数的解释）、
`fg-howto`（怎么看这张图）、`fg-legend`（三态含义）。

**对第一次看的人这是必要的，对老手这是噪音。** 主人要求「一个开关控制注释显示」
——正确，因为同一份界面要服务两类读者。

## 2. 四个角色会怎么设计

### 2.1 产品经理视角：先定「这页回答什么问题」

一个状态页最怕的是「把所有数据摆出来」。先定它要回答的三个问题，
再倒推信息层级：

| 用户问题 | 对应数据 | 层级 |
|---|---|---|
| **她还好吗？**（要不要担心） | 精力/心情/耐心 + 主导驱动力 | **第一屏，大字** |
| **她在想什么？**（为什么这样） | 自我叙事、价值倾向、最近体验 | 第二层，可展开 |
| **她对谁/记得什么？**（追溯） | 关系场分布 + 记忆最近 | 第三层，可跳转 |

产品判据：**主人打开这一页后 5 秒内能不能说出「她现在怎么样」**。
说不出来，就是设计失败——不管塞了多少数据。

副产品：`Dashboard`（导航「概览」）和右栏「糖糖状态」**是同一个东西的两种尺寸**，
必须共用一套组件（否则两份实现必然漂移，教训 #47）。

### 2.2 前端分析师视角：缺的不是数据，是「可视化语法」

同一个 `snapshot`，不同的数据形状要用不同的图形，而不是一律「标题+进度条」：

| 数据形状 | 现状 | 该用什么 |
|---|---|---|
| 单标量 + 量程（精力 31/100） | 一根细条 | **仪表卡**：大数字 + 档位词（偏低）+ 极值刻度 + 颜色语义 |
| 6 个可比标量（驱动力） | 6 根同宽条 | **排序条形图**：按值排序、主导项高亮、`urgent` 打急躁标 |
| 比例分布（289 人 = 34/15/240） | 一行文字 | **堆叠条（stacked bar）** + 图例，一眼看出「她认识的人里 12% 是知己」 |
| 时间线（近期体验 5 条） | 竖排小字 | **时间轴**：时间点在左、事件在右，可展开更多 |
| 长文本（叙事/价值观） | 裸引用块 | **引用块 + 折叠 + 来源标注**（什么时候形成的） |
| 计数（记忆 22669） | 一行文字 | **大数字 + 增量 + 入口按钮** |

另外三条工程判据：

1. **每个数值都要有锚**——要么给量程（/100），要么给档位词（偏低），
   要么给对比（比 1 小时前 ↓12）。三者至少给一个，否则数字没有意义。
2. **不编数据**：后端没有的（例如驱动力阈值）就不画阈值线，
   不为了好看造一条假刻度（教训 #4/#18：显示层不能编造事实）。
3. **空态要说话**：`snapshot` 每个分区独立 try，可能为 null；
   每个区块都必须有「暂无数据」的降级文案，而不是塌掉。

### 2.3 用户（主人）视角：我打开只是想看一眼她还好吗

- 我不想滚动 9 屏。**先给我一句话。**
- 「精力 31」——**这是什么意思？要不要管？** 请告诉我「偏低，她会更容易累」。
- 「她为什么突然这么主动？」——**我要看主导驱动力**，而不是 6 根等长条。
- 「她最近记住了什么？」——**点一下就跳过去**，不要让我自己去找菜单。
- 我不需要每次都被解释。**给我一个开关，关掉讲解就只剩数据。**
- 我不喜欢一动不动的东西——**能点的要有反馈，能深挖的要有去处。**

### 2.4 项目经理视角：分期、验收、风险

| 期 | 内容 | 验收 |
|---|---|---|
| **P0（本轮）** | ① 讲解模式开关（全局）② 「糖糖状态」重排成「结论→现在→原因」三层 + 仪表卡/排序条/堆叠条/时间轴 ③ 每个区块的跳转入口 | 5 秒能答「她怎么样」；点得动；开关生效 |
| **P1** | 趋势（1h/6h/24h 变化）、记忆图谱入口联动、关系分布点开看人 | 数值有对比，跳转能落到目标 |
| **P2** | Dashboard 与会客厅右栏共用 `<StatusPanel>`、指标可勾选 | 两处同一套组件，无重复实现 |

**风险 1：两处状态视图漂移。** 对策：本轮就把「状态呈现」抽成
`components/StatusPanel.tsx`，`Console` 与 `Dashboard` 都 `<StatusPanel>`，
只靠 `variant="panel" | "full"` 区分密度。

**风险 2：讲解开关变成「藏问题的开关」。** 对策：开关只控制**解释性文字**
（role/logic/param-doc/howto/legend），**不控制**数据、结论、异常原因（`note`）。
关掉讲解后，界面必须仍然能看出「这站坏了」。

**风险 3：为了好看编数据。** 对策：所有图形只映射后端字段，
没有的就不画；闸门（闸门在测试里）+ 代码注释写明「不要加假刻度」。

## 4. 讲解模式（主人第 3 条要求）

**机制**：`html[data-explain="off"]` 下隐藏 `.explain-only`，纯 CSS 生效，
不需要给每个组件传 prop（少一条容易断的线）。

**存在哪**：`localStorage.tangtang.explainMode`，默认 **开**（新用户/小白需要）。

**开关在哪**：标题栏右侧（和主题切换并排），图标 + 「讲解」二字。

**控制什么**（明确清单，避免变成「藏问题开关」）：

| 隐藏（解释性） | 保留（事实性） |
|---|---|
| 站点 `role`「这站做什么」 | 站点标题、耗时、状态灯 |
| `logic`「判断依据」 | `did`「实际发生了什么」 |
| 每个参数的 `doc` 解释 | 参数名与值 |
| `howto`「怎么看这张图」 | 冻结的三态图例 → 改为 tooltip |
| 三态图例整行 | 异常原因 `note` |
| 情绪/驱动力旁的档位解释 | 全部数值与图形 |
