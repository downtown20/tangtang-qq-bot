### ② 私聊真的只显示私聊（数据正确性优先）—— ✅ 已修（2026-10-25 第 17 轮）

> **结论**：前端一行没改；根因在 `agent/store.py` 两个函数漏了私聊限定。
> 取证、修法、7 条闸门、3 个变异、端到端对账全在

- **第一步不是改前端，是取证**：读 `tools/desktop_bridge.py` 里「按会话 key 取消息」的实现，
  确认 `private:<qq>` 是否被当成 `desktop:<id>` 或没过滤 `group_id`。
- **可能的根因**：
  1. 会话 key 解析后没带进 SQL → 取到全量 chat_log（最可能）；
  2. `chat_log.group_id` 私聊行是空串、群聊是群号，过滤条件写反/漏写；
  3. 前端按 `kind` 选了 key，但列表数据本身就没分组。
- **验收**：私聊会话里 `SELECT group_id FROM chat_log WHERE id IN (显示的 id)` 必须全为空；
  群会话里必须全等于该群号。**可写成闸门测试**（数据结构断言，不靠肉眼）。

## 3. 执行顺序（2026-10-25 23:35 定版 · **按此顺序动工**）

### 3.0 排序原则

> 1. **先「看得见」再「能改」**——参数先只读暴露（证据齐全），再给可调入口。
>    反过来的风险是：改错了却不知道改的是什么（预算类常量改错会**静默**改变她的记忆容量）。
> 2. **先低风险高确定性，后需要取证分析的**——设置页补键是「加数据行」，
>    群聊记忆块 61% 要先回答「预算不够 vs 检索本身弱」，性质完全不同。
> 3. **一条做完、跑完三件套（pytest / 静态检查 / 变异）再动下一条**（教训 #5：
>    一口气改太多没验证）。
> 4. **主人明确说「放最后」的，就真的放最后**（③ 指标可勾选）。

### 3.1 总览

| # | 任务 | 依赖 | 量级 | 完成判据 | 状态 |
|---|------|------|------|----------|------|
| **1** | 设置页补 **19** 个真缺口键 | 无 | 小（schema 加行 + 契约测试） | 设置页能改、保存后 `config.yaml` 落盘、**新增契约闸门**防下次再漏 | ✅ **已完成 2026-10-25 23:45** |
| **2** | 参数来源面板（45 常量只读清单） | 1 | 中（1 端点 + 1 组件） | 数字与代码一致（**脚本生成，不手抄**）、每个标 `文件:行` | ⬜ |
| **3** | 群聊记忆块注入率 61%（私聊 95%） | 无 | 大（**先取证**） | **先回答「预算不够还是群聊检索本身弱」**再谈改法；禁止抑制/限流/按比删减 | ⬜ |
| **4** | 指标可勾选（③） | 无 | 中 | 勾选落 `localStorage`、刷新保持、Dashboard 清单驱动 | ⬜ 主人要求最后 |
| **5** | 删 `糖糖控制台_qt.py` | 1 | 小 | 功能覆盖核对 → `_backups/` 备份 → 删除 | ⬜ |

**为什么 1 在 2 前面**：1 是「把已有参数接出来」（数据在 `config.yaml`，只缺 UI 行），
