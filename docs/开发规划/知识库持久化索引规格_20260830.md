# Spec：知识库持久化索引（阶段 1～1.5：元数据、检索与证据）

## Objective

为 `knowledge/` 建立可重启复用、可审计、可回滚的 SQLite 索引和证据层，解决 chunk 只存在
进程内、重启后丢失稳定标识、无法可靠判断文档增删改以及检索结果缺少来源的问题。当前阶段
已包含文档/chunk 元数据、模型指纹 embedding BLOB、FTS5 CJK bigram、Dense/RRF 旁路和结构化
证据；旧 `KnowledgeBase.search()` 契约保留，索引故障仍可回退内存路径。

### 已采用的假设

1. 知识库规模仍是单机公共文档，索引数据库放在 `knowledge/.knowledge_index.sqlite3`，
   与 `memory.db` 分离，避免知识库重建阻塞记忆事务。
2. `knowledge/` 中只有经过 `discover_document_files()` ACL 过滤的 `.md/.txt` 才能进入索引；
   敏感目录不能因索引而扩大可读范围。
3. 文档 ID 由规范化相对路径派生，内容变化保留文档 ID；chunk ID 由文档 ID、块序号和块
   内容 hash 派生，内容变化产生新 chunk，旧 chunk 在同一事务中移除。
4. SQLite 不可用时保留当前内存检索路径并记录告警；索引不是启动硬依赖。
5. embedding 只有在引擎提供稳定 fingerprint 时才持久化；无 fingerprint 的测试/旧引擎不
   共享向量缓存。
6. 结构化证据必须保留稳定 chunk/document ID、相对路径、字符偏移、内容 hash、各路分数和
   `match_type`；不得把缺失排名伪装成零分。

## Project Structure

- `agent/knowledge_index.py`：SQLite schema、事务同步、FTS5 CJK bigram、快照和 embedding 元数据接口。
- `agent/knowledge.py`：发现文档、切块，并把当前内存 chunk 映射到索引元数据。
- `agent/knowledge.py`：`search_evidence()`/`format_evidence()` 结构化召回与来源协议；线上
  工具优先使用结构化路径，异常才回退旧文本路径。
- `tests/test_knowledge_index.py`：临时目录中的重启、增删改、偏移和 embedding 指纹回归。
- `tools/knowledge_retrieval_eval.py`：固定问句集的只读检索质量基线。
- `docs/开发规划/ROADMAP.md`：阶段结果、证据、回滚点和后续门槛。

## Code Style

索引写入必须是单次事务，并以路径集合做删除检测；任何异常回滚整批变更：

```python
stats = index.sync(documents)
```

`sync()` 内部以 `BEGIN IMMEDIATE` 包住文档、chunk 和删除检测；调用方只能在返回成功后
把元数据投影回内存。

实现使用标准库 `sqlite3`、显式列名、参数化 SQL 和 UTC 时间；不引入新的运行时依赖，
不在 SQL 中拼接用户查询或文件内容。

## Testing Strategy

- 单元/集成：临时 SQLite 文件验证 schema、稳定 ID、字符偏移、重启复用和删除检测。
- 兼容性：现有 `KnowledgeBase.search()` 返回字符串和召回顺序必须保持不变。
- 结构化路径：`search_knowledge` 优先交付稳定来源、偏移、hash、各路分数和 `match_type`；
  结构化失败才回退兼容文本路径，并在线程边界执行同步检索。
- 质量门：固定基线正例命中率和负例空召回率不得低于改造前；失败时保留旧内存路径。
- 运行验收：机器人手动重启后检查索引文件、同步统计和检索 trace；本阶段不以离线测试
  代替真实 canary。

## Boundaries

- Always：只索引公共发现器返回的文件；事务提交后才更新内存映射；记录 schema 版本和
  embedding fingerprint；改动后跑全量测试、pyflakes、compileall。
- Ask first：改变 `memory.db` schema、引入外部向量数据库、让线上检索强依赖新索引，或
  删除旧内存检索路径。
- Never：把敏感目录、LLM 自我回复或聊天记忆写进公共知识索引；索引失败时清空现有知识；
  通过关键词替 LLM 决定是否检索。

## Success Criteria

1. 同一相对路径重启后 `document_id` 不变；未改变文档的 chunk ID/hash/offset 不变。
2. 文档修改会原子替换对应 chunk；删除文件会清理文档、chunk 和 embedding 记录，不影响
   其他文档；重复同步幂等。
3. 索引损坏或 SQLite 异常不会阻止 KnowledgeBase 启动，旧检索仍可用且日志有明确告警。
4. 现有 1706+ 测试和知识库固定基线保持通过；真实 BGE 语义基线仍为 10/10。
5. 同一模型 fingerprint 的向量可跨 KnowledgeBase 重启复用；不同 fingerprint 不得复用旧
   内存或 SQLite 向量。
6. SQLite 支持 FTS5 时，中文 bigram 和英文词可通过 `search_lexical()` 召回稳定 chunk；
   FTS5 不可用时不影响文档/chunk/embedding 主表。
7. `search_knowledge` 的结构化结果经过有界线程门交给 LLM；异常回退有日志，闲聊/无关问句
   不因 Dense 轮单独命中；证据格式可由 LLM/日志核验来源。

## Open Questions

后续阶段再决定 embedding BLOB 的压缩/量化、线上 FTS/Dense/RRF 分布式评估、自适应分块与
overlap、parent-child 上下文扩展、文档版本 diff/回滚和轻量实体关系。当前真实基线为 12
文件/156 块，块长中位数 283.5 字、p95 未超过 1496 字，热路径检索 p50 2.14–2.79ms；
因此下一步先补长文、多来源、版本变更和线上 trace 样本，再决定是否引入 overlap/parent-child，
不以 WeKnora 的能力清单替代本项目测量。不引入完整 WeKnora sidecar，也不在没有线上证据前
固定新的融合权重。
