# 记忆变更留痕（memory revisions）——系统梳理与实施方案

> 2026-10-24。触发：主人「未来所有记忆更正都留痕」这件事更彻底系统梳理一遍计划后执行。
> 上一轮只补了 `correct_memory` 这一条路径的 `superseded_by`（见 `link_superseded`），
> 那是从一个洞里掏出的一勺水。本文是把整个桶翻过来数洞。

---

## 一、问题是什么

「记忆更正都留痕」不是「纠正工具要写指针」的同义词。它问的是：

> **一条记忆从诞生到消失之间，任何一次内容或真值的变化，事后能不能被完整复原？**

现状只能部分回答。现有留痕机制全部集中在 `memories` 的三个列上：

| 列 | 能表达 | 不能表达 |
|----|--------|---------|
| `status` | 有效 / 被否定 / 被替代 / 已履行 | 谁改的、为什么改、改之前是什么 |
| `valid_to` | 失效时刻 | 改的动机 |
| `superseded_by` | 被哪一条取代（仅 1:1 或 N:1） | 字段级变更（value 改了一半、importance 提了 2） |

所以「行被整条替代」这类事件有痕迹；而**内容被就地改写**「行被物理删除」这两类事件，事后完全不可复原。

## 三、设计

### 3.1 一张 append-only 表

```sql
CREATE TABLE IF NOT EXISTS memory_revisions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    entity TEXT NOT NULL,               -- memories / cluster_facts / fact_clusters / people
    entity_id TEXT NOT NULL,            -- 目标主键（people 用 qq_id）
    qq_id TEXT NOT NULL DEFAULT '',     -- 归属主体，支持「按人查全史」
    op TEXT NOT NULL,                   -- update / status / supersede / retract / fulfill / delete / migrate
    field TEXT NOT NULL DEFAULT '',     -- value / importance / trust_level / status / notes / summary / ''
    before_value TEXT NOT NULL DEFAULT '',
    after_value TEXT NOT NULL DEFAULT '',
    reason TEXT NOT NULL DEFAULT '',
    actor TEXT NOT NULL DEFAULT '',
    created_at TEXT NOT NULL
);
```

只 INSERT，永不 UPDATE/DELETE。表里没有外键——**删除的记忆必须在流水里继续存在**，
加 `ON DELETE` 语义就自相矛盾了（`memory_reverification_events` 用
`ON DELETE RESTRICT`，那是为了保护复核记录不被删；这张表的定位是记录删除本身，
所以不能有外键约束）。

### 3.2 四个不可让步的设计决定

1. **同事务写入**。留痕调用放在写方法的同一个 `with self._connect()` 事务里，
   和业务 UPDATE 一起 commit。这样「改了但没留痕」在结构上不可能发生，
   不需要靠调用方自觉。

2. **字段级，不是整行 JSON**。一次操作改几个字段就写几条。
   理由：演化史要回答的是「这句话被改过几次、每次改成什么」，
   按 `(entity_id, field)` 分组直接出时间线；整行 JSON 每次都得自己做 diff，
   而且 SQLite 里没法索引。

3. **`actor` 必填，默认 `unknown`**。这是整个机制的灵魂——没有 actor 的流水
   只是一句「变了」，回答不了「是谁改的」。写测试断言**生产代码里不存在
   `unknown`**（谁新增写路径没标 actor 就红）。

   actor 取值约定：
   `tool:correct_memory` / `tool:forget_memory` / `synthesis:profile` /
   `synthesis:fact` / `dedup:exact` / `dedup:semantic` / `decay` /
   `migration:<版本>` / `script:<文件名>` / `console`。

4. **`reason` 写人话**。纠正时放 `wrong_fact` → `corrected_fact`；
   合成时放 key；衰减时放条件；删除时放触发条件。
   没有 reason 的流水等于「变了，但不知道为什么」，不足以优化糖糖。

### 3.3 边界：什么不记，以及为什么

- **`insert_memory` 不记**：新行本身就是它诞生的记录（`timestamp` / `ingested_at`）。
  再记一条只会让 22k 条流水淹没真正的更正。
- **`reinforce_memory_by_id` 不记**：每次召回 +1，是统计漂移不是决策。
  记它会让表按「召回次数 × 记忆数」爆炸，而信息量已经由 `recall_count` 承载。
  **但 `set_memory_importance`（显式设定）要记**——那是决策。
  这条边界必须写进 docstring，否则以后会有人「补全」它。
- **embedding 不记**：纯派生数据，`value` 变了可以重算。
- **历史不回填 1261 条断链**：数据不存在，任何「补」都是编。
  现有 `valid_to` / `superseded_by` 已经把那些信息表达了，回填只是换个地方存一遍，
  却会让「当时记的」和「事后推断的」混在一起。演化史 UI 明确分两块展示。

## 六、已知限制（写进文档，避免以后误判）

1. **2026-10-24 之前的历史变更无法复原**——流水从实施时刻开始记。
2. `memories` 表仍有 1,261 条 `superseded` 无指针，本次不尝试修复。
3. `_apply_extraction_item` 的更新分支只记 importance/evidence 变化，
   如果未来它开始改 `value`，闸门不会拦（闸门只查是否调用了留痕方法，
   不查字段覆盖是否完整）——需要人看 diff。
4. 流水表会单调增长。当前写入频率估算：纠正/合成/去重是低频，
   删除是低频，**预估 < 100 行/天**，可接受。若未来接入高频路径需加保留策略。
5. **`tools/` 下的一次性运维脚本不写流水**（`清理垃圾记忆.py`、`dedup_memories.py`、
   `诊断对话质量.py` 等直接 `DELETE FROM memories`）。理由：它们是人工执行、
   已有 `memories_backup` 表或文件备份、且不是「糖糖在运行中更正记忆」。
   如果哪天要彻底统一，做法是让这些脚本也 `INSERT INTO memory_revisions`，
   但它们跑在真实 `memory.db` 上、无法被 pytest 覆盖，改它的风险大于收益。
   **判据**：问题若是「糖糖自己改错了记忆」，查流水；若是「人跑脚本删了东西」，
   查那个脚本的备份。

### 执行中发现的真问题（变异对照逮住的）

`link_superseded` 最初把幂等条件写了**两遍**（查询一遍、UPDATE 一遍）。
变异对照 M4 试图去掉 UPDATE 上的条件时判定为 **GREEN / 假变异**——因为
流水集合由查询决定，改成单向不影响流水条数。

这个假变异暴露的不是测试太弱，而是**代码里有两个判定点**：两处条件一旦漂移，
就会出现「UPDATE 了但没留痕」或「留痕了但没 UPDATE」——正是本机制要防的事。
已改成**单一判定点**：查询出 `pending`，流水与 UPDATE 共用同一批 id。
改完 M4 变真红。

### 执行中发现的第二个问题（全量测试逮住的）

`test_fact_cluster_store_calls_are_offloaded_from_event_loop` 断言
`len(store.thread_ids) == 7`，实测变 6。

根因不是线程数不稳定，而是测试里的假 store
`_FactClusterStore.update_cluster_summary(self, *_args)` **不吃关键字参数**，
而真实 `Store` 的方法现在带 keyword-only 的 `actor` / `reason`。调用点外面
包着 `except Exception: pass`，于是 `TypeError: got an unexpected keyword
argument 'actor'` 被**静默吞掉**，唯一的外在表现就是「少一次 store 调用」。

修法是让 mock 跟上真实签名（`**_kwargs`），**不是**把断言从 7 放宽到 6——
那条精确计数断言是唯一能抓住这类静默失配的东西。已在测试里写明理由防止被放宽。

### 执行中顺带发现的第三个问题（与留痕无关，但会挡住验证）

从**本 Agent 会话**里启动打包好的桌面端会失败：`小糖糖桌面端.exe --no-sandbox`
报 `bad option: --no-sandbox`、退出码 9。

根因：DSH 自己就是 Electron 应用，给子进程留下了 `ELECTRON_RUN_AS_NODE=1`。
带着它启动 electron.exe 会被当成 Node 运行，任何 Chromium 参数都不认、GUI 也不起。
用户双击 `.lnk`（从资源管理器启动）继承不到这个变量，所以**只影响从会话里拉起**。
修法：拉起前 `env.pop("ELECTRON_RUN_AS_NODE", None)`。已验证清除后 4 个进程正常起来。
