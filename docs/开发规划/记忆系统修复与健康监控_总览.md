## 一、根因分析（源自《记忆系统全面诊断_20260804》）

### 1.1 诊断背景

糖糖在对话中报告记忆错误（冲突数据、"聊0次 vs 聊645次"），触发全系统诊断。手段：

- 逐文件审查 handler.py / memory.py / store.py
- 数据库 4745 条记忆全量分析
- GitNexus 影响分析与调用链分析
- code-reviewer Agent 审查修复代码 + explorer Agent 扫描遗漏缺陷

### 1.2 三层阻断——记忆系统为什么没活过

**不是某个 bug，是三层阻断叠加：**

```
旧 flash 模型（质量差）→ 提取的记忆全是垃圾
    +
_llm_busy 即时跳过（架构冲突）→ 活跃时段提取永不触发
    +
阈值太高（群15/私12）+ 重启清零 → 管道饥饿
    =
2-5% 提取效率，17 人聊>50次零记忆，主人 645 次聊天零记忆
```

### 1.3 因果链：主人零记忆的完整追溯

1. 旧 flash 模型提取质量差（conf 全 0.7，cognitive 全 semantic，问句当事实）
2. 主人积累了 ~25 条低质记忆 → 垃圾清理脚本删除（判断正确：这些确实是垃圾）
3. 清理后新提取被三重阻断，4285 条消息（含"大二学生""住在郴州苏仙区"等高信息量内容）全部未被提取
4. 结果：主人零记忆

### 1.4 诊断时点关键指标（2026-08-04）

| 指标 | 数值 | 判定 |
|------|------|------|
| LLM 提取效率 | 2-5%（100条消息→2-5条记忆） | 🔴 管道饥饿 |
| 零记忆用户（聊>50次） | 17人 | 🔴 系统失败 |
| 主人记忆 | 0条（645次聊天） | 🔴 最差情况 |
| 自忆产量(8/3) | 301条（vs LLM提取95条） | 🔴 正则绑架系统 |
| 自忆注入方式 | 无条件注入每条消息 | 🔴 污染所有对话 |
| `_llm_busy` 阻塞 | 活跃时段提取全被跳过 | 🔴 架构冲突 |
| recall_count 膨胀 | 最高 262 次 | 🔴 陈旧记忆滚雪球 |
| 重复记忆 | 「不是gay」×3、「最喜欢无职转生」×3 | 🔴 去重失效 |
| LLM 推理泄露 | SKIP/前者/后者 存入记忆值 | 🟡 校验盲区 |
| 记忆值硬截断 | `value[:100]` 切碎句子 | 🟡 碎片来源 |

## 二、已修复问题清单（18 项 = 17 项常规修复 + 1 项 P0）

### 2.1 系统级缺陷（8项）

| # | 问题 | 根因 | 修复 |

| # | 问题 | 根因 | 修复 |

### 2.5 P0：bot_qq 在 people 表中显示为"路人" ✅ 已修复

**现象**：糖糖自己的 QQ（10001）→ `_qq_suffix` 截为 "4170" → people 表 nickname 为空、chats=0 → 格式化输出为 `📋 (ID:4170) | 聊0次 | 路人`。糖糖看到自己的档案写着"聊0次的路人"，推理出"这是系统把我的档案搞串了"——推理完全正确。

**根因**：
1. bot_qq 在 people 表中 nickname 为空——`get_or_create_person` 创建记录时没设
2. `_get_self_memory_context` 用 `format_compact_memories(bot_qq).replace(魔术字符串)`——两个 replace 都不匹配实际输出，静默失败（CLAUDE.md 错误十三再现）

**修复（不入侵公共方法契约）**：
1. `handler.__init__`：`update_person(bot_qq, nickname="小糖糖")` ——修数据
2. `_get_self_memory_context`：不再用 `format_compact_memories/.replace`，直接用 `_format_self_memories(selected)` ——修调用方
3. `memory.py`：新增 `_format_self_memories()` 私有方法——第一人称自我叙事格式
4. `recall_formatted` 和 `format_compact_memories` 保持不变——不入侵公共契约

**自审通过**：无魔术字符串、无契约变更、无静默失效路径。直接消除了 replace 而不是修 replace 的匹配字符串。

### 2.6 P1：浪浪（10002）intimacy=100 但 chats=0（暂不修）

**根因**：intimacy 可能来自场景绑定（`scenario_targets`）或被手动设置，与 chat_count 不同步。两个数据源独立更新，没有一致性检查。

**方案**：暂不修——这是设计层面的问题。intimacy 和 chat_count 本来就是两个维度（关系质量 vs 互动数量）。100 intimacy + 0 chats 在场景绑定场景下是合理的。只需确保格式化输出时 chat_count=0 不会让 intimacy=100 看起来像 bug。

## 三、新 flash 模型验证（2026-08-04，源自《记忆系统修复方案_20260804》）

测试消息：

```
小明: 我昨天去了趟医院，感冒拖了一周没好
小明: 我是湖南长沙人，在大连读大学，学计算机的
小明: 怎么突然叫我老公了？
小明: 我不太喜欢喝咖啡，更喜欢喝茶
小明: 我是废物，什么都做不好
```

提取结果：

| 值 | cognitive | confidence | importance | 判定 |
|----|-----------|------------|------------|------|
| 昨天去了医院，感冒拖了一周没好 | episodic | 0.9 | 3 | ✅ |
| 是湖南长沙人 | semantic | 0.95 | 9 | ✅ |
| 在大连读大学 | semantic | 0.95 | 8 | ✅ |
| 学计算机的 | semantic | 0.95 | 8 | ✅ |
| 不喜欢喝咖啡，更喜欢喝茶 | semantic | 0.9 | 5 | ✅ |

- 问句「怎么突然叫我老公了？」→ 正确跳过 ✅
- 自贬「我是废物」→ 正确跳过 ✅
- cognitive 全部分类正确 ✅（旧 flash 99.1% 全 semantic）
- confidence 0.9-0.95，无一条默认 0.7 ✅（旧 flash 98.3% 全 0.7）
- importance 分档合理 ✅

**结论：新 flash 提取质量已达标。问题在管道不通，不是模型不行。不再需要换 pro 做提取、不再需要 few-shot prompt 补强。**

## 五、系统健康自检机制（源自《记忆健康监控_设计文档》+ 实际实现）

### 5.1 设计原则

1. **自报家门，不等用户问。** 糖糖在启动时、每天定时、以及 `/状态` 命令中主动报告系统健康。
2. **对比"宣称"和"实际"。** 不只是报告指标数值——要对比：这个功能宣称在跑，实际跑了吗？
3. **静默失败 = 告警。** 任何组件如果应该产出但没有产出，必须被报告。
4. **糖糖是最终消费者。** 健康报告用自然语言生成，糖糖能读懂、能转述给主人。

### 5.2 架构

```
metrics.py (采集)  →  health_check.py (判断)  →  self_state (糖糖感知)
                           ↓
                      /状态 命令输出
                      糖糖的自然语言表达
```

- `metrics.py` 是**数据采集层**——计数器只采不判，O(1) 不阻塞，内存缓冲 + 定时 flush 到 `kv_store`
- `health_check.py` 是**判断层**——读 metrics 数据 + 数据库查询 → 判断健康/异常 → 生成自然语言
- 存储：`kv_store` 表，格式 `metric:{date}:{name}`，另存 `metric:latest:{name}` 快照
- metrics flush：**每 10 分钟**（自治循环内）
- 每日聚合：`_maybe_daily_metrics_aggregate`——**每日自治循环首次触发时执行**（原始设计为凌晨 2:00 调度，实际实现不同）

### 5.3 指标定义（15 项——只保留指标语义）

| # | 指标 | 语义 |
|---|------|------|
| M1 | `extract_attempts` | 今日 LLM 提取触发次数 |
| M2 | `extract_successes` | 今日成功产生记忆的提取次数 |
| M3 | `extract_memories_total` | 今日 LLM 提取的记忆总条数 |
| M4 | `extract_rejected` | 今日被校验拦截的记忆条数 |
| M5 | `extract_llm_failures` | LLM 调用失败/返回空次数 |
| M6 | `extract_busy_skipped` | 因 `_llm_busy` 跳过的提取次数 |

| M8 | 置信度分布 | 今日新记忆按区间计数（实现为 `confidence_high/mid/low` 计数器，非平均值） |

### 5.4 health_check 检查项（16 项——实际实现）

> 原始设计文档写"12 项"、阈值与实现不符。以下以 `health_check.py` 实际实现为准。

| # | 检查项 | 频率 | 判定标准（实际阈值） |
|---|--------|------|---------------------|
| 1 | extract_running | hourly | 今日触发 0 次且已过中午 → warn |
| 2 | extract_busy | hourly | busy 跳过率 > **50%** → warn（分母含跳过次数） |
| 3 | extract_success | hourly | 提取成功率 < 30% → warn（分母剔除 busy 跳过） |
| 4 | stale_extraction | hourly | >3 个用户积压 >30 条未提取 → warn |
| 5 | reasoning_leaks | daily | 今日有推理泄露入库 → error |
| 6 | duplicate_memories | daily | 今日有重复记忆入库 → warn |
| 7 | confidence | daily | 高置信度(≥0.8)占比 < **30%** → warn |
| 8 | reinforce_cooldown | daily | recall_count 最高值较上次增长 >5 → warn |
| 9 | owner_memories | daily | 主人 0 条 → error；<10 条 → warn |
| 10 | zero_memory_users | daily | 聊>50次零记忆 >5 人 → warn |
| 11 | profile_coverage | daily | 记忆>10条但无画像 >10 人 → warn |
| 12 | embedding_coverage | daily | 覆盖率 < **80%** → warn |
| 13 | cleanup_ran | daily | 今日未执行陈旧清理 → warn |
| 14 | episodes | daily | 表空 → ok（提示等待积累，新接入功能） |
| 15 | extraction_state_file | startup | 文件损坏 → error（重启后进度将丢失） |
| 16 | autonomous_loop | hourly | 上次 metrics flush >30 分钟 → warn |

调度：startup 全量 / hourly 轻量 / daily 全量（0点触发）。

## 七、决策记录：不做的事

源自《记忆系统修复方案_20260804》：

| 项目 | 原因 |
|------|------|
| 换 pro 做提取 | 新 flash 质量已达标（见第三章验证） |
| prompt few-shot 强化 | 新 flash 不需要 |
| 重建记忆库 | 提取管线修好后存量数据自然更新 |
| 换向量数据库 | SQLite + BGE 单机够用 |
| 改写 recall 算法 | 分步修——先修好写入端再调检索 |
