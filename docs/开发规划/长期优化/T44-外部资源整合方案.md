# T44 · 外部资源整合方案（狗头军师 / goutoujunshi）

> 2026-10-14。承接主人三项要求：① 样本分析 ② 外部资源整合办法 ③ 整合 goutoujunshi。
> 本文件只写**方案与边界**；执行记录另落 `记录/T44-*.md`。

## 一、被整合对象

`shengjidaguai-china/goutoujunshi` —— **7839 star / 781 fork / MIT / Python**，
一个 **Codex Skill**（`SKILL.md` + `references/` + `scripts/`）。

| 目录 | 内容 | 体量 |
|---|---|---|
| `references/knowledge/` | **20 篇**关系心理学/法律/伦理知识 | ~100 KB |
| `references/practical/` | **26 篇**沟通话术（接话/夸人/拒绝/吵架/气场/人脉）| ~230 KB |
| `SKILL.md` | Skill 定义与工作流 | 9.6 KB |
| `scripts/memory_store.py` | 它自己的长期记忆实现 | 23.8 KB |
| `documentation/` | architecture / flows / permissions / variables 等 7 篇 | ~22 KB |

**它为什么贴合本项目**：它做的四件事里有三件是小糖糖已经在做的——
情绪先于建议、长期记忆、多元关系不预设。差别只在**它的目标是「给用户建议」**，
而小糖糖是**人格 bot**（她自己就是关系中的一方，不是顾问）。

## 二、第一原则：**知识可以进，身份不能进**

这是整个方案里唯一真正重要的判断。

小糖糖的架构把两件事分得很清：

| 层 | 载体 | 作用 | 整合时 |
|---|---|---|---|
| **她是谁** | `role_card.md` | 身份、性格、说话方式 | ❌ **一个字节都不改** |
| **她怎么做事** | `protocols.py` | 行为协议、边界 | ⚠️ 只加「怎么看这些资料」的说明 |
| **她知道什么** | `knowledge/` | 可检索的资料 | ✅ **整合目标** |

**为什么这条是第一原则**：那 46 篇文本是**写给「军师」的**——语气是「你应该先做 A 再做 B」。
如果原样进知识库又不加约束，小糖糖检索到之后**很可能变成咨询师腔**，
那就直接违背她的根本设定（CLAUDE.md 第零节：「**她不是客服机器人**」）
和本次目标的第三条（「语言自然、接近真人私聊」）。

## 三、整合办法：**用已有的递归扫描，零代码改动**

### 3.1 机制上为什么不用写代码

项目里已经有两条现成通道：

1. **`knowledge/` 递归扫描**——`knowledge/色色参考/` 就是子目录先例，已被加载
2. **`search_knowledge` 是 LLM 自主调用的工具**——`handler.py:3970` 注释写明
   「系统不替 LLM 决定『该查知识库』；需要时 LLM 自主调 search_knowledge」

所以**丢进目录即可生效**，不需要新工具、不需要关键词门控、不需要改检索逻辑。
这同时满足铁律「最小改动」和「禁止关键词替 LLM 决策」。

### 3.2 落地布局

```
knowledge/
  恋爱军师/                    ← 新建（子目录，递归扫描自动加载）
    README.md                  ← 来源 / 许可 / 版本 / 边界（必写）
    知识/                      ← references/knowledge/ 的 20 篇
      01-证据分级与内容边界.md
      ...
    话术/                      ← references/practical/ 的 26 篇
      00-导读与使用分级.md
      ...
```

**为什么保留原目录名 `知识/` `话术/` 而不拍平**：
日后上游更新时能一眼看出哪些文件该覆盖，也让「这段知识来自哪」在检索结果里可辨认。

### 3.3 注入量是安全的

`knowledge.py` 的硬上限：`MAX_TOTAL_CHARS = 3000` / `MAX_PER_CHUNK = 1500` / `MAX_RESULTS = 3`。
**无论知识库多大，单次注入不超过 3000 字符**——所以 330 KB 不会撑爆上下文。
这正是「能力数据按需注入」原则已经解决的问题（歌单只随 sing 工具出现，同源）。

## 四、必须做的三件事（不是可选）

### 4.1 `README.md` 写清来源与许可

MIT 许可要求保留版权声明。文件需含：上游仓库 URL、commit SHA、许可、拉取日期、
**以及一句「本目录内容未经改写，仅供检索」**。

### 4.2 一条协议：说明「这些是资料，不是她的口吻」

进 `protocols.py`（**不进 role_card**——角色卡有「只写身份不加规则」的机器闸门）。
要点：

- 检索到的是**参考观点**，不是必须转述的结论；
- **不主动索取隐私**（本次目标的硬边界）；
- **不扮演咨询师**——她是在聊天，不是在给建议；
- 涉及危机（自伤/暴力/法律）时，`17-中国法律安全与危机转介.md` 的转介义务**优先于**
  「不追问创伤细节」的既有两个边界；
- 与 `psychology.yaml` 场景的边界**并列不冲突**。

### 4.3 一条测试：防止这批文件被静默丢弃

参照本仓的教训 #30/#31（检查器写了从没生效 / 白名单漏了整个二进制类型），
**新增的文件必须有测试确认它真的被 `knowledge/` 扫描到了**，
而不是只在文件系统里躺着。判据：扫描结果里出现 `恋爱军师/` 前缀的条目数 ≥ 46。

## 五、明确不整合的部分

| 内容 | 为什么不进 |
|---|---|
| `scripts/memory_store.py` | 小糖糖有 `memory.py` + `store.py`（SQLite 唯一访问层）。**两套记忆系统并存**是反模式 #8（两套工具系统并存）的同形；它的记忆语义（跨任务记住双方档案）与 `people.notes`/`memories` 重叠 |
| `documentation/` | 是**它的**开发文档，与小糖糖无关，只会稀释检索 |
| `agents/openai.yaml` | 它的 Codex agent 定义，本项目不用 |
| `SKILL.md` | 它是**给 Codex 读的 Skill 契约**。小糖糖不是 Codex，这份契约没有消费方 |
| `assets/` | 一张 949 KB 的 PNG，纯装饰 |

**但 `SKILL.md` 值得读一遍**——它的**工作流设计**（先接住情绪 → 拆事实/推测/未知 → 给可执行下一步）
是有价值的思路，若日后要改 `psychology.yaml`，那是参考对象。**读它，但不搬它。**

## 六、备选方案（记录被否决的理由）

| 方案 | 否决理由 |
|---|---|
| 装成 Codex Skill | 那是给**开发者（我）**用的，不改变 bot 行为——解决不了「让糖糖用上」 |
| 做成新场景（`scenario.yaml`） | 场景是**行为准则**层，会把她绑成「军师」；而知识是**资料**层。层次错了 |
| 拍平成知识库根目录 | 46 篇会淹没原有 16 篇的检索权重，且丢失来源可追溯性 |
| 只整合 `knowledge/`，不整合 `practical/` | `practical/` 的 26 篇「怎么把话说好」与本次目标（回复自然）**直接相关**，放弃可惜。风险由 4.2 的协议兜住 |

## 七、执行顺序（每步可独立回滚）

1. 建 `knowledge/恋爱军师/` + 抄入 46 篇（**只读拷贝，不改写任何一字**）
2. 写 `README.md`（来源/许可/SHA）
3. 写扫描验证测试 → **先让它红**（证明它测得到）→ 放文件 → 变绿
4. 加协议到 `protocols.py` + 补对应闸门测试
5. 跑全量 `pytest` + `pyflakes`

## 九、风险与对策

| 风险 | 对策 |
|---|---|
| 检索到「你应该…」的建议腔文本，她照搬 | 4.2 协议明说「是参考观点，不是转述模板」；观察期看实际输出 |
| 46 篇稀释原有 16 篇的检索权重 | 子目录隔离；若观察发现原有知识被挤掉，用 `search_knowledge` 的返回条数（`MAX_RESULTS=3`）调优先级 |
| 上游更新后本地版本过时 | `README.md` 记 commit SHA，可 diff 出上游改了哪几篇 |
| 话术类内容让她的回复变「套路化」 | **这恰恰是本次目标要防的**——观察期重点看这一项；若退化，只留 `知识/`、撤 `话术/` |
