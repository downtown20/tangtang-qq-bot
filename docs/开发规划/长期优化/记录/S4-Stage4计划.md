### T4.5 FAIL 的根因（本次最重要的发现）

接线是**完整的**，我逐点核过：

- 群聊注入点 `agent/handler.py:4017-4021`（`if _mood_report_turn:` → append 协议 + `logger.info`）
- 私聊注入点 `agent/handler.py:5116-5118`（同口径）
- 回灌调用点 `handler.py:4381`（群）/ `5351`（私），都传 `injected=_mood_report_turn`

分母为 0 的真正原因在闸门（`handler.py:3122` 群 / `4587` 私）：

```python
feedback_candidate = self._take_feedback_candidate(group_id, user_id, 60)   # 群：60 秒
feedback_candidate = self._take_feedback_candidate(priv_key, user_id, 120)  # 私：120 秒
_mood_report_turn = bool(feedback_candidate)
```

**只有「她刚说完、对方在 60s（群）/120s（私）内接着回」才注入协议。** 而生产 15 天里这个窗口一次都没满足。

**这不是缺陷，是审计「不要动」第 11 条的刻意设计**（不加无条件常驻注入；2026-08-17 同形注入被实测有害）。代码注释 4014-4016 的原话：「这里的条件是闸门本身，不是优化」。

所以 T4.5 的真实问题是：**完成标准与设计约束冲突**。规划假设「注入回合数」是个可观测量，但它被 60s 闸门挡死、恒为 0，于是比值永远算不出来。

**这个发现反过来印证了审计 C3 的误判成因**：C3 当年把「心情自报回灌=0」读成「LLM 没遵从协议」，而真相是**分母从来就是 0**。T1.2 加注入日志正是为了把这两件事分开，而数据现在证明：分开之后，分母确实是 0。

  - 分母改为「**LLM 输出里出现过 `[心情:...]` 标记的次数**」，完全不依赖注入闸门；
  - **不改 `_mood_report_turn` 的任何语义**（那是审计「不要动」第 11 条的落地，不碰）。
- **风险与对策**：日志量未知 → 先只记 info 且不带大 payload；跑一个周期看频率再决定是否降级。
- **验收**：

- **回滚**：改动只在 `_apply_mood_report` 一个方法内，锚点 `.bak-20261014-T48`。
