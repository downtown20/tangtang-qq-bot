## 3. 取证结果（全部实测，2026-10-14）

探针：`.trash/长期优化/probe_relay_vision.py`、`probe_vision_control.py`、`probe_stream_vision.py`

### 3.1 中转确实支持多模态（阳性 + 阴性对照，`CLAUDE.md` 教训 #30 纪律）

| 对照 | 输入 | 输出 | 判定 |
|---|---|---|---|
| 阳性 | 纯红图 `RGB(220,20,20)` | `"红色"` | ✅ |
| 阳性 | 纯蓝图 `RGB(20,20,220)` | `"蓝色"` | ✅ |
| 阳性 | 白底黑字 `AAA-777` | `"AAA-777"`（逐字符正确） | ✅ |
| 阳性 | 白底黑字 `ZZZ-333` | `"ZZZ-333"` | ✅ |
| 阴性 1 | 坏 base64（`b"not-an-image-at-all"`） | **HTTP 400** `code 11135 Please start a new conversation, replace the image, and try again.` | ✅ 有真校验 |
| 阴性 2 | 不给图、只问同样问题 | HTTP 200，**content 为空串** | ✅ 无图时不编造 |

⇒ **结论：中转 `deepseek-v4.1-flash` 是真看图，不是文本兜底。** 四种图给出四种正确答案，坏图被服务端拒绝。

### 3.2 流式 + 多模态 + 历史混用

探针 `probe_stream_vision.py`：`stream=True`，messages 里 system/user/assistant 历史用**字符串** content，
当前轮用**数组** content（image_url + text）。
结果：**HTTP 200，73 个 chunk，累计 content = `'AAA-777'`**。
⇒ 流式多模态可用；**历史字符串 content 与当前轮数组 content 可以混用**（改造时不必重写历史消息）。

### 3.3 请求构造（`agent/handler.py`）

- `_endpoint(base, path)`（line ~723）：`return f"{base}/v1{path}"` —— **URL 归一已存在，识图直接复用**
- `_call_deepseek`（line 6077）：`api_messages = [{"role":"system","content":system_prompt}]` → `extend(history_messages)` → `append({"role":"user","content":user_message})`；body 含 model/max_tokens/temperature/messages + `_thinking_body(...)` + 可选 `user_id` + `extra_body` 覆盖
- `_stream_deepseek`（line 6335，签名 `(self, body: dict, base: str, api_key: str) -> tuple[str, dict|None, float]`）：浅拷贝 body、置 `stream=True`、走 `self.llm.stream(...)`，解析 `data: ` 行
- ⚠️ line 6365 `prompt_len = sum(len(m.get("content","")) for m in body.get("messages", []))` —— 遇到数组 content 时 `len()` 返回元素个数（不崩，但语义错）。改造后错误日志里的 prompt_len 会失真 → 顺手修
- `_call_vision` 尾部日志（line 8370/8372）用 `router.provider` 拼串 → 改造后要改文案

## 4. 设计（最小改动 + 向后兼容）

**保留唯一入口 `Handler._call_vision` 与其全部缓存/取图逻辑**，只替换"用哪个后端"：

1. 新增模块级函数 `_vision_llm_config(llm_cfg) -> dict | None`：
   读 `llm.vision.enabled`（bool）。**注意 `enabled=false` 的历史语义是"识图关"**，
   而主人要的是"识图可用"——因此改造后 `enabled` 的语义**保持"识图总开关"不变**，
   真正决定后端的是新字段 `llm.vision.provider` 的值：
   - `provider == "main"`（**默认**）→ 走主 LLM 多模态
   - `provider in ("local", "api", "qwen")` → **旧双后端保留**（回退路径，零风险）
2. 新增 `async def _describe_via_main_llm(self, img_bytes, prompt) -> str`：
   复用 `self.llm` 客户端 + `_endpoint` + `_stream_deepseek`，构造
   `content = [{"type":"image_url","image_url":{"url":"data:image/jpeg;base64,"+b64}},{"type":"text","text":prompt}]`，
   **不发 tools**（识图不需要工具循环）、temperature 用主配置。
3. `_call_vision` 分支：`provider == "main"` → 主 LLM；否则走既有 `get_vision_router()`。
4. 缓存键 `(sha256(img_bytes), prompt)` **保持**（与后端无关，切换后端后旧缓存最多复用 600s，无害）。
5. 日志文案：`识图[main-llm]` / `识图[local]` / `识图[api]`；失败时 `识图: 后端不可用（provider=…）`。
6. 配置与控制台同步（铁律 E8）：`llm.vision.provider` 的 choice 从 `["local","api"]` 改为 `["main","local","api"]`，
   默认 `main`，并把 model/base_url 两项标注为"仅 local/api 方式使用"。

**为什么不是"直接删掉两个后端"**：删除是不可回退的破坏性改动，且 `provider=local` 是当前生产值——
一刀切会把"识图完全不可用"的风险一次性引入。先让 `main` 成为默认并验证可用，再在**后续任务**里退役旧后端（`deprecation-and-migration`）。
