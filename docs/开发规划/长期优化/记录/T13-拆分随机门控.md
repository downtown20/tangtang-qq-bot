## 一、问题（四段式）

**位置**：`agent/reply_pipeline.py:402`（修复前）

```python
# 基于长度决断而非随机：>80 字必拆，40-80 按段落拆
if len(reply) < 80 and random.random() > 0.50:
    return [reply]
```

**证据**：
1. 该行在 maybe_split_reply（群聊系统拆分的唯一入口）内，是 40-80 字区间唯一的返回路径；
2. random.random() > 0.50 是抛硬币，同一输入两次调用可能得到 [reply] 或进入拆分逻辑；
3. 注释自己写着「基于长度决断而非随机」，代码没做到那句话；
4. random 在文件里另有 3 处（516/554/595 行）全是 asyncio.sleep(random.uniform(...)) 的发送间隔抖动，那是合理用途，不动。

**根因**：系统用随机数替 LLM 决定「这条消息拆不拆」。违反 CLAUDE.md 教训 #9/#10（单脑架构：系统不替 LLM 做决策）。

**为什么这是「消息密度不合理」的直接机制原因**：同一句话，这次发 1 条、下次发 2 条，密度不稳定且不可预测。用户反馈的「消息密度不合理」不是 LLM 的问题，是这行代码。

---

## 二、修法（最小改动：1 个文件，逻辑 1 行）

把随机项删掉，40-80 字区间恒定不拆：

```python
if len(reply) < 80:
    return [reply]
```

外加 8 行注释说明历史与理由（含为什么不再用随机数、群聊系统拆分只是长度兜底、真要拆应由 LLM 用 分段 决定）。

**没做的**：
- 不动 maybe_split_reply 的其它逻辑（断点选择、尾部过短保护、CQ 码保护）；
- 不动私聊路径（send() 里 target_type 不是 group 时恒一条，本就确定）；
- 不动 random 的另 3 处发送间隔抖动（合理用途）；
- 不给群聊开放 分段——那是另一个决定（需主人拍板），本任务只修 bug。

## 四、踩坑（记入环境事实）

1. 测试文件的引号嵌套：用 JS 数组拼 Python 源码时，docstring 的三引号与字符串里的双引号反复冲突，连错 4 次（marker 行少闭引号、docstring 三引号被写成普通文本）。最终解法：全文件 docstring 统一用三个单引号，字符串统一用单引号，需要双引号时用 chr(34) 拼。
2. 测试数据踩了两次边界：中文文本按字数算，45 字、71 字都没过 80 门槛；且逗号不在断点字符集（。！？!? 加换行）里，导致长度过了也没拆。改为句号加 4 句才稳定。
3. ReplyPipeline 构造签名：不是 sticker_manager=，而是 napcat/stickers/store/short_term/bot_nicknames/bot_qq（照 tests/test_reply_pipeline.py 的既有写法）。
4. 变异探针的字符串拼接：多行 Python 字符串里同时含分段标记与 random 字样，隐式拼接缺加号报语法错。解法：每行显式加 NL，双引号用 chr(34)。
