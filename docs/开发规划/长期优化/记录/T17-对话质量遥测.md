## 一、取证推翻了原计划（两次）

### 第一次推翻：不该从日志采集

原计划是「扩 `tools/长期优化快照.py`，从 `tangtang.log` 统计回复长度分布 / 气泡数 / anti-tell 命中」。
我按这个写了采集器，跑出来 `replies_seen: 3437`、`anti_tell_total: 0`。**两个数字都是假的**——
去查日志实际格式后发现：

```
2026-10-14 06:00:41+0800 | boot=a5010b6d cid=evt-761ec06b7421 | 糖糖.SnowLuma | INFO | 📤 私聊已发送 → 2524950083 (msg_id=283694197)
```

**日志只有发送回执，不含回复正文。** 我的 3437 全是误命中——「糖糖」出现在 logger 名字 `糖糖.Handler` 里。
这正是 CLAUDE.md 教训 #36 的翻版：**工具报的 0 是关于这个工具的事实，不是关于代码的事实**。

### 第二次推翻：基础设施已经有了，缺的是读取方

查 `memory.db` 时发现 **`reply_metrics` 表早已存在**（3658 行，2026-08-17 起连续到今天），
每行记 `reply_len` / `meow` / `bracket_action` / `question_end` / `assistant_tell` / `hard_turn`。
建表注释原话：「对话质量遥测：每条已发送回复一行聚合指标（无正文，只有可计数特征——隐私安全；
**盲测/A-B 的观测基础**）」。

写入器 `store.record_reply_metric()` 也**已接线**（`agent/handler.py:13402-13403` 的发送提交点）。

**但它没有任何读取方**——全项目搜索只有：`store.py` 定义 + 写入、`tests/test_store.py` 一处断言。
这是 CLAUDE.md 教训 #12/#14 的同形：**写了 infra 代码 ≠ 接入了业务**；**引擎在转，离合器没接上**。

**所以 T17 的正确做法不是新建采集器，而是给这个孤儿子系统接上读取方。**
这也直接落实了用户的要求「避免重复造轮子」。

## 二、做什么

`tools/长期优化快照.py` 新增 `collect_dialog_quality(days: int = 30)`，挂进 `collect_all()` 的 `dialog_quality` 键。

采集四项：

| 项 | 内容 |
|---|---|
 | reply_len | 长度分桶（<=30 / 31-60 / 61-100 / 101-150 / 151-250 / >250）+ 均值 / 中位 / 极值 |
 | feature_hits / feature_pct | bracket_action（括号动作镜头）、assistant_tell（助手腔 7 条）、meow（喵）、question_end（问句收尾）、hard_turn |
 | by_type | 群聊 vs 私聊分列（用户目标是「接近真人私聊」）|
 | window_days / samples | 窗口与样本量，避免拿旧版本数据当现状 |

### 三条硬约束（都有测试钉住）

1. **只读**——`mode=ro` 打开，且结构性闸门禁止出现 `INSERT/UPDATE/DELETE/DROP/ALTER`；
2. **不设目标数值**（用户明说）——结构性闸门禁止 `assert` / `raise`，返回体显式带 `note: 只观测口径；不设目标数值（用户明说）`；
3. **窗口语义成立**——30 天样本必须是 10 年窗口的子集。

## 三、第一批实测数据（直接回答用户的问题）

**近 30 天（n=1331）**：

| 指标 | 数值 | 读数 |
|---|---|---|
 | 平均回复长度 | **134.7 字**（中位 123）| 用户反馈「回复长度不稳定」有了量化证据 |
 | 长度分布 | 61-100: 304 ／ 101-150: 384 ／ **151-250: 375** ／ **>250: 95** | **超 100 字的占 64%** |
 | 私聊 vs 群聊 | 私聊 avg 136.3（n=846）／ 群聊 avg 132.0（n=485）| 私聊更长——而目标是「接近真人私聊」|
 | meow | **58.38%** | 「喵」出现在近六成回复里；config.yaml 那条「每条都是就是复读机」正是指它 |
 | bracket_action | **0.98%**（30天）／ 4.37%（全量）| 已从 2026-08-17 取证的 11.8% 降下来了 |
 | assistant_tell | **0.0%** | **助手腔几乎不存在——它不是主要矛盾**，推翻了「语言机械 = AI 腔」的直觉假设 |

**这批数据对 S5 后续的意义**：
- 「语言机械」的主因**不是**助手腔（0%），而是**长度（134 字）与复读感（喵 58%）**；
- T14/T15 才是对的方向——config.yaml 那 26 条里有「嘿嘿/喵~每条说就是复读机」，T15 有「默认一两句说完」；
- 下次观测可以直接看这两项有没有下降。

## 五、踩坑

1. **第一版采集器是「假绿」**：从日志统计得到 `replies_seen: 3437`、`anti_tell_total: 0`，
   数字看着像正常工作，实际数据源根本不含回复正文。**靠「去查日志实际长什么样」才发现**。
   这是教训 #36 与 #30（检查器写了但从没生效）的同源问题——**必须验证数据源真的含你要的东西**。
2. **生成的采集器块有语法错误**：我在生成 SQL 时想用 `.replace(",?)'", ",?)")` 这种运行时技巧拼字符串，
   产出的 Python 无法通过 `ast.parse`。改用脚本按行替换整块后通过。
   教训：**生成代码时不要用「运行时字符串手术」绕语法问题，直接把正确形态写出来。**
3. **变异脚本 M1 锚点不匹配**：我按记忆写 `"dialog_quality": collect_dialog_quality(),`，
   实际文件里引号形式不同。改为从文件里 `[l for l in lines if 'dialog_quality' in l][0]` 动态取锚点后通过。
   教训：**锚点不要凭记忆写，从文件读。**
4. **全量测试跑早了**：我在写 T17 测试文件之前启动了全量 job，结果它报 2602（不含新测试）。
   我一度以为新测试没被收集，查 `--collect-only` 确认是 2617 才定位到是时序问题。
   教训：**启动全量验证前先确认所有改动已落盘**。
