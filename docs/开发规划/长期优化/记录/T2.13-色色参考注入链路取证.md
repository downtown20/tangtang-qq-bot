## 四、为什么这是「契约冲突」而不是「谁写错了」

- 设计意图明写：`SEDUCTIVE_SLOT_BUDGETS`（1500/3800/6800）+ `SEDUCTIVE_TOTAL_BUDGET = 13500`，
  注释「**运行时绝不截断**——截断等于静默遗漏」（`handler.py:842-852`）。实测三槽位 1396/3639/6375
  **全部贴着预算但不超**，所以那句 warning 从来不响 ⇒ 加载侧以为「我全给你了」。
- 下游 `knowledge_block()` 只为**检索结果**设计：1,500 字封顶 + 「参考观点」caveat；再往下它进的是
  **1200t 公共背景池**，而且优先级最低。**两侧各自都自洽，合起来等于 0～333 字。**
- 规模对照：11,410 字 ≈ **20,000+ tokens**（本仓估算器中文 1.8 t/字），而整个背景池只有 **1,200t**
  ⇒「全量注入」在当前架构里根本放不下。这个冲突必须显式拍板，不能靠巧合。

   把 `SEDUCTIVE_TOTAL_BUDGET` 当作**唯一预算闸门**（超了继续蒸馏，不截断）。
   代价：一处新函数 + 两处调用点 + 常量闸门/测试。风险：常驻体积（见第 3 条）。

4. **先加观测再决定**：色色回合记一行「注入字数 / 是否被裁或被丢」，用真实数据决定走 1 还是 2。
