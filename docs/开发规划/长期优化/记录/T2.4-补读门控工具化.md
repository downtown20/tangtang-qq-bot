# T2.4 补读门控工具化（2026-10-16）

> 教训 #9「关键词替 LLM 决策」的**现役违规**之一：群聊组装区用 11 条短语 + 疑问词检测
> 决定要不要注入「补读」背景块。本轮把判断权交还给她：材料还在，取回权改成工具。

## 一、改造前的形态

`agent/handler.py:4093-4099`（群聊组装区）：

```
if self.catch_up and self._check_catch_up_query(clean_text):   # 11 条短语 + 疑问词
    _catch_summary = self.catch_up.get_summary(group_id)
    if _catch_summary:
        backgrounds.append(("补读", f"糖糖刚才不在的时候，群里聊了这些：{_catch_summary}"))
```

门控函数 `_check_catch_up_query`（原 `handler.py:10541-10552`）把「不在的时候聊了什么」「你错过了」
等 11 条短语与「什么/哪/怎么/吗/呢」做子串/包含判断——系统替她回答「这句话是不是在问补读」。
这正是 2026-08-16 范式转换（教训 #24）已经清理过一遍的那类代码，只是漏在了这条路径上。

## 二、改造后

1. **门控与函数整段删除**（组装区只留一条注释说明来龙去脉，防「好心修复」）。
2. **新工具 `get_offline_summary`**：
   - schema 在 `_build_memory_tools`（描述写明：想回答「我不在的时候你们聊了什么」或需要补上下文时调用）；
   - 执行器在 `_execute_tool`，返回**摘要原文 + 一行材料抬头**，不改写成台词（材料归她，措辞归她）；
   - 空摘要/无补读记录时返回一句**事实性**空提示。
3. **策略表**：`agent/memory_access.py` 的 `GROUP_SCOPED_TOOLS` 增加 `get_offline_summary`。
   离线摘要是**群作用域材料**（群里才成立），交给统一授权点绑定 `group_id`——
   执行器**不自己判权限**，避免出现第二套作用域判断（`handler.py:7567-7581` 是唯一授权入口）。
   后果（符合预期）：非主人私聊 → fail-closed 拒绝；主人私聊 → 放行但没有群 id → 拿不到群摘要。

## 三、这不是「砍功能」

- 材料仍在：`CatchUpManager.get_summary(group_id)` 原样保留，零改动。
- 变的只是**谁决定取回**：从「系统按关键词预判」变成「她调工具」。
- 兜底也在：T57 的缺口告知会告诉她「补读」这块丢了、以及 `search_chat_history` 可以取回（`_BG_RECOVERY_TOOLS`）。
- 已知代价（接受）：她若判断不需要，这一轮就没有补读材料——这是单脑原则的定价，不是缺陷。
