# T2.5 工具接入记忆访问策略的闸门（2026-10-16）

> 补 T2.4 暴露的窟窿：**加工具时漏登记进 `MEMORY_ACCESS_TOOLS` 会静默失效**。
> 这次是靠人肉发现的（工具返回「没有记录」而不是报错）。现在有机器闸门了。

## 一、失败形态（真发生过）

`agent/handler.py:7557-7581` 是唯一的授权入口：

```
memory_access = None
if name in MEMORY_ACCESS_TOOLS:
    memory_access = authorize_memory_access(...)
    if memory_access is not None:
        ...
        if memory_access.group_id:
            args["group_id"] = memory_access.group_id   # ← 作用域靠这一步绑定
```

不在策略表里的工具 → `memory_access` 为 `None` → `args["group_id"]` **永远不会被绑定**。
执行器读 `args.get("group_id")` 只会拿到空串，于是返回「没有记录」这种看似正常的答案。
加 `get_offline_summary` 时就踩了这个坑：工具是好的，但它永远看不到本群数据。

## 二、闸门（`tests/test_tool_policy_contract.py`，5 条）

用 AST 扫 `agent/handler.py`，得到两个集合：`_build_memory_tools` 里注册的工具名、
`_execute_tool` 的 `if name == "..."` 分支（以及该分支**是否读** `args.get("group_id")`）。然后：

| # | 闸门 | 拦住什么 |
|---|---|---|
| 1 | 读 `group_id` 的工具必须在 `MEMORY_ACCESS_TOOLS` 里 | 漏登记 → 静默拿不到本群数据 |
| 2 | 策略表里的名字必须是**真实注册**的工具 | 表腐烂、想象出来的能力 |
| 3 | 策略表里的工具必须有执行器分支 | 「登记了但没接线」 |
| 4 | 例外清单必须仍然用得上 | 例外腐烂（工具不再读 group_id 就该删） |
| 5 | **扫描器阳性对照**（教训 #30） | 检查器本身失效（种一个真样本必须抓得住） |

例外只有一类，且写明理由：**出站工具** `group_say` / `group_say_later`——它们的 `group_id` 是
「她要去哪个群说话」的**目标参数**，不是查询作用域；权限走 `_allowed_groups` 白名单
（`handler.py:7642` 分支内显式检查）。

## 四、遗留

- 闸门只覆盖 `handler.py` 的**内联**工具（`_build_memory_tools` + `_execute_tool`）。
  经 `agent/skills.py` 的 `@register_skill` 注册的技能走另一条路（`build_tool_definitions()`），
  本轮探针显示那些技能不在 `_execute_tool` 的 37 个分支里——**它们的权限模型另论**，未纳入本闸门。
- 出站工具（`group_say` 系）只有白名单，没有「谁能让糖糖代她发言」的判据；属教训 #33 的同类问题，
  本轮只登记不动作。
