# T2.6 社交小动作交权（点赞 / 戳一戳不再由骰子决定）

> 2026-10-16 夜，T59 轮「给 LLM 减负」主线第二例。上一例是 T2.4（补读关键词门控 → 工具）。

## 一、问题：系统用骰子替她做社交判断

取证（`agent/handler.py`，改造前行号）：

| 位置 | 旧行为 | 决定的是什么 |
|---|---|---|
| `_natural_like`（2139-2159） | 被 @ 时 **80%** 概率点赞、亲密度 ≥60 时 **40%**、熟人 **5%** | 要不要给这个人点赞 |
| 群聊回复后（4523-4527） | 对方发的是图片 → **无条件**点赞 | 同上（连概率都没有，系统直判） |
| `_try_proactive_poke`（2312-2314） | **50%** 概率直接 return | 要不要替她戳这个人 |

共同点：**系统在执行一个对他人可见的社交动作，而判断依据是随机数**。
这属「系统替 LLM 做决定」这一族（2026-08-16 范式转换同族：内容判断是 LLM 的决策域；
教训 #9 同族）。它甚至比关键词门控更隐蔽——门控至少还有一条规则可查，骰子连规则都没有。

## 二、处置：能力交给她，风控留在系统

| 谁 | 负责什么 |
|---|---|
| **她（LLM）** | 要不要点赞 / 要不要戳、对谁（= 此刻和她说话的人） |
| **系统** | ① 提供能力（两个工具）② 绑定目标（schema 里**没有** target 参数，目标由执行层从 `current_user` 取）③ 平台风控（冷却 / 日上限 / 亲密度下限）④ 把执行**事实**回给她 |

为什么目标必须由系统绑定：`poke_user` / `like_user` 这两个旧工具是**特权工具**
（`handler.py:7621-7625`：只有主人/群主会话才注入，且执行侧复验），普通群聊里她根本调不到；
而这次的场景恰恰是普通群聊里「她回复完群友」——所以不能直接放开旧工具（那等于让她能给任意第三人点赞）。
新工具没有参数，她只能作用于**本回合说话人**，越权面为零。

### 代码落点

- `agent/handler.py` `_try_like`：风控不过从「静默 return None」改为返回状态（`ok` / `skipped` / `failed`）。
- `agent/handler.py` `_natural_like`：**整体删除**（连注释说明一起留下，写明为什么不能加回来）。
- `agent/handler.py` 群聊回复后（原 4521-4536）：三个自动调度点删除，替换为一段说明注释。
- `agent/handler.py` `_try_proactive_poke`：删 50% 骰子；`intimacy` 可留空自取；返回状态
  （`ok` / `too_cold` / `no_channel` / `cooldown` / `capped_user` / `capped` / `failed`）。
- `agent/handler.py` `_build_memory_tools`：新增两个工具 schema（`like_speaker` / `poke_speaker`，无参数）。
- `agent/handler.py` `_execute_tool`：两个执行器分支（空 `current_user` fail-closed；私聊不戳）。
- `agent/handler.py` `_HANDLER_METHOD_TYPES`：两个新工具归 `behavior`（否则会多一轮 LLM 收尾）。
- `agent/handler.py` 主人自然指令 `poke` / `like_cmd`：改用状态回执（见下）。

## 三、顺手修掉的两个「假确认」

改造前的行为取证：

1. 主人私聊说「戳一下XX」→ `_try_proactive_poke(target_qq, "0")` **少传两个参数** → TypeError
   → 被 `except` 吞成「❌ 戳失败」。**这条路径从未真正生效过**，而且分不清是「没戳成」还是「代码坏了」。
2. `like_cmd` 直连 `send_like` API，**绕过 `_can_like`** 的频率/日上限，失败时静默返回 None；
   而「戳」路径更是无条件回「✅ 已戳 XX 一下~」——不管有没有真的戳出去。

两条都属 ADR-002 那一族（不确定 ≠ 已完成）。现在：状态从执行层返回，消息按状态如实回。

## 五、边界（没解决 / 没做）

- **主动戳的 50% 骰子删了，被动被戳的 4 个骰子还在**：`handle_poke`（约 2390-2420）里
  30% 反戳、`random.choice(replies)` 从三条**系统写死的台词**里挑一句、50% 图/文字、40% face。
  那是更严重的一处（系统在替她说话），但它要把「被戳」变成一条进 LLM 的输入，
  属另一个改造（下一项），本轮只登记不动作。
- **私聊戳不了**：本仓没接 `friend_poke`，NapCat 的 `group_poke` 只在群里有效。
  现在私聊里明确回「戳不了」（此前是假成功）。要不要接 `friend_poke` 需先实测平台支持。
- **关系档案/背景块无关**：本项不碰任何预算/优先级常量。
