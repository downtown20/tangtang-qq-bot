# T2.9 测试子进程编码两端钉死（假红收口）

> 2026-10-16 夜，goal round 5。前置：连续两轮全量里出现「同一批代码，有时绿有时红」。

## 一、问题

本仓测试里有几处 `subprocess.run(..., text=True)` 跑 Python 子进程（静态检查闸门、README
数字复现）。父进程**没有指定解码编码** → 按 Windows locale（GBK）解子进程输出；而子进程
的输出编码由**环境变量**决定（`PYTHONIOENCODING`）——两边各说各话，判据就随「谁在跑测试」变化：

| 外部环境 | 子进程输出 | 父进程解码 | 结果 |
|---|---|---|---|
| 干净 | GBK | GBK | 绿 |
| 注入 `PYTHONIOENCODING=utf-8`（某些 shell / CI 包装） | UTF-8 | GBK | 中文判据变乱码 → **假红** |
| 注入 `latin-1` | 子进程自己抛 UnicodeEncodeError | — | 红（但理由也不对） |

## 二、取证（先证明，再改）

- `tests/test_release_readme_contract.py:129-130` 与 `:244-246` 是**同一个动作的两个副本**：
  前者 `text=True` 无 `encoding=`，后者已经写了 `encoding="utf-8", errors="replace"`。
  ⇒ 不是「没人想到」，是**改了一处漏了另一处** —— 教训：#33「成对出现」的测试版。
- `tests/test_static_check.py:101-102` 有 `errors="replace"`（不崩）但没有 `encoding=`：
  乱码不会抛异常，只会让 `扫描文件数 = (\d+)` 匹配不到 → 报「输出里没有文件数」这种
  **指向错误的**失败信息。
- 实测原文（变异注入 latin-1 时子进程的报错）：
  `UnicodeEncodeError: 'latin-1' codec can't encode characters in position 0-4: ordinal not in range(256)`。

## 三、处置

1. 两个测试文件各加一个 `_run_capture(args)`：**两端都钉** —— 子进程 `PYTHONIOENCODING=utf-8`
   + `PYTHONUTF8=1`（覆盖外部注入），父进程 `encoding="utf-8", errors="replace"`。
   docstring 写明「不要退回 `text=True` 就走」。
2. 三处调用点统一走它（`static:101`、`readme:129`、`readme:_collect`）。
3. 两条**阳性对照**（教训 #30：检查器必须能红）：注入 `PYTHONIOENCODING=latin-1` 后仍应读得到中文。

## 四、变异（含一次自我打脸）

| 变异 | 期望 | 实测 |
|---|---|---|
| A：删掉 `test_static_check.py` 的 env 钉死 | 对照红 | **RED ok**（`UnicodeEncodeError`） |
| B：删掉 `readme` 的 env 钉死 | 对照红 | **第一版 GREEN = 假对照**；改判据后 **RED ok** |

**第一版 readme 对照为什么是假的**：它只跑 `pytest --collect-only`，而输出全是 ASCII
（文件路径 + 用例名）⇒ latin-1 也能解，测试恒绿 —— 与教训 #30「跑起来没报错 ≠ 真的扫了」同族，
只是这次「不报错」的是我自己的对照。改法：让子进程**真的打印中文**（`-c 'print("扫描文件数 = 1")'`），
环境变量一赢就必然红。两次变异都逐次还原并核对 SHA256 未变。
