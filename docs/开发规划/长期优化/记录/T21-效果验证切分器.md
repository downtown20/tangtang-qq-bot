## 一、为什么需要它

T19 时我差点报告「平均长度 172.8 → 67.4，降 61%」。
逐条核对时刻后发现：当天那 16 条**全落在 06:23–06:43**，而改动 **08:09** 才落地，
且 bot **需重启才生效** ⇒ **那是日内波动，不是修复效果**。

**教训：要谈因果，必须先证明变化发生在修复之后。**

而当时我是**手工**去核时刻的——下次还会忘。所以把这条纪律**机器化**：
给快照工具加一个按时刻切分、对比两窗口的命令。

## 二、做了什么

### 新增 `compare_dialog_quality(split_ts, days=7)`

按调用方给的 `split_ts` 把 `reply_metrics` 切成 **before / after** 两个窗口，各自给：

- `samples` / `avg` / `median` / 长度分桶 / `over_100_pct` / `meow_pct` / `hard_turn_pct`
- 两侧都有样本时才给 `delta`（均值差 / 超 100 字百分点差 / 喵百分点差）

### 新增 CLI `--quality-split TS`

```
python tools/长期优化快照.py --quality-split '2026-10-14 08:09'
```

### 三条设计原则（都有测试钉住）

1. **切点是调用方给的，代码不猜**——不知道部署时刻就不该假装知道。
2. **单侧为空绝不算差值**——那正是 T19 的错法：把「修复后 0 条」渲染成一个下降数字。
   实测输出：`修复后: 0 条 … (某一侧样本为 0，不算差值——先积累数据)`。
3. **只观测**——不设阈值、不判「变好」，差值留给读的人判断。
   （判定需要多少样本取决于效应大小，代码不该替人拍板。）

## 三、写测试时抓到的**真 bug**（本次最有价值的发现）

第一版实现里我写的是：

```python
cur.execute("... WHERE ts >= datetime(?, 'localtime', ?) AND ...", (split_ts, f'-{days} days'))
```

测试报 `after` 恒为 0、`before` 拿到全表 3674 条。手工验证 SQL 发现：

```
split='2026-10-14 00:00' -> datetime(...,'localtime') = '2026-10-14 08:00:00'   # +8 小时偏移！
```

**根因**：`ts` 列本身就是 `datetime('now','localtime')` 写入的**本地时刻**，
而我给 `split_ts` 又套了一次 `datetime(?, 'localtime')`——**把本地时刻当 UTC 再转一次**，
于是 `2026-10-14 00:00` 变成 `08:00`，当天所有行都被错误划进 `before`。

**修法**：切点直接字符串比较（两侧同为 `YYYY-MM-DD HH:MM:SS` 本地时刻文本），
只有下界 `-N days` 才走 `datetime` 运算。

**这个 bug 如果没被测试拦住，会静默制造一个漂亮的假效果**——
正好又是 T19 那类错误的另一种形态。

### 14 条测试覆盖

### 一个测试假设错误（我错，不是代码错）

我最初写「远未来切点 → 全在 before」，实测两侧都空。
查证后确认：`days` 是**相对 split 的下界**（不是「最近 N 天」），
所以 `split=2099` 会把下界一起推到 2089，自然什么都取不到。
改用仍在数据范围内的切点后通过。**测试假设错了要改测试，不是改代码迎合假设。**
