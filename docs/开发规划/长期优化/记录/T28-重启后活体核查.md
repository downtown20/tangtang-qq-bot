## 二、启动健康检查里的两条告警 —— 查完都不是缺陷

### 告警 1：`memory_truth: 12182 条 active 记忆缺少可验证信任等级，已排除自动召回`

**看起来像灾难**（「记忆被排除了」），实测是**设计中的门控在正常工作**：

| active 记忆 trust_level | 条数 | 能否召回 |
|---|---|---|
| `legacy_unverified` | 11980 | 排除（2026-08-16 事故防线，刻意停用）|
| `verified` | **4746** | **可以** |
| `unverified` | 202 | 排除 |
| `corrected` | 20 | 可以 |

11980 + 202 = **12182**，与告警数字**精确吻合** ⇒ 告警没算错，只是**语气像灾难**。
**4766 条可召回记忆足够 recall 正常工作**，不是「记忆全被挡了」。

### 告警 2：`extract_success: 协议成功率 7%，产出率 0%，JSON无效率 93%`

**这是小样本假警报**，而且**每次重启必然出现**：

1. 该检查读的是 **进程内累计计数器**（`handler.metrics`），**重启即清零**；
2. 检查自身的护栏是 `outcomes <= 5` —— **门槛低到没有意义**；
3. 于是重启后 2 分钟（09:55:26）用 **约 14 条样本**算出了「JSON 无效率 93%」。

**实际提取是健康的**：`extraction_jobs` 表 **10212 done / 0 failed / 0 dead**，今日新建 13 条。

**这与 T27 是同一种错误**：用小样本算出一个像结论的百分比，并且**顶着 WARNING 级别**。
本项目自己的教训 #30 变体：**假红会训练人忽略红** —— 每次重启都来一次的假红，代价是以后真红也没人看。
