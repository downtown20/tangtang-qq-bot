# T29 · 健康检查的小样本假警报 —— 每次重启都喊一次狼来了

> 完成日：2026-10-14 ｜ 状态：**已完成（待重启生效）**

---

## 一、现场

bot 每次重启后，「启动健康检查」都会印出：

```
🩺 [warn] extract_success: 协议成功率 7%，产出率 0%，JSON无效率 93%，调用异常率 0%
```

**而同一时刻** `extraction_jobs` 显示 **10210 done / 0 failed** —— **管道是健康的**。

---

## 二、两个原因（都在 `agent/health_check.py`）

### 原因 1：**它没看保温期，而它兄弟看了**

| 检查 | 是否调 `_in_warmup()` |
|---|---|
| `_check_extract_running` | **是**（`if now_hour >= 12 and not _in_warmup():`）|
| `_check_extract_success` | **否** ← 本次修的 |

**同一个文件里两个检查对「刚启动」的判断不一致** —— 是 T35 那类「两份拷贝漂移」的同族。

### 原因 2：样本下限只有 5

```python
outcomes = m.get_current("extract_outcomes_total")
if outcomes <= 5:
    return {"status": "ok", "message": "提取结果样本不足（等待至少 6 次）"}
```

`get_current` 读的是**进程内累计**计数器，**重启即清零** ⇒ 重启后头十几次提取
就被当成「成功率」。而热身阶段的失败率不代表稳态（模型首次加载、连接预热都在这里）。

---

## 三、修法（1 个文件）

```python
MIN_EXTRACT_OUTCOMES = 30   # 新增模块常量

if _in_warmup():
    return {"status": "ok", "message": f"启动保温期内，提取样本积累中（{outcomes} 次）"}
if outcomes < MIN_EXTRACT_OUTCOMES:
    return {"status": "ok",
            "message": f"提取结果样本不足（{outcomes}/{MIN_EXTRACT_OUTCOMES} 次），暂不判断成功率"}
```

**两个门槛缺一不可**：保温期挡「刚启动」，样本下限挡「启动久了但今天特别闲」。

---

## 四、为什么值得修（不是「让日志好看点」）

**假警报会训练人忽略警报。** 这一条本仓已经付出过代价（T3 的普查里就有
「假红训练人忽略红」的记录；T3.2 那次硬编码 `case_count == 70` 每次加维度都假红一次）。

**每次重启都喊一次狼来了**的后果是：真出问题那天，这条 warn 看起来一模一样。

而且这里有**反面证据可对照**：`extraction_jobs` 是持久表（10210 done / 0 failed），
它不受重启影响 —— **两个数据源给出相反结论时，先问哪个会被重启污染**。

### 第 4 条为什么必须存在

修「假警报」最危险的失败模式是**把闸门一起修瞎**（永远 ok）。
所以测试里专门有一条：**样本 100 条、协议成功率 30% 时，必须仍然报 warn**。
没有这条，`return {"status": "ok"}` 一改就全绿，而闸门从此不存在。
