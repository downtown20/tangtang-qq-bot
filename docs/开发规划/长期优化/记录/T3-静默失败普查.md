## 1. 【T9 - Critical】self_state.save() 7 个调用点失败处理三种不一致

- **位置**：`agent/self_state.py:601`（save() 本体，AST: try=0 logger=0 raise=0 pass=0，失败即抛）；
  调用点 `agent/handler_autonomy.py` **1553/1565/1574/1672/1701**（5 处 except Exception: pass）、
  `agent/handler.py:1929`（stop_services() **无 try**）、`agent/handler.py:1963`（_do_scheduled_restart() 落在外层裸 except）。
  唯一正确：`agent/handler.py:1926`（flush_pending_save，有 logger.warning）。
- **证据**：AST 逐点列出；`main.py:550 await self.handler.stop_services()` 无 try；`main.py:585-587 except KeyboardInterrupt: await tangtang.stop()`。
- **守护什么**：糖糖的**冷热场学习**（COLD_FIELD_PENALTY/WARM_REPLY_BONUS）、per-user 主动私聊冷却、24h 冷场结算、优雅退出持久化。
- **后果**：
  - _adjust_willingness(1553) 失败，意愿分回退，**重启后再次主动私聊同一人**（CLAUDE.md 教训 #15 原话：重启 7 次骚扰同一人 7 次）；
  - _mark_seek_sent(1565)/_mark_seek_gave_up(1574) 失败，无冷却记录，可立即再次打扰；
  - _settle_stale_seeks(1672) 失败，重启后重复看到旧 pending，重复惩罚（注释 1669-1671 自己写着否则中性结算路径重启后会再次看到旧 pending）；
  - stop_services(1929) 失败，异常冒到 main.stop()，**后续清理（metrics.flush / 后台任务取消 / LLM 客户端释放）全部不执行**；
  - _do_scheduled_restart(1963) 失败，被裸 except 吞，日志只有一行正常的「凌晨6点定时重启」，**重启后丢状态且无人知道**。
- **根因**：2026-08-16 按教训 #15 修的是「**没落盘**」；这次是「**落盘失败不可见**」——**同一个错误的第二形态，更隐蔽（代码看起来是对的）**。
- **违反的自身承诺**（同文件 docstring）：L1544「冷场教训不能重启丢」、L1559「重启不丢」。
- **最小修复**：1 个 `_persist_self_state(what)` helper（fail-open + logger.error + metrics 计数）收敛 7 处；
  测试 monkeypatch save 抛异常，断言 1) 不抛上层 2) error 日志 3) 指标 +1（**这条测试就是修复自己的阳性对照**）。
  **改动 2 文件 + 1 测试文件**，符合 B2。

## 2. 【T10 - Critical】tools/准备发布.py 清理器与检查器正则口径漂移

- **位置**：`tools/准备发布.py`（prep 用 WINPATH_RE/KEY_RE，chk 用 WIN_RE/KEY_RE，**两份独立正则**）。
- **证据**：队友阳性对照矩阵（probe13 拿正则原文 + probe14 逐用例对比）：

| 用例 | prep | chk | 备注 |
|---|---|---|---|
| access_token 10+ 字符 | HIT | **miss** | DRIFT |
| VOLC_TOKEN 字面量 | HIT | **miss** | DRIFT |
| C:/ 路径 | HIT | **miss** | DRIFT |
| E: 路径 | HIT | **miss** | DRIFT |
| file:///D: | HIT | HIT | - |
| 双反斜杠 | HIT | HIT | - |
| api_key long | HIT | HIT | - |

  prep 的 KEY_RE 比 chk 多 access_token / VOLC_TOKEN / _TOKEN= 三类模式；WINPATH_RE 也比 WIN_RE 宽。
- **后果**：1) 清理器清掉的信息检查器不认，检查器可能对已清理文件报零（**假绿**）；2) 只跑检查器不清洗，**漏报真实泄漏**。
- **根因**：**同一逻辑两份实现，口径漂移** = CLAUDE.md 教训 #30 的同族复发（#30 原文：正则写错从上线起就没匹配过任何东西；#31：白名单漏类型）。
- **最小修复**：prep 与 chk 共用**单一来源**的模块级正则常量，test_release_sanitizer.py 的阳性对照**同时覆盖两侧**。
- **附带已验证有效**（好消息）：scan_sensitive 对 5 个种植文件 4 命中；binary leak 的 UTF-8 判别有效；noise 0（probe5）。

## 3. 【T11 - Critical】tools/同步skills.py robocopy 失败但主流程无失败信号

- **位置**：`tools/同步skills.py` 的 _robocopy() 与 main()。
- **证据**（probe8 阳性对照，种 3 个 skill：1 正常 + 1 超长 description + 1 无 frontmatter，并把 dst 指向 bogus root）：
  - _robocopy(...) 返回 False（**它自己知道失败**）；
  - main() 返回 None；
  - main() 打印的行里 containing failed = []（**空**）。
- **后果**：skill 没同步成功，但脚本看起来正常结束、退出码不报错，造成「同步完成了」的错觉。
  与 frontmatter 检查（同一探针里 _check_frontmatter 正确报出 2 个问题）**行为不一致**：检查会报，复制不报。
- **最小修复**：main() 汇总 _robocopy 返回值，失败时 logger.error + 非零退出码（或至少在输出里打失败标记）。

## 4. 【T12 - Important】tools/同步codex_mcp.py 的 build_block 对退化输入产出跑不起来的配置

- **位置**：`tools/同步codex_mcp.py` 的 build_block()。
- **证据**（probe9）：输入 {'args': ['a']}（既无 url 也无 command），输出
  [mcp_servers.weird] / command = "" / args = ["a"] —— 一个 **command 为空**的 MCP server 块。正常输入（有 url）则输出正确。
- **后果**：cc-switch 里配置不完整的 server 会被静默写成一个永远起不来的块，无告警。
- **附带实测**：~/.claude.json 现有 servers = node_repl / anysearch / gitnexus / github / chrome-devtools；[mcp_servers.anysearch] 标记在 toml 中为 True（幂等标记按子串匹配，当前工作）。
- **最小修复**：build_block 对「无 url 且无 command」的输入返回 None 并在调用侧告警跳过，不要产出空 command 块。
