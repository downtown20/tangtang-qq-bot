## 二、摸底结论（决定了实现形态）

| 项 | 实测 |
|---|---|
| `tools/runtime_observer.py` | **154605 B / 3361 行**，**只有测试与文档引用，零生产调用方** |
| 它的性质 | 自带**阻塞**采样循环（`time.sleep`，`--interval-seconds` 默认 300、`--duration-hours` 默认 2）|
| `TaskManager` | 提醒语义（SQLite `tasks` 表，`add`/`add_at`/`cancel`/`retry`），**不是通用 cron 调度器** |
| 既有可复用面 | `agent/health_check.py` 的 `SystemHealth`（`register`/`run_hourly`/`_run_one`/`summary`/`self_state_context`）|
| 既有周期循环范例 | `handler_autonomy.py:319 _autonomous_loop`（`sleep(120)` → `while True` → `sleep(600)`）|

### 关键设计决定：**不把观察器塞进事件循环**

它自带阻塞 `time.sleep` 采样循环，进程内跑会占住事件循环（而事件循环里是糖糖的回复路径）。
所以改成**心跳 + 缺席检测**两段：

```
观察器跑完 → 往 kv_store 写一条心跳（health:observer_last_run）
健康检查    → 读心跳，≥2 个周期没更新 ⇒ error 告警
```

观察器本身仍由运维/主人在**进程外**跑（`--once` 一次就够）。
这既满足「挂计划任务」，又不把 3361 行的阻塞工具塞进事件循环。

## 三、实施（4 个文件）

### 1. `agent/health_check.py` 新增观察器缺席检查

| 常量 | 值 | 说明 |
|---|---|---|
| `OBSERVER_HEARTBEAT_KEY` | `health:observer_last_run` | 与观察器侧同名（有测试钉住相等）|
| `OBSERVER_ABSENCE_CYCLES` | `2` | 缺席 ≥2 个周期才算告警（审计判据）|
| `OBSERVER_MAX_AGE_SECONDS` | `3600.0` | 一个周期的定义 |

`_check_observer_absence(handler)` 四态：

| 情形 | 判定 |
|---|---|
| 刚跑过 / <2 周期 | `ok` |
| **≥2 周期未运行** | **`error`**（审计判据）|
| 从未跑过 + 启动宽限期内 | `ok`（那是「还没轮到」，不是缺席）|
| 时间戳无法解析 / 读库失败 | `warn` |

**冷启动豁免的边界写清楚了**：「还没开始」是预期，「开始后停了」是故障——这两种性质不同，不能一视同仁。

### 2. `agent/health_check.py` 新增管线积压体检（满足标准 ②）

`_check_pipeline_backlog(handler)` 一次消费 **7 条**健康查询（≥6 达标）：

| # | 查询 | 在体检表里读什么 |
|---|---|---|
| 1 | `store.get_decision_run_health()` | 未知/损坏的决策回合——**真的**要看的（卡住的行）|
| 2 | `store.get_inbound_event_health()` | 入站事件积压 |
| 3 | `store.get_proactive_event_health()` | 主动事件积压 |
| 4 | `store.get_action_receipt_mailbox_health()` | 回执信箱未结 |
| 5 | `store.count_quarantined_chat_logs()` | 隔离聊天记录 |
| 6 | `store.count_memories_today()` | 今日记忆（健康度基线）|
| 7 | `store.get_persisted_unprocessed_backlog()` | 未提取积压条数/人数 |

**为什么是这 7 条**：它们全是**无参或近无参的聚合计数**，恰好构成一张「各条管线有没有积压」的体检表。
而这张表的读者，正是定时健康检查——**写好了没人问就是死代码，接进来立刻变成活信号**。

返回 `warn` 而非 `error`：**积压是「需要看」不是「坏了」**。真坏了由各管线的专属检查负责（`extraction_queue`/`stale_extraction` 等）。
本项负责的是它们之间的**横向对照**——单看一条像正常，七条一起看才看得出「都在涨」。

实跑输出（真实数据）：

```
warn: 未提取积压 574 条/174 人；回执信箱未结 2；隔离聊天记录 14065（今日记忆 2 条）
```

### 3. `agent/handler.py` 注册两项检查

```python
self.health.register("observer_absence", lambda: _check_observer_absence(self), "hourly")
self.health.register("pipeline_backlog", lambda: _check_pipeline_backlog(self), "hourly")
```

### 4. `tools/runtime_observer.py` 写心跳

新增纯函数 `record_heartbeat(db_path, *, at=None) -> bool`，在 `main()` 里**报告写出成功之后**调用。

**落点很重要**：心跳必须在 `_write_outputs` 之后。写在之前的话，**一个坏掉的观察器也会显得「在跑」**——
那就把缺席告警变成了「掩盖问题」的工具。

**失败返回 False 而不抛**：观察器的主职责是观测，心跳写不上不该让它崩。

## 五、变异阳性对照 6/6 —— 其中两次「不变红」挖出真问题

M0 绿 / M1 阈值 2→0.5→红 / M2 心跳移到报告之前→红 / M3 假表名→红 / M4 摘掉两条接线→红 / M5 还原绿

### v1 的两次「不变红」及诊断（这是本轮最有价值的部分）

**M2 第一次不变红** → 诊断（按纪律先查「变异是否真打中目标」）：

v1 的变异是在原心跳**之前再插一份**，两份都在 `_write_outputs` 之后 —— 顺序契约仍成立，所以合理地不红。
**但诊断过程中发现了真正的测试缺陷**：`main()` 里有**两个** `_write_outputs` 调用——
循环内的检查点写入（`len(snapshots) >= 2` 时）和循环后的最终写入。
我的断言用 `find()` 取的是**第一个**（循环内的），而**真正要守的不变量是「心跳在最终报告之后」**。
改用 `rfind()` 取最后一个 `_write_outputs` 后，正确变异（把心跳移到最终写入之前）立刻变红。

**M4 第一次不变红** → 诊断：我接了 **7** 条但断言写的是 `>= 6`，摘掉 1 条剩 6 条仍然通过。
**是我的变异不够狠，不是测试无效**——改为摘掉 2 条（7→5，跌破阈值）后立刻变红。

**两条方法论**（都值得记住）：
1. **变异不变红时，先证明它是否打中了目标，再判断测试是否无效。** 这次一种是「没打中」（M2 v1 的插入位置）
   ，一种是「打中了但测试的断言指向了错误的调用点」（M2 的真缺陷）——后者只有靠诊断才看得出来。
2. **断言要指向真正的不变量。** 「心跳在某个报告之后」和「心跳在**最终**报告之后」是两个不同的命题，
   而 `find()` 与 `rfind()` 的差别正好是这两个命题。
