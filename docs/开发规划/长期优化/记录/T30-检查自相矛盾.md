## 一、起因：两个数字对不上

重启后的启动日志里，两行健康检查报的是**同一件事**，结论却相反：

```
[warn] pipeline_backlog: 未提取积压 579 条/173 人；回执信箱未结 2；隔离聊天记录 14065
[ok]   stale_extraction: 积压579条/173人，到期0，等待584，oldest=2026-09-25，state=normal
```

而提取 worker 每 15 秒说一次 `open=0 … idle_reason=no_open`。
**三个数字指向同一件事，两个结论。**

---

## 二、先把「到底哪个对」查清楚

### 两个计数器的口径不同

| 来源 | 口径 |
|---|---|
| `get_extraction_backlog_snapshot()` | `chat_log` 里**超过该用户提取游标**的行 |
| `get_extraction_queue_health()` | 队列里**已入队的任务** |

### 为什么 579 条积压却 `admitted=0`

准入判据在 `agent/extraction_policy.py:17`：

```python
IMMEDIATE_MESSAGES = 10            # >=10 条 → 立即
STALE_MESSAGES = 3                 # >=3 条 且 >=7 天
ONE_OFF_AFTER_SECONDS = 21 天      # 其余：等 21 天
```

实测分布（173 用户 / 584 条，人均 3.4）：

| 人均待提取 | 用户数 |
|---|---|
| 1 条 | 55 |
| 2-3 条 | 49 |
| 4-5 条 | 32 |
| 6-9 条 | 37 |
| **>=10 条** | **0** |

**没有任何用户达到 10 条** ⇒ 走不到「立即」；`eligible_messages = 0`，
`deferred_messages = 584`，最旧 2026-09-25（19 天前，还差 2 天到 21 天阈值）。

⇒ **`stale_extraction` 是对的：提取策略在按设计工作**，584 条全在等时间阈值。

## 三、缺陷：那行 warn 是**我加的**

对比两条检查：

| | `_check_stale_extraction`（既有）| `_check_pipeline_backlog`（**我 T3.1 加的**）|
|---|---|---|
| 口径 | 有 `eligible/deferred` 拆分 | `get_persisted_unprocessed_backlog`，**只有原始计数** |
| 消息 | `到期0，等待584，state=normal` | `未提取积压 579 条/173 人` |
| 判定 | `eligible == 0` → **ok** | 积压 > 0 → **warn** |

**同一个 579，一行 ok 一行 warn。**

而且我自己的 docstring 写着：

> 真坏了由各管线的专属检查负责（extraction_queue / stale_extraction 等）

**我写了「判定归它们」，然后又用原始计数独立判了一次。**

### 还有第二个冻住的读数

`隔离聊天记录 14065` —— 查库后：

```
隔离时间范围: 2026-08-28 03:30:05 → 2026-08-28 03:30:05    # 同一秒，一次批量操作
近 7 天新增隔离: 0
```

**一个冻住的存量**。它会在**每次启动**都贡献一次 warn —— 那不是告警，是噪音。

这与 T29（`extract_success` 每次重启都因小样本报 WARNING）是同一类：
**永久性的假警报会训练人忽略警报。**

## 四、修法：把「读数」与「判据」分开

判据的界：**与基线无关、非 0 即为错** 的才进 `parts`（触发 warn）；
**存量数字**进 `context`（只作读数，不触发告警）。

| 项 | 归类 | 理由 |
|---|---|---|
| 未提取积压 | **读数** | 判「到期」需要 eligible/deferred 拆分，那是 `stale_extraction` 的职责 |
| 隔离聊天记录 | **读数** | 冻住的存量（一次批量，近 7 天 0）|
| 未知/损坏决策回合 | **判据** | 状态机里有卡住的行——与基线无关，非 0 即错 |
| 回执信箱未结 | **判据** | 同上 |

**读数不许被藏起来**：它们仍然出现在消息里（`（读数：…）`），
只是不再单独触发 warn。而且积压那条**点名了它的归属检查**
（`到期判定归 stale_extraction`）——让读的人知道该去看哪一行。

**没做的**（B3，一次一件事）：
- 不改 `extraction_policy.py` 的任何阈值（21 天/7 天/10 条）——那是产品行为，
  实测它在按设计工作，改它需要主人拍板；
- 不删 `_check_pipeline_backlog`——它的横向对照价值仍在（unknown/receipt 那两判据）；
- 不动 `_check_stale_extraction`——它本来就是对的，是**我该向它对齐**。

## 六、我自己的错（写测试时）

第一版 fixture 我写的是：

```python
BACKLOG_579 = [('q%d' % i, 3, ...) for i in range(173)]   # 173 × 3 = 519
```

**变量名说 579，实际是 519。** 两条断言（`'579' in message`）当场变红。
**是断言抓到了我起错的常量名，不是代码缺陷。**
改成 60 个 4 条 + 113 个 3 条 = 579，13/13 全绿。

**教训：用数字命名变量时，先算一遍它是不是那个数。**
