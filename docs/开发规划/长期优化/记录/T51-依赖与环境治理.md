## 一、torch：nightly → 稳定版 2.13.0

### 起因
`agent/reranker.py:31-46` 的 `_reranker_runtime_check()` 只看一个字符串：
版本号里含 `.dev` 就 `return False`，重排模型被静默跳过、退化为纯余弦排序。
本机装的是 nightly `2.14.0.dev20260727+cu130`，于是重排**从来没有生效过**。

### 选版过程（download.pytorch.org 索引实测，cp310-win_amd64）
| 通道 | torch 最高稳定版 | torchaudio 最高版 | 能配对的最高版 |
|---|---|---|---|
| cu130 | 2.14.1 | **2.11.0** | **2.11.0** |
| cu128 | 2.11.0 | 2.11.0 | 2.11.0 |
| cu126 | 2.14.1 | 2.11.0 | 2.11.0 |
| cu124 | 2.6.0 | 2.6.0 | 2.6.0 |

**torchaudio 在这个平台上停在 2.11.0**，所以 torch 2.13.0 没有同版本 audio 配对。
——这是选 2.13.0 之前不知道的事实，与「干脆降到 2.11.0 凑一对」是两个取舍；
选 2.13.0 + 保留现有 torchaudio，并**实测**兼容性（见下）。

### 执行
    pip install "torch==2.13.0+cu130" --index-url https://download.pytorch.org/whl/cu130 --no-deps

`--no-deps` 是故意的：torch 会顺手把 numpy 顶到 2.x，而项目把 numpy 钉在
`<1.24`（RVC / pyworld / numba 0.56 都要）。装完 diff `pip freeze` 基线，无漂移。

### 验收（全部实测）
| 判据 | 结果 |
|---|---|
| 版本 | `torch 2.13.0+cu130`，不含 `.dev` |
| CUDA | `is_available()=True`，NVIDIA GeForce RTX 5070 |
| 算力架构 | `['sm_75','sm_80','sm_86','sm_90','sm_100','sm_120']`，`get_device_capability()=(12,0)` |
| 真算 | 256×256 矩阵乘在 cuda 上跑通 |
| **守卫** | `_reranker_runtime_check() -> (True, '')` —— **不再跳过** |
| **重排可用** | `ready=True, device=cuda`，加载 10.6 s |
| 重排正确性 | 问「她上次说过喜欢什么花」→「她提过最喜欢向日葵」得 **3.55**，「主人养了只猫」得 **-8.94**，排序正确，**177 ms** |
| BGE 向量 | `ready=True, dim=512, BAAI/bge-small-zh-v1`，encode 0.02 s；开心~心情好 **0.8405** / 开心~签证 **0.2542** |
| 依赖未漂移 | numpy 1.23.5 / transformers 4.57.6 / faiss 1.7.4 / sentence_transformers 4.1.0 |
| torchaudio | 2.11.0.dev20260727+cu130 **导入正常、resample 正常**（保留不动） |
| GPT-SoVITS 端到端 | 服务启动成功、权重全加载；`POST /tts` → **HTTP 200 / 395,564 字节 / 有效 RIFF-WAVE / 5.6 s** |

### 显存预算（同机三件事共用一张 12 GB 卡）
GPT-SoVITS ≈ 5.2 GB，reranker 上 GPU 后 **+2.3 GB → 7.7 GB / 12.2 GB**，余 4.5 GB。
BGE 留在 CPU（载入前后显存不变），没有额外占用。

### 遗留（不是问题，是事实）
* **torchaudio 无法与 torch 2.13 同版本对齐**（平台无 2.13 轮子）。实测兼容故保留。
  将来若要动它，先读 `requirements.txt` 里那段注释。
* 项目文档里 torch 一直被当作 **CPU 依赖**（`requirements.txt:25` 原文
  「torch 另装 CPU 版」）。CPU 版没有 sm_120，在 5070 上等于废卡。**已改掉这条注释**。

## 二、ffmpeg 入 PATH

### 查到的真相（与既有认知不同）
1. `C:\Windows\System32\ffmpeg.exe` **早就在**（`tools/快速安装ffmpeg.py` 老版本
   把它复制进去的）——所以 `shutil.which("ffmpeg")` 一直有值。
2. 但那份是 **static 版，一个 DLL 都没有**。
3. System32 里还另躺着一个 **143 MB 的 `ffprobe.exe`**，于是
   `ffmpeg`/`ffplay` 解析到新装的、**唯独 `ffprobe` 仍解析到旧的那个**。
4. 注册表 PATH（HKLM 851 字符 / HKCU 1543 字符）**都不含任何 ffmpeg 目录**。
5. **torchcodec 要的是共享库（`avcodec-*.dll` 等），static 版给不了。**

### 所以「不加入 PATH」的后果
| # | 失效的东西 | 触发点 | 表现 |
|---|---|---|---|
| 1 | **语音消息听不懂** | `agent/asr.py:331` `shutil.which("ffmpeg")` | silk/amr → 16k wav 转码没有工具，`_convert_to_wav` 返回 None，识别整条跳过；日志只有一句「ffmpeg 未安装」，用户侧是「她不回我语音」 |
| 2 | 共享库缺失 → torchcodec 报错 | `import torchcodec` | `RuntimeError: FFmpeg is not properly installed` ——**加 PATH 也修不好**，除非装的是共享库版 |
| 3 | TTS 输出 wav→mp3 失败 | `agent/voice.py:623`（CosyVoice 分支）、`tools/rvc_sing.py:222`（唱歌）、`tools/打包发布版本.py:158`（发布打包） | FileNotFoundError 或退出码非 0；唱歌/发布产物缺 mp3 |
| 4 | 参考音频准备失败 | `tools/prepare_michele_refs.py:72,93,119` | 要 ffprobe + `ffmpeg silencedetect`；**ffprobe 从来没进过 System32**，这条一直断 |
| 5 | 体检/安装器**报假绿** | `tools/体检.py:304`、`tools/安装糖糖.py:350` | 只判断 `which()` 有没有值。System32 那份让它恒有值 → 检查项失去意义（本仓教训 #30 同型） |
| 6 | 静音降级 | 以上各处的 except 分支 | 语音相关能力整体退到文字，用户看不出原因 |

**第 5 条是最阴的**：它不是「功能坏了」，是「坏了但检查说好」。

### 执行
`tools/快速安装ffmpeg.py` **重写**（老版本就是复制 exe 进 System32 的元凶）：
1. 下载 BtbN **共享库版** `ffmpeg-master-latest-win64-gpl-shared.zip`（84.7 MB）
2. 解压到 `依赖/ffmpeg/`（项目内，不是 C 盘）
3. `依赖/ffmpeg/bin` 写进 **HKLM 系统 PATH**
4. 把 System32 里的 `ffmpeg.exe` / `ffprobe.exe` / `ffplay.exe` **隔离**到
   `依赖/ffmpeg/_quarantine/`（System32 在 PATH 最前，不清掉就一直遮住新装的）
5. **阳性对照**：DLL 数量 > 0 且三个 exe 都能 `--version`

### 验收
* `依赖/ffmpeg/bin/` 有 **7 个 DLL**（`avcodec-63`、`avdevice-63`、`avfilter-12`…）
* 三个 exe 都跑得起来（`N-127507-g24e860f6d3-20261013`）
* 全新环境解析：`ffmpeg` / `ffplay` → 项目内；`ffprobe` 隔离后也 → 项目内
* 注册表：HKLM PATH 已写入；System32 残留：**已清**
* **闸门测试** `tests/test_ffmpeg_installer.py`（11 条）钉死三件事：
  再也不能出现 `shutil.copy` 往系统目录塞二进制；`STALE_NAMES` 必须穷举三个名字；
  `check()` 必须**能失败**（空目录 → False，阳性对照）

### 补救的一处连带坑
把 System32 的 exe 隔离之后，**任何环境块陈旧的进程都会解析不到 ffmpeg**
（写注册表只对之后新启动的进程生效）。bot 常由早就启动好的控制台拉起 →
语音识别会静默失效。所以加了进程内兜底：
`agent/paths.py:ensure_ffmpeg_on_path()`（找项目自带目录 → 前置进 `os.environ["PATH"]`
→ 顺便 `os.add_dll_directory` 给 torchcodec），并在 `main.py` 启动早期调用一次。
闸门 `tests/test_ffmpeg_path_fallback.py`（10 条）。

同时改掉 `agent/asr.py:333-338` 里那条**害人提示**——
它原先教用户「下载 ffmpeg.exe 放到 C:\Windows\System32\」，那正是这次假安装的来历。

## 三、依赖迁移到项目内

### 现状（迁移前）
| 位置 | 体量 |
|---|---|
| `C:\...\Python310\lib\site-packages` | 7,403.9 MB / 110,704 文件 |
| `C:\...\Roaming\Python\Python310\site-packages` | 4,106.2 MB / 7,580 文件（**其中 4,044.7 MB 是 pip 中断留下的死目录 `~orch`**） |
| `C:\Users\...\.cache\torch`（torch.hub 缓存，demucs 用） | 1,199.6 MB |
| **C 盘可用** | **4.06 GB** |

`~orch` 只有 `lib/` 和 `_C.cp310-win_amd64.pyd`——pip 升级时改名待删、删除失败留下的
残骸，波浪号开头的包名连 import 语法都不合法，**纯垃圾**。直接删，回收 4,044.7 MB。

### 做法：搬迁 + 目录联接（junction）
新增 `tools/依赖迁移.py`（带 `--dry-run / --apply / --verify / --rollback / --purge-backup`）：

1. `robocopy` 复制 → 项目内 `依赖/`
2. **逐项核对文件数与总字节**，不一致就中止、源目录原样保留
3. 源目录**改名**（不删除）为 `<名字>.C盘备份-<时间戳>`
4. `mklink /J` 在原位置建目录联接
5. 读回验证

**为什么不用 venv**：项目大量代码直接用 `sys.executable` 跑主环境
（`service_manager.py:458` 就是用它启动 GPT-SoVITS），换 venv 要动代码、
要重装 371 个包（fairseq / jieba-fast 还要 MSVC）。联接对进程**完全透明**——
`sys.path` 里的路径字符串一个字没变，解释器照旧解析，零代码改动。

### 验收
| 判据 | 结果 |
|---|---|
| 三项核对 | 110,704 / 7,403.9 MB、7,580 / 59.7 MB、14 / 1,199.6 MB **全部一致** |
| 联接生效 | `site-packages` → `依赖/site-packages`（另两项同） |
| `sys.path` | 未变 |
| 解释器 | `import torch/transformers/numpy/faiss` 全 OK |
| GPT-SoVITS | 启动 traceback 里的路径已是 `<项目根>\依赖\site-packages\torch\...` —— **确实走的联接** |
| 回滚可用 | `--rollback` 只删联接（`rmdir` 对联接不动目标）+ 备份改名搬回 |

**C 盘备份暂留**（安全网）。确认长期无异常后再 `--purge-backup`，届时 C 盘可回收约 8.6 GB。

## 四、安装位置可配置（Windows 原生目录选择）

单一事实源 `tools/依赖位置.py`：

* `get_deps_root()` 三级回退：环境变量 `TANGTANG_DEPS_ROOT` → 项目根 `依赖位置.json`
  → **项目内 `依赖/`**（默认值**不是 C 盘**）
* `set_deps_root(path)` 落盘
* `choose_directory(title, initial)` 弹**系统原生**目录选择框（Qt 优先，回退 tkinter）
* `is_on_system_drive(path)` 只做警告，不硬拒绝（项目本身装在 C 盘时不把路堵死）
* `describe_deps_root()` 告诉用户当前在哪、来自哪一级

### 接进 tools/安装糖糖.py（+146 行，1132 → 1278）
* 新增 `--deps-root PATH` / `--deps-root=PATH` / `--yes` / `-y`；
  交互运行时弹目录选择框，**取消 = 用默认值继续**（不是失败）
* 落盘点全部改走依赖根：pip `--cache-dir`、modelscope `cache_dir`、
  `temp_files`、模型下载落点
* **关键设计**：运行期读取点是硬编码项目内路径（`agent/embeddings.py:23-25`、
  `reranker.py:26-27`、`mood_tracker.py:23-24`、`asr.py:30`、
  `service_manager.py:23`），只把下载目标换盘等于「装了但读不到」。所以
  `_deps_target()` 做三档：
  1. 依赖根 == 项目根 → `BASE/<rel>`（老行为逐字不变）
  2. `BASE/<rel>` **已是真实目录** → 原地用，**绝不自动搬用户数据**
     （本机 `models/` 是 6 GB 真目录，实走这一档）
  3. 其余 → `<依赖根>/<rel>`，并在 `BASE/<rel>` 建**目录联接**指过去
     （与 `tools/依赖迁移.py` 同一手法；失败则退回项目内并告警）
* `check_environment()` 的 ffmpeg 检测补了落盘位置兜底 —— 原先只用
  `shutil.which`，而安装器自己就是那个「PATH 还没生效」的进程，会把已装好报成未找到

## 五、连带修掉的两处

1. **`docs/发布/README.md` 测试数徽章 2400 → 2900**。
   契约测试要求「真实收集数 − 徽章下限 ≤ 500」，T51 新增约 60 个用例后
   2935 − 2400 = 535 > 500 → 红。**这是本次改动引起的，不是既有失败**
   （改动前 2888 − 2400 = 488 ≤ 500，本来是绿的）。
2. **`-X utf8` 会让该契约测试炸出另一种错**：它在子进程里跑
   `pytest --collect-only`，UTF-8 模式下父进程按 utf-8 解码，子进程仍按
   cp936 输出 → `UnicodeDecodeError` → `out.stdout` 为 None →
   `re.search` 抛 TypeError。**跑全量请用项目自己的命令，不要加 `-X utf8`。**
