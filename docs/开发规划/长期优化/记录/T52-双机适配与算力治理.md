## 四、语音超时自适应（本次最硬的一条修复）

### 实测（同一台机器、同一批中文文本，GPU 与 CPU 各跑一遍）

| 文本长度 | GPU（RTX 5070） | CPU（无加速卡） |
|---|---|---|
| 2 字 | 1.2 s（冷启动） | 42.8 s |
| 18 字 | 1.5 s | 40.2 s |
| 50 字 | 2.7 s | **80.9 s** |
| 100 字 | 5.4 s | **198.2 s** |

### 缺陷

`agent/voice.py:526` 原来写死 `httpx.AsyncClient(timeout=60.0)`。

**CPU 上 50 字要 80.9 秒 —— 超过 60 秒 ⇒ 长语音在笔记本上必然失败。**
而且失败链路会**自己加重**：3 次重试全部撞在同一个还占着单 worker 的请求上，
白等 3 分钟才降级发文字，期间服务端队列被压深。这不是「偶尔慢」，是「一定发不出去」。

### 修法（agent/voice.py，1 文件）

1. `tts_timeout(text)` 按设备与长度给预算（抽成模块级函数**是为了可测**——
   写在调用点里就只能靠真跑一次超时来验，而那是分钟级的）：

       accelerated: 60 s（100 字实测 5.4 s，失败要**快速**暴露）
       cpu:         max(180, 60 + 3.0 × 字数)

   对实测值：2 字 180/42.8=4.2×、18 字 4.5×、50 字 210/80.9=2.6×、100 字 360/198.2=1.8×。

2. **超时不重试**：判类型（`isinstance(e, httpx.TimeoutException)`）而不是判文本 ——
   httpx 超时异常的 `str(e)` 是**空串**（T50 取证的「失败:  (text=」那句就是它）。
   预算已是实测值的两倍，超时说明是异常不是「慢」；再发一次只会把队列压得更深。
3. 失败日志改成真实的尝试次数（原来是写死的「3次」）。

## 五、GPT-SoVITS 设备归一化（gpt-sovits/start_api_patched.py，1 文件）

T50 的 `_ensure_gpu_device()` 只认 cuda，且「已经是 cuda 就直接 return」。
现在：

1. 设备目标走 `_load_devices()` → **按文件路径**加载 `agent/devices.py`。
   不 `import agent` 的原因：启动时 cwd 是 gpt-sovits、`sys.path[0]` 也是它，
   把项目根 insert 进去会让 GPT-SoVITS 自己的 `tools/` 等模块被项目同名目录抢走。
2. **每次启动都归一化**，而不是「已是 cuda 就返回」——这个 yaml 会随 Syncthing 在两台
   机器间来回，不归一化就会留下「台式机写的 cuda 被笔记本读到」的跨机残留。
3. `CUDA_VISIBLE_DEVICES=-1` → 强制 CPU。那是 service_manager 表达「本次运行别再碰
   加速卡」的方式，不尊重它的话，GPU 原生崩溃后的 CPU 兜底会变成「切到 XPU」。
4. `is_half` 只在 cuda 上开。上游自己的自动判定（configs/config.py:195）也是
   「没有 CUDA 就 fp32」；XPU 上开 fp16 没经过本项目验收，不冒险。
5. YAML 重写抽成纯函数 `_rewrite_device_yaml(text, target)`（可测：直接跑
   `_ensure_gpu_device` 会改到真实的 tts_infer.yaml 上）。

**阳性对照（真跑）**：把 tts_infer.yaml 伪造成「笔记本同步过来的」7 个 profile 全
`device: cpu / is_half: false` → 用补丁启动器拉起 → 输出
「tts_infer.yaml 已切到 cuda（7 个 profile，is_half=true；上游原样备份在
tts_infer.yaml.cpu-default）」→ YAML 实测 7× cuda、0× cpu、7× is_half:true，
API 读到 `device: cuda`。
**幂等性实测**：`_rewrite_device_yaml(cur,"cuda") == cur`、逐行 diff = **0 行**、
写盘前后字节数 2484 = 2484（纯 CRLF，56 个）⇒ **不会给 Syncthing 制造无关变更**。

## 六、两台机器各装什么（已写进 requirements.txt）

    ┌ 台式机（RTX 5070 / sm_120）→ CUDA 版
    │   pip install "torch==2.13.0+cu130" \
    │       --index-url https://download.pytorch.org/whl/cu130 --no-deps
    └ 笔记本（Intel Arc 130T 核显）→ XPU 版
        pip install "torch==2.9.1+xpu" "torchaudio==2.9.1+xpu" \
            --index-url https://download.pytorch.org/whl/xpu --no-deps

**为什么两台不能共用**：CPU 版没有 sm_120 → 台式机的 5070 等于废卡；CUDA 版在笔记本上
没卡可用 → 白占 1.8 GB。
**为什么两台都不能用 nightly**：`agent/reranker.py` 的守卫只放行稳定版（含 `.dev`
直接跳过加载）—— 那是 2026-08-15 加载事故的防线。
**torchaudio 两条线不一样是正常的**：cp310-win 上 cu130 线最高 2.11.0（无 2.13 配对），
xpu 线有**匹配的** 2.9.1 对。不要为了「统一」去动它们。

⚠ **XPU 那条路径本机无法实测**（这台机器没有 Intel 显卡）。所以它的设计原则是
「有就用，没有就安静退到下一档」：装了 torch+xpu 且 `torch.xpu.is_available()` 为真，
阶梯自动点亮；没装或驱动不对，一切照旧走 CPU，**不会更糟**。
笔记本侧的验证命令：`python -c "import torch;print(torch.xpu.is_available())"`，
以及 `python tools/体检.py` 的第 6 节（现在会同时报 CUDA 与 XPU 两档）。

## 九、过程中的两处自我纠正（值得记下来）

### 1. 本仓自己的「零调用闸门」抓住了我写的死代码

新增 devices.py 时我顺手写了 `torch_device(prefer=None)` —— 用起来舒服，但**没有任何调用方**。
全量测试里 `tests/test_integration_contract.py::TestZeroCallerGate` 当场变红：

    agent/devices.py:147 :: torch_device

这正是本仓教训 #14（「写了 infra 代码 ≠ 接入了业务」）与反模式 #6（框架先行）的闸门，
**它是对的**。处理：删掉 `torch_device()`（真要用，`torch.device(...)` 在调用点只有一行）。

同一轮里还发现 `summary()` 也是死的 —— 闸门没抓到它，因为 `summary` 这个名字在别处
有同名调用（按名字匹配的粗粒度盲点）。**不能因为闸门没抓到就留着**：把 `体检.py` 第 6 节
改成直接打印 `_devices.summary()`，既给了它真实调用方，又替体检省掉一段手写格式化。

### 2. 线程数调参：测了，**决定不动**

CPU 上 torch 默认 `get_num_threads() == 物理核数`。本机实测 1024×1024 矩阵乘：

| threads | 4 | 8（默认） | 12 | 16 |
|---|---|---|---|---|
| ms | 6.0 | 3.2 | **2.7** | 3.0 |

超出物理核数最多换来 **1.19 倍**，而且**最优点因机器而异**（笔记本是 6P+8E+2LPE 的混合核，
「物理核数」这个概念本身都不清晰）。这正是本仓教训 #7「**在调参数时问自己：方法本身有问题吗**」——
真正的大头是**换设备**（GPU 5.4s vs CPU 198.2s，37 倍），不是拧这 19%。**故不写死任何线程数。**
