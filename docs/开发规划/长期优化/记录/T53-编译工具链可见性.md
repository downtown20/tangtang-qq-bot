# T53 编译工具链的可见性（MSVC cl.exe）（2026-10-14）

**起因**：主人在安装依赖时看到「MSVC cl.exe: [√] ...」，问：本项目需要依赖它吗？做什么用的？
不装会怎样？换到别的电脑会提示吗？这四个问题值得逐条**取证**回答 —— 结果查出一条体检的缺口。

---

## 一、它是什么：**安装期工具链依赖，不是 Python 运行时依赖**

`main.py` 与 `agent/` **没有一行代码调用 cl.exe**。它只在 `pip install` 时被用到：
某些包在 PyPI 上**没有 Windows 预编译轮子**，pip 只能下源码包现场编译，而 Windows 上编译
C 扩展就要 MSVC 的 `cl.exe`。

这不是新结论 —— 项目自己在 `docs/开发规划/换机依赖与GPT-SoVITS启动修复计划_20260905.md:104`
就是这么定性的（「这不是 Python 运行时依赖，而是**安装期工具链依赖**」）。本次是把它**核实**了一遍。

---

## 二、到底哪几个包需要它（查 PyPI 实证，2026-10-14）

| 包 | PyPI 最新 | 文件类型 | win_amd64 轮子 | 需要编译？ |
|---|---|---|---|---|
| **jieba-fast** | 0.53 | 只有 sdist | **0** | ✅ 需要 |
| **fairseq** | 0.12.2 | bdist_wheel + sdist | **0** | ✅ 需要 |
| pyworld | 0.3.6 | bdist_wheel | 3 | ❌ 有轮子 |
| numba | 0.68.0 | bdist_wheel + sdist | 7 | ❌ 有轮子 |
| jieba | 0.42.1 | 只有 sdist | 0 | ❌ **纯 Python，不需要编译器** |
| torchfcpe / librosa / edge-tts | — | 纯 Python | — | ❌ |

⇒ **只有两个**：jieba-fast（GPT-SoVITS 的分词加速）与 fairseq==0.12.2（歌唱工作室的 RVC/HuBERT）。
两个在安装器里都是 **soft 组**（`tools/安装糖糖.py:196, 211`）—— 失败**只警告不中断**。

---

## 三、不装会怎样（实测，不是推测）

### jieba-fast 装不上 → 影响**几乎为零**

GPT-SoVITS 的 `text/chinese.py` 是**硬 import** jieba_fast，缺了服务起不来；所以
`gpt-sovits/start_api_patched.py:15-36` 的 `_ensure_jieba_fast()` 把纯 Python jieba
映射成 `sys.modules["jieba_fast"]` 顶上去 —— **服务照常启动**。

代价实测（450 字中文文本 × 200 轮）：

| | ms/次 |
|---|---|
| jieba_fast（C 扩展） | **0.205** |
| jieba（纯 Python 回退） | 0.558 |
| 比值 | 2.72× |

看着是 2.7 倍，但**绝对差只有 0.353 毫秒**。而 GPT-SoVITS 合成同一批文本要
CPU 42.8~198.2 秒 / GPU 1.2~5.4 秒（T52 实测）—— 分词耗时占比在 **0.001% 量级**。
**用户侧完全无感。**

### fairseq 装不上 → **这个是真损失**

`tools/rvc_convert.py:30-42` 用 `fairseq.checkpoint_utils` 加载 HuBERT 做特征提取；
装不上就打印「⚠️ fairseq HuBERT 加载失败」→ 返回 None → **歌唱工作室的翻唱（RVC）不可用**。
（预录成品的**播放**不受影响，只影响「做新翻唱」。）

---

## 四、换到别的电脑会提示吗 —— **安装器会，体检原来不会（本次补上）**

| 位置 | 改前 | 改后 |
|---|---|---|
| `tools/安装糖糖.py` | ✅ 扫 VS2022 路径找 cl.exe，找不到打三段提示（`cl_paths` 只用于打印，**从不阻断安装**） | 判据改走共享函数，提示补上「影响 1 / 影响 2」 |
| `tools/体检.py` | ❌ **一个字都不提 MSVC** —— 换到没装 VS 的电脑上，这件事在体检里完全不可见 | ✅ 新增两行 |
| `docs/用户手册/使用说明.md:68-70`、`文件同步指南.md:145` | ✅ 已有说明 | 不动 |

**缺口的具体形状**：换机纪律是「打包 → Syncthing 同步 → 解包 → **体检** → 启动」，
而体检恰恰是那句纪律里唯一被执行的检查 —— 它不报，就等于换机时不报。

### 顺带修掉第二个盲点：检查的是「装上了」而不是「在加速」

`体检.py` 原来只判 `import jieba_fast` 能不能成功。但 **jieba_fast 的包体是纯 Python 外壳**，
真正干活的是**顶层模块** `_jieba_fast_functions_py3.pyd`（实测 29,696 字节，装在
`site-packages/` 根，**不在** `jieba_fast/` 包目录里 —— 我第一次就是在包目录里白找了一圈）。

⇒ 只判前者，会把「**只有外壳**」误报成「装好了」。这和本仓教训 #30（检查器写了但从没生效）/
#36（把「工具报 0」当成「事实是 0」）是**同一个形状：检查要对着真东西，不要对着名字**。
现在体检会明确分两行报：

    [√] MSVC cl.exe           C:\...\VC\Tools\MSVC\14.38.33130\bin\Hostx64\x64\cl.exe
    [√] jieba-fast C 扩展      在（真的在加速）

---

## 五、单一判据

新增 `agent/paths.find_msvc_cl()` 与 `agent/paths.has_jieba_fast_c_extension()`，
安装器与体检**都走它**。理由与 T52 的 devices.py 相同：本仓已四次踩「同一规则的多份拷贝」
（T10/T12/T25/T35/T42），而 MSVC 扫描当时已经是「安装器一份、体检零份」的不对称状态。

闸门 `tests/test_build_toolchain.py`（7 条）钉住：

1. 探测永不抛异常
2. 找到的路径必须真的存在、是 Hostx64 的 cl.exe
3. C 扩展的模块名是**顶层**那个（防止后人猜成 jieba_fast.xxx）
4. **阳性对照**：判据结果必须与 `importlib.util.find_spec` 一致（两边都能动）
5. **安装器与体检里不许再出现 `VC/Tools/MSVC` 这个扫描标记**（挡第三份拷贝）
6. MSVC 缺失**不得中止安装**（源码闸门：检测段里没有 sys.exit / return 路径）
7. 安装器必须**按文件路径**加载 `agent/paths.py`（它要在依赖装齐之前就能跑）
