# T57 背景块裁决权（2026-10-16 落地）

> 台账号 T57。三条改动：**定序原则改为「丢了能不能用工具取回」**、**真有淘汰/裁剪时把缺口告诉她**、
> 以及一份**否决清单**。全部落在 `agent/protocols.py` 的 `fit_backgrounds` 一带。

## 一、为什么是这两条（而不是加预算）

前一版（T56）解决了「生产端没有体积契约」：关系档案正文封顶 470t，整块 ≤ 600t。
但**池子只有 1200t**，而一个高活跃关系的一轮材料实测在 **1.9–2.2k**（窗口 636t、关系档案 453t、
自忆 422t、记忆 ~250t、反思 184t、画像 382t）——**超订 60–80%**。所以每轮都在丢东西；
问题不是「丢不丢」，是**丢谁**、以及**她知不知道丢了**。

旧行为两点都不对：

1. **丢谁由「谁更重要」的直觉决定**——关系档案登记在 P9（倒数第 6），而它是全库**唯一没有工具**
   能取回的材料（`relationship_summary` 只有「注入」一个读取点，见
   `docs/审查/文档核查_20261015/关系档案注入调查.md` §4）。结果是：取不回来的先丢，
   能用 `search_chat_history` / `search_facts` 捡回来的反而留着。
2. **丢得静默**——T56 只让淘汰/裁剪进了日志，进的是运维的眼睛，不是她的上下文。
   她照常开口，不知道「ta 刚发的东西没进来」，用户看到的是「你忘了」。

## 二、改动

### 1. 定序原则：按「可恢复性」排序（`protocols.py:445` 一带）

`BACKGROUND_PRIORITY["关系档案"]` **9 → 4**（非证据类 flex 首位）。判据一句话：
**丢了能自己取回的材料，必须先让位给取不回的。**

| 块 | 旧 | 新 | 有工具能取回吗 |
|---|---|---|---|
| 关系档案 | 9 | **4** | ✗ 没有（全库唯一读取点就是注入） |
| 窗口 / 补读 | 5 | 5 | ✓ `search_chat_history` |
| 交叉 / 关系 | 6 / 13 | 6 / 13 | ✓ `search_relations` |
| 记忆 | 7 | 7 | ✓ `search_facts` / `search_memories` |
| 自忆 | 10 | 10 | ✓ `search_memories`（可恢复性未单独取证，故不动） |
| 日记 | 11 | 11 | ✓ `search_episodes` |

### 2. 缺口告知（`_bg_gap_notice`，`protocols.py:390` 起）

真有淘汰/裁剪时，注入**一行事实**（新增块标签 `缺口`，优先级 1 = 保护级，允许 overflow、永不被裁）：

```
（这一轮有几块材料没放进来：窗口（只放了一部分）、记忆。要的话你可以自己取回来：
窗口用 search_chat_history；记忆用 search_facts / search_memories。）
```

- 只报告**事实**：哪些块没进来、哪些能用什么工具取回。**不写指令、不写建议**
  （同 T58 的 `memory_recall_hint`、同「歌单只随 sing 工具出现」）。
- 取回工具只登记**确实注册过**的五个 `search_*`（`_BG_RECOVERY_TOOLS`）；
  关系档案/画像/反思/情绪/知识库**不写**——不在这里替她发明能力。
- 没有淘汰也没有裁剪时返回空串：**非饱和回合逐字节不变**。

### 3. 与审计文档 §6.5 的关系（必须交代的一条）

`关系档案注入调查.md` §6.5 写过「**不推荐单独用调优先级/预算数字治标**」，理由是
「问题是总量超订，把关系档案提到 P8/P7 只是池内搬运」。**那条结论仍然成立**，
本次改动不与它冲突，因为改的是另一件事：

| | §6.5 反对的 | 本次做的 |
|---|---|---|
| 目的 | 让关系档案**不再被裁**（假装解决体积超订） | 让**先丢的恰好是能捡回来的** |
| 池子 | 不动 1200t，却当成「已解决」 | 不动 1200t，**也不声称解决**（体积由 T56 的生产端契约管） |
| 判据 | — | 可恢复性（有工具 / 没工具） |

§6.5 末句指出的真问题——「保护块（协议）最多吃掉 84% 预算」这一结构问题——**仍未解决**，
已登记进 `未完成事项.md`（B 区）。

## 三、实测（生产函数 + 生产形态复刻）

饱和复刻（`协议` 120 字 + `窗口` 360 字 + `记忆` 200 字 + `关系档案` 250 字，预算 1200）：

| | 旧（关系档案 P9） | 新（P4） |
|---|---|---|
| 进池顺序 | 窗口(裁) → 记忆(裁) → 关系档案**整块丢** | 关系档案 → 窗口(裁) |
| 结果 | 关系档案不可恢复地消失 | 关系档案保留；记忆被丢**且她被告知**「记忆用 search_facts 取回」 |

（这条形态已固化成回归测试：`test_relationship_archive_survives_a_saturated_round`，
并把「旧优先级下必然整块丢」写进 docstring——防止有人日后把数字调回去。）

### 连带修正（T56 的两条测试按位置取块）

`缺口` 块插在**最前**（因为「协议紧贴用户原文」是 `fit_backgrounds` ③ 的既有不变量，
插在末尾会把它挤开一格），于是 T56 留下的两处**按位置**取块的断言失效：
`test_relationship_block_keeps_contract_after_truncation` 与 `test_truncated_block_is_logged`。
已改成**按标签取块**——它们守的契约（契约行在块首、裁剪留痕）没变，变的是「第一块材料」不再等于 `out[0]`。
同一原因顺带修了 `test_current_turn_evidence_survives_protected_overflow` 的顺序断言（排除系统注入的告知）。

## 五、没做什么（边界）

- **没扩容**：`BACKGROUND_BUDGET_TOKENS` 仍是 1200（抬预算需先拿到 supply 分布，见台账 D 区）。
- **没分层**：生产 69 次淘汰里只有 1 次是「保护块吃满」形态，池子分层仍被否决。
- **缺口告知只报事实**，不告诉她「这块材料你该不该要」——要不要取回是她的判断。
- **画像 P8 是登记-消费漂移**（全仓无生产点），本轮只标注不清洗。
- 告知本身的 token 也入账（会把日志里的 `used` 推高一点）；保护块允许 overflow，故不会挤掉任何块。
