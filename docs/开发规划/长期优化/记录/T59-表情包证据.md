## 二、机制：图片来源怎么被识别、怎么进历史

### 2.1 ws 层定形（`onebot/ws_client.py:1919 _extract_text`）

- `seg.type=='image'`：`sub_type=='1'` → `[表情]`（:1936-1937）；有 `summary` → `[图片:{summary[:20]}]`（:1938-1940）；否则 `[图片]`（:1941-1942）。
- **生产实测：`sub_type=1` 在 `chat_log` 里命中 0 行** —— QQ「动画表情」是以 `image` + `summary="[动画表情]"` 到达的，走的是 :1938 那条分支。

### 2.2 handler 层分类（`agent/protocols.py:199 looks_like_sticker`）

判据全部来自平台元数据：`raw` 含 `sub_type=1` → 是；`text` 含 `[表情]`/`[动画表情]` → 是；`[图片:X]` 中 X 含「表情」→ 是（:207-212）。

### 2.3 五个 `_call_vision` 调用位（`agent/handler.py`）

| 位 | 行 | 触发条件 | 是否影响是否回复 |
|---|---|---|---|
| 群·按需识图 | `3844` | `has_image and vision_enabled`（:3831），在回复判定之后 | 否（但每回合调一次 API） |
| 群·自然识图 | `4059` | 同上，构造 `turn_image` 时 | 否 |
| 群·偷图打标签 | `8757` | `_steal_count % 10 == 0`（:8754），fire-and-forget | 否 |
| 私聊·自然识图 | `5216` | `"[CQ:image" in raw and vision_enabled`（:5195） | 否 |
| `analyze_image` 工具 | `8029` | LLM 自主调用（定义 :7014，过滤 :7208） | 否 |

⇒ **五个位都不决定「要不要回」**——两次回复的成因在更上游（见第三节）。

### 2.4 进历史的样子

- 入口缓冲先中性化：`_protocols.normalize_image_placeholder(text)`（`protocols.py:154-162`）→ `（发了张图片）`；调用点 `handler.py:3382`（群 buffer）、`:4820`（私聊落库）。
- 真图识图后**写回**：`enriched = f"（发了张图片，内容是：{brief}）"`（`handler.py:4067` 群 buffer / `:5224` 私聊 DB），写库入口 `_enrich_image_message_store`（:10028）。
- `user_text` 组装时再兜底一次同样正则（`handler.py:3987` / `:5153`）。
- 表情包（T59 后）：`looks_like_sticker` 为真 → 只注入事实串，不写回内容（群 `:4055-4056`、私聊 `:5213-5214`）。

## 三、判定链：哪一行让一条消息变成两次 LLM 调用

1. **一条 QQ 消息 = 一个 ws 事件**：`onebot/ws_client.py:788 _dispatch` → `:921 _event_worker` → `:1043 _handle_group` → 回调 `handle_group_message`。两条消息天生两个事件、两个 `cid`。
2. **批处理分流**（`agent/handler.py:3210-3221`）：
   - `raw` 含 `[CQ:at,qq={bot_qq}]` → `batcher.debounce_at`（1.5s 防抖，**不合并**，`message_batcher.py:34/71`）；
   - 否则 `not is_engaged(user, group)` 且 `batcher.enqueue_group(msg)` → return（2s 合并窗，`message_batcher.py:31/55`）；
   - **窗口内（`is_engaged` 为真）两条分支都不走 → 逐条直通**。
3. **窗口定义**：`agent/conversation_tracker.py:28 ENGAGED_WINDOW=120` / `:29 GRACE_PERIOD=10` / `:30 FADE_PERIOD=300`；`is_engaged` 在 `:432`。
4. **窗口内强制进入 LLM 决策**（`agent/handler.py:3550-3566`）：
   ```
   in_conv, threshold = await self._conv_tracker.get_window_bonus_async(user_id, group_id)   # :3550
   if in_conv and threshold == 50 and not should_reply:                                     # :3564
       should_reply = True                                                                  # :3565
       reply_reason = "活跃对话窗口(交由LLM自主判断)"                                          # :3566
   ```
5. **于是文字和图片各自**走到 `:4182 reply, turn_actions = await self._call_llm_with_skills(...)` → `:4350 ok = await self._checked_send("group", ...)`。
   - 18 例双回复的 A 侧 `reply_reason`：**12 例「活跃对话窗口(交由LLM自主判断)」**（`:3566`）+ **6 例「被@了」**（`:3461`）——**没有一例**来自插话评分（`:3591`）。B 侧（图片那条）**18/18 全部**是「活跃对话窗口」，因为图片本身从不 @ 人。
6. **窗口外也不一定合并**：`batcher` 只聚合「同一 2s 批窗内到达」的消息（`message_batcher.py:131/138`）。文字在 T 到达、图片在 T+3s 到达 → 两批 → 仍可能两次；日志里「同时有 N 个人找你」合并视图全量只有 **40 次**（N=2:31、N=4:4、N=3:2、N=5/7/23 各 1）。
7. **T59 修复点（已写盘、未运行）**：`agent/handler.py:3118 _attach_as_media_followup`，接线在 `:3436`（群，位于所有记账副作用之后、`should_reply` 判定之前）与 `:4835`（私聊）；判据 `protocols.py:184 is_pure_media_message` + `:173 MEDIA_ATTACH_WINDOW_S = 120.0`。命中即 `return`，不开新回合。

## 五、未知 / 待验证假设

1. **群聊双回复率的真实值**：DB 口径 20/3415 = 1%，但日志可判区间只有 10-14 起 212 组（1 例）。两个分母不可比；「群聊 1% vs 私聊 50%」的差异**没有证据支撑**，需按 `cid` 对齐重算才能定论。
2. **私聊 61/61 = 100% 的解释**：DB 只按时间戳判断「有回复行」，**不区分**「这张图换来回复」还是「前一条文字的回复迟到落在窗口里」。假设：其中一部分是迟到归账，不是新回合。待验证（需按 `cid` 或 `event_key` 对齐）。
3. **`_last_image` 不区分发送者**：写点 `handler.py:3847`（群·按需）、`:8763`（偷图）、`:10161`（`_quick_vision_lookup`，死代码），读点 `:3850-3855` 只按 `group_id` 取。假设：群里 A 发的图描述会被注入到 B 的回合（`:3855` 用 `img['sender']` 拼文案，语义上会带出 A 的名字）。代码看着成立，**无日志实锤**。
4. **偷图与按需识图互相覆盖**：`_steal_stickers`（`:8742`）每 10 次才识图一次（`:8754`），但命中时同样写 `_last_image[group_id]`（`:8763`）——与按需识图写同一个键。假设：会互相覆盖描述。待验证。
5. **T59 修复对本次 18 例的覆盖率：代码路径核对为「全部覆盖」（已核验，非假设）**。
   - 18 例的 A 侧全部走到过 `handler.py:3436`：A 是实质发言 → `_attach_as_media_followup` 会执行 `self._last_real_utterance[scope]=now`（`:3135`）。证据：A 侧都打印了 `💭 糖糖决定回复`（`:3672`，位于 `:3436` 之后）。
   - @消息那一支看似会提前 return，实际不会：`debounce_at`（`:3218`）返回 True 后确实 return，但 1.5s 后 `_wait_then_process` 置 `_debounced=True` 重入（`message_batcher.py:87-94`），而批处理分支的前置条件是 `not msg.get("_debounced")`（`:3210`）⇒ 重入时**跳过批处理、直达 `:3436`**，锚点照常设置。
   - 18 例里 A 侧无「窗口消息进入LLM决策」的 **6 例**，其 `reply_reason` 全部是「**被@了**」——因为 `:3564` 的条件是 `and not should_reply`，@ 已先置 True 才不打窗口行（`handler.py:3460-3461`）。这是**日志形态**差异，不是分支未走到。
   - 结论：18 例的 A 全是实质发言（锚点被设）、B 全是纯媒体、dt 最大 25s < 120s（`MEDIA_ATTACH_WINDOW_S`）⇒ 按 T59 判据**应全部不再产生第二次回复**。仍待重启后实测（见下条）。
6. **重启后能否复现**：验收判据「文字（已回复）→120s 内一张表情包 → 不产生第二次回复」目前**无法用日志验证**（T59 日志文案 `附件化` 命中 0，因为没运行）。重启后应能在 `日志/tangtang.log` 里 grep 到 `🖼 附件化：纯媒体消息并入上一次发言`（`handler.py:3137-3139`）。
7. **120s 窗口是否够**：实测连发对 dt 分布为 dt≤2s 767 组 / ≤5s 1302 / ≤10s 724 / ≤30s 719 —— 绝大多数落在 5s 内，120s 足够；锚点 key 是 `group:{group_id}:{user_id}`（`handler.py:3436`），只在本人消息上移动，跨用户不受影响（正确）。待验证：同一个人「发文字 → 别人插话 → 他再发图」时锚点是否仍有效。
