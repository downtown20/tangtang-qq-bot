## 二、为什么不建议现在拆（决定性证据）

### 证据 1：局部变量跨整函数流动

我量化了「写入行 → 最后一次读取行」的跨度。结果：

| 函数 | 跨 100 行以上流动的变量 |
|---|---|
| `handle_group_message` | **56 个**（183 个局部变量里的 31%）|
| `_execute_tool` | **30 个** |
| `handle_private_message` | **38 个** |

最极端的几个：

```
handle_group_message:
  user_id          写入 L3047 → 最后读 L4406（跨 1359 行）
  group_id         写入 L3046 → 最后读 L4405（跨 1359 行）
  nickname         写入 L3048 → 最后读 L4405（跨 1357 行）
  _mood_report_turn 写入 L3122 → 最后读 L4381（跨 1259 行）
  turn_image       写入 L3057 → 最后读 L4063（跨 1006 行）

_execute_tool:
  m                写入 L7221 → 最后读 L8241（跨 1020 行）
  memory_access    写入 L7363 → 最后读 L8274（跨 911 行）
```

**这意味着这些函数不是「很长的函数」，而是「一整个流程被写在一个函数里」。**
拆分必须把几十个变量串成参数或上下文对象，而每一处传递都是出错机会。

### 证据 2：这不是「巨石函数」，是流水线

`handle_group_message` 里有 **199 条顶层注释段**——它们不是杂乱堆积，而是**有序的处理阶段**：
消息过滤 → ASR 规范化 → 图片捕获 → 防抖/批处理 → 感知反馈 → 机器人过滤 → 白名单 →
群名片 → 高频检测 → 权力结构 → 指令 → 文件/图片/偷图 → buffering → 记忆提取 →
插话 → 去重 → 忙线 → 亲密/纪念日 → 上下文并行查询 → 场景 → 历史组装 → llm_message 组装 →
上下文预算 → 引用 → 协议注入 → LLM 调用 → 标记解析 → 发送 → 归账 → 经验积累。

**关键点：这个顺序本身是语义。** 注释里到处是「必须在批处理之前」「必须早于 ASR」「必须在 clean 之前」
（例如 L3077「必须早于 ASR/图片/feedback/buffer 等业务副作用」、L4105「必须在 ReplyPipeline 清洗前冻结」）。

拆成方法后，「谁在谁前面」从**一个函数的行序**（编译器/读者都能直接验证）变成**调用图上的隐式约定**——
这正是 CLAUDE.md 教训 #16/#25/#28 那一族：**顺序约束一旦离开行序，就靠人记，而人会忘**。

### 证据 3：拆分的收益与风险不对称

| 维度 | 收益 |
|---|---|
| 可读性 | 真实，但**可通过注释段导航弥补**（已有 199 条阶段注释）|
| 可测试 | 部分真实——但这是**编排代码**，逻辑大多已在被调用的子模块里（`memory`/`store`/`protocols`/`reply_pipeline`）|
| 性能 | 无 |

| 风险 | 说明 |
|---|---|
| 顺序破坏 | 上百处「必须早于/必须之后」约束依赖行序，拆后靠人记 |
| 状态泄漏 | 56 个跨 100+ 行变量需重新组织；漏传/错传是静默 bug |
| 回归面 | 这是消息路由中枢，**每一条路径都是生产流量**；测试覆盖的是行为不是路径（教训 #25：测试绿 ≠ 路径被覆盖）|
| 收益/风险比 | 收益是「读起来更舒服」，风险是「聊天机器人主链路行为变化」|

## 三、结论

**不建议整体拆分 `handle_group_message` / `_execute_tool` / `handle_private_message`。**

理由一句话：**它们的长度来自流程本身，不来自坏味道。** 强行拆分会把「显式的行序约束」换成「隐式的调用约束」，
在没有测试覆盖每条路径的前提下，这是用高回归风险换可读性。

### 但有一条低风险、有真实收益的路（如果要动）

**只抽取「零依赖的纯计算块」**——即：不读外部变量、不写外部变量、无副作用的连续片段。
这类块抽取后：

- 顺序无关（纯函数，放哪都一样）；
- 可单测（输入→输出）；
- 失败可回滚（一次一个）。

候选示例（需逐个取证确认零依赖）：

- `_execute_tool` 里大量「参数校验 + 权限判定」的纯判断块（如 L8109-8120 的隐私闸门、L7417-7419 的控制工具权限复验）——
  这些是**安全关键**的，抽成具名函数后可以单独写闸门测试，收益最实在；
- `handle_group_message` 里的「引用解析 / 昵称映射」纯转换块。

**这不是 T6 的执行范围**——它是 T6 的产出建议。若主人同意，作为独立任务登记（一次一个块，各带测试与变异对照）。

## 四、另一个更该优先的方向

评估过程中发现：`__init__` **657 行、155 个 self.* 属性**、`if` 只有 16 个——
它不是「长逻辑」，是**巨型初始化清单**（把所有子系统接上）。

这类函数的拆分风险**显著低于**消息处理器：拆成若干个 `_init_xxx()`，
顺序依赖大多真实存在但**边界清晰**（「先建 store 再建 memory」这类），且没有每消息流量路径。

**若主人想动 handler.py，建议从 `__init__` 开始，不从消息处理器开始。**
