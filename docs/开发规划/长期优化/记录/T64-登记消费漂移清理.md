# T64 · 清理「登记-消费漂移」+ 把它机器化

> 2026-10-23。动因：`未完成事项.md` 里**同一条病被登记了两次、每次都说「留给专门的漂移任务」**——
> 「`BACKGROUND_PRIORITY["画像"]` 与 `_BG_RECOVERY_TOOLS["补读"]` 对应一个**不再产生的块**…留作一次统一的漂移清理」（T2.4 轮）。
> 本轮就是那次清理。

## 一、病根：手写的登记表 vs 代码里的消费点

`agent/protocols.py` 有两张**手写登记表**：

- `BACKGROUND_PRIORITY`（块标签 → 优先级，决定池子紧时先丢谁）
- `_BG_RECOVERY_TOOLS`（块标签 → 她能用哪个工具自己取回）

而块是 `agent/handler.py` 里 `backgrounds.append(("标签", …))` **产出的**。
两边没人比对，于是表里攒下了**永远不会出现的标签**。

**这为什么值得修**（不是「多一个数字」那么轻）：留着的代价是**下一个人会以为这些块存在**——
去改它们的优先级、或替她登记一个取回工具。而「补读」**真的被登记过**
（`_BG_RECOVERY_TOOLS["补读"] = "search_chat_history"`），也就是说：
**她已经被告知「补读这块丢了可以用 search_chat_history 取回」，可那块自 T2.4 起就不存在了。**

## 二、取证（AST，不是 grep）

用 `ast.walk` 扫 `agent/*.py` 里所有 `backgrounds.append((标签, …))` / `insert` 形态，实测 20 个标签有生产点：

```
引用 协议 证据纪律 姿态 窗口姿态 提及 文件 图片 关系档案 窗口
交叉 反思 记忆 自忆 日记 关系 情绪
```

对照 `BACKGROUND_PRIORITY` 的 20 个键，**多出三个**：

| 标签 | 为什么不再产生 | 处置 |
|---|---|---|
| **画像** | 画像行在**记忆块内部**渲染（`protocols.py` §4 的 C4），从来没有独立块 | 删键 |
| **补读** | T2.4 把关键词门控换成 `get_offline_summary` 工具后，这个块不再产生 | 删键 + **删 `_BG_RECOVERY_TOOLS` 里的对应行** |
| **知识库** | T2.14 把色色范本改走 `pinned`（不进 `fit_backgrounds`）之后，`backgrounds` 里已无该块追加（`handler.py:4151/5308` 两处注释明写「原来的知识库追加已删」）| 删键 |

⚠ **为什么必须用 AST 而不是 grep**：这些标签名大量出现在**注释和 docstring** 里
（本文件的说明文字就写着「画像」「补读」「知识库」）——文本匹配会被自己的说明糊过去。
这正是 T2.2 记录的**自指陷阱**。

## 三、改动（2 文件）

| 文件 | 改动 |
|---|---|
| `agent/protocols.py` | `BACKGROUND_PRIORITY` 删 3 键；`_BG_RECOVERY_TOOLS` 删「补读」；注释改为交代清楚「删了什么、为什么」而不是「留给专门任务」 |
| `tests/test_background_gap_notice.py` | 修 1 条手抄清单（见下）+ **新增双向闸门 3 条** |

**顺带修掉一处「手抄清单」**：`test_relationship_archive_outranks_tool_recoverable_blocks` 原来手抄了
`recoverable = ["窗口", "补读", "交叉", "记忆", "自忆", "日记", "关系"]`——**里面就有已经死掉的「补读」**。
改为从 `_BG_RECOVERY_TOOLS` **推导**。这是 CLAUDE.md §三那条「技能与工具清单不在这里手抄」的同一条纪律：
**手抄清单必然腐烂**。

## 四、新增闸门（3 条，双向对账）

| 闸门 | 判据 |
|---|---|
| `test_every_priority_label_has_a_producer` | 表里每个键**必须有生产点**（否则就是漂移） |
| `test_every_produced_label_has_a_priority` | 每个生产点**必须在表里登记优先级**（否则落到默认 9，被旧记忆挤掉） |
| `test_recovery_tools_only_name_real_blocks` | 取回工具表**不许点名不存在的块** |

白名单 `_GATE_PRODUCER_EXCEPTIONS` **只有一个条目**（`缺口`）——它由 `fit_backgrounds` 内部插入，
不经 handler 的 `append`。**这是设计上的唯一例外，不是逃生门**（注释里写死了「不要为了变绿往这里加」）。

## 六、方法论沉淀

**「同一条病被登记两次、每次都说『留给专门任务』」是文档层的病，不是代码层的病。**
T2.4 轮与 T59 轮各登记过一次，措辞几乎一样，两次都没动手——
因为它们都被写成「低优先、可延后」，而延后的东西不会自己回来。

**能机器化的判据不该留在待办里**：这条漂移的本质是「两张表没人对账」，
而对账是**完全可自动化**的。写一次闸门（约 40 行）比登记三次「待清理」便宜得多，
而且**它防的是下一次**（以后任何人加块/加优先级，漂移当场红）。
