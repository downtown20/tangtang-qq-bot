# 模型自动切换 · 实施与验证记录

> 完成日：2026-10-14 ｜ 需求方：主人
> 需求：模型不可用（限额等）时自动切备用模型，任务不中断。
> 备用顺序：WorkBuddy Step-5-Preview → WorkBuddy AI Deepseek-V4.1-Flash 0.03 倍率 → cainiao（OpenAI 端点）deepseek4.1flash。
> 强度默认最高（上下文 1M / 输出 256K 等），支持手动调。

---

## 一、结论：复用开源，不造轮子

| 候选 | 是什么 | 判定 |
|---|---|---|
| `@deepseek-ai/dsh-llm-retry`（DSH base 自带） | 同模型重试执行器 | **不够**：只重建同一个 provider/model 请求；always mode「会重试永久性失败——认证、配额…持续到成功或取消」= 限额时反而卡死烧钱 |
| **`dsh-llm-fallbacks@0.6.5`** | 自动 provider/model fallback 链，专治「重试耗尽/权限/配额/限流 429」 | **采用** |
| `@kongfun2018/dsh-llm-fallback@0.1.3` | 同类实现（跨 provider + 配额感知） | 备选；0.6.5 迭代更深（35 个版本）且更匹配本机 peerDeps |

### 它精确挂在我独立推导出的官方扩展点上

```js
// dsh-agent-loop/lib/index.js:1140 的真实契约
const action = await this.dispatch.waterfall('agent/request-error', {
    turn, step, provider: request.provider, failure: finish.failure,
    retryPolicy: preparedCall?.retryPolicy, signal,
}, () => Promise.resolve(void 0));
if (action?.kind !== 'retry') throw new LlmError(...);
continue;
```

分层：`llm-retry`（base 层）先同模型有界重试；耗尽后 waterfall 流到 `llm-fallbacks`，
识别 `triggerCodes` → 解析链 → 写 pending switch + cooldown → 也返回 `{kind:'retry'}`；
下一步 `agent/request` 时它 `await next()` 之后覆盖 provider/model。

**bundle 顺序保证分层**：插件自带 patch 注释明确要求「profile 必须把 llm-retry 排在
dsh-llm-fallbacks 之前」，安装器已自动把 `dsh-llm-fallbacks` 追加到第 14 位（dsh-base 之后）。

复用了它的：cooldown、step 失败集、`CONTEXT_WINDOW_EXCEEDED` 上下文窗口过滤、
`provider/*` 通配、maxSwitchesPerStep 上限、revertPolicy 冷却回默认。均读源码确认。

## 二、三个模型的真实定位（实测，不靠猜）

模型目录：`~/.dsh/.workbuddy-ai-catalog.json`（workbuddy-ai:app）、`~/.dsh/.workbuddy-catalog.json`（workbuddy:cli）。

| 需求描述 | 实际 provider/model | 上下文 | 输出上限 | 倍率 |
|---|---|---|---|---|
| WorkBuddy Step-5-Preview | `workbuddy-ai/step-5-preview` | 1,000,000 | 64,000 | free（独家限免） |
| Deepseek-V4.1-Flash **0.03 倍率** | `workbuddy-ai/deepseek-v4.1-flash-sg` | 1,000,000 | 128,000 | **x0.03** |
| cainiao（OpenAI 端点）deepseek4.1flash | `cainiao-oai/deepseek-v4.1-flash` | 1,000,000 | 256,000 | 走 `CAINIAO_API_KEY` |

**0.03 倍率的定位**：cli 源里没有 x0.03（只有 hy4-preview x0.29 / hy3-x x0.05 / space-bunny x0.08 /
deepseek-v4.1-flash x0.11）；app 源里 `deepseek-v4.1-flash-sg` 正是 `credits: x0.03`，`-sg` = Singapore。

**cainiao 无需新增配置**：本机 `llm-pi-ai` 插件的 providers 下已声明 `cainiao-oai`
（`api: openai-completions`、`baseURL: https://buddybackend.cloud/v1`、模型 `deepseek-v4.1-flash`
已是 contextWindow 1000000 / maxTokens 256000 / input text+image / reasoningEfforts off|low|medium|high）。

### 「强度默认调到最高」怎么落的

上下文窗口与输出上限由各 provider 的模型声明决定，插件按声明原样派发。这三个模型的声明都是
顶配（1M 上下文 / 128K–256K 输出），**默认已是最高强度**。

要手动调强度：改 provider 那条模型声明的 `contextWindow`/`maxTokens`（`llm-pi-ai` 的 patch）
或 `agent-default-model` 的 `reasoningEffort`——不需要动 fallback 链。

## 三、落地内容

### 安装

```
dsh plugin --profile web add dsh-llm-fallbacks@0.6.5
```

安装器自动做了三件事（都已核对）：
1. `package.json` 加依赖 `dsh-llm-fallbacks: 0.6.5`；
2. `dsh.profile.bundles` 末尾追加 `dsh-llm-fallbacks`（第 14 位，dsh-base 之后）；
3. `cordis.patch.yml` **未被改动**（插件自带 patch 只 insert 一行 `config: {}`）。

### 配置（写在 profile anchor 层 `cordis.patch.yml`，带 30 行注释说明每个决定的理由）

```yaml
- id: llm-fallbacks
  name: 'dsh-llm-fallbacks'
  config:
    triggerCodes: [AUTH, QUOTA, RATE_LIMIT, CONTEXT_WINDOW_EXCEEDED]
    rootChain:
      - workbuddy-ai/deepseek-v4.1-flash-sg     # 备用1（0.03 倍率）
      - cainiao-oai/deepseek-v4.1-flash         # 备用2（cainiao OpenAI 端点）
      - workbuddy-ai/step-5-preview             # 默认模型（链尾兜底）
    cooldownMs: 300000
    maxSwitchesPerStep: 8
    alwaysModeRetryCap: 5
    revertPolicy: cooldown-expiry
    roleAutoMatch: false
    roles: { list: [], rules: [] }
    timeSlots: []
```

**链序关键**：源码 `const first = surviving[0]`，filter 会跳过当前正在失败的那个模型。
所以 rootChain 前端是降级路径、最后一项是默认模型。默认模型失败 → 先切 0.03 倍率 → 再切 cainiao。
（第一版我曾把顺序写反成 cainiao 优先，读源码发现后已修正——链条目顺序就是优先级顺序。）

### 备份

`~/.dsh/profiles/web/` 下四个文件已备份（纯 LF，bytes I/O）：
`cordis.patch.yml.bak-20261014-model-fallback`(8444B)、`package.json.bak-20261014-model-fallback`、

## 五、已知事项

### 1. 一条启动告警（可接受，不消）

```
llm-fallbacks: rootChain must end with exactly one official model
(deepseek-official/deepseek-flash or deepseek-official/deepseek-v4-pro)
— time-slot rows and the virtual picker row stay inert until the all-day chain tail conforms
```

读源码确认影响面为零：`isAllDayConforming()` 只被 `resolveSlotState()` 调用一次，
唯一作用是「尾巴不合规就忽略 timeSlots」；我们用 `timeSlots: []`（不要分时），没有可被禁用的东西。
`isFallbackActive()` 只看 `rootChain.length > 0`，不看尾巴。

本机没有 `deepseek-official` provider，而主人指定的三个模型就是这三条——
**为消告警换默认模型 = 违背指令**，故保留告警。

### 2. peer 依赖警告

`[WARN] Issues with peer dependencies found`——缺的是纯 client UI peer
（`dsh-api-session-controller` / `dsh-client-store` / `dsh-client-ui-chat` / `dsh-client-ui-plugin-manager`）。
只影响 Web 设置卡 UI，不影响 host 边自动切换（第 2、3 层已验证）。配置写在 profile 层，不依赖 UI。
若主人要 Fallbacks 设置卡，需另行补装那几个包。

### 3. 需重启 DSH 会话生效

配置在 profile 启动时加载，当前会话已在跑，**新会话才会应用**。

### 4. 中途的自我纠错（记录，防复发）

验证中途我曾据「`agent/request-error` payload 里没有 agent」判定「开源插件契约不匹配、不可用」，
准备改走自研。继续挖 `dsh-agent/lib/index.js` 发现：

```js
function agentEvents(ctx, agent, carrier = agentCarrier(agent)) {
	const fused = (payload) => ({ ...payload, agent });   // agent 在这里注入
	waterfall(name, payload, ...rest) { return ctx.waterfall(carrier, name, fused(payload), ...rest); }
}
// agent-loop: this.dispatch = agentEvents(loopCtx, this)
```

**agent 由 dispatch 层注入，不在字面 payload 里。** 是我的 harness 漏了这层，不是插件的问题。
补上后 5/5 全绿。教训：判定「契约不匹配」前，必须把 dispatch/emit 的 enrich 层挖完。
