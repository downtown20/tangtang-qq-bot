## 51. 同一屏自相矛盾（items 说「已注入」、did 说「没进」）

**出现**：2026-10-25 第 47 轮，做「她怎么想的」账本时的视觉验收。

**现象**（真实截图，`v2:private:2524950083:1792899595…` 那一轮）：

第 5 站「记忆召回」的明细行写着「记忆块：**已注入**」，

第 4 站更离谱：结论句写「**0 块**进了 prompt」，同一站下面又列着 7 个
「注入了哪些背景」的标签。

**根因**：同一个事实（记忆块有没有进 prompt）有**两个派生点**——

- 明细行用的是 `memory_injected = memory_status in (kept, truncated) or "记忆" in labels`；
- 结论句用的是 `if/elif` 链，最后那个 `else` 只在 `memory_status` 为空时兜底，
  兜底文案写的是「没进 prompt」。

老 trace 只有 `user_bg_labels`、没有 `backgrounds.blocks`
（逐块命运是当天才落库的），于是 `memory_status` 是空串——
明细行说「已注入」（对，标签里有「记忆」），结论句说「没进」（错，但也对得上
它自己那个 `else` 分支）。

**为什么这类错比「信息少」更糟**：信息少的时候运营者知道自己不知道；
自相矛盾的时候他不知道该信哪一行，会去查一个不存在的故障。
主人要的是「取代日志的存在」——日志不会自相矛盾。

**修法**：补一个 `elif memory_injected:` 分支，判 `warn` 并明说
「看不出有没有被裁」；第 4 站同样用标签数兜底并**注明口径**。
两处都改成「一个事实、一个派生点，另一处引用它」。

**闸门**：`test_recall_phase_is_not_self_contradictory`、
`test_inject_phase_counts_labels_when_blocks_missing`
（变异对照两条：把 `elif memory_injected:` 改成 `elif False:` 必须红）。

**同一天犯的同类错（一并记在这里）**：先写了「工具调用 ≥4 次就预警」
（而 `tool_loop_limit` 默认就是 4），又写了「背景预算 ≥90% 就预警」
（而 `fit_backgrounds` 的设计就是把预算填满，实测每轮 90~103%）。
两条都是**每轮都为真**的量。判据自检要多问一句：

**修法三条**：

1. **脚本写文件用「每步即写」或「先写临时再 rename」**，不要把所有 write 堆在最后。

2. **CRLF 感知**：读用 `newline=""`，替换时把锚点的 `\n` 换成文件真实的换行符。
   本仓 `config.yaml`、`console_api.py`、`tests/test_private_interjection.py` 都是 CRLF，
   `agent/handler.py` 也是——**不能假设 LF**。
3. **收工前 grep 落盘证据**：改了 CSS 就 `Select-String max-height`，
   改了 py 就 `静态检查.py`，改了前端就 `tsc --noEmit` + **起浏览器读 computed style**。

**这一条最贵的地方不是代码**：「报已修但没修」会让主人基于假信息做决定
（他可能以为可以不用重启、不用再看）。**汇报的可信度是一次性的**。

**闸门**：这类错误测试抓不到（脚本是外部的）。只能靠纪律：
**汇报里的每一个「已」，都要能指到一次读回来的输出。**

同一个值存在 N 份副本 + 隐式优先级（谁先被遍历到谁生效）= 改哪份生效不可知。

**当时怎么踩的**（2026-10-26 主人当场报的三件事）：

主人的原话：「我的协议条目好像有点乱，具体是怎么理解和怎么回这两部分有一些乱」。
拆开来是三个症状，**看起来毫无关系**：

1. **改 `group` → 条目跑了**。`prompts/comprehension.md` 的文件头里
   `group: understand` 被改成 `reply`，它就从「怎么理解对方」挪到「怎么回」。
   证据在 `_backups/编辑_20261026_20{3534,3546,4229,4244}_*/prompts/comprehension.md`：
   20:35–20:42 七分钟内 `group` 在 understand/reply 之间来回改了**四次**——
   那不是手抖，是「想让这条换个组，但不知道还能怎么换」。

2. **改 `group_title` → 不生效**。`list_overrides()` 收集组标题用的是
   `file_titles.setdefault(g, gt)`：同组排在前面的文件先占位，后面几条改了
   **静默忽略**。memory 组有 6 条，用户改第 6 条当然没反应——
   而且他不可能知道「该改哪一条才算数」。

3. **两个组被合并**。前端 `renderPromptTree` 是按**显示标题文字**切组的
   （`if (title !== cur)`），所以两个不同 key 只要最终标题相同就被渲染成一整组；
   反过来，同一个组若被后端排到不相邻的位置又会被切成两段。

还有一个同族的静默失效：`origin` 字段。文件头里写着 `origin: 知识`，
但 `list_overrides()` 只读代码里的 `PROMPT_ORIGIN` 表——
**文件里那一行从来没有被读过**。主人报「标签 origin 更改保存后不生效」就是这个。
（判定细节还有一个坑：区分「没写 origin」和「写了空 origin」必须用
`"origin" in meta` 而不是 `meta.get("origin")` 的真值判断——后者下
「清空来源标签」永远不生效，因为空串是假值。）

**修法**：组级的东西收敛到一份文件，条目只写**引用**。

| 是什么 | 拥有者 | 住在哪 |
|---|---|---|
| 组的顺序 / 显示名 / 一句话说明 | 组 | `prompts/_groups.yaml`（唯一真相） |
| 这一条归哪个组 | 这一条 | 文件头 `group: <key>`（只做引用） |
| 这一条的说明 / 来源 | 这一条 | 文件头 `desc` / `origin` |
| 默认值 | 代码 | `PROMPT_GROUPS` / `PROMPT_META` / `PROMPT_ORIGIN`（文件没写才用） |

配套的三个细节，缺一个就会长回原样：

- **前端按 key 切组，不按文字切**。按文字切等于把后端的分组扔了。
- **未知 key 要报出来**（`group_known=False` → 界面标红「分组不存在」），
  不能静默落「未分组」——静默落下去就又是一次「改了没反应」。
- **旧字段要报出来**（`stale_group_title`）。文件头里残留的 `group_title`
  已经不再生效，界面必须说「这行没用了」，否则用户还会去改它。

改标题走**文本级替换**只动目标那一块的 `title:` 行，不做 `yaml.safe_dump`
整份重写——那份文件顶部的说明注释是它能被读懂的一半（`config.yaml` 上踩过两次，见 #7）。

**为什么这条比单个 bug 重要**：这三个症状没有一个能在单元测试里被抓出来，
因为它们全都只在「界面 + 后端 + 配置文件」三者一起看时才现形。
而它们的共同形状——**冗余存储 + 隐式优先级**——在任何一处出现都会
长出一模一样的「改了不生效 / 莫名其妙合并」。

**闸门**：`tests/test_prompt_groups.py`
（`test_group_title_in_file_header_is_ignored`、`test_unknown_group_key_is_flagged`、
`test_each_group_is_one_contiguous_block`、`test_frontend_splits_groups_by_key_not_by_title`）；
变异对照 `变异_协议分组.json`（7 变异）+ `变异_协议分组前端.json`（2 变异）。

## 55

**错误模式**：拿 `Path.relative_to()` 当「这个路径在不在目录里」的校验。

**怎么认出来**：凡是「拒绝目录外的路径」的代码，问一句——
`dir / "../secret.txt"` 会怎样？`relative_to` 是**纯字符串前缀比较，不解析 `..`**，
所以它返回 `../secret.txt`、**不抛异常**，校验静默通过。

**当时怎么踩的**（2026-10-26 第 63 轮，写图库打标时）：

新模块 `agent/image_tagger.py` 的「试打一张」要按文件名找图，写了：

```python
d = gallery_dir(cfg)
path = d / name
try:
    path.relative_to(d)        # ← 以为是越界校验
except ValueError:
    return {"ok": False, "error": "路径不在这图库里"}
```

单测 `test_describe_one_rejects_path_escape` 传入 `../secret.txt`，
**期望被拒**，实际走到了后面的逻辑——断言失败暴露出来。
这个 bug 的形状是最坏的那种：**校验写了、看着很像、实际上永远不触发**（教训 #30 同族）。

**修法**：`resolve()` 之后再比。

```python
d = gallery_dir(cfg).resolve()
path = (d / name).resolve()
try:
    path.relative_to(d)
except ValueError:
    ...
```

`resolve()` 会把 `..`、符号链接、Windows 的短名/大小写都规范化，
之后的 `relative_to` 才是真的「在不在下面」。

**为什么值得单独记一条**：这类 bug 不会被「功能验证」发现——
正常点按钮永远传合法文件名。只有**主动喂一个穿越样本**才会露出来。
所以这条的闸门不是「有个校验」，而是「有个**会红的阳性对照**」。

**闸门**：`tests/test_image_tagger.py::test_describe_one_rejects_path_escape`
（变异对照 `变异_图库打标.json` 里有一条「路径不 resolve」必须真红）。

## 56

**错误模式**：用 `<input type="number">` 配受控 `value` 做数字输入。

**怎么认出来**：用户说「这个框填不进 0.0x 的数」时，先做一件事——
**在 DevTools 里给这个 input 直接设 `value = "0."`，再读回来是什么？**

2026-10-27 实测（`input[type=number]`）：

```
"0" → "0"      "0." → ""        "0.0" → "0.0"    "0.08" → "0.08"
".5" → ".5"    "-"  → ""
```

**number 的 DOM 根本存不下小数/负数的中间态**——用户敲小数点的瞬间，
`input.value` 返回的是**空串**。

**当时怎么踩的**：设置页的数字字段写成

```tsx
<input type="number" value={String(value)}
       onChange={(e) => onCommit(coerce(type, e.target.value))} />
```

于是想输默认的 `0.08` 时，实际发生的是：

```
打「0」→ 0 ／ 打「.」→ parseFloat("0.")=0 → 小数点被重置掉 ／ 打「0」→ 0 ／ 打「8」→ 8
```

结果只能得到 `0.8` 或 `8`，永远输不进 `0.08`。

**危害比「用起来别扭」大得多**：`config.yaml` 里 `behavior.interjection_thirst`
实测是 **`0`**（默认应为 `0.08`，主人的本意是「调低频率」）。
**UI 把它静默写成了「完全关掉」**——而那正是他当天要求「精确调参」的两个字段。

**修法**：`type="text"` + `inputMode` + 本地 draft（只在「看起来是完整数字」时提交）
+ 失焦兜底提交。抽成 `SettingsFields.tsx` 导出的 `NumberField`，
`SettingsFields` / `SpecialMode`（两处）/ `Tuning` 全部复用。

**闸门**：`tests/test_desktop_number_input_contract.py`
（全仓禁止真实的 `type="number"` 属性；`NumberField` 必须保留 text/inputMode/draft/onBlur）；
变异 `变异/数字输入.json` 4/4 真红。

**为什么值得单独记一条**：它是「用户报的现象」与「真实根因」隔了两层的典型——
用户说的是「0.0 几填不进去」（输入层现象），根因一半在 DOM 规范、一半在受控渲染。
只修任何一层都不行：只加 draft 不改 type，DOM 仍把 `"0."` 变成空串；
只改 type 不加 draft，`parseFloat` 的 round-trip 照样把小数点吃掉。
