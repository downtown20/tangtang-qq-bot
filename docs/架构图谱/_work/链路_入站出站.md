## 2. WS 事件解析（onebot/ws_client.py）

### 2.1 连接与守卫
- ws_client.py:1-5 docstring：**本程序是 WS 服务端**，SnowLuma 主动连过来；API 走 HTTP。
- ws_client.py:719-724 内层 `handler(websocket)` 只接受 `127.0.0.1/::1/localhost`，否则 `close(1008)`。
- ws_client.py:725-730 置 `client_ws/_ws_connected/_ever_connected` 并 `await self._safe_callback(self.on_connected)`。
- ws_client.py:733-748 `async for raw in websocket` → `json.loads` → list 逐项 `_dispatch`，否则整体 `_dispatch`；`JSONDecodeError` 记 `[SKIP]`，其他异常记 `[ERROR]`，`ConnectionClosed` 记 warning。
- ws_client.py:749-757 `finally` 里**仅当 `client_ws is websocket`** 才清理 + `on_disconnected`（防止旧连接的 finally 清掉新连接状态）。
- ws_client.py:690-697 `ready_to_send = _qq_online and (_ws_connected or testing_mode) and not _closed`。

### 2.2 分发：去重 → 背压 → 持久 inbox → 入队
`_dispatch` ws_client.py:788-879，顺序严格：
1. :790 `_accept_events` 守卫；:793 `events_ingress` 计数。
2. :795 `_event_route(data)` → :881-901 映射：`message+group→("group:{gid}","_handle_group")`、`message+private→("private:{uid}","_handle_private")`、`notice→_handle_notice`、`request→_handle_request`、`meta_event→("gateway","_handle_meta")`，其余 None（丢弃）。
3. :800-805 **进程内 dedup**：`_event_dedup_key`（:903-913 只对 `post_type=="message"` 返回 `build_platform_event_key`）+ TTL 300s（:27-33 `EVENT_DEDUP_TTL_SECONDS=300.0`）。
4. :807-828 **三层背压**：全局 `_event_inflight >= EVENT_TOTAL_INFLIGHT_MAX(4096)` / 单 scope `queue.full()`(`EVENT_SCOPE_QUEUE_MAX=128`) / `len(_event_workers) >= EVENT_ACTIVE_SCOPE_MAX(2048)` —— 三处都 `logger.error` + metric + return。
5. :830-851 **持久 inbox 登记**：`durable_key = build_platform_event_key(message_type, data)` → `register_inbound_event`；`status != "received"` 即 return（`events_deduped_persistent`）；登记**抛异常**时只 `inbox_errors` + `logger.error`，**降级为进程内去重继续处理**。
6. :853-870 `queue` 不存在则 `asyncio.Queue(maxsize=128)` + `create_task(_event_worker)`（登记进 `_event_workers`/`_event_tasks`），然后 `put_nowait(_InboundEvent(...))`。
7. :871-879 `_event_inflight += 1`，写 dedup（带 LRU 淘汰，`EVENT_DEDUP_MAX=20_000`）。

### 2.3 Worker：claim → 回调 → complete/fail
`_event_worker` ws_client.py:921-1039：
- :926-932 `wait_for(queue.get(), timeout=60s)`；超时且 `queue.empty()` 则退出（worker 回收）。
- :935 `async with self._event_concurrency`（`EVENT_HANDLER_CONCURRENCY=8`，全局信号量）。
- :938-992 持久 inbox **claim**：`claim_and_mark_inbound_event_executing`（或 `claim_inbound_event`+`mark_inbound_event_executing`）；claim 失败 → `continue`（已被其它 worker 领取或完成）。
- :993-999 记录 lag → `handler = getattr(self, envelope.handler_name)` → `with correlation_scope(envelope.event_id): handled = await handler(envelope.data)`。
- :1000-1001 `if handled is False: raise RuntimeError("event callback failed")`。
- :1002-1010 `complete_inbound_event`，未完成 → raise。
- :1013-1030 except：`fail_inbound_event` + `callback_errors` + `logger.exception`。
- :1031-1039 finally：`queue.task_done()`、`_event_inflight -= 1`、回收 worker/queue。

### 2.4 归一化
- `_handle_group` ws_client.py:1043-1080：`_resolve_forwards` → 结构化 `mentions`（seg.type=="at"）→ msg dict（`type/group_id/user_id/nickname/card/title/role/mentions/message=_extract_text(raw)/raw_message/message_id/time/is_at_bot=_check_at_bot`）→ :1076 `msg["_inbound_event"] = normalize_inbound_event("group", msg)` → :1078-1080 `return await self._safe_callback(self.on_group_message, msg)`。

- `_extract_text` ws_client.py:1919-2004：`text/image/reply/forward/file/at/video/record` 逐段映射；**reply 段无原文时写 `[回复了上面的消息]`**（:1961），有原文写 `[引用内容：…]`（:1959，截断 120 字）；**at 段 name 优先、qq 兜底写 `@QQ{qq}`**（:1987-1992）。

## 7. 发现的问题

> 分级：Critical = 必须修；Important = 应该修；Minor = 可选。
> 每条：位置 → 证据 → 根因 → 最小修复建议。

### 7.1 [Important] 工具执行器内同步调 LLM：15s 阻塞 + 静默降级（教训 #27 的**未修变体**）
- **位置**：agent/handler.py:7610-7614（`send_message` 工具内 `execute_send_action(llm_call=self._call_llm_light, ...)`）、agent/handler.py:5547-5583
- **证据**：`_execute_tool` 由工具循环调用（handler.py:6296-6305），而工具循环运行在 `_call_llm` 持锁区间内（handler.py:5676 `await self._llm_lock.acquire()`，:5703-5707 才 release）。`_call_llm_light` 在 handler.py:5578 用 `await asyncio.wait_for(self._llm_lock.acquire(), timeout=15)` —— **没有** `_call_llm` 那样的重入检查（对比 handler.py:5670-5678 的 `_llm_owner_task` 判定）。同一 Task 再 acquire 非重入 Lock 必等到 15s 超时 → :5579-5583 `extract_busy_skipped`/`light_lock_timeout` + 返回 `""` → send_actions.py:119 `actual = await _natural_rewrite(...) or requested` **静默回退成原文**。
- **根因**：`_call_llm_light` 缺少与 `_call_llm` 同款的重入门；调用方（工具执行器）处于持锁上下文。
- **最小修复建议**：在 `_call_llm_light` 开头加与 handler.py:5670-5674 相同判据（`_llm_owner_task is current_task` → 跳过 acquire，直接走 `_attempt()`，finally 不 release）；或把 natural 改写改为 fire-and-forget（教训 #27 的标准解法）。修后需补"工具内 natural 模式"的回归测试。

### 7.2 [Important] `@` 防抖的"取消前一条"实际无效 → 多人同时 @ 触发多次 LLM 回合
- **位置**：agent/message_batcher.py:78-85, 97
- **证据**：:78-80 `prev = self._at_timers.pop(group_id, None); prev.cancel()`；:84-85 `future = loop.create_future(); self._at_timers[group_id] = future`——存的是 **Future**，而真正在跑的计时器是 :97 `asyncio.create_task(_wait_then_process())`，**该 Task 未被任何字段持有**。`prev.cancel()` 取消的是 Future（且 :85 注释 `# type: ignore` 正说明类型不符：字段声明为 `dict[str, asyncio.Task]`，message_batcher.py:49）。docstring :72-73 声称"多人同时@糖糖 → 取消前一次等待，只处理最后一条"，实际每条 @ 都会在 1.5s 后经 :93-94 重入 `handle_group_message`。
- **根因**：把"取消令牌"（Future）与"执行体"（Task）混为一谈；`_cancel_at_timer`（:102-106）同样对 Future 调 cancel。
- **最小修复建议**：:85 改存 `asyncio.create_task(_wait_then_process())`，并把 :97 的 create_task 结果赋给该字段（或在 :84 删掉 Future，直接 create_task + 存 Task）。补测试：连续两次 `debounce_at` 后，只应有一次 `handle_group_message`。

### 7.3 [Important] `sing_ordinal` 只有读、没有写 → sing 工具分支的 ordinal 恒为 0
- **位置**：agent/handler.py:4264、:5330（读）vs :7436-7445（写的是 `sing_actions[].ordinal`，**不是 `sing_ordinal`**）
- **证据**：全仓 grep `sing_ordinal` 仅命中 handler.py:4264 与 :5330 两处**读取**；`sing` 工具写入的是 `turn_actions["sing"]`、`turn_actions["sing_version"]`、`turn_actions.setdefault("sing_actions", []).append({..., "ordinal": ordinal})`（:7438-7444）。对比 `cg` 分支 :7797-7799 显式写 `turn_actions["cg_ordinal"] = ordinal`——同族字段一边写一边没写。
- **根因**：字段名分叉（`sing_actions[].ordinal` vs `sing_ordinal`），工具分支漏写回合级 ordinal。
- **最小修复建议**：在 :7437-7444 补 `turn_actions["sing_ordinal"] = ordinal`（保持与 cg 同构），或把 :4264/:5330 改为读 `sing_actions[-1]["ordinal"]`。修后核对 `_send_singing_actions(ordinal_start=...)` 的 child 序号与 `action_intents` 一致。

### 7.4 [Important] 自检拦截的兜底文案**不归账** → 用户收到消息但 chat_log 无记录
- **位置**：agent/handler.py:13380-13405（拦截分支只设 `_last_checked_send_delivered` / `_last_checked_send_payload`，**不设 `_last_checked_send_parts`**）、:13561-13563、:4312-4317
- **证据**：`_last_checked_send_parts` 在 :13353 被清空后，拦截分支（:13380-13405）直接 `return False`，从未赋值 → `_account_confirmed_prefix` 里 `parts = []`（:13561）且 `joined_reply = reply if ok else ""` = `""`（因为 `ok=False`，:4315）→ :13562 `if not joined_reply and not parts: return 0` **零归账**。而 :13402-13404 已明确记录"兜底文案**确实送达**"这一事实。自治路径已消费该事实（handler_autonomy.py:705、:1445），但主对话路径的账本/历史仍缺这条。

### 7.5 [Important] `testing_mode` 在群聊与私聊**不对称**，且群聊丢弃点晚于全部副效应

## 8. 待验证假设（无充分证据，**不得**当结论）

1. **`raw_message` 的 `[CQ:at]` 形态**：handler.py:3138 用精确子串 `f"[CQ:at,qq={self.bot_qq}]"` 判 @，若 SnowLuma 输出的 at 段带附加参数（`[CQ:at,qq=…,name=…]`），该判定失配 → @ 消息会走批处理合并而非 1.5s 防抖；而结构化 `is_at_bot`（ws_client.py:2006-2011）仍为 True，所以最终仍会回复，只是延迟/合并语义变化。**需样本**：日志中 grep `[CQ:at` 命中 0（日志不含 raw_message），需现场抓一条真实事件或查 `chat_log.raw_message` 列。
