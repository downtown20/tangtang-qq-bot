# 第 11 轮：一个从来没人写入的字段（2026-10-25）

> 起点不是 bug 报告，是主人的一句价值目标：「达到甚至胜过人的记忆能力」。
> 我把它拆成六条判据（[记忆能力判据](../开发规划/记忆能力判据_20261025.md)），
> 然后去查第一条判据（J1：该想起来的时候想得起来）的**测量基础**——
> 发现那个基础是一个**从上线起就没被写入过的字段**。

---

## 1. 立项：判据没有测量基础

J1 想测的是「她该想起来的时候想不想得起来」。要测它，系统必须先能回答一个更朴素的问题：

> **这条记忆，被想起过吗？**

`memories` 表有 `last_recalled`（TEXT）和 `recall_count`（INTEGER）两列。
它们正是 Bjork 双强度模型里的**提取强度**（retrieval strength）——存储强度只增不减，
提取强度随「想不想得起来」变化。schema 设计得完全正确。

然后查库：

```
promise  523 条 | 从未被召回 523 条 (100%) | recall_count 全 0
said    1038 条 | 从未被召回 1038 条 (100%)
```

**1561 条，一条都没有。** 不是「很少」，是**零**。

---

## 2. 取证：三件静默失效

追下去发现链路是**完整的，唯独没人调**：

```python
store.reinforce_memory_by_id()   # store.py:11793，有完整 SQL
memory.reinforce()               # memory.py:624，有 30 分钟冷却 + summarized 跳过
grep '\.reinforce('  →  只有 tests/test_read_side_quality.py:48,55
```

**但真相不是「从未接」，是「接了之后在重构中掉了」。**

查 `last_recalled` 的**日期分布**：

```
2026-08-17  251 条   2026-08-24  223 条   2026-08-16  185 条   2026-08-15  158 条
2026-09     几乎为 0
2026-10-25  11:18 之前：0（当天新写的除外）
```

这条链路**曾经是通的**。某次重构把调用点弄丢了，而**没有任何测试能发现**——
`tests/test_read_side_quality.py` 自己调 `reinforce`，所以测试一路是绿的。
（`origin='summarized'` 也有 322 条有值，而现在的 `reinforce` 明确跳过 summarized
——这正是「历史上有过别的实现」的痕迹。）

后果三件，全是静默的：

### ① 休眠降权从上线起就是死的

`memory.py` 的 Phase 2 里有：

```python
last_rec = r.get("last_recalled", "")
if last_rec:                      # ← 永远为空，进不去
    ...
    if dormant_days > 60:
        score *= 0.5              # 「两个月没被想起就大幅降权」
```

**这段代码从来没有执行过一次。** 而第 8 轮曾把它当成一个真实现象去观察
（「`mem#17589` 因 60 天未召回被 ×0.5，排到候选池第 21 位」）——
那个观察建立在错误前提上，已在交接单里标为**作废**。

### ② `cleanup_stale_memories` 一直把所有记忆当「从未用过」

它的删除条件是（`store.py:11190` 起）：`importance <= 2` 且 `recall_count = 0` 且 `>90 天`。
而 `recall_count` 恒为 0 → **每一批清理都在用「这个字段恒为 0」做判断**。

它确实在跑：`main.py:399`（启动时）+ `handler_autonomy.py:422/2410`（定时）。
目前没出事只是因为自忆 `importance >= 4`，被第一道条件挡住了。

### ③ 健康检查在监控一个恒为 0 的量

`health_check.py:715-739`：

```python
"""reinforce冷却是否生效——最高recall_count是否停止增长"""
...
return {"status": "ok", "message": f"recall_count 最高值稳定 ({max_rc})"}
```

`max_rc` 永远是 0，所以它**永远报 ok**。
**一个从不变化的指标，它的「正常」不携带任何信息。**

## 3. 去伪存真：不是「加一行调用」那么简单

最直觉的修法是「在 `recall()` 里加一句 `self.reinforce(...)`」。做完发现有三处必须**不**接：

| `recall()` 的内部调用点 | 用途 | 能否强化 |
|---|---|---|
| `recall_uncertain` | 模糊档（无原话佐证） | **不能**——强化会 `importance+1`，让「她不确定的事」一路爬到可信档，等于用**被检索次数伪造证据等级** |
| `get_stats` | 统计 | **不能**——查一次统计不算「想起来」 |
| `search_relation_triples` | 关系检索，**`limit=None` 取全量** | **不能**——否则该主体名下**所有**记忆一次性 `importance+1` |
| `recall_formatted` / `search_fact_clusters` | 生成型上下文 / 对话工具 | 可以 |
| 直接调用（handler 各处） | 对话主路径 | 可以 |

所以 `recall()` 加了 `reinforce_after: bool = True` 开关，上面三个显式关掉。

**接线位置也有讲究**：接在 `recall()`（唯一公共入口）而不是 `_get_self_memory_context`
（只覆盖自忆）。第 9 轮的「假取回路径」就是**只看了上层**——这次一开始就接在底层。

### 还有一条副作用是「设计意图」

`store.reinforce_memory_by_id()` 不只记录，它还 `importance = MIN(10, importance + 1)`。
所以回写一开：**被用起来的记忆会缓慢变重要**（30 分钟冷却 + 上限 10 兜着）。
这是设计意图，不是 bug——要在 docstring 里写明，否则下一个人会把它当漂移修掉。

---

## 4. 修法

`agent/memory.py`：

1. `recall()` 增加 `reinforce_after: bool = True`
2. 返回前调用 `self.reinforce(qq_id, entries)`，包在 `try/except` 里——**fail-open**
   （写库失败绝不能让召回失败：否则「她想不起来」会被放大成「她这一轮没说话」）
3. `recall_uncertain` / `get_stats` / `search_relation_triples` 显式传 `False`
4. docstring 写清三件静默失效 + 两个必须不写的路径 + 「排序漂移是设计意图」

**没有改 `reinforce` 的内部实现**（保留 30 分钟冷却 + `summarized` 跳过）：
最小改动优先，先让它跑起来看数据；性能若成问题再批量优化。

### 4.5 第一版踩的坑：默认开启 → 写放大（**这一段比修复本身更值钱**）

第一版把 `reinforce_after` 默认设成 **True**，理由写得很自信：
「接在 `recall()`——唯一公共入口，接一次覆盖全部调用点」。

重启复验：**两分钟内 96 条**记忆被 `importance + 1`，`recall_count` 甚至涨到 15。

原因：`recall()` 不只服务对话——**启动时的记忆整理、反思、关系合成都在批量调它**。
而「被后台扫过」**不等于**「她想起了」。把两者混起来，排序就被后台任务污染了。

**这是第 9 轮那个错的同族：**

| | 核了什么 | 没核什么 |
|---|---|---|
| 第 9 轮 | 「工具存在」 | 「工具**作用域**」 |
| 第 11 轮 | 「接在底层能覆盖**全部**调用点」 | 「全部里**哪些不该**覆盖」 |

修法：**默认改 False（fail-closed）**，只有 5 处对话路径显式 opt-in ——
群聊记忆块 / 私聊记忆块 / `search_memories` 工具 / 自忆的两个分支（BGE + 降级）。
方向定死：**漏标一个调用点 → 不强化（安全）**；而不是 → 过度强化（污染排序）。

⚠ **已写入的 96 条无法回滚**：`reinforce_memory_by_id` 刻意不写 `memory_revisions`
（见其 docstring：否则流水会按「召回次数 × 记忆数」爆炸）。它们的 `importance`
偏高 1~2，影响有限（`recall()` 里相关性权重占 0.90，importance 只做有界调权）。
**不回滚，记录在此，供后续评估。**

## 6. 这一轮真正的意义

它不是一个「补一行调用」的修复。它把**整个记忆能力判据的地基**接上了：

- **J1（该想起来的时候想得起来）** 从此可测——因为知道哪条被想起过
- **J2（保持率）** 从此可测——因为知道「上次想起」是什么时候
- 休眠降权、陈旧清理**第一次用上了正确的判据**
- 健康检查从「监控常量」变成**真检查**

而这一切的前提，是主人 2026-10-25 那条价值决策：**不做自然遗忘**。
因为不做遗忘，就只剩一条路来判断「哪条记忆有价值」——**看它有没有真的被用上**。
这条链路就是那个「用上」的记录。

## 7. 教训 #41

> **监控一个恒为常量的量，等于没有监控**
>
> `health_check` 里那条「recall_count 最高值是否停止增长」，永远报 ok——
> 因为 `recall_count` 从来没被写入过。**一个从不变化的指标，它的「正常」不携带
> 任何信息。** 同类还有：`last_recalled` 全空 → 休眠降权分支从上线起就是死的；
> `cleanup_stale_memories` 判「从未回忆」用的也是这个恒为 0 的列。
>
> 这是 #12（写了 infra 没接业务）/ #37（假绿）的合流形态，但更隐蔽：
> **代码在跑、日志有输出、健康检查报 ok，三样都正常——唯一不正常的是那个数字
> 从来没变过。**
>
> 两条纪律：
>
> ① **加监控前先问「这个量会不会变」**——上线后观察一天，数字纹丝不动就是没接线。
>    更硬的做法：监控项附带「最近一次变化的时间」，长期不变本身就是告警。
> ② **设计字段时要同时写清「谁写它」**。只有读、没有写的字段等于**常量**，
>    而常量会让所有依赖它的分支变成不可达代码——**代码审查时看不出来，
>    因为 `if x:` 语法完全合法**。
