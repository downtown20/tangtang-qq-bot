# 第 12 轮诊断：`open_loops` 0 行 —— 接在**死方法**上的线，和一把**永远报 0** 的尺子

- 日期：2026-10-25
- 上一轮：[第 11 轮_提取强度从未写入](第11轮_提取强度从未写入_20261025.md)
- 本轮入口：执行计划 §2 挂着「`open_loops` 为什么 0 行」——它是判据 **J6（主动提起）** 的载体
- 一句话结论：**L2（提取→落库）把 open_loop 写进了一个生产零调用的死方法；而唯一能证明"它没在工作"的验收工具，从诞生起每次都在说"没有"。**

### 2.2 实测一：提示词本身能不能产出 `open_loop`？

自造 4 条必提样本（明天面试 / 下月体检 / 答应写文章 / 和好还没开口）+ 2 条对照组

|---|---|
| 旧验收工具的调用（不关思考） | `{"outcome":"invalid_json","raw_length":0}` —— **拿到空回复** |
| 生产口径（`THINKING_OFF`） | `{"outcome":"success_with_items","raw":5}`；**4/4 必提命中**，对照组一个判成 event、一个被丢弃（正确） |

**提示词是有效的。** 所以①不成立。

### 2.3 实测二：真实语料能不能产出？

用带将来时词汇的真实历史消息抽样（`--future`），改成与生产同预算后：
**5 批全部有效、29 条记忆、6 条未闭合事件**（raw=8/8/7/9/0 五批）。

**结论：写侧能力不是问题，③也不成立。** 那答案只能是②——判出来了，没落库。

### 2.4 实测三：落库路径是死的（本轮真根因）

`grep '_persist_extracted_items'`（排除 tests/tools）：

```
agent/handler.py:12998        def _persist_extracted_items(...)   ← 唯一的调用点在它自己方法体里
tests/test_integration_contract.py:352  ('agent/handler.py','_persist_extracted_items'):
                              'T 类（仅测试引用）——测试仍在调；生产零调用'
```

生产提取走的是：

```
handler._process_extraction_batch
  → store.mark_extraction_job_ready(job, all_items, aggregate)     # 只暂存
  → store.complete_extraction_job(job)                             # 单事务落库
      → for item in items: self._apply_extraction_item(conn, ...)  ← 生产真正的写入口
```

而 `_apply_extraction_item` 的 `type_map` 里**没有 open_loop**：

```python
type_map = {"identity": "fact", "preference": "like", "habit": "habit",
            "event": "event", "relationship": "fact", "note": "said"}
key = type_map.get(str(item.get("type") or "note"), "fact")   # ← open_loop 落到默认 "fact"
```

**于是 L2 的 open_loop 落库写在一个死方法里，从未执行过。**
11145 个任务、0 行不是"数据里没有"，是**代码没跑**。

> 这条是队友（审计员）在并行审计里发现的，我用 `grep` + 读
> `complete_extraction_job`/`_apply_extraction_item` 复核确认。复核的价值在于：
> 它同时解释了「为什么 memories 一直在长（event 6005 条）而 open_loops 一直是 0」——
> 同一个方法写记忆成功、写悬事那步不在方法里。

### 2.5 为什么闸门没拦住：它只查"符号有没有调用点"

`tests/test_integration_contract.py:315-316` 当时写着：

```
# ✅ 2026-10-25：`add_open_loop` 已由 L2 接上（handler._persist_extracted_items
#    处理 type="open_loop" 的提取条目），条目已按棘轮删除。
```

闸门的判据是「这个符号在生产有没有调用点」——`add_open_loop` 确实有调用点，
于是它判"已接"。**它不回答「那个调用点所在的方法可不可达」**，
而后者恰恰是这次的真相。同一文件 352 行还自己登记着 `_persist_extracted_items`
「生产零调用」——**两条登记自相矛盾，却都被闸门判为通过。**

## 三、我判错过一次（写下来防复发）

看到"真实语料能产出、生产 13 批只有个位数命中"时，我先得出过：
**「0 行是低频 × 小样本的正常结果，不能判写侧有罪」**——这个解释在当时的数据上

它是错的。错在**把"证据支持"当成了"唯一解释"**：三组证据里两组为真

真正推翻它的是另一条独立证据：`_apply_extraction_item` 的 `type_map` 里没有
open_loop——一条读代码就能拿到的硬事实，而我先做的是"算概率"。

> 教训对应 #18：修复假设先取证（查 DB、查日志、查注入源），**别用统计推断替代

## 四、修复 A：把 L2 接在生产真正走的路上

只动 `agent/store.py`，**一个事务**、**一处去重实现**：

| 改动 | 说明 |
|---|---|
| 抽出 `_upsert_open_loop_conn(conn, ...)` | 原 `add_open_loop` 自己开连接、自己 commit；提取落库是 `BEGIN IMMEDIATE` 单事务，**不能**在同一库再开第二个写者。抽成 conn 版，`add_open_loop` 变成它的薄包装——去重规则只有一份（教训 #38：同一个量不许两个换算点） |
| 新增 `_record_open_loop_if_needed(conn, qq_id, item, memory_id, source_group)` | 按 `type=open_loop` 分派，在**同一事务**里补 `open_loops` 行，`source_memory_id` 指回刚写的记忆 |
| `type_map` 加 `"open_loop": "event"` | 记忆侧要回答"她什么时候说过这话"，落成 event；此前落到默认 `fact`，等于把悬事记成事实 |
| 两处 `return 1` 前都调用助手（新建记忆 / 同值合并） | 合并路径也要跟上，否则同一件事再次提到时 `expected_at` 不更新、`source_memory_id` 停在旧行 |
| `handler._persist_extracted_items` docstring 加警示 | 明写"生产零调用，不要再往这里加落库行为" |

代价：**0 行新增 SQL 风险面**——表结构没动、索引没动、状态机没动，只是把
"该在事务里写的那一行"补上。

## 九、教训（入 CLAUDE.md #42）

**「线接在死方法上，尺子量不出东西——两者都长得像"一切正常"」**

这次的三个环节各错一处，方向完全一致：

| 环节 | 错法 | 表面现象 |
|---|---|---|
| 接线 | open_loop 落库写进生产零调用的 `_persist_extracted_items` | 闸门查到"符号有调用点" → 判已接 |
| 映射 | 活路径 `type_map` 没有 open_loop → 落到默认 `fact` | 记忆照写、表照空，没有任何报错 |
| 验收 | 工具三处口径错（思考/失败归类/预算） | 每次输出"合计 0 条"、退出码 0 |

**三处叠加的净效果是：一条从未运行过的链，配上一把从不报警的尺子，
在文档里被记为「✅ 已接」。** 而 `open_loops` 空表是最不容易被质疑的状态——
空表没有错误、没有异常日志、没有失败计数。

配套纪律：

1. **接线要问"这条路生产走不走"**：不只 grep 调用点，还要看那个调用点所在的
   方法有没有生产调用方（可达性，而不是存在性）。本项目零调用闸门管的是前者。
2. **一个写库语义只许有一个实现**：事务内版本与自开事务版本必须共用同一段去重
   逻辑，否则迟早漂移（#38 同族）。
3. **验收工具必须与生产共用请求口径**（思考开关、预算、模型）；能抽纯函数就抽，
   闸门断言**结构**（AST），不要断言"注释里写了"。
4. **失败要有自己的出口**：`protocol_ok=False` 不许走"没有"的分支；
   「0 条」只有在"每批都成功"时才是结论。
5. **当某张表是空的，先问"谁读它"，再问"谁写它"，最后才问"数据是不是本来就没有"**。
   前三问的顺序错了，就会用统计解释代替代码取证（§三 我就这么错过一次）。
