## 二、修法（按方案文档 §2.3–§2.5，三层）

### L3 注入（`agent/protocols.py` + `agent/handler.py`）

```
<背景·悬着的事>
- #1 明天要去医院复查（原定 2026-10-26，还有 1 天）——还没问过
- #2 下周三要交报告（原定 2026-11-01，还有 7 天）——已问过 1 次
</背景·悬着的事>
```

| 决定                                   | 理由（每条都对应一次踩过的坑）                                                                           |
| ------------------------------------ | ----------------------------------------------------------------------------------------- |
| **只提供事实，不判断「该不该问」**                  | 反模式 #9/#10：系统不替 LLM 做决策。说不说、怎么说是她的事                                                       |
| **行内带 `#id`**                        | 不带 id，`resolve_open_loop(loop_id=…)` 无从下手，同一件事会永远浮上来                                      |
| **带「问过几次 / 原定何时 / 已过几天」**            | 不告诉她，她会重复追问；到期/超期的事实是她判断「该开口了吗」的唯一依据                                                      |
| **渲染不回写 `asked_count`**              | 「被注入」≠「她问了」。第 11 轮写放大（启动两分钟 96 条被 +1）就是「底层被调用 ≠ 她想起来了」；把「看见」记成「问过」会让上限 2 提前用光，而且**她根本没问** |
| **失败 fail-open**                     | 查库异常只 warn、返回空串，绝不影响回复                                                                    |
| **优先级 P5**                           | 它**没有取回工具**（`resolve_open_loop` 是收尾不是取回），取不回来就要优先保留；与窗口同级、排在关系档案之后（档案错了会答错人，悬事丢了她只是少问一句）  |
| **不登记 `_BG_RECOVERY_TOOLS`**         | 登记一条「取不回材料」的路径正是第 9 轮的错（#39）                                                              |
| **第一版只开私聊**                          | 群里把甲的悬事说给全群，错配影响面是全场（方案文档 §三）                                                             |
| **开关 `memory.open_loops_injection`** | 关掉即回到原状；数据侧 `DROP TABLE open_loops` 完全回滚                                                  |

### L4 收尾工具（`resolve_open_loop`）

- 只给私聊（群里给了工具却看不到材料＝发明能力）
- 参数 `loop_id` / `outcome`（asked / resolved / dropped）/ `note`
- **三条拒绝全在 store 侧**（不存在 / 跨人 / 终态不可逆）——「谁能收尾」的判断只留一处
- 工具描述写明：从对话里知道结果才用 resolved，不确定不要猜着收尾

### L5 过期清理

启动清理与每日汇总两处都调 `expire_open_loops(days_overdue=30, max_asked=2)`：  
只清「到期 30 天且已问过 2 次仍没结果」的，**没问过的不许替她放弃**。

## 三、踩到的一个新坑（写下来防复发）

`resolve_open_loop` 的执行分支第一次放在了 **`if not query: return "(empty query)"` 之后**——  
而这个工具不收 `query`，于是 LLM 每次调用都拿到 `(empty query)`，**工具静默失效**。

- 发现方式：单测只测了「schema 里有这个工具」和「直接调 `resolve_open_loop` 分支」，  
  但真实调用顺序会先撞上通用的 query 守卫；
- 教训：**新工具的分支位置要放到通用 guard 之前**，并且执行器分支必须有  
  「真跑一次 `_execute_tool(name, args)`」的测试（只测分支内部逻辑测不出位置错）。

## 五、端到端实证的新问题（第 14 轮第一件事）

**同一件真实事件被拆成两行**（上一轮预测、本轮实证）：

- 她为了收尾同一件事，得调两次工具、写两条 `resolution`；
- 如果两行 `expected_at` 不同，注入时会出现两条看起来不同的悬事 → **可能问两遍**。

去重键现在是「归一化 topic 完全相等」，而 LLM 对同一件事的两次表述字面不同  
（`明天要去医院复查` / `明天早上八点起来抢医院复查的号（还没预约）`）→ 不合并。

第 14 轮先定口径（二选一，要取证再定）：

1. **提取侧**：prompt 加一句「同一件事只输出一条 open_loop，细节并进 value」；
2. **注入侧**：按 `expected_at` + 高相似度合并展示（需要一套可解释的相似度判据）。

**不要**在 store 里加模糊匹配——两张擦边的表搅在一起，且不可解释。

## 七、教训（入 CLAUDE.md #43）

**「只提供事实」不等于「提供一堆没有句柄的噪音」**

本轮把「系统只提供事实」这条原则落地时，发现它需要三条配套硬约束，否则事实本身  
没用、甚至有害：

1. **事实必须可操作**：行内带 `#id`，否则她无法调用收尾工具，同一件事永远浮上来；
2. **事实必须带历史**：告诉她已经问过几次、原定何时、已过几天——否则她重复追问；
3. **「看见」不能自动记账**：状态改写只能由她（LLM）经工具触发。系统代记等于替她  
   编造了一次「问过」，这正是第 11 轮写放大（底层被调用 → 96 条 importance+1）的同族错误。

另一条工程教训：**新工具的执行分支要放在通用守卫之前**。`resolve_open_loop` 第一次  
被放到 `if not query: return "(empty query)"` 之后，每次真实调用都静默拿到  
`(empty query)`——而单测（只测分支逻辑、只测 schema 存在）全绿。  
判据：执行器必须有一条「真跑一次 `_execute_tool(name, args)`」的测试，  
并且**阳性对照要跑通成功路径**，不能只测拒绝路径。
