## 二、取证：先量频率，再定修法（这一步改变了结论）

### 2.1 那两行是同一批提取产出的

```
job 73054（2026-10-25 12:09:59, qq=2524950083）的 result_json：
[{type:event,     value:"今天有点累，事情很多"}
 {type:open_loop, value:"明天要去医院复查",                     expected_at:"2026-10-26", evidence:[301037]}
 {type:open_loop, value:"明天早上八点起来抢医院复查的号（还没预约）", expected_at:"2026-10-26", evidence:[301040]}]
```

同一批、两条都判成 open_loop、`expected_at` 相同、`value` 高度重叠——**拆分实证**。

### 2.2 但全量扫一遍，问题不在拆分

零 LLM 成本地扫全部 `extraction_jobs.result_json`（11178 个任务，其中 1791 个非空）：

| 指标 | 实测 |
|---|---|
| 产出过 open_loop 的批次 | **1 个**（就是上面那个） |
| 非空批次总数 | 1791 |
| 含将来时词的条目总数 | 158 |
| 这 158 条的 type 分布 | `event` **116**、`note` 21、`habit` 9、`identity` 7、`preference` 3、**`open_loop` 2** |

被错判成 event 的原句（历史 result_json 原文）：

| 原话 | 被判成 |
|---|---|
| 明天去学校拿录取通知书 | `event` |
| 明天彻底初中毕业 | `event` |
| 明天要回乡下去给爷爷烧钱 | `identity` |
| 明天10点有事，需要人叫醒两个小时 | `event` |

**结论**：`open_loop` 在「最可能产出它的 158 条」里召回率 = **2/158 ≈ 1.3%**。
这不是「真实数据里没有悬事」，是**分类根本没被选中**。

### 2.3 抽样复核：改之前 47 条真实消息 0 命中

`python tools/提取抽样.py --future --users 3 --limit 20` → 3 批全成功、19 条记忆、**0 条 open_loop**。
人工标注这 47 条消息，至少有 3 件明确的未结事：

- 「咱们下下周也运动会」
- 「明天月考了喵」/「明天还要考」← 同一件事的两次表述
- 「还剩两天假 明天还有 亲人做客 作业一笔未动」

**提取器 0 命中**。而且 #2 那两条正是「同一件事两次表述」——一旦命中就会立刻变成两行，
与医院复查同形态。**拆行问题的前提是「先要产出」，而它根本没产出。**

> 方法上的教训：计划里写的是「先查同 expected_at 的行数，再跑抽样看拆分频率」。
> 如果只做这一步，会得到「现有 2 行 = 1 组，太少了，没法判断」——然后误以为问题低频。
> 真正给出结论的是**扫全量 result_json 的分类分布**（零成本、大样本）。

## 三、真因：prompt 里 event 的定义没写「必须已经发生」

`agent/memory.py` 原 prompt（改前）：

```
- event: 生活事件、经历（去过哪里、做了什么、发生了什么）
- open_loop: 一件还没结的事——对方说将来要做的、承诺的、担心的、有截止日的事。
  ✅ 算：「明天要去面试」「下个月体检」…
  🚫 不算：已经完成的事…
  🚫 不算：糖糖自己的承诺…
  🚫 不算：无时间指向的空泛愿望…
```

| 缺陷 | 后果 |
|---|---|
| `event` 定义举的全是过去时例子（去过/做了什么/发生了什么），但**没有明说「还没发生的不要写成 event」** | 见到「明天去学校拿录取通知书」，最贴近的类型仍是「生活事件」→ event |
| `open_loop` 排在类型列表第 8 位，且带 3 条 🚫 排除 | 出场次序 + 负例密度都把它压到最低倾向 |
| 只有一条 JSON 示例（在输出格式后面单列） | 教科书句能中、真实句不中——**尺子只在教科书上有效** |

---

## 四、修法（只动 prompt 三处，一行代码逻辑都不加）

`agent/memory.py` 的提取 system prompt：

1. **event 定义限定为已发生**：
   `- event: **已经发生**的生活事件、经历（…）。🚫 还没发生的事（明天/下周/周末要做的）不要写成 event——用下面的 open_loop`
2. **open_loop 加一条唯一判据 + 4 条真实数据正例**：
   `⚠ **判据只有一个：这件事发生了没有？** 还没发生 → open_loop；已经发生 → event。`
   正例直接抄历史被错判的原句（`明天去学校拿录取通知书` / `明天要去医院复查` /
   `明天10点有事，需要人叫醒` / `国庆假期作业还没动笔`）
3. **同一件事只输出一条**：`几句话说的是同一件事时…合并成一条 open_loop，细节并进 value；拆成两条会让她对同一件事问两遍、收两次尾。`

**为什么只用 prompt、不在代码里加关键词改判**：把「明天/还没」这类词做成后置改判，
等于用正则替 LLM 做判断（反模式 #9/#10），而且「明天」常出现在已发生叙述里
（「昨天说好明天去，已经去了」）。分类是语义判断，只能归 LLM。

## 六、踩到的坑（写下来防复发）

### 6.1 第一版两个变异是「假绿」

第一版测试写 `assert "还没发生" in system_prompt`、`assert "已经发生" in system_prompt`。
变异（删掉判据句 / 删掉 event 定义里的「已经发生」）**跑出来是 GREEN**——因为 prompt
别处还有这两个词（`🚫 还没发生的事…`、`；已经发生 → event`）。

修法：断言必须**唯一到判定本身**——
- 判据句断言 `"还没发生 → open_loop"`（原文唯一）
- event 定义用 `_event_definition_line()` 取出 `- event:` 那一行再断言含「已经发生」

这是教训 #37「假绿比假红危险」的**第 N 次复发**，也是本轮最该记住的一条：
**断言「某个词在长文本里出现过」几乎必然假绿。**

### 6.2 LLM 输出不稳定，验收必须多跑

同一批 14 条消息，DESC 顺序跑出 12 条、ASC 顺序跑出 0 条（`raw_length: 2` = `[]`）。
所以「改完跑一次得到 11 条」不能当作稳定结论——**本轮的验收带了 5 批 + cases 双口径**。

### 6.3 `expected_at` 会算错一天

抽样里「明天10点有事」→ `expected_at=2026-10-25`（当天），应为 `2026-10-26`。
注入块会显示「就是今天」。**这是独立缺陷，没在本轮修**（属日期推算，与分类无关），
记入待办。

### 6.4 内容变多把旧的「固定窗口」闸门挤红了

全量 pytest 第一次跑出 **1 failed**：

```
tests/test_open_loop_extraction.py::test_prompt_has_exclusion_rules_for_open_loop
  AssertionError: 没写「已完成的不算」
```

它（第 12 轮写的）用 `system_prompt.find("open_loop")` 定位，然后取 `+700 字符` 窗口。
本轮给这一段加了判据句和 4 条真实正例（约 +300 字符），把「🚫 不算：已经完成的事」
挤出了窗口 → **红，而 prompt 的行为其实是变好的**。

修法：改成按 `- open_loop:` 段定位（找到段首、截到「认知类型」为止），不再用固定字符数。
**并且改了定位方式就重新证明它还能红**——另建 `变异_open_loop提取判据_旧闸门.json`
（3 个变异：删「已完成不算」/ 删「糖糖自己的承诺不算」/ 删「空泛愿望不算」），
实测 **3 真红**。

> 这是教训 #37 的一个新变体：**不只是「断言太弱会假绿」，「断言太硬（固定窗口/固定字数）
> 也会假红」**——假红会让人以为改坏了，然后去回滚一个其实更好的改动。

## 八、教训（已并入 CLAUDE.md #44）

**「链路接好了」和「链路上有原料」是两件事。** 第 12 轮错在调用点不可达（接在死方法上），
第 13 轮错在没数据可读（表里只有 2 行），第 14 轮挖出来的才是根：**上游的分类器根本不用这个类型**。
三层都「接好了」、单测全绿、端到端也能跑，因为端到端是我自己构造了标准样本喂进去的——
**真实数据里 98.7% 的悬事从未进入这条链**。

判据是：**看产出分布，不看接线证据。** 一个类型/分支/工具的在用率可以用一行 SQL 量出来
（`result_json` 里 type 的分布），而「有调用点」「有测试」「端到端通过」都证明不了它在真实数据上工作。
