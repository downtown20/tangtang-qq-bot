| 层级 | 结论 | 证据 |

**根因**：私聊口径漏了 `group_id` 为空这一条，两处：

- `Store.list_chat_scopes('private')`（`store.py:13256`）——
  `where = [f"{col} != ''", "COALESCE(quarantined_at,'') = ''"]`，`col = qq_id`。
  只按 `qq_id` 分组 ⇒ **该 QQ 在群里说的每一句话都被算成「和他的私聊」**。
- `Store.read_chat_feed('private', qq)`（`store.py:13322`）——
  `col = "c.qq_id"`，`WHERE c.qq_id = ?`。同理，群消息全部进私聊正文。

不是设计如此——同文件另有 **17 处**私聊口径都正确写了 `COALESCE(group_id,'')=''`
（`get_user_recent_messages`、`_chat_scope`、活跃统计、未读计数、`is_bot_reply` 的
隔离子句……），只有这两个函数漏了。**教训 #38 的原形：同一个物理量有两个换算点，
只改了其中一个。** 这里更糟——19 个换算点，漏了 2 个。

## 3. 修法（最小改动，只动 `agent/store.py` 两处）

```python
# list_chat_scopes（13257）
if kind == "private":
    where.append("COALESCE(group_id,'') = ''")

# read_chat_feed（13322）
scope_cond = (f"{col} = ?" if kind == "group"
              else f"{col} = ? AND COALESCE(c.group_id,'') = ''")
```

两处 WHERE 由 `{col} = ?` 改为 `{scope_cond}`。参数个数不变（仍是 1 个 `scope_id`），
所以 `after_id` 分支与首次分支都不用改参数。

**前端一行没改**——数据对了，界面自然对。

## 5. ① 本地发消息看不到思维链

### 5.1 取证：数据在，通路断

| 证据 | 事实 |
|---|---|
| `turn_traces` | 146 条，**全部** `v2:` 键，**146/146** 能按 `event_key` join 上 `chat_log` |
| `状态/.会客厅.db` 的 `console_messages.meta_json` | 有 `reasoning_chars` / `ms` / `tokens` / `model` / `finish_reason` |
| `ConsoleApi._turn_meta` | **没有 `event_key`** ⇒ 前端拿不到键，换不回全文 |
| `ConsoleApi.feed` 的 `desktop:` 分支 | `"trace": None, "event_key": ""` ⇒ 前端 `TraceCard` 永不渲染 |

前端本身**早就写好了**：`Console.tsx:1059` 的
`{m.trace && rid && <TraceCard … onReplay={() => openReplay(m.event_key || m.trace!.event_key)} />}`
——条件一满足就出「💭 思考 N 字 / 展开 / 回放」。`openReplay` 走 `/api/console/replay`，
`toggleTrace` 支持只有 `event_key` 的 `trace`（`summary.run_id ? … : {event_key}`）。

⇒ 所以 ① **前端一行没改**，是后端两个缺口。

### 5.2 修法（`agent/console_api.py` 两处 + 一个纯函数）

1. `_identity_turn`：从 `build_msg(text)` 已经生成的 `_inbound_event` 取 `event_key`，
   写进 `meta`。这个键与 `turn_traces` / `chat_log` 用的是**同一个值**——不是新造的键，
   所以 `/trace?event_key=` 与 `/replay?event_key=` 两条现成路径都能用。
2. `feed` 的 `desktop:` 分支：用新增的纯函数 `_local_trace_from_meta(meta)` 把 meta
   投影成 `ConsoleTraceSummary`（字段集与 `desktop/src/lib/api.ts` 严格对齐）。
3. 老消息（改动前的回合）meta 里没有 `event_key` → 函数返回 `None` → 界面隐藏那块，
   **不报错**（历史消息本来就没留痕，回放端点也是这么约定的）。

### 5.3 验证

- 历史消息无 `event_key` → 无 trace；
- 没思考也没工具 → 无 trace（不塞空卡片）；
- 脏类型（`"120"` / `None`）容错；
- `feed` 的 desktop 分支真实投影（走真 `ConsoleStore`）；
- 老消息照常显示、只是没有 trace；
- 增量轮询（`after_id`）也带 trace。

**变异**（`变异_本地思维链通路.json`，2/2 真红）：
- M1 去掉 `event_key` 守卫 → 红「没有 event_key」；
- M2 feed 不投影 trace → 红「增量轮询丢了 trace」。

## 6. ④ 「她怎么想的」→ 流程时间轴（第一版七段）

### 6.1 原料全在，只是从没拼到一起

| 阶段 | 原料 | 实测（trace #147） |
|---|---|---|
| 1 收到消息 | `chat_log` 行 | 原文 / 时间 / 来源 / 说话人 |
| 2 窗口与历史 | `prompt_digest.history_count/history_chars` | 14 条 / 506 字 |
| 3 背景注入 | `prompt_digest.user_bg_labels` + `system_sections` | 7 块 / system 10 段 / 3314 字 |
| 4 记忆召回 | `prompt_digest.memory_marks` | ✏️ 纠正 1 / 不确定 2 |
| 5 工具调用 | `tool_steps_json` | 0 个（该轮纯文本） |
| 6 生成 | `duration_ms` / `reasoning_text` / `model` | 7201ms / 860 字 / v4.1-flash |
| 7 发送与反应 | `decision_runs` + `feedback` | reply / completed / 她的正文 |

`prompt_digest` 是 2026-10-25 第三轮就落盘的（8 个字段：system 段/背景块标签/历史条数/字符数/memory 标记），
**但它从来没被任何界面读过**——和 ① 一样是「数据在、通路断」。

### 6.2 实现

**后端**：`console_api._build_turn_flow(...)` 纯函数（不查库、不改状态），
`turn_replay` 的返回**多一个 `flow` 字段**（七段数组），四个老字段一个不动。

选「加字段」而不是立项里写的「新加 `/api/console/turn-flow` 端点」——前端
`TurnReplay` 已经在调 `/replay`，加字段省一次往返，也不必让前端多一条 api 函数。
（这是对计划的偏离，理由写在这里，不藏在代码里。）

**前端**：`TurnReplay.tsx` 加「完整流程」section（默认展开、放最前），
`FlowTimeline` 组件画竖线时间轴；异常段标红 + 徽章显示「N 段异常」。
样式单独放 `TurnReplayFlow.css`（`TurnReplay.css` 已近 600 行）。

**关键设计：空段本身就是发现**——每段都带 `ok` 与 `note`。
只画时间轴不给判据，等于让人肉眼找问题（第 8 轮「裁剪尺子差 2.5 倍藏了 9 天」就是这个）。

### 6.3 验证

**闸门**（`tests/test_console_turn_flow.py`，9 条）：七段顺序/字段集、
全绿回合每段都有值、工具耗时累加、无工具/无记忆块/无背景块各有对应 note、
老回合无 digest 降级、全空回合不崩、长文本截断。

**变异**（`变异_七阶段流程.json`，3/3 真红）：
记忆块判定恒真 / 背景注入段恒绿 / 工具耗时不算——三条都让判据红了。

**端到端**（真实 `/replay`，三个回合）：
```

回合 3（群 833475319）：同上
```

### 6.4 端到端立刻暴露的两件事

**① 群聊记忆块注入率只有 61%（私聊 95%）** —— 全量统计：

| 范围 | 私聊 | 群聊 |
|---|---|---|
| 最近 60 条 trace | 40/42 = **95%** | 11/18 = **61%** |
| 全量 70 条 trace | 46/52 = 88% | 11/18 = 61% |

不是「从未注入」，是**部分回合被裁掉**：群聊候选块有 11 个
（协议/窗口/窗口姿态/证据纪律/关系/自忆/交叉/提及/缺口/反思/记忆），私聊只有 8~9 个，
预算一样紧 → 记忆块先被淘汰。**这是下一轮的调查线索**，不是本轮该改的
（本轮已经在改三件事，按「每轮只打一类」的纪律不动它）。

**② 第 7 段原先永远是「（feedback 未采集到）」——一个长期存在的匹配 bug**

`turn_replay` 调 `find_feedback_for_turn(user_qq, after_ts, reply_text)`，
而它的匹配条件是「两边文本有前缀关系」，第三参必须是她**真正发出去的那句话**。
生产代码传的是 `row.get("message")` = **触发消息**（对方说的那句）——
对方的原话与她回复的前缀几乎不可能相同 ⇒ `feedback` 长期返回 `None`。
**不是「对方还没反应」，是永远查不到**（回放里「对方怎么反应」那段一直是空的）。

修法：新增 `store.get_bot_reply_text_for_trigger(trigger_id)`
（查 `delivery:<触发id>:%` 的多条气泡按 id 升序拼接），先取回她真正说的话再匹配；
同时 `find_feedback_for_turn` 的返回补上 `bot_reply`（原投影只有 6 个字段，
看得见「对方怎么反应」却看不见「她到底说了什么」）。

验证：`tests/test_console_replay_feedback.py`（5 条）+ 变异 1/1 真红；
真实数据对照——14:00 那批有反馈的回合，第 7 段现在完整显示她 100+ 字的正文。

## 6.5 第二轮整改：主人要「彻底可视」，七段扩成九段 + 全参数

> 主人原话：「你只是做到了我说的那部分，呈现方式也很简单。」四条要求：
> ① 校验「完整流程」的完整性；② 暴露背景块/记忆块等**参数**；
> ③ 后端参数不止这些，要梳理清楚一并公开；④ 彻底的前端可视；⑤ 视觉要美观专业。

### 6.5.1 完整性：七段确实不够，补了两段

对着真实链路逐段核对，缺口是**头**和**尾**：

| # | 阶段 | 变化 |
|---|---|---|
| 1 | 收到消息 | 加 params（chat_log id / 全文长度 / 会话） |
| **2** | **路由与窗口** | **新增**——通道分域 / 决策动作 / 起止时间 / 工具数 |
| 3 | 系统提示与历史 | 原来是「窗口与历史」，现在带 **system 段清单** |
| 4 | 背景注入 | **重点**：预算 + 每块三态 + token + 内容预览 |
| 5 | 记忆召回 | **重点**：记忆块状态 + 逐条记忆 |
| 6 | 工具调用 | params 里放**完整**入参/返回（原来截 60/80 字） |
| 7 | 生成 | 加 **token 各段账本** |
| 8 | 发送 | 从「发送与反应」拆出，正文改从 `chat_log` 取 |
| 9 | 对方反应 | 从「发送与反应」拆出 |

### 6.5.2 参数是怎么补出来的：原来只写日志、从不落库

三处**「有事实、没出口」**（和第 8 轮那个「裁剪尺子藏了 9 天」同族）：

1. **`protocols.fit_backgrounds`** 里有完整的降级信息（哪块被淘汰、哪块被裁、
   裁前/裁后 token、预算是否超顶、证据保底是否动用）——**只写一行 INFO 日志**。
   → 加**出参 `report`**（不改返回值，返回值形态被两条回复路径和一批测试钉着），
   填 `{budget, blocks[{label,priority,tokens,tokens_before,status,preview}], gap_notice}`。
2. **`TokenReport.sections`** —— `context_builder` 从没填过分账，生产上只有 `tools`
   （另一个「有账本没有分账」）。→ 在 `_persist_turn_trace` 里用同一把尺子
   `estimate_tokens` 按字符数补 system/history/user。
3. **`turn_trace` 的 digest 上限是 4000 字符，且用硬切片**（超了会切成非法 JSON，
   既有隐患）。→ 背景块预览按类型定长（记忆/自忆/反思 260~300 字，其余 100 字），
   实测整份 digest **2024 字符**，安全。

> 4. 以「使用者是一个小白运营者」为前提：他需要看懂整个流程，也需要知道**哪个环节没有坏、哪个环节出了问题**。

上一轮我交的是「九段 + 参数明细」——参数齐了，但**参数是给懂行的人看的**。
一个不写代码的运营者看到「预算上限 1100t」「P7 294→190t」仍然不知道
该不该在意、这算不算坏。四条要求逐个落到具体机制：

| 主人要求 | 落到什么 | 不这么做的后果 |
|---|---|---|
| ① 参数解释 | 每个参数带 `doc`（一句人话） | 一串数字，看不懂等于没有 |
| ② 四问 | 每站 `role`/`logic`/`did` + `group` | 只知道「发生了什么」，不知道「该发生什么」 |
| ③ 图谱 + 配合 | 三层递进 + `carries`（交给下一站什么） | 一条很长的清单，看不出结构 |
| ④ 哪坏了 | 四态 `status` + 体检结论 `flow_summary` | 数不清「打折」和「异常」的差别 |

### 6.6.2 后端：六个教学字段（`agent/console_api.py`）

`_station()` 统一构造每一站，加六个字段。它们全部由后端算好，前端只画——
判据只有一处（第 47 条教训：同一语义 N 个实现点，漏一个就静默错）。

| 字段 | 回答的问题 | 例（真实回放） |
|---|---|---|
| `group` | 属于哪个大阶段 | 进入 / 理解 / 决策 / 输出 |
| `role` | 这一站在干什么 | 「把关系档案、记忆、自忆、悬着的事塞进 prompt」 |
| `logic` | 判断依据是什么 | 「按淘汰优先级排序，预算用完就裁块或整块淘汰」 |
| `did` | 这一轮实际发生了什么 | 「6 块进了 prompt（1 块被裁），1 块被淘汰；预算 1022/1100t」 |
| `status` | 四态 | `ok` / `warn` / `error` / `skip` |
| `carries` | 交给下一站什么 | 消息原文 / 会话 / 聊天记录编号 |

`params[].doc` 是参数解释。写在后端而不是前端，因为**参数是后端造的**，
只有造它的人知道口径：「token 合计 9265t」到底是成本还是回复长度？

`carries` 集中在模块级常量 `_FLOW_CARRIES` 里，而不是散在 9 处调用点——
改口径只改一处。

### 6.6.3 为什么必须四态：布尔的三种误导

上一版 `ok` 是布尔。对着真实回放逐站核对，发现它会把三件事混成两件：

| 真实情况 | 布尔会说 | 应该是 |
|---|---|---|
| 记忆块被裁，只留开头 | `ok=false`（红） | **warn**——她还能看见记忆，只是不全 |
| 这一轮没调工具 | `ok=true`（绿） | **skip**——"没调工具"是可观察事实，标绿等于看不见 |
| 对方还没回话 | `ok=false`（红） | **skip**——等对方开口，不是故障 |
| 没采集到 prompt 摘要 | `ok=false`（红） | **error**——这才是数据缺口 |

`skip` **不是故障**。把「没调工具」标红，运营者会去修一个不存在的 bug；
把「对方没回」标红，他会以为感知系统坏了。`ok` 字段保留（= `status` 是
`ok`/`skip`），老前端与老测试不破；闸门断言两者必须一致。

### 6.6.4 前端：三层递进（`TurnReplayFlow.tsx` + `.css`，全新建）


## 6.7 ⚠ 事故：我把对外 README 写坏了（已恢复，教训 #49）

### 6.7.1 经过

收官时想把 `docs/发布/README.md` 里的反模式计数 47 → 48 同步，用了：

```powershell
$t = Get-Content $f -Raw
$t = $t.Replace("项目记录着 47 条错误模式", "项目记录着 48 条错误模式")
Set-Content -Path $f -Value $t -NoNewline -Encoding UTF8
```

PS 5.1 的 `Get-Content` **按 ANSI(cp936) 解码** UTF-8 文件 → 全文中文变
mojibake（`🍬 小糖糖` → `馃崿 灏忕硸绯`），`Set-Content -Encoding UTF8`
再把乱码固化成 UTF-8（还带 BOM）。**295 个字节在 cp936 解码时永久丢失**，
逆向（mojibake → 编回 cp936 → 当 UTF-8 解）只能恢复约 98%，剩下的 `?`
不可还原——「一个 `?` 占位意味着那 1~2 个原始字节再也回不来了」。

发现方式很朴素：改完 `grep "48 条"` 一无所获——因为整个文件已经不是中文了。

### 6.7.2 抢救（这轮最有价值的一段取证）

1. **先找版本控制**：`git cat-file -p HEAD:docs/发布/README.md` 拿到 HEAD 版本

   字节数 19320 vs **19311**（只差 9）。⇒ 两份是**同一篇文档的两个修订**，
   差异一定很小。
3. **逐行比对**（`_backups/README抢救_20261025/_diff_lines.py`）：
   对每一行，把「WORK 里还能读出来的字符（去掉损坏符与通配 `?`）」当作
   needle，问它是否是 HEAD 同行的**子序列**——是则该行内容没变，不是则该行被改过。
   **253 行里只有 6 行被改过**：

   | 行 | HEAD | 工作区 |
   |---|---|---|
   | 11 | `tests-2900` | `tests-3400` |
   | 83 | 有 1100 多个 | 有 **1400** 多个 |
   | 99 | 36 条错误模式（5 个例子） | **47 条**（扩写成一长串例子） |
