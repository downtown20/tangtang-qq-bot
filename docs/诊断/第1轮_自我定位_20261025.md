## 第 3 步 归因（是「不知道」还是「知道但用错」）

### 缺陷 A（S-1）：历史消息里的 @ 是裸数字，她不认识——包括指向她自己的那个

- **判断：不知道。** 材料里根本没有「这串数字是谁」的映射。
- 取证链：
  1. `chat_log#300159` 存的是 `……😢@QQ2693914170`；`people` 表里 2693914170 的昵称**就是「小糖糖」**。
  2. `turn_traces#41` 的原话把她自己推给了别人。
  3. 会客厅第 6 轮她亲口承认「我自己的号……没记住」。
- 根因：**buffer 是 LLM 历史消息的直接来源**，而 buffer 只存
  `normalize_image_placeholder(text)` 的结果，`@QQ<号>` 原样入 buffer。
  当前消息在 `_build_user_message` 里会被 `_nick_for_qq` 解析成 `@小糖糖`，
  历史却不解析——**同一批对话两种形态并存**，她更难对上号。
- **不是**「prompt 少写了一句她的 QQ」——那是让她背数字，真人不背自己的号。
  修在渲染层：别人 @ 她，她应该看到自己的名字。

### 缺陷 B（T-1）：默认上下文只有「现在是深夜」，没有日期/星期/时分

- **判断：不知道。** 材料里没有日期。
- 取证：`personality._get_time_context()` 旧版只返回一个时段词。
  对照 `turn_traces#25`（自编「周五上午」）与 `turn_traces#59`（调工具后
  「25号星期日」完全正确）——**能力在，锚点不在**。
- 附带发现：`_get_time_context` 和 `sensory.get_current_time` 是**两套词表**
  （prompt 用 6~9「早上」、工具用 5~8「清晨」），同一天可能两个说法。

### 排除的伪缺陷（重要，防止瞎修）

| 现象 | 为什么不是缺陷 |
|---|---|
| 她说「才两分多钟」这类流逝感 | **算对了**——有窗口时间戳做锚，她能推出相对时长 |
| 「蓝鲸计划」她说不知道 | **正确行为**：先搜证，再说不知道，没编造 |
| 记忆复述与她之前说的一致 | 一致即正确；重复措辞属于「表达风格」不是「记错」 |

### 第 4 步追加：修完 B2 之后，复验失败暴露了真正的根因（B-3）

复验时问她「明天几号」，她答对了（10 月 26 日、星期一），但 `turn_traces#66`
显示她**调了 `get_time`**——不是读到了 prompt 里的日期。紧接着 `turn_traces#67`
她的 reasoning 原话：

> 「等下——我上一轮说了「10月26号，星期一」，但这个日期可能是我编的？
> **我没有查时间。** 背景缺口提示可以查。为了不再出错，应该 get_time。」

**她看不到我加的时间块。** 于是回头查 `context_builder.build()`：

| 量 | 值 |
|---|---|
| `personality_base` 估计 tokens | **4542** |
| 截断预算（CORE 1800 + RELEVANT 800 + SUPPLEMENTARY 400） | **3000** |
| 时间块在 `personality_base` 里的位置 | **2908 / 2994 字符 = 97.1%** |
| `_truncate_text` 的行为 | `text[:token_budget/1.8]`——**从头保留，砍尾部** |
| 不可裁白名单 | 只有「## 必须遵守」「## ⚙️ 当前运行模式」 |

结论：**时间块过去从来没有进过她的上下文**——不是「说了没用好」，是从头到尾
根本没送到。连 2026-08-17 那版「现在是深夜。」也一样被砍。

所以 B-3 才是「没有活人的时间观念」的**真正根因**，B-2 只是让被砍掉的那句话
更有信息量。修法：把时间块升级成独立段 `## 此刻` 并加入不可裁白名单
（不放到稳定前缀之前——它每分钟变，放前面会让 DeepSeek 隐式缓存永远 miss）。

> **顺带发现一个更大的问题（未修，记入台账）**：`estimate_tokens` 按「1 中文字
> ≈ 1.8 tokens」估算，而真实中文约 1 字 ≈ 1 token——**尺子高估 80%**，
> 于是 3000 的预算实际只装了约 1666 字符。实测渲染后的 system prompt 只剩
> **1580 字符**，被砍掉的是「## 关系」「风格锚」「FOLLOW_UP_PROTOCOL」等整段。
> 这不属于本轮「时间/身份」一类，单独开一轮处理（改预算或改系数都会影响
> 所有路径，必须单独评估 + 变异对照）。

## 第 5 步 复验（重启后回会客厅问同一个问题）

第一次复验（B-2 之后、B-3 之前）**失败**：她答对了日期，但 trace 显示是现查
`get_time` 得来的；下一轮 reasoning 里她自己说「这个日期可能是我编的，
我没有查时间」——暴露了 B-3。

B-3 修完重启后再问「我这个点还不睡，明天早上会不会很难受」：

| | 修复前 `trace#67`（01:09） | 修复后 `trace#68`（01:12） |
|---|---|---|
| reasoning 里的时间 | 「这个日期可能是我编的？我没有查时间」 | 「**已经半夜1点12分**」——准确对得上 `recorded_at` |
| 工具调用 | 1 次 `get_time` | **0 次** |
| 回复 | 追问 + 想查证 | 「你现在睡还能凑够六个来小时」——由 1:12 推算出来 |

**这就是「活人的时间观念」**：不用查就知道现在几点，还能拿它做生活判断。

身份侧（缺陷 A）的复验**没有可测的对话入口**——她知道自己号是多少并不重要
（真人不背自己的号），要验证的是「别人 @ 她时她认不认得出」。这只能等群里
真实出现 `@QQ2693914170` 时看 `turn_traces`，已记为观察项。
