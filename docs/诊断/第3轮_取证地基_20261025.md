# 第 3 轮｜补上取证的另一半 —— 「她这一轮看到了什么」

> 2026-10-25 06:00–06:25。工作流见
> [自主发现修复闭环_毛选视角](../工作方式/自主发现修复闭环_毛选视角_20261025.md)。
>
> 前两轮的共同困境：每次排查都要**本地复刻 prompt + 读源码推断**。
> 第 1 轮断言「时间块被截断吃掉」、第 2 轮断言「44% 说明书被砍」，
> 两轮都是靠推理得出，不是靠观察。这轮把观察能力补上。

---

## 第 0 步 立项

预测：`turn_traces` 缺的是「输入侧」；补上之后**第一次用就能发现一个新问题**
（判据：新留档里能读到前两轮修复的效果，且能看到此前完全不知道的事实）。

---

## 第 1 步 调查

| 表 | 记什么 | 缺什么 |
|---|---|---|
| `decision_runs` | 决定了什么（reply/skip/fade + 工具名） | 怎么想的 |
| `turn_traces.reasoning_text` | **怎么想的**（思维链） | —— |
| `turn_traces.tool_steps_json` | 查了什么 | —— |
| `turn_traces.prompt_chars` | —— | **恒为 0**（`_persist_turn_trace` 根本没传这个参数，78/78 行都是 0） |
| （不存在） | —— | **她收到了什么**：system prompt 有哪些段、注入了哪些背景块、历史几条 |

结论：观察窗口只装了「输出侧」，**输入侧完全空白**。

---

## 第 2 步 建真值

这不是「她答错」的问题，是**取证能力缺失**：

- 第 1 轮要证明「时间块没进上下文」，只能本地跑 `build_system_prompt()` 复刻；
- 第 2 轮要证明「说明书被砍」，同样只能本地渲染对比；
- 而「她记错了」这类问题**根本无法用复刻法查**——因为不知道她当时手上有什么。

工作流文档 §五 早就写了「没有第四行，第 3 步的二分判断就只能靠猜」。
两轮之后，这条从「已知缺口」变成「实际障碍」。

---

## 第 3 步 归因

**是「观察工具」缺陷，不是她的行为缺陷。** 前两轮的修复都没有错，
但**验证方式都靠推理**——这在教训 #37（假绿）的谱系上：推理得出的结论
看起来和观测得出的结论一样可靠，直到它错了。

---

## 第 4 步 修复

### 加 `prompt_digest`（存结构不存全文）

`memory.db` 已经 900MB，一轮的 system prompt 有 3000+ 字符、history 十几条，
全存每轮涨几 KB。而要回溯的是**结构**：

```json
{
  "system_chars": 3313,
  "system_sections": ["你是谁","性格","说话","称呼","@提及","说话示范",
                      "回复的分寸","必须遵守","⚙️ 当前运行模式…","此刻"],
  "user_chars": 675,
  "user_bg_labels": ["关系档案","协议","窗口","缺口"],
  "history_count": 0,
  "history_chars": 0,
  "total_chars": 3988
}
```

每个字段都对应一个**真实会出的故障**：

| 字段 | 能回答什么问题 |
|---|---|
| `system_sections` | 「说明书缺了哪段」——第 2 轮那个 44% 截断，一眼可见 |
| `user_bg_labels` | 「她为什么没看到我刚发的事」——注入了哪些材料 |
| `history_count` / `history_chars` | 「她记不记得上一句」——历史窗口是否按预期拼接 |
| `total_chars` | 同步写进此前恒为 0 的 `prompt_chars` |

### 改动清单

| 文件 | 改动 |
|---|---|
| `agent/store.py` | 建表加 `prompt_digest TEXT NOT NULL DEFAULT ''`；**老库 PRAGMA 检查 + ALTER 迁移**；`record_turn_trace` 加参数并序列化（上限 `TRACE_DIGEST_LIMIT=4000`）；3 处 SELECT 加列；`_turn_trace_dict` 解析成 dict（老行返回 `{}` 不抛） |
| `agent/handler.py` | 新增模块级 `_summarize_prompt()`；`_begin_turn_trace` 容器加 `"prompt"` 槽；`_call_deepseek` 拼完 `api_messages` 后写 `trace["prompt"]`；`_persist_turn_trace` 传 `prompt_digest` + 用 `total_chars` 填 `prompt_chars` |
| 降级保护 | writer 不接受 `prompt_digest`（测试替身/老 store）时 `TypeError` 回退，**丢字段不丢整条痕迹** |

## 第 6 步 复验（生产实测，两个回合）

```
trace#80  06:19:22  total=3988  history_count=0   bg=['关系档案','协议','窗口','缺口']
trace#81  06:20:07  total=4101  history_count=2   bg=['关系档案','协议','缺口']
```

**这一屏直接确认了前两轮的修复**：

- `system_sections` 里有 `说话示范`、`回复的分寸`、`此刻`——第 2 轮之前这三个
  都在被截断的那一侧（实测渲染只剩 1580 字符、缺「关系」「说话」）；
- `total_chars=3988`，说明 `prompt_chars` 不再是 0；
- `此刻` 在场 = 第 1 轮的时间锚点确实送到了。

**而且第一次用就抓到一个此前完全不知道的问题**：

`trace#80` 是 bot 重启后的第一轮，`history_count=0`——**重启把对话历史清空了**，
她那一轮只收到当前这一句话。第二轮回升到 2 条，证实是「内存态 buffer 被清」，
不是「会客厅永远不拼历史」。

这就是留档的价值：第 1、2 轮都只能看见「她说错了什么」；现在能看见
「她当时手上有没有东西」。要是没有这份留档，上面这段只能靠猜。

> **副产品（记入台账，下一轮候选）**：`memory.short_term` 是纯内存态，
> bot 重启后对话窗口归零——而会客厅的 `sessions` 表其实存着这些消息。
> 属于教训 #15 的教科书案例（「持久化做了一半」）：写下去了，但没有回灌。
> 主人侧体感就是「她突然不记得刚才聊的」。
