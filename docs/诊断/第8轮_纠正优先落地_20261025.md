## 2. 决策 B：corrected 优先

### 2.1 先更正我自己的假设——那两条记忆**属于同一个人**

我原先在交接单里写的是「`mem#17589`（2377255095）vs `mem#18121`（2524950083）」。
**查库后不成立**，两条都是 `qq=2524950083`：

| 记忆 | trust | key | 内容 |
|---|---|---|---|
| `mem#17589` | **corrected** | `fact_correction` | 成展是大学大二学生（不是高中生） |
| `mem#18121` | **verified** | `fact` | 今年7月刚靠指标生名额考上一中，是高一新生 |

而真正的「高一新生」在 `mem#17485`（`qq=2377255095`，corrected）——**另一个人**。

**所以 `mem#18121` 不是「另一种说法」，它是错的**：把 2377255095 的身份记到了
2524950083 头上。

### 2.2 因果链（为什么纠正没撤掉它）

`mem#18121` 的证据只有一条：`chat#199048`（2026-08-17 11:42:21）。原文是：

> 帮我修正一下「穷到吃外卖」的记忆：他说的「33岁上班族」是开玩笑的，不是事实。
> **他**实际是今年7月刚靠指标生名额考上一中的高一新生，8月19号要去军训。
> 用 correct_memory 工具修正一下。

这是主人**转述别人**的一句话（「他」= 穷到吃外卖 = 2377255095），提取器把它
记成了主人自己的事实——正是第七轮定性的**第三人称转述缺陷**。

时间线（这是关键）：

```
2026-08-17  纠正流程跑起来 → 成功撤掉 mem#17475 / mem#17476（同批的错误纠正行）
            → 写入 mem#17589「成展是大学大二学生（不是高中生）」
            → 但 mem#18121 当时还是 legacy_unverified，纠正的搜索口径碰不到它
2026-10-24  证据回挂批次（tools/语义回挂证据.py）给它补上 chat#199048 作为证据
            → 因为当时还没置信度门，它被升成 verified
2026-10-25  它与 corrected 结论同时 active、同时注入、文本毫无区别
```

**结论：纠正机制本身没坏，坏的是「纠正之后又被另一条通道升回可信」。**
所以这不是「再对话一次就能修好」的事——搜索口径没变，同样的残局会留下。

### 2.3 三项改动

**(a) 数据：撤回 `mem#18121`**

新工具 `tools/撤回记忆.py`（dry-run / `--apply` / `--restore`）：

  **`retracted`** 而不是 `superseded`，也**不挂** `superseded_by`——那个字段的语义是
  「被谁取代」，用在「被否定」上会污染演化史；

**同一批还有第二条**：`mem#18122`（同一个人，「8月19号要去军训」，证据 `chat#199093`——
主人把那句话在 08-17 12:08 又说了一遍）。

只修 `mem#18121` 会留下「成展要去军训」——**同一个事故的另一半**。所以按

**(b) 机制：注入层让「哪条被纠正过」可见**

| 文件 | 改动 |
|---|---|
| `agent/store.py` | 新增 `TRUST_INJECT_PRIORITY = {corrected:3, manual:2, verified:1}` —— `TRUSTED_TRUST_LEVELS` 是**集合**（能不能注入），这是**有序表**（注入时谁先） |

判真假，变异 M-CP3 专门钉这个。

三档现在的样子：

```

模糊 → 💭~ 内容    + 块尾：UNCERTAIN_MEMORY_CONTRACT
```

## 2.5 真正的根因：裁剪尺子还停在旧口径（**本轮最重要的发现**）

### 现象

按 §2.3 / §2.4 做完之后去会客厅实测，`turn_traces.prompt_digest` 里：

```
memory_marks : {'corrected': 0, 'uncertain': 0}
```

**一条标记都没进她的 prompt**——而离线调 `format_compact_memories` 明明有 3 条 ✏️。

差别在哪？日志给了答案：

```
🧺 背景块淘汰/裁剪: 保留flex=4 裁=3（窗口 243→70t、记忆 294→70t、自忆 255→60t）| 预算 790/900
```

记忆块被裁了。裁剪函数 `protocols.truncate_bg_block`：

```python
char_limit = max(40, int(token_limit / 1.8))   # ← 旧尺子
```

而 token 估算 `context_builder.estimate_tokens` 的中文系数，**第 6 轮已经改成 0.72**。

两把尺子差 **2.5 倍**：按新尺子量出「70t 的块」，按旧尺子只准留 `70 ÷ 1.8 = 38` 个字——
正好是记忆块第一行标题 `📋 名字(ID:xxxx) | 聊N次 | 等级`，**一条记忆都不剩**。

所以那一轮她确实没看到任何标记；而日志写「记忆块保留了」（它确实在），
从日志和界面都看不出来。

### 为什么第 6 轮没抓到

第 6 轮修的是「预算太小」（480→720→900），修的是**数字**；系数漏在另一个文件的
另一个函数里。当时的验证是 `test_memory_block_survives_default_budget`——它证明
「记忆块没被整块**淘汰**」，而「被**裁剪**」是另一条路径。

**教训（已写进函数 docstring）**：同一个物理量如果有两个换算点，改一处必须 grep
另一处（教训 #4 / #35 的变体）。

### 修复

```python
char_limit = max(40, int(token_limit / 0.72))   # 与 estimate_tokens 同口径
```

### 影响面（这不是小修）

所有走 `truncate_bg_block` 的块都受影响（关系档案 / 窗口 / 记忆 / 自忆 / 反思 …），
它们此前**只被允许保留 40% 的预算**。修完之后同样的预算能装 2.5 倍内容。

### 闸门

新增 `tests/test_bg_truncate_ruler.py`（8 条）：

- **正向**：裁完不超预算；
- **反向**：裁完要贴近预算（≥ 80%）← **这条才是关键**。旧实现「也不超预算」
  （它裁得太狠，永远超不了），只有反向断言抓得住；
- 端到端：记忆块被裁到 70t 之后**第一条记忆必须还在**（只剩标题行就是故障形态）。

变异 **3/3 真红**（退回 1.8 / 改成 0.36 / 完全不裁）。

### 行为验证（改前 / 改后对照，同一句话）

| 时间 | 尺子 | `memory_marks` | 她的回答 |
|---|---|---|---|
| 08:32 | `/1.8` | `{corrected: 0, uncertain: 0}` | 「有学籍的是你，大二，郴州那边」——答对了，但靠画像/窗口，不是记忆块 |
| 08:37 | `/0.72` | **`{corrected: 2, uncertain: 2}`** | 「10月14号你**自己亲口说的**『最近没有什么报错』，我**记岔被你说了一顿，已经改过来了**」 |

第二句是**契约语言**（「带 ✏️ 的是 ta 亲口纠正过的结论，不是你自己记的」）——
标记不只是出现了，**被用上了**。

### 同一预算下，裁剪前后的真实数字（08:37:27 日志）

```
🧠 记忆块装入: #25300:corrected | #19880:corrected | #9636:verified
              | #10296:legacy_unverified | #9846:legacy_unverified
🧺 背景块淘汰/裁剪: 保留flex=3 淘汰=2（反思157t、自忆266t）
                  裁=2（窗口 277→185t、记忆 294→214t）| 预算 860/900
```

对比改前（08:33:10，同一预算 900）：

```
🧺 背景块淘汰/裁剪: 保留flex=4 裁=3（窗口 243→70t、记忆 294→70t、自忆 255→60t）| 预算 790/900
```

| | 记忆块 | 窗口块 | `memory_marks` |
|---|---|---|---|
| 改前（`/1.8`） | 294 → **70t** | 243 → 70t | `{corrected:0, uncertain:0}` |
| 改后（`/0.72`） | 294 → **214t** | 277 → 185t | `{corrected:2, uncertain:2}` |

**同样 900 的预算，记忆块从 24% 提升到 73%**——预算没变，是尺子修好了。

顺带看到 `记忆块装入` 的顺序：两条 `corrected` 排在最前，然后是 `verified`、
`legacy_unverified` —— §2.3 的稳定排序也在同一轮里生效了。

### 为了这次取证补的两个观测点

| 观测点 | 回答什么问题 |
|---|---|
| `turn_traces.prompt_digest.memory_marks = {corrected, uncertain}` | 标记有没有**活到最终 prompt**（在裁剪之后的 `user_message` 上数，按行首） |
| 日志 `🧠 记忆块装入: #id:trust \| ...` | 这一轮记忆块里装了**哪几条、什么信任等级** |

两者合起来才能区分「**没被选中**」和「**被裁掉了**」——这两种情况的修法完全不同
（前者调精排，后者调预算）。本轮就是靠这个区分才找到根因。

## 3. 遗留观察项（下一轮候选）

### 3.1 休眠降权把纠正结论压到底部（**本轮实测发现，未修**）

改后查库：`mem#17589`（corrected，importance=10）在候选池**第 21 位**，`eff=7.17`，
而同 importance 的 corrected 行 `eff=14.0`。

差 2 倍的原因是 `recall` 的休眠降权：

```python
if dormant_days > 60: score *= 0.5      # 两个月没被想起——大幅降权
```

**「长期没被召回」和「不可信」是两件事**，但对 corrected 结论来说前者恰恰意味着
「它很久没机会被看见」。这条降权会把最该优先的真相压到候选池尾部——真实路径里
靠 BGE 精排救回来，但降级链（无 BGE/Reranker 时的关键词兜底）就不一定了。

### 3.2 corrected 档里混着大量「对话流水式纠正」

2524950083 名下 14 条 active corrected 里，绝大多数是**一次性的对话澄清**：

- 「最近没有报错」
- 「志愿者活动是测试，实际没有这回事」
- 「没有答应过中午提醒吃饭，是糖糖记混了」

它们 importance=10、confidence=1.0，在纯 eff 排序下会**挤占**真正的人物事实
（本轮验证时 `max_facts=8` 就看到了 8 行全是这类）。真实配额是 3、且靠 BGE 精排，
所以线上影响有限——但值得观察「✏️ 行占比」是不是过高。

### 3.3 `corrected` 行的 `event_time` 为空

`mem#17589` 的 `event_time` 是空串，所以它既不参与时间衰减、也不拿到「最近 7 天
新记忆 +1.0」的加分。本轮它排在 21 位有一部分是这个原因——**这是「侥幸不衰减」而
不是「设计上不衰减」**，下次改动 recall 排序时容易踩。

### 3.4 尺子修好后的新权衡：自忆 / 反思被淘汰得更频繁（**要盯的一条**）

同一预算 900，改前改后的块分配完全不同：

| | 保留 | 淘汰 | 裁剪 |
|---|---|---|---|
| 改前 08:33 | flex=4 | — | 窗口 243→70t、记忆 294→70t、自忆 255→60t |
| 改后 08:37 | flex=3 | **反思 157t、自忆 266t** | 窗口 277→185t、记忆 294→214t |

窗口和记忆因为尺子修好各多占了一块，反而把自忆（P10）和反思（P7）挤掉了。

**这不是回归，是暴露了原来的「假平衡」**：以前是靠把每一块都砍到 60–70t 来
「全都放进去」，结果每块都只剩一个头（I-4 类缺陷）；现在每块都完整了，但块数少了。

下一步两个方向，都要先有数据再动：

1. **提高总预算**（900 → 更大）——第 6 轮刚从 480 提到 900，再加要评估 token 成本；
2. **重审优先级**——`自忆` P10 是最后一位，而「她记得自己说过什么」是 S-2 类缺陷
   （第 1 轮修过）的地基。

**观察指标**：接下来几天她「不记得自己说过的话」有没有变多。
查到就开下一轮，别提前改。
