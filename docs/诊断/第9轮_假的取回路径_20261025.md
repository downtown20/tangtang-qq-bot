# 第 9 轮：一条**假的**取回路径（2026-10-25）

> 这一轮的起点是上一轮留下的观察项「尺子修好后自忆/反思被淘汰得更频繁」。
> 顺着它查下去，挖到的不是「预算不够」，而是一条**承诺了却做不到的路径**。

---

## 1. 立项：自忆块到底被淘汰得多频繁

第 8 轮尾留了一句「接下来几天留意她是不是更常『不记得自己说过的话』」。
先别猜，直接统计 15 天日志里的背景块淘汰记录（390 条）：

| 整块淘汰 | 次数 |
|---|---|
| **自忆** | **365** |
| 记忆 | 236 |
| 反思 | 200 |
| 关系 | 70 |
| 知识库 | 33 |
| 交叉 | 27 |
| 窗口 | 2 |

**自忆是第一名**——不是偶发，是常态：它的存活率只有个位数百分比。

对照被**裁剪**（不是整块扔）的分布：窗口 206、记忆 81、关系档案 40、自忆 13、反思 13。
可以看出**自忆几乎不会走到「被裁剪」这一步，它直接掉出预算**——因为它排在最后一位。

---

## 2. 取证：为什么它排在最后

`BACKGROUND_PRIORITY` 上方有一段注释，写明了这张表的**定序原则**：

> 「定序原则从『谁更重要』改成『丢了能不能用工具取回』」
> 「关系档案 P9→P4 —— 它是全库唯一没有工具能取回的材料」

也就是说：**能取回的块可以让路，取不回来的必须优先保留。**

按这条原则，自忆排 P10（最后）只有一个可能的前提——**它能取回**。
而它确实登记了：

```python
_BG_RECOVERY_TOOLS = {
    "窗口": "search_chat_history",
    "记忆": "search_facts / search_memories",
    "自忆": "search_memories",        # ← 这一行
    ...
}
```

而 `protocols.py` 紧挨着这张表的上方就写着：

> 「只登记确实存在的工具（handler 里注册的 search_* 五个）；取不回来的不写——
> **不在这里替她发明能力**。」

---

## 3. 去伪存真：那条路径走不通

去读 `search_memories` 的执行体（`handler.py:9068`）：

```python
results = await self._run_store_io(
    "recall",
    self.memory.recall,
    qq_id,                       # ← 当前对话对象
    ...
)
```

`qq_id` 是**当前对话对象**（主人 / 群友）。而自忆写在 `bot_qq`（她自己的 QQ，
`2693914170`）名下——`_extract_self_memories` 写的就是 `bot_qq`。

**两个主体不是同一个。** 用 `search_memories` 查到的永远是**对方的**记忆，
查不到她自己的话。

于是形成一个闭环缺陷：

```
自忆块 94% 的回合被整块淘汰
  → 缺口块照实告诉她：「自忆没放进来，要的话可以用 search_memories 取回来」
  → 她照做，查回来的是对方的记忆
  → 她既没有自己的过去，也不知道自己其实没有
```

**这不是「多一行无害的提示」。** 它让她**以为**自己有一条退路，而那是一条死路。
`_BG_RECOVERY_TOOLS` 的每一行都在承诺「你照这个做就能拿回来」——承诺必须是能兑现的。

**这行代码正是那句「不在这里替她发明能力」的作者写的**：他核了「工具名存在」，
没核「工具检索的主体是不是这块材料的主体」。

---

## 4. 归因（二分问题的答案）

按工作流的二分：**她是「不知道」，还是「知道但用错」？**

→ **不知道**。自忆块 94% 没进上下文，她根本收不到自己的过去。修注入源。

而修法被代码自己的原则直接决定了，**不是价值判断**：

1. 删掉假的登记 → 自忆变成「取不回来」的一类；
2. 按「丢了能不能取回」的原则，取不回来的必须优先保留 → **P10 → P6**；
3. 但 900 预算装不下「关系档案 + 窗口 + 记忆 + 自忆」四个大块 → **预算 900 → 1100**。

**三处是同一条推理的三段**，缺一段整个修法就不成立：

| 只做其中一部分 | 后果 |
|---|---|
| 只删登记 | 她连「自忆没进来」都不会被告知——比修之前更差 |
| 只提优先级 | 假路径还在，偶尔淘汰时仍把她引向查不到东西的工具 |
| 只加预算 | 自忆排在最后一位，加多少都被别人先吃（离线实测：预算 1200 自忆仍被淘汰） |

## 5. 离线复现（改前改后对照）

用**日志实测的块价**构造同一回合（关系档案 500t、窗口 277t、记忆 294t、
反思 157t、自忆 266t、协议 120t），跑 `fit_backgrounds`：

| 预算 | used | 自忆 | 记忆 |
|---|---|---|---|
| 900（改前） | 868 | ❌ 淘汰 | ✅ |
| 1000 | 883 | ✅ | ❌ |
| **1100（改后）** | **1050** | **✅ 215t** | **✅** |
| 1200 | 1119 | ✅ | ✅（与 1100 相同，已饱和） |

`1100` 是「两块都要」的**最小值**，不是拍的整数。

## 8. 这一轮真正的方法论收获

不是「发现了一个 bug」，而是**一种缺陷形态**：

> **登记表承诺了一个能力，而那个能力的作用域是错的。**
> 核「工具存在」是不够的，必须核「工具检索的主体是不是这块材料的主体」。

它和教训 #12（写了 infra 没接入）、#14（引擎在转离合器没接上）同族，
但更隐蔽：**工具确实存在、调用也不报错、返回结果还很像样**（对方的记忆也是记忆），
唯一的破绽是「她怎么查都查不到自己」。

**这一类只能靠「读执行体的作用域」发现，不能靠「名字像不像」判断。**

## 10. 遗留观察项

1. **预算 1100 是这笔账的新起点**。如果将来再加块（比如「知识库」重新产生），
   同样会挤——届时要重算，不要凭感觉加数字。
2. **自忆块的内容质量**：`_get_self_memory_context` 取最近 5 条，本轮只验证了
   「块能进来」，没验证「进来的 5 条是不是最该进来的」。下一轮候选。
3. 第 8 轮遗留的「corrected 档混着大量对话流水式纠正」仍未处理——本轮她引用
   「我记岔了」时用的正是这类，暂时无害，但占比值得盯。
4. **`test_store_io_is_bounded_and_reports_queue_wait` 是 flaky**（2026-10-25
   全量时红、单独跑绿）。它断言的是「队列等待有没有被上报」，而全量跑时机器负载高、
   时序被拉长——正是教训 #37 形态②「判据测的是环境不是行为」。本轮不动它
   （一次只打一类缺陷），但它是下一轮「把 flaky 修成确定性判据」的现成样本。
