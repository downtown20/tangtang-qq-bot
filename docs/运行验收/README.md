# 小糖糖生产运行验收

这套验收用于回答“机器人实际运行时，各条功能链是否真的工作”。观察器只读
`memory.db` 和新产生的 `tangtang.log`，不会发送 QQ 消息、调用 LLM、修改配置或
保存消息正文。观察器本身可与 bot 同时运行；由于本轮同时补了单行安全日志和
LLM 回合完成标记，**首次正式观察前要重启一次 bot**，之后无需为观察器重复重启。

## 先做 2 小时冒烟

在项目目录另开一个终端：

```powershell
python tools/runtime_observer.py --duration-hours 2
```

确认没有系统性失败后，再做一次不少于 12 小时的持续观察：

```powershell
python tools/runtime_observer.py --duration-hours 12
```

默认每 5 分钟做一次脱敏快照。运行中可以正常使用糖糖；终端不需要一直盯着。
观察器只读，不会替你制造测试流量；因此功能样本按日常使用自然产生即可。
提前按 `Ctrl+C` 也会基于已经取得的样本生成报告。

仅验证观察器能否读取当前环境时可运行：

```powershell
python tools/runtime_observer.py --once
```

单次快照通常返回 `INSUFFICIENT`，退出码为 3，这是预期结果，不是观察器故障。
完整退出码为：0=`PASS`，2=`FAIL`，3=`INSUFFICIENT`，4=观察器自身错误。

### 推荐启动顺序

1. 先重启一次 bot，让新的 `boot`、回合完成标记和后台心跳生效。
2. 确认 `tangtang.log` 已存在，在**另一个终端**启动观察器；不要加 `--from-start`。
3. 先跑 2 小时冒烟；没有系统性 `FAIL` 后，再单独跑 12 小时稳定性窗口。
4. 结束后把同一 run 的 `.md`、`.json` 和 `.jsonl` 交回审查。观察器每个完整区间都会更新检查点，窗口中途关闭也不会失去最后结果。

正式模式从日志当前尾部开始追读。启动瞬间已经在处理、随后对应收尾宽限（当前约 210 秒）内完成的 LLM/语音回合会标为边界样本或证据不足，不会凭一条孤儿完成日志直接误报；`--from-start` 仅用于严格的历史取证。

### ADR-005 定时文本上线闸门

安全重启后先运行一次 `python tools/runtime_observer.py --once`。只有以下聚合字段同时
满足，才开始 2 小时观察：`task_action_schema_missing=false`，且 `open`、
`needs_review`、`stale_sending`、`linked_invariant_violations`、`bare_sending_tasks` 均为
0。随后通过正常 QQ 对话建立一个几分钟后到期的无害纯文本提醒；它必须只发送一次，
报告中的 reminders 要有 durable confirmed 证据，数据库不得残留 linked outbox。

若新链路异常，先把 `tasks.text_action_outbox_enabled` 设为 `false` 并重启，停止领取新
文本任务，同时保留 outbox worker 收敛已有任务。只有发送 worker 本身必须冻结时，才
再关闭 `tasks.send_outbox_claims_enabled`；程序也会在后者关闭时联动关闭前者。不要降级
旧二进制、删除 attempt/outbox 或把 uncertain 手工改回 pending。

## 观察期间至少触发一次的样本

不需要连续刷指令。在 2 小时窗口内分散完成下列动作即可；其余时间按平常方式聊天：

| 功能链 | 最小真实样本 | 自动判定依据 |
|---|---|---|
| QQ 接入、发送、LLM | 私聊和群聊各进行一轮普通文字对话 | 端口、事件丢弃计数、发送三态、LLM 完成与延迟 |
| 窗口自主对话 | 在同一话题中自然追问几句，也留一两条不需要回复的消息 | `reply / skip / fade` 决策计数 |
| 语音输出 | 请糖糖发一条语音 | 触发、生成及 QQ 确认送达 |
| 语音输入 | 给糖糖发一条清晰的 QQ 语音 | SILK/ffmpeg/ASR 成功或失败 |
| 识图、贴图 | 发一张图片并询问内容；再自然请求一个表情 | 识图完成与贴图实际送达，不以工具调用代替送达 |
| 知识检索 | 询问一个确实需要读取知识库文档的问题 | `search_knowledge / read_document` 的真实调用 |
| 唱歌 | 请求一首已配置歌曲 | 音频生成并确认送达 |
| 角色切换 | `/角色 米雪儿`，验证后再 `/角色 糖糖` | 角色对应表情包切换；专属权重切换另列证据 |
| 定时行为 | 建立一个几分钟后到期的无害提醒 | 到期动作确认送达 |
| 自治 | 正常使用，不为测试强行诱导 | 只有自然发生并确认送达才通过；没发生保持证据不足 |

可以在开始和结束时各执行一次 `/状态` 作为人工对照，但 `/状态` 成功不等于所有
功能都成功。端口在线也只证明服务存活，例如不能替代“语音已生成并送达”的证据。

## 记忆与对话质量怎么验

观察器会自动检查提取积压、消费速率、死信、当次新增推理泄露和重复记忆；这些是
运行完整性证据。它不能只靠计数证明“回忆内容语义一定正确”。观察期间可用一条
不敏感、带明确时间的事实做人工 canary，等提取完成后隔一段时间或重启后再询问，
核对来源、人物、时间、群私边界和不确定性。系统性的正确性验收属于 ROADMAP P6-B
黄金集，不会被运行观察器伪装成已通过。

同理，窗口回复是否“自然”、关系是否“像同一个人持续成长”需要真实样本复核；
运行报告先证明链路与统计没有坏，再由 P6-C/P6-D 做语义验收。

## 看结果

结果位于 `artifacts/production_monitor/`：

- `runtime-时间.jsonl`：每 5 分钟的脱敏原始快照；
- `runtime-时间.json`：机器可读的最终判定；
- `runtime-时间.md`：直接阅读的功能域报告。

JSONL 的 `log_summary` 是本 5 分钟区间增量，`log_totals` 是累计的紧凑计数和延迟直方图；不会在高流量时反复堆写原始延迟列表。LLM 的 P50/P95/P 最大值从直方图计算，若摘要被截断会明确标为证据不足。

报告顶部有两个结论：

- “核心运行健康”覆盖 QQ 接入、发送、记忆、LLM、运行日志和后台任务；
- “全功能样本覆盖”还要求语音、唱歌、识图、贴图、知识、角色、自治和各类定时动作有样本。

所以核心健康可以通过，而生日当天才会自然发生的生日祝福仍可诚实保留为证据不足。
每个功能域的判定只有三种：

- `PASS`：本观察区间有对应真实证据，且未越过失败门槛；
- `FAIL`：出现失败、未确认送达、事件丢失或完整性异常；
- `INSUFFICIENT`：没有触发或样本不足，不代表故障，也绝不会按通过处理。

容量趋势至少观察 5 分钟才开始判定，正式晋级仍以 2 小时/12 小时窗口为准。
当前 LLM 运行预算是前台 P95≤30 秒、后台 P95≤60 秒；同一区间超过 2 个
429/5xx，或存在未完成的前台回合，会判失败。

后台循环不是“日志里出现过一次就算正常”。报告会分别显示自治、任务、调度和反思循环的首末心跳、当前进程 `boot`、最大心跳间隔和启动宽限；首个心跳之后若间隔过长、只剩旧进程心跳或心跳汇总了子步骤错误，会判 `FAIL`。日志轮转/截断、短暂缺失、非结构化错误行、指标非法值、计数器回退也会进入“观察器完整性”，防止监测器自身假绿。

“端口在线”只回答服务是否活着。真正的功能结论以端到端证据为准：例如语音必须同时看到触发、生成和 QQ 确认送达；贴图、知识、识图、唱歌和角色切换同理。未触发的可选功能保持 `INSUFFICIENT`，不需要为了让报告变绿而强行执行。

正式观察不要加 `--from-start`，否则会把启动观察器之前的旧日志混入本次结果。
运行结束后把最新的 Markdown 报告交给 Codex，或直接说“观察跑完了”，即可继续做
逐项取证和 P6-A2/P6-A3 晋级判断。
