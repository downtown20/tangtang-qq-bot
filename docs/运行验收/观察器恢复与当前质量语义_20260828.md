# 观察器恢复与当前质量语义（2026-08-28）

## 结论

首轮生产基线同时暴露了两类“历史发生过异常，但当前状态已恢复”的误判：GPT-SoVITS 重建成功后仍永久计作后台失败；feedback 新方向绑定已达到 100%，却被旧版隔离数据稀释为 39%。两者都不是降低告警阈值，而是补齐时间与状态边界。

- 旧群记录按迁移设计保持不可信，未进入 LLM 反思读路径；禁止回填为可信。

## 恢复 episode 契约

观察器按 boot 保存低基数 TTS 恢复状态：

1. ServiceManager 的任一后台失败进入当前 TTS episode。
2. 同 boot 后续 `GPT-SoVITS 已就绪` 关闭此前全部 TTS 失败。
3. 先出现的 ready 不能为后出现的失败背书；新失败会重新打开 episode。
4. ready 不跨 boot 配对；TTS 恢复不能抵消其他 logger 的失败。
5. 配对摘要可跨日志读取分块合并，内部 boot 状态不落入公开报告。

报告同时保留 `raw_failures`、`recovered_failures` 和 `failures`。只有未恢复失败决定后台域 FAIL，因此审计信息不会因自愈而丢失。

## 零记忆覆盖的关系口径

- 首轮新 boot 报告 8 个 `total_chats>50` 且零记忆用户。
- 只读分层后确认：8 人私聊均为 0，只在一个群发言，机器人对其回复为 0–3 次；`total_chats` 统计了环境群消息，不能直接代表关系互动。
- 新口径仍保留 `total_chats>50` 容量门槛，同时要求至少 5 次私聊消息或机器人实际回复；达到直接互动证据却零记忆才告警。
- 生产数据按新口径为 0；旧数据不删除、不回填。回归同时覆盖纯群环境噪声不告警和 6 个直接互动用户零记忆必须告警。

这种拆分与主流指标模型一致：累计计数用于保留发生史，当前健康用有限时间窗或 delta 观察。参考 [Prometheus metric types](https://prometheus.io/docs/concepts/metric_types/) 与 [OpenTelemetry metrics data model](https://opentelemetry.io/docs/specs/otel/metrics/data-model/)。

## 回归门禁

- TTS：正常自愈、无 ready、跨 boot、倒序 ready、跨日志分块、多失败单次恢复、不得掩盖其他后台失败。
- feedback：当前 20% 覆盖仍告警；7 日旧债很多但当前 100% 时恢复正常。
- 上线后必须重启，再跑 2 小时对照观察；旧版基线报告不重算、不覆盖。
