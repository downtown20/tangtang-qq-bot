# 记忆系统技术文档

> 结构化记忆层（fact_clusters）的完整技术说明——架构、流程、参数、踩坑记录。

---

## 一、为什么需要这一层

糖糖的记忆系统经历过多次迭代：

| 阶段 | 方案 | 问题 |
|------|------|------|
| 1 | `memories` 表——碎片记忆 | 散、杂、检索不准 |
| 2 | + `chat_index` —— 聊天语义索引 | 原始消息噪声大，LLM 容易编造 |
| 3 | + `fact_clusters` —— 结构化事实簇 | **当前方案**：三层互补 |

核心思路来自毛泽东"抓主要矛盾"：碎片记忆和聊天索引的共同问题不是"数据不够"，而是**数据没组织**。LLM 面对一堆杂乱记忆会被干扰，产生幻觉。

fact_clusters 做的事：**把每个人说过的话提炼成按主题整理的事实档案**。LLM 对话时优先查这一层——精确、结构化、不编造。

---

## 二、三层架构

```
LLM 对话中的记忆检索优先级：

  ① fact_clusters（结构化事实簇）── 命中率高、准确
       ↓ 找不到
  ② chat_index（聊天记录语义索引）── 14 万条原始消息兜底
       ↓ 还找不到
  ③ memories（记忆碎片）── 注入系统提示词做背景参考
```

| 层 | 数据库表 | 粒度 | 检索方式 | 用途 |
|----|---------|------|---------|------|
| 事实簇 | fact_clusters + cluster_facts | 人 × 主题 | BGE 语义 → 格式化文本 | **对话中优先检索** |
| 聊天索引 | chat_index | 每条消息 | BGE 语义 → 原始消息 | 事实簇没结果时兜底 |
| 记忆碎片 | memories | 单条记忆 | 关键词 + 语义 → 背景注入 | 系统提示词背景 |

## 三、数据库设计

### fact_clusters —— 簇表

```sql
CREATE TABLE fact_clusters (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    subject_qq  TEXT NOT NULL,          -- 谁的记忆
    category    TEXT NOT NULL,          -- 8 类之一
    title       TEXT NOT NULL,          -- 2-6 字标签
    summary     TEXT DEFAULT '',        -- LLM 生成的 1-2 句连贯摘要
    fact_count  INTEGER DEFAULT 0,      -- 下面挂了多少条事实
    permanence  TEXT DEFAULT 'normal',  -- permanent / stable / normal / transient
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL,
    embedding   BLOB                   -- title 的 BGE 向量
);
CREATE INDEX idx_fact_clusters_subject ON fact_clusters(subject_qq);
```

### cluster_facts —— 簇内事实

```sql
CREATE TABLE cluster_facts (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    cluster_id   INTEGER NOT NULL,       -- FK → fact_clusters.id (CASCADE)
    subject_qq   TEXT NOT NULL,
    fact         TEXT NOT NULL,          -- 一句话事实
    source_qq    TEXT DEFAULT '',
    evidence_ids TEXT DEFAULT '',
    confidence   REAL DEFAULT 1.0,       -- LLM 提取时的置信度 0-1
    importance   INTEGER DEFAULT 5,      -- 1-10
    created_at   TEXT NOT NULL,
    embedding    BLOB,                   -- fact 的 BGE 向量
    FOREIGN KEY (cluster_id) REFERENCES fact_clusters(id) ON DELETE CASCADE
);
CREATE INDEX idx_cluster_facts_cluster ON cluster_facts(cluster_id);
CREATE INDEX idx_cluster_facts_subject ON cluster_facts(subject_qq);
```

### 8 个类别

| category | 含义 | 例子 | permanence 倾向 |
|----------|------|------|----------------|
| health | 持续性健康问题 | 慢性病、过敏、心理疾病、长期失眠 | 高——不会过期 |
| identity | 身份信息 | 职业、学校、年龄、性别、所在地、独居/合住 | 中高——相对稳定 |
| relationship | 人际关系 | 家庭、朋友、恋人、社交状态 | 中高 |
| work | 工作/学习 | 项目、考试、工作任务 | 中 |
| preference | 喜好 | 喜欢的食物、音乐、颜色、游戏 | 中 |
| experience | 经历 | 被骗、搬家、旅行、买了什么 | 可变——重大事件保留 |
| habit | 习惯 | 作息、口头禅 | 中 |
| note | 其他 | 临时状态、计划、日常琐事 | 低——多数 transient |

## 四、提取流程

### 4.1 触发机制

在 [handler.py](../agent/handler.py#L5501-L5507) 中，每条消息处理后检查：

```python
total_chats = person.get("total_chats", 0)
threshold = 20 if self._last_fact_extraction.get(user_id) is None else 50
if total_chats - (self._last_fact_extraction.get(user_id) or 0) >= threshold:
    self._last_fact_extraction[user_id] = total_chats
    self._save_fact_extraction_state()
    asyncio.create_task(self._extract_fact_clusters_task(user_id))
```

- **首次**：累计 20 条消息就触发
- **后续**：每新增 50 条触发
- 状态持久化到 `.fact_extraction_state.json`，重启不丢
- 后台异步执行，不阻塞消息回复

### 4.2 提取流程图

```
新消息达到阈值
      ↓
取最近 30 条未处理消息（get_unprocessed_messages）
      ↓
LLM 提取 → JSON 数组
  [{"topic":"心脏健康","category":"health","fact":"有先天性心脏病","importance":9,"confidence":1.0},
   {"topic":"饮食偏好","category":"preference","fact":"喜欢吃火锅","importance":4,"confidence":0.95}]
      ↓
逐条处理：
  ├─ confidence < 0.5 → 丢弃
  ├─ fact 长度 < 4 → 丢弃
  └─ 通过 →
      ├─ BGE 编码 topic 向量
      ├─ 与已有簇的 title 向量做相似度比较
      │    ├─ 相似度 > 0.60 → 归入已有簇（add_cluster_fact）
      │    └─ 相似度 ≤ 0.60 → 新建簇（upsert_fact_cluster + add_cluster_fact）
      └─ permanence 由系统判定（_derive_permanence）
      ↓
所有被修改的簇 → _regenerate_cluster_summary()（LLM 重新生成 1-2 句摘要）
      ↓
提取完毕 → merge_similar_clusters()（检查是否需要合并相似簇）
```

### 4.3 提取 Prompt

核心约束（[memory.py:832-858](../agent/memory.py#L832-L858)）：

| 规则 | 原因 |
|------|------|
| ✅ 提取用户本人的真实情况 | 这是"关于用户"的记忆，不是聊天记录 |
| ✅ 保留原话的具体信息 | "花10块买了盗版模组"不要泛化成"有过消费经历" |
| 🚫 不提取问句、反问、对别人的描述 | 不是用户自己的事实 |
| 🚫 不提取自贬 | "我是废物"是情绪症状，不是事实（与记忆系统一致） |
| 🚫 不提取角色扮演/游戏设定 | "我是猫娘""被设定为主人"是 RP 对话 |
| 🚫 不提取用户对糖糖说的话 | "糖糖你好可爱"——这是对话，不是用户信息 |
| 每条一句话，一个信息点 | 拆分复合陈述——"有心脏病，喜欢火锅"→ 两条 |
| 重要性分级 | 永久事实(疾病/家庭成员)=9-10，长期(职业/学校)=7-8，偏好/习惯=3-5，日常=1-2 |
| confidence | 明确陈述=1.0，暗示=0.7-0.8 |
| 宁可多不要漏 | 低重要度也提取 |

### 4.4 LLM 不输出 permanence

**为什么不让 LLM 输出 permanence？** 早期版本让 LLM 同时输出 `permanence` 字段，结果 LLM 把健康问题（先天性心脏病）标成了 `transient`。LLM 不理解"永久"在记忆系统中的含义——它觉得"任何事都可能改变"。

现在的方案（[memory.py:862-883](../agent/memory.py#L862-L883)）：`_derive_permanence()` 是纯函数，根据 (category, importance) 查表决定。

```python
@staticmethod
def _derive_permanence(category: str, importance: int) -> str:
    if category in ("health",):
        return "permanent" if importance >= 6 else "stable"
    if category in ("identity", "relationship"):
        return "stable" if importance >= 5 else "normal"
    if category in ("work",):
        return "stable" if importance >= 6 else "normal"
    if category in ("preference", "habit"):
        return "normal"
    if category in ("experience",):
        if importance >= 8: return "stable"    # 重大人生事件
        if importance <= 3: return "transient"  # "昨天去了趟超市"
        return "normal"
    if importance <= 2: return "transient"
    return "normal"
```

四级 permanence：

| 级别 | 含义 | 典型例子 |
|------|------|---------|
| permanent | 不会改变 | 慢性病、过敏史、家庭成员 |
| stable | 长期稳定 | 职业、学校、居住地、社交状况 |
| normal | 正常波动 | 偏好、习惯、一般经历 |
| transient | 短期/临时 | 日常状态、临时计划 |

## 五、合并流程（merge_similar_clusters）

### 5.1 为什么需要

一次提取可能产生多个相关但分开的簇。比如第一轮提取出"饮食习惯"和"食物偏好"，实际上是同一主题——但 LLM 在不同的 batch 里用了不同的标签。

### 5.2 流程

```
提取全部完成后
      ↓
获取此人所有簇
      ↓
BGE 编码每个簇的 "title + summary" 向量
      ↓
O(n²) 比较所有簇对
  → 相似度 > 0.7 的对 → 提交 LLM 判断
      ↓
LLM 输出 YES/NO + 新 topic
  YES → 合并所有事实到 ci，删除 cj，重新生成摘要
```

### 5.3 两个阈值

| 阈值 | 值 | 用途 | 为什么是这个值 |
|------|-----|------|-------------|
| MERGE_THRESHOLD | **0.60** | 提取时：新事实 → 已有簇的 topic 匹配 | 0.55 过度合并（健康→饮食习惯），0.65 碎片化 |
| 合并触发线 | **0.70** | 合并时：两个簇 summary 的相似度 | summary 比 topic 更精确——只有内容真相似的才让 LLM 判断 |

## 六、检索流程（search_fact_clusters）

LLM 在对话中通过 tool calling 调用（[memory.py:1093-1128](../agent/memory.py#L1093-L1128)）：

```python
def search_fact_clusters(self, subject_qq, query, embed_engine, top_k=3):
    ① BGE 编码 query 向量
    ② SQL 余弦相似度搜索 fact_clusters（排除 embedding IS NULL）
    ③ 取 top_k 个结果
    ④ 每个结果 → title + category + permanence 标签 + summary
    ⑤ 加载该簇下的详细事实（最多 8 条）
    ⑥ 格式化为文本返回给 LLM
```

返回格式示例：

```
## 心脏健康 (health, 🔒永久, 匹配度:92%)
有先天性心脏病，不能剧烈运动。在考虑做微创手术。

详细事实：
  ✓ 有先天性心脏病
  ✓ 医生建议微创手术，还在犹豫
  ↑ 小时候做过一次大手术
```

各符号含义：

| 符号 | confidence |
|------|-----------|
| ✓ | ≥ 0.95 |
| ↑ | 0.75-0.94 |
| ~ | 0.50-0.74 |
| ? | < 0.50（理论上不会出现，<0.5 的已被过滤） |

## 七、批量构建工具

[tools/_build_fact_clusters.py](../tools/_build_fact_clusters.py) —— 为所有历史数据一次性构建事实簇。

```bash
python tools/_build_fact_clusters.py
```

### 处理逻辑

1. 找出 `chat_log` 中所有人（≥10 条消息，含私聊+群聊）
2. 按消息数降序排列
3. 逐个用户：
   - 清空旧簇（delete_cluster CASCADE 删除 facts）
   - 取所有消息，清洗 CQ 码，保留 ≥4 字
   - 每 50 条为一批，调用 `extract_fact_clusters()`
   - 全部批次完成后，调用 `merge_similar_clusters()`
4. 汇总输出

### 注意事项

- max_tokens=4096，temperature=0.3——提取类任务低温度更可靠
- 分批处理避免单次 LLM 调用上下文溢出
- 私聊和群聊消息都纳入——糖糖应该记住这个人的一切

## 八、关键设计决策

### 8.1 为什么 permanence 由系统判定

**教训来自 memory.py 的 `_derive_permanence` 历史**：LLM 输出的 permanence 全错——它把健康问题标成 transient。LLM 不知道"记忆持久性"是什么概念。硬约束的逻辑应该由系统执行，LLM 只做它擅长的事——从自然语言中提取事实。

这也是 CLAUDE.md 中"LLM 是唯一决策者，系统只执行 LLM 的指令"原则的反面——permanence 不是 LLM 的决策，是系统的存储策略。

### 8.2 为什么提取时匹配 topic 而不是 summary

topic（2-6 字标签）是高度压缩的语义单元，"心脏健康"和"心脏问题"的 BGE 向量几乎重叠。summary 是一段话，匹配精度反而不如短标签——噪声更多。

合并阶段则相反——用 summary 向量比较，因为需要精确判断两组内容是否重复。

### 8.3 为什么合并阈值是 0.70 而不是 0.60

0.60 用于"新事实 → 已有簇"的匹配——保守一点，宁可归入已有簇也不新建。但簇间合并不一样：一旦合并出错，两个不相关的主题被揉在一起，信息污染不可逆。0.70 更严格——只有真相似的才合并。

### 8.4 为什么自贬过滤在提取层也在记忆层也在

两层防御，互不依赖：
- **记忆层**（`auto_learn` + `extract_semantic_memories`）：过滤"我是废物"类陈述
- **事实簇提取层**（`_EXTRACT_FACTS_PROMPT`）：Prompt 中明确"不提取自贬"

如果 Prompt 没拦住（LLM 不听话），还有 confidence 过滤兜底——自贬陈述的 confidence 通常 < 0.5。

## 十、调参与踩坑

### 10.1 MERGE_THRESHOLD 调参过程

| 值 | 效果 | 结论 |
|----|------|------|
| 0.55 | 健康事实合并到"饮食习惯"，关系事实合并到"睡眠状态" | ❌ 过度合并 |
| 0.65 | 本该在一起的事实被拆成多个簇 | ❌ 碎片化 |
| **0.60** | 当前值——平衡点 | ✅ |

### 10.2 Prompt 迭代

- 第一版：LLM 输出 permanence → 全错 → 改为系统判定
- 第二版：提取太少（8 条事实）→ 加"宁可多不要漏"+"重要性 1-5 也要提取"
- 第三版：角色扮演内容被提取 → 加反 RP 过滤规则
- 当前版：64 条事实 / 14 个簇（米雪儿测试数据），质量稳定

### 10.3 常见问题

**Q: 提取的事实太少？**
- 检查 `max_tokens` 是否够（最少 4096）
- 检查消息是否被 CQ 码清洗掉了有效内容
- 有效消息不足 8 条不会触发

**Q: 簇太多太碎？**
- 运行 `merge_similar_clusters()` 
- 或调低 MERGE_THRESHOLD（谨慎——太低了会过度合并）

**Q: 重启后重复提取？**
- `.fact_extraction_state.json` 记录每个人的 `total_chats` 快照
- 只有当新消息数超过阈值时才触发
- 如果文件丢失 → 清空重来，浪费一些 API 调用但不影响功能

## 十一、LLM 记忆检索工具（2026-07-28 新增）

LLM 通过 tool calling 自主选择检索方式，共 10 个工具：

| 工具 | 数据源 | 检索方式 | 用途 |
|------|--------|---------|------|
| `search_facts` | fact_clusters | BGE 语义 | 查记住的结构化事实 |
| `search_chat_history` | chat_index | BGE 语义 | 搜聊天记录中的话题 |
| `search_keywords` | chat_log | SQL 精确匹配 | 搜具体词/短语 |
| `search_memories` | memories | 关键词+语义 | 搜零散偏好和事实 |
| `get_recent_messages` | chat_log | 时间倒序 | 某人最近说了什么 |
| `get_messages_by_date` | chat_log | 日期过滤 | 某天聊了什么 |
| `get_last_conversation` | chat_log | 时间倒序交错 | 糖糖和某人的上次对话 |
| `count_messages` | chat_log | 聚合统计 | 某人发了多少条/某词几次 |
| `get_first_met` | people 表 | 直接查 | 什么时候认识的 |
| `get_group_activity` | chat_log | 聚合统计 | 群整体活跃情况 |

涉及文件：[handler.py](../agent/handler.py)（工具定义+分派）、[store.py](../agent/store.py)（SQL 查询方法）。

### 设计原则

- **LLM 自己判断用什么工具**——语义搜话题用 BGE，精确搜词用 SQL，时序查询用时间排序
- **不替 LLM 做判断**——只在工具描述里说明用途，让 LLM 自己选
- **按需查询，不预取**——除了事实簇在消息处理时自动增量提取，其他都是 LLM 主动调 tool

### StructBERT 模型损坏（2026-07-28）

心情追踪 `mood_tracker.py` 用的 StructBERT 模型（`models/iic/nlp_structbert_sentiment-classification_chinese-base`）从 ModelScope 下载后状态字典损坏，`transformers` 无法加载。HuggingFace 镜像因 SSL 证书问题无法访问。

**影响**：心情追踪不可用，不影响聊天和记忆。**待修复**：换个模型源或改用 LLM 直接判断情绪。
